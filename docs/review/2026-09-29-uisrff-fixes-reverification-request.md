## 2. UISRFF-01 (Med) — 「창」이라 불렀지만 창이 아니었습니다

**지적이 맞고, 같은 자리에서 두 번째 착각입니다.**

「유한 창이라 창 밖의 기여는 0」이라고 적어 놓고, **100ms 칸 근사를
쓰는 `RollingLeq` 를 그대로 썼습니다.** 닫힌 칸 30개에 아직 안 닫힌
칸을 함께 더하므로 실제 평균 구간이 3.0~3.1초를 오갑니다. 창이 0.1초
더 뻗으면 그 안의 큰 소리가 섞입니다.

먼젓번은 **지수 평활**을, 이번은 **칸 근사**를 「창」이라고 불렀습니다.
둘 다 기다리는 시간을 늘려서는 못 고칩니다.

### 고친 방식

보내 주신 구조를 그대로 받았습니다(`enableExactWindow()`).

- `RollingLeq` 안에 **옵트인 정확 창**. 최근 `샘플레이트 × 3` 표본의
  제곱을 링에 들고, 밀려난 것을 합에서 뺍니다 — 창 밖 기여가 **정확히
  0**.
- 초당 48,000번 더하고 빼는 자리라 **보정 합산(Kahan)** 으로 긴 측정의
  드리프트를 막습니다(예배 두 시간이면 3억 번이 넘습니다).
- **켜는 것은 보정용 엔진뿐**입니다. 화면의 계기·기록은 그대로 칸
  근사를 씁니다.
- 잘림·공백에서는 버퍼를 **버리지 않고 비웁니다**(3 MiB 넘는 자리라,
  손뼉 한 번에 다시 잡게 두지 않습니다).

### 확인한 것

보내 주신 회귀 3개를 정규 경로로 옮겼습니다
(`dsp/.../IndependentExactWindowTest.kt`). 칸 위상 10~90ms,
44.1/48kHz, 혼합 블록, A/C/Z 를 봅니다.

| | 결과 |
|---|---|
| 정확 창 **켠** 상태 | 3/3 통과 |
| 정확 창 **끈** 변이 | **3/3 실패** |

같은 순서를 짧게 재현하는 회귀도 하나 더했습니다
(`CleanWindowTest.칸 경계에 걸쳐도 창 밖의 큰 소리가 안 섞인다`):
진폭 0.9 로 5.02초 → 0.009 로 3.02초에서 Z 가중 잔류 **0.1 dB 미만**.

> 되묻습니다:
>
> 1. **3.3 MiB** 의 추가 버퍼(A/C/Z × 48kHz × 3초 × double)를 세션마다
>    잡습니다. 보정에 실제로 쓰는 것은 **고른 가중 하나**인데, 고르는
>    일이 주 스레드에 있어 셋 다 들고 있습니다. 하나만 두도록 구조를
>    바꾸는 편이 낫겠습니까? 아니면 이 정도는 감당할 만합니까?
> 2. 기기 CPU/GC 와 2시간 부하는 **아직 측정하지 않았습니다.**
> 3. 보정 합산이 이 규모에서 정말 필요한지도 재지 않았습니다 —
>    없으면 얼마나 어긋나는지 보여 주는 시험이 없습니다.

## 3. UISRFF-02 (Low) — 빈 읽기가 나이를 0 으로 되돌렸습니다

보내 주신 패치를 그대로 받고 주석만 이 저장소 문체로 바꿨습니다.

세션에 `lastValidInputNs` 를 따로 두고 `frames > 0` 일 때만 갱신합니다.
하나는 「저장해도 되는가」를, 다른 하나는 「소리가 오고 있는가」를
말합니다 — 같은 값으로 둘 다 답할 수 없었습니다.

> 되묻습니다: 「첫 정상 입력 전에 빈 블록만 반복」하는 시나리오는
> **아직 회귀로 두지 않았습니다**(추가 권장이라 하신 것). 제품 코드
> 로는 `lastValidInputNs` 가 null 이라 `startedNs` 로 떨어지므로 맞게
> 동작한다고 읽었는데, 시험 없이 그렇게 말해도 됩니까?

## 4. UISRFF-03 (Low) — 서명 확인이 다른 파일을 봤습니다

- `bundleRelease` 가 내놓는 **AAB** 를 `jarsigner -verify` 와
  `keytool -printcert -jarfile` 로 봅니다. APK 는 따로 나눠 줄 때만.
- **종료 코드 0 으로는 모자라다**고 적었습니다 — `jar verified`,
  서명된 항목, SHA-256 지문 셋을 눈으로 봅니다.
- 도입부의 「키를 잃으면 영영 갱신 불가」를 **Play App Signing 여부로
  갈랐습니다.** 본문 아래쪽에는 맞게 적어 두고 도입부만 어긋나 있었습니다.
- 「`signingConfig` 를 지정했다」는 사실만으로는 막히지 않으므로, **키
  파일까지 보고 release 패키징을 명시적으로 실패시키는** 예를 더했습니다.

> 되묻습니다: 그 `doFirst` 검사 예시를 **실제 `build.gradle.kts` 에
> 넣지는 않았습니다**(키가 없어 돌려 볼 수 없어서). 문서에만 두는 것이
> 맞습니까, 아니면 키 없이도 지금 넣어 두는 편이 낫습니까?

### 5-2. 제 판단이 틀렸다고 확인된 것

다음 사람이 같은 길로 가지 않도록 모아 둡니다.

1. **「틀리게 맞추면 화면이 곧바로 이상해진다」**(UIS-02).
   오프셋이 `기준값 − 읽는 값`이라 맞춘 직후는 반드시 기준값입니다.
2. **「지연만 보면 된다」**(UISR-03). 콜백 중단·회복·표본 나이까지
   판정할 수 있다는 결론은 성립하지 않습니다.
3. **「잘렸으면 3초 기다리면 된다」**(UISRF-01). 지수 시간가중은
   기다리는 것으로 막히지 않습니다.
4. **「유한 창이라 창 밖은 0」**(UISRFF-01). 그렇게 적어 놓고 **칸
   근사**를 썼습니다.
5. **「시험이 있으니 지켜진다」**(UIS-07, 그리고 정책 링크). 문자열
   검색 시험이 **두 번** 뚫렸습니다.

1~4 는 모두 **상태·계산의 뜻을 잘못 읽은 것**이고, 5 는 **시험이
무엇을 지키는지 확인하지 않은 것**입니다.

### 5-3. 정책 링크 시험이 뚫린 건 (4회차 6장 지적)

호출부를 지워도 다섯 개가 다 통과했습니다. 이제 **선언 말고 호출**을
세고, 호출이 선언보다 앞에 있는지까지 봅니다. 여는 일도 밖에서 받게
뺐습니다(`openUrl: (String) -> Boolean`).

**변이 확인**: 호출부를 지우면 실패합니다.

> 되묻습니다: 이것도 여전히 **소스 문자열 검사**입니다. Compose 시험이
> `androidTest` 에만 있어 기기가 필요한데, 주입 가능한 `openUrl` 을
> 열어 둔 지금 상태에서 **계측 시험을 붙이는 것이 값어치가 있습니까?**

### 5-4. lint

`SessionExport` 에 **진짜 BOM 문자**가 박혀 있던 것을 `"﻿"` 로
바꿨습니다. `:app:lintDebug` 가 통과합니다(전에는 error 1).

### 5-5. 손뼉 보고 정정

- 3초 동안 「단추를 누를 수 없다」가 아니라 **게이트가 거절합니다.**
  `enabled` 는 `currentDbfs != null` 이라 눌립니다.
- 19.7 → 10.0 → 6.7 → 8.3 을 「시간에 따라 줄어든다」고 적었는데
  **단조 감소가 아닙니다.** 손뼉이 여러 번이라 그때마다 다시
  벌어졌습니다.
- 두 숫자의 차이가 **기준 음압의 정답을 말해 주지 않는다**는 것도
  함께 적었습니다.

- 교정기 94/114 dB 음향 정확도, 제조사 이전 도구, Play Console.

### 6-1. 실기기에서 손뼉으로 확인했습니다 (추가)

Galaxy S23 + UMC404HD, 병합본(`7c0d157`). 담당자가 업무 중에 손뼉을
**두 번** 쳤고, 보정 카드를 0.6초 간격으로 70장 찍었습니다.

| 프레임 | 지금 읽는 값 | 보정에 쓸 값 |
|---|---|---|
| #08 | −25.3 dBFS | **잘리지 않은 소리 2.7초 더 필요** ← 손뼉 1 |
| #11 | −33.2 | **0.9초 더 필요** |
| #13 | −38.3 | −49.9 dBFS · 3초 평균 ← **복귀** |
| #15 | −24.6 | **2.8초 더 필요** ← 손뼉 2 |
| #18 | −32.6 | **0.9초 더 필요** |
| #20 | −38.1 | −57.8 ← **복귀**(차 **19.7 dB**) |
| #22 | −42.8 | −56.7 |
| #25 | −49.5 | −55.6 |
| #30 | −56.7 | −55.0 |
| #55 | −58.2 | −59.1 |
| #65 | −59.9 | −59.8 |

읽히는 것 셋:

1. **손뼉마다 창이 비워지고 남은 시간이 줄어듭니다** — 2.7 → 0.9 →
   복귀. 3초 창이 **실제로 3초만큼** 다시 채워집니다.
2. **복귀 직후 두 값이 크게 벌어집니다.** #20 에서 화면은 −38.1,
   보정에 쓸 값은 −57.8 — **19.7 dB.** 유한 창에는 손뼉이 한 표본도
   남아 있지 않은데, 지수 평활은 아직 내려오는 중입니다.
3. 방이 조용해지면 둘이 **수렴합니다**(#55·#65에서 1 dB 안).

**이 관측이 증명하지 **않는** 것**: 잘림에서 창이 비는 것은 칸 근사도
했을 일입니다. **UISRFF-01 의 0.1초 경계 차이는 화면에서 읽을 수
없습니다** — 그쪽은 `IndependentExactWindowTest` 3개가 덮습니다
(정확 창을 끄면 3/3 실패). 이것은 소프트웨어 동작의 관측이고 음향
정확도 측정이 아닙니다.

## 7. 가장 보고 싶은 것

1. **정확 창이 정말 정확한지.** 구조는 주신 것을 받았지만 반영은
   제가 했습니다.
2. **또 「뜻」을 잘못 읽은 자리가 남았는지.** 다섯 번째입니다.
3. **3.3 MiB 와 링 갱신 비용**이 감당할 만한지.
4. **시험이 무엇을 지키는지.** 이번에 새로 쓴 것들
   (`IndependentExactWindowTest` 를 옮긴 것 포함)에도 같은 구멍이
   있는지 변이로 봐 주십시오.
