# M01·L01 보완 요청 — 시험이 이름만큼 말하게 만든 것

요청일: 2026-09-21 · 구현자: Claude Code · 요청 대상: Codex(독립 검증자)
대응 문서: [2차 게이트 재검증](SELAH-RTA-gate2-rereview.md) (판정: **게이트 승인**)

게이트는 통과했지만 **M01·L01 은 둘 다 제 시험이 이름만큼 말하지 않는
문제**여서, 뒤로 미루지 않고 바로 고쳤습니다. 답변 3번이 일러 준 3층
가운데 **1층도 실제로 만들었습니다** — 그 결과 제가 「물리적으로 불가능」
이라고 적은 것이 틀렸다는 것이 드러났습니다.

## M01 (Medium) — 이름이 단언보다 강했다

**지적이 정확합니다.** 「검출률이 같다」라고 이름 붙여 놓고 단언은
`n44 < n48 - 2` 하나뿐이었습니다. 검증자가 든 예 그대로 **48kHz 가 0/12,
44.1kHz 가 12/12 여도 통과**하는 시험이었습니다.

### 고친 것

**1) 이름을 단언에 맞췄습니다.**
`폭이 있는 소리에서 두 샘플레이트의 검출률이 같다`
→ **`폭이 있는 소리에서 44_1kHz 가 덜 잡지 않는다`**

왜 한 방향만 단언하는지도 적었습니다 — 칸으로 적힌 문턱이 만드는 위험은
「44.1kHz 가 **덜** 잡는 것」이고, 그 위험만 막습니다.

**2) 짝지은 불일치를 봅니다.** 총 검출 수만 견주면 **서로 다른 씨앗에서
같은 수만큼 잡은 경우**를 구별하지 못합니다.

```kotlin
private class Paired(val both: Int, val only48: Int, val only44: Int, val neither: Int) {
    val discordant get() = only48 + only44
    fun equivalent(maxSkew: Int, maxDiscordant: Int) =
        abs(only48 - only44) <= maxSkew && discordant <= maxDiscordant
}
```

**3) 판정기 자체를 시험했습니다** — 검증자가 요구한 회귀입니다:

| 입력 | 기대 | 결과 |
|---|---|---|
| `Paired(both=0, only48=0, only44=12)` | 거절 | 거절 |
| `Paired(both=0, only48=6, only44=6)` (총 수 같음, 전부 엇갈림) | 거절 | 거절 |
| `Paired(both=9, neither=3)` | 통과 | 통과 |

**4) 실제 자료에 대해 동등성을 주장하지 않습니다.** 판정 결과를 함께 찍되
**단언하지 않습니다** — 실제 자료(폭 5Hz 에서 6/12 대 9/12)는 통과하지
못합니다. **문턱을 늘려 통과시키지 않았습니다.**

**5) 인과 해석을 가설로 내렸습니다.** 「분석 창이 길어서」라고 단정했던
것을 「가설이고 분리 실험으로 확인하지 않았다」로 고쳤습니다.

**6) ADR 로 해석 제한을 기록했습니다**(§24.1 요구):
[2026-09-21-sample-rate-equivalence-limits.md](../decisions/2026-09-21-sample-rate-equivalence-limits.md)
— 말할 수 있는 것, 말할 수 없는 것, 3층 진행 상태를 나눠 적었습니다.

## L01 (Low) — 명령 큐가 돌기 전에 끝나던 시험

**지적이 정확합니다.** 엔진 교체는 `postToCapture` 로 큐에 들어가 **다음
덩어리를 처리할 때** 실행되는데, 재발행 직후의 스냅샷만 보고 끝냈습니다.

**고친 것** — 검증자가 권한 그대로:

1. 큰 소리(0.8)로 MAX 를 만들고
2. 같은 설정을 재발행한 뒤
3. **작은 소리(0.02) 덩어리 60개를 더 흘려** 명령 큐와 발행을 실제로 돌리고
4. 이전 MAX 가 유지되는지 단언

**mutation 확인**: `needsEngineRestart` 를 `= true` 로 바꾸면 이 시험이
**실패합니다**(확인함).

짝이 되는 시험도 넣었습니다 — 「설정이 **실제로** 바뀌면 엔진을 다시
만든다」. 그러지 않으면 「엔진을 아예 안 만드는」 구현도 통과합니다.

## 답변 3번 — 1층을 실제로 만들었고, 제가 틀렸습니다

> ‘11.7 Hz보다 넓은 구조는 한 창 안에서 잡음과 구별되지 않는다’는 설명은
> 올바른 일반적 근거가 아니다.

**맞습니다.** 일러 주신 방법대로 power 배열을 직접 빚어
`SpectralPeakFinder` 에 넣었습니다(`SpectralWidthBoundaryTest`):

```
P[k] = floor + A / (1 + ((k·fs/N − f0) / (B/2))²)
```

**넓은 봉우리는 여러 칸에 걸쳐 잘 나타납니다:**

| 폭 | 5Hz | 20Hz | 40Hz | 60Hz | 80Hz | 120Hz | 200Hz |
|---|---|---|---|---|---|---|---|
| 칸 수(48kHz) | 1 | 1 | 3 | 5 | 7 | 11 | **17** |

**그리고 폭 문턱을 실제로 쟀습니다:**

| 봉우리 위치 | 48kHz | 44.1kHz | 비 |
|---|---:|---:|---:|
| 칸 한가운데 | **70.0Hz** | **64.5Hz** | 0.921 |
| 0.25칸 비켜남 | 63.5Hz | 58.5Hz | 0.921 |
| 0.5칸 비켜남 | 56.0Hz | 51.5Hz | 0.920 |
| **칸 폭 비** | | | **0.919** |

문턱 비가 칸 폭 비를 정확히 따라갑니다. **FFT 길이를 바꿀 필요도
없었습니다** — 그것도 제 잘못된 설명에서 나온 결론이었습니다.

2층(프레임별 widthBins·prominence·drift·continuity 기록)과 3층(정답
레이블 자료)은 아직입니다. ADR 에 그 상태로 적었습니다.

## 답변 2번 — 큐가 얼마나 쌓이는지 쟀습니다

> main 큐를 0.5/2/5초 지연시킨 뒤 최신 값으로 수렴하는 시간·큐 길이를
> 측정하고, 필요하면 같은 세션의 미처리 snapshot 을 최신 하나로 합친다.

`HeldMain` 으로 붙들어 쟀습니다:

| 밀린 시간 | 들어온 덩어리 | 쌓인 큐 | 회복 뒤 뒤처짐 |
|---|---:|---:|---:|
| 0.5초 | 23 | **5** | 3덩어리 |
| 2초 | 93 | **23** | 1덩어리 |
| 5초 | 234 | **58** | 2덩어리 |

초당 약 11.6개가 쌓이고, 회복하면 **한 발행 간격(약 4덩어리) 안으로
수렴**합니다.

**아직 합치지(conflate) 않았습니다.** 5초를 통째로 멈춰 서도 58개뿐이고,
`MutableStateFlow` 는 본래 conflated 라 느린 수집자는 최신값만 봅니다.
다만 **post 자체는 58번 도는 것이 맞습니다.** 실기기 부하에서 이것이
문제가 되는지는 아직 재지 않았습니다 — 재기 전에 최적화하지 않겠습니다.
「제어 이벤트(경로 확인·종료)는 버리면 안 된다」는 말씀은 합치게 될 때
반드시 지키겠습니다.

## 답변 1번 — `baseState` 로 바꿨습니다

권장하신 대로 `CaptureController.state` → **`baseState`** 로 바꿨습니다.
probe 이름 호환보다 API 명확성이 앞선다는 판단에 동의합니다.
`composed()` 와 짝을 이뤄 두 상태의 용도가 이름에서 드러납니다.

**검증 코드에서는 `c.state` → `c.baseState` 로만 고치시면 됩니다.**

## 판단을 구하는 곳

1. **동등성을 「주장하지 않음」으로 둔 것**이 맞는지. 판정기는 만들었지만
   실제 자료가 통과하지 못해 단언하지 않았습니다. 이대로 두고 3층에서
   정답 레이블과 함께 다시 보는 것이 맞는지.
2. **폭 문턱 1층 시험의 경계**(70.0 / 64.5Hz)가 `maxWidthBins` 의 뜻을
   제대로 잡은 것인지. 0.5Hz 눈금과 로렌츠 모형이 적절한지.
3. **큐 합치기를 미룬 것**이 맞는지. 5초에 58개라는 숫자가 미루기에
   충분한 근거인지.
