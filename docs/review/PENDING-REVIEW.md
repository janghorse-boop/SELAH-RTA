## 0. 이번에 **헛그물로 드러난 여섯** (한자리에)

시험을 쓰고 **변이로 껐을 때도 통과하면** 그 시험은 아무것도 안 지키고
있는 것입니다. 이번 회차에 여섯이 그랬습니다. **숨기지 않고 모아 둡니다** —
제 시험을 어디까지 믿어도 되는지가 여기에 있습니다.

| 어디 | 무엇이 안 잡혔나 | 어떻게 했나 |
|---|---|---|
| `ReportPdf` | **요약을 아예 안 넘기는 실수.** 전문·요약을 목록 둘로 받고 개수를 `require` 로 검사했는데, 제품 쪽 한 줄이 통째로 빠져도 전부 통과 | **짝(`ReportWarning`)을 그대로 넘기게** 바꿔 어긋난 상태를 못 만들게 함 |
| `ReportPageLayout` | **죽은 줄.** 전문이 쪽을 넘쳤을 때 본문을 새 쪽에서 시작시키는 검사 | 바로 아래 `place` 가 같은 일을 하고 있어 **지움** |
| `Reanalysis` | **FFT 길이.** 이어지는 순음은 길이를 바꿔도 값이 거의 같아 설정을 통째로 무시해도 통과 | 낮은 대역(30Hz)으로 바꿔 잡음 |
| `Reanalysis` | **진행 알림 간격.** 시험 파일이 2초(47덩어리)라 걸러 낼 것이 없었음 | 200덩어리로, 횟수가 아니라 **간격 자체**를 봄 |
| `Reanalysis` | **잘림 깃발.** 제가 따로 세던 것이 엔진이 이미 보는 것과 같았음 | 시험을 덧대지 않고 **코드를 지움** |
| `SelahApp` | **화면에 콜백을 넘기는 한 줄.** 기본값이 있어 빠뜨려도 조용히 컴파일되고 단추만 아무 일도 안 함 | **기본값을 없애 컴파일이 막게** 함 → 그 자리에서 **다른 호출부 하나를 잡아냄** |

**셋은 시험을 고쳤고, 셋은 코드를 고쳤습니다.** 「시험이 못 잡으니
시험을 더 쓴다」가 늘 답은 아니라고 보았습니다 — **죽은 코드는 지우고,
틀릴 수 있는 자리는 못 틀리게** 만드는 편이 나은 경우가 있었습니다.

**제 변이 도구도 두 번 스스로를 망가뜨렸습니다.** 되돌릴 때 **역치환**을
썼는데, 빈 문자열이나 짧은 문자열을 되돌리면 **엉뚱한 자리에 끼워
넣습니다.** 소스가 깨진 채로 돈 회차의 결과는 **무효로 보고 다시
돌렸습니다.** 지금은 스냅샷에서 되돌립니다.

## 1. R2-02·R2-03 — 언제 시작해 언제 닫는가 (계약으로 못박음)

**제안하신 것보다 더 옮겼습니다.** 「n 과 sum 을 같은 잠금에서 읽는다」로는
모자라다고 보았습니다.

**한 일**

- **`close(offsetDb)` 하나로 떠 옵니다** — 평균·창 수·덮은 길이·원점·마지막
  창 끝이 **한 잠금 안에서** 한 덩어리(`RtaCoverageResult`)로 나옵니다.
  **닫은 뒤에 온 창은 거절**되므로 결과가 다시 바뀌지 않습니다. 떼어 내는
  명령이 언제 처리되는지에 기대지 않습니다.
- **구간과 한 표본도 안 겹치는 창은 합·개수에도 안 넣습니다.**
- **원점을 분석 스레드에서 박습니다**(`armAt(inputFrame)`). 첫 창에서
  원점을 잡으면 **시작에서 놓친 시간이 원점째로 밀려 사라진다**는 지적,
  그대로 맞았습니다. 이제 첫 창이 늦게 오는 만큼 **앞이 비어 보입니다.**

**계약으로 적었습니다** — 부분 중첩 창은 **통째로 넣습니다.** 창 하나의
전력은 되돌릴 수 없어, 겹친 길이로 곱하는 것은 「고르게 퍼져 있었다」는
가정이고 경계에 큰 소리가 걸리면 그대로 오차가 됩니다. 그래서 coverage 와
평균은 **서로 다른 것을 셉니다**: coverage 는 잘라 낸 겹친 길이의 합집합,
평균은 통째로 넣은 창들의 것.

**봐 달라**: 이 계약이 맞는 선택인지. 그리고 **원점을 박는 자리**가
맞는지 — `postToCapture` 로 오디오 스레드에 넣어 거기서 `inputFrameCount`
를 읽습니다.

**변이 확인**: 닫힘 검사 제거 → `닫은 뒤의 창은 결과를 바꾸지 못한다` 실패.
구간 밖 거부 제거 → `outsideWindowMustNotChangeMean` 실패. 창 수를 잠금
밖에서 읽기 → `meanMustUseOneAtomicSnapshot` 실패. 원점 박기 제거 →
`원점을 박으면 늦게 시작한 만큼 비어 보인다` 실패.

## 2. R2-01 — 무음이 사라지던 것 (High)

**두 군데를 고쳤습니다.**

- 평균의 **마지막 dB 변환**에 옛 길과 **같은** `SILENCE_DBFS` 를 겁니다.

**봐 달라**: 저장 실패로 돌리는 것이 맞는지(대안은 「경고와 함께 저장」).

**변이 확인**: 바닥값 제거 → `silentPcmMustHaveFiniteStoredBands` 실패.

## 3. R2-04 — **제 주장이 거짓이었습니다**

지적하신 그대로입니다. 「새 길은 그 구간의 **참값**이다」, 「같은 크기의
소리는 자리를 옮겨도 늘 같은 값」 — **둘 다 거짓입니다.** 시험을 **이미
셈해 둔 밴드 전력 배열**로만 돌렸기 때문입니다.

**까닭까지 확인했습니다.** Hann 은 50% 겹침에서 **창 자체**의 겹침 합이
1 로 일정하지만(COLA), 전력은 **창을 제곱**해서 씁니다:

```
w(n)=0.5(1-cos θ), w(n+N/2)=0.5(1+cos θ)
w² 합 = 0.5(1 + cos²θ) → 0.5 ~ 1.0,  비 2.0 = 3.0103dB
```

주신 실측 3.0136dB 와 맞습니다.

**정의를 그대로 적었습니다** — 「정한 경계 규칙에 따라 고른 FFT 창들의,
**평활하지 않은 밴드 전력의 선형 평균**」. 참값·위치 불변 주장은
설계 문서·시험 KDoc·이 문서에서 모두 **철회**했습니다.

**대신 주장하는 것**: **덩어리를 어떻게 잘라 넣든 같은 값**입니다.
같은 PCM 을 8192·1024·3000 표본씩 넣어 `1e-9` 안에서 같은 것을 시험으로
굳혔습니다(`RtaAveragePcmTest`). 옛 길에는 그 성질이 없었습니다.

**주신 반례는 지우지 않고** 단언을 참인 쪽으로 돌려 남겼습니다 —
자리를 타되 **3.02dB 를 넘지 않는다**. 지우면 다음에 누가 같은 주장을
다시 적습니다.

**봐 달라**: 이 정의 문장이 충분한지. 그리고 「블록 크기 불변」 말고 더
주장해도 되는 것이 있는지.

## 4. PDF — 권고 둘을 닫으러 갔다가 **결함을 하나 더 찾았습니다**

**새로 찾은 것**: `PdfDocument.writeTo` 가 스트림의 `IOException` 을
**삼킵니다.** 모든 바이트에서 던지는 스트림을 주었는데 `write` 가
**1장을 썼다고 돌려주었습니다.** 한 바이트도 안 나갔는데 「됐다」가
됩니다 — **R2-01 과 같은 성질**입니다. 사이에 스트림을 끼워 첫 실패를
붙들었다가 다시 던지고, **한 바이트도 안 나간 경우도 실패**로 봅니다.

**권고 둘**:
- **들여쓰기와 wrap 폭의 차이** — 12pt 들여 쓰면서 줄은 전체 폭으로
  끊었습니다. 꽉 찬 줄이 여백을 넘어 **잘린 글자가 사라집니다.**
  들여쓰기를 치수로 올려 **재는 폭과 그리는 자리가 같은 값**을 봅니다.
- **`finally` 정리** — `writeTo` 가 던지면 `close` 를 못 지나갔습니다.

**「핵심 요약은 늘 되풀이하고 전문은 따로」도 했습니다.** 처음에는
미루었다가 담당자 지시로 이어서 했습니다.

- **첫 쪽에 전문**이 온전히 남습니다. 한 쪽을 넘치면 **다음 쪽으로 이어
  적습니다** — 자르지 않습니다.
- **둘째 쪽부터는 핵심 한 줄**입니다. 「미보정 — 아래 dB 값은 참고용입니다」
  처럼 **읽는 사람이 숫자를 어떻게 다뤄야 하는지**를 남겼습니다.
- 요약이 종이 절반을 넘기면 그때는 줄이되 **「경고 전문은 1쪽에」**라고
  적어 찾아갈 수 있게 했습니다. **전문은 이미 1쪽에 온전하므로 잃는 것이
  없습니다.**

**설계에서 한 번 물러섰습니다.** 처음에는 전문과 요약을 **목록 둘**로
넘기고 개수가 같은지 `require` 로 검사했는데, **변이로 보니 요약을 아예
안 넘기는 실수를 아무 시험도 잡지 못했습니다.** 그래서 **짝**
(`ReportWarning`)을 그대로 넘기도록 바꿨습니다 — 어긋난 상태를 만들
수가 없습니다. 검사를 하나 더 두는 것보다 **못 틀리게 만드는 편**이
낫다고 보았습니다.

**죽은 줄도 하나 지웠습니다.** 전문이 쪽을 넘쳤을 때 본문을 새 쪽에서
시작시키는 검사를 넣었는데, **변이로 지워도 아무 시험이 안 잡혔습니다** —
바로 아래 `place` 가 같은 검사를 이미 하고 있었습니다.

**봐 달라**: 핵심 한 줄의 **문구**가 뜻을 줄이지 않았는지. 그리고 전문이
쪽을 넘칠 때 **본문보다 앞**에 이어 적는 것이 맞는지(부록으로 뒤에 두는
쪽도 있습니다).

**변이 확인**: `failOnProblem()` 제거 → `쓰다 실패해도 다음 장을 뽑을 수
있다` 실패. wrap 폭을 전체 폭으로 되돌림 → `경고는 들여쓴 만큼 좁은
폭으로 끊는다` 실패.

## 5. Recording-D — 그래프를 눌러 그 시점의 소리로 간다

| | |
|---|---|
| PR | #104 |

## 6. Recording-E — 저장한 WAV 를 다시 분석한다 (새 기능)

| | |
|---|---|
| PR | #105(셈) · #106(저장 구조·화면) |

**`analysisVersion` 칸만 있고 다시 분석하는 코드가 없었습니다.** 저장한
소리를 **다시 읽을 길 자체가 없어** `WavReader` 부터 지었습니다.

**왜 필요한가** — 예배가 끝난 뒤에 보정을 합니다. 그러면 **이미 담아 둔
소리**를 새 잣대로 다시 셈할 수 있어야 합니다. 그러지 못하면 보정 전의
기록은 영영 「참고용」으로 남고, **그 예배는 다시 오지 않습니다.**

### 라이브와 **같은 코드**를 씁니다

`SessionRecorder` 를 그대로 돌리고 마이크 대신 `WavReader` 를 물립니다.
재분석 전용 경로를 따로 지으면 **두 길이 조용히 갈립니다.**

### 원본을 지키는 방식 — **여기를 가장 봐 주십시오**

| | |
|---|---|
| **원본** | 처음 다시 분석할 때 `timeline-v1.bin` 으로 복사, **그 뒤로는 덮지 않음** |
| **지금 것** | `timeline.bin` 자리 그대로 |
| **소리** | 손대지 않음(시험으로 못박음 — 내용·고친 시각 둘 다) |

**두 번째 재분석이 첫 번째 결과를 「원본」으로 만들면 처음 잰 것이
사라집니다** — 그 경우를 따로 잡았습니다.

`timeline.bin` 자리를 지킨 까닭: 다른 이름으로 두면 **읽는 쪽을 전부
고쳐야 하고**(화면·CSV·PDF), 하나를 빠뜨리면 **어떤 화면은 옛 숫자를
보여 줍니다.**

### 겉장 판을 **3 으로** 올렸습니다

`reanalyzedAtEpochMs` 와 `originalTimelineName` 두 줄이 붙습니다. 없으면
「한 번도 안 한 것」이라 뜻이 분명해 **옛 기록도 그대로 읽힙니다.**

### **놓친 조각 수는 건드리지 않습니다**

녹음이 놓친 조각은 **파일에 아예 없습니다.** 다시 읽어서는 몇 개를
놓쳤는지 알 길이 없고, **0 으로 적으면 「안 놓쳤다」는 거짓**이 됩니다.

### 봐 달라

1. **원본 보존 방식**이 맞는 선택인지. 「새 세션을 만든다」 쪽도 있었는데,
   소리 파일이 옛 세션 폴더에 있어 **옛 것을 지우면 새 것이 깨집니다.**
2. **`timeline.bin` 을 갈아 끼우는 것**이 맞는지(읽는 쪽을 안 고치려고).
3. **겉장에서 무엇을 바꾸고 무엇을 그대로 두는가**의 경계.
   지금은 「셈해서 달라지는 것만」인데, `conditions`(가공 여부·입력 경로)를
   그대로 두는 것이 맞는지.
4. **WAV 읽기의 관용 범위** — 모르는 덩어리는 건너뛰고, **꼬리가 잘린
   파일은 있는 만큼** 읽습니다(녹음 중에 앱이 죽으면 그렇게 됩니다).
   너무 관대한지.

### 못 되살리는 것 — 문서에 적었습니다

- WAV 는 **16비트로 눌린** 소리라 아주 조용한 구간은 원본과 **딱 같지
  않습니다**(16비트 바닥 -96dBFS 쯤). 시험은 **0.1dB 안**으로 견줍니다.
- 녹음이 **놓친 조각은 파일에 없으므로** 다시 분석해도 되살아나지 않고,
  원본의 `missing` 행과 **다르게** 나옵니다.

### 변이에서 **헛그물이 넷** 나왔습니다

| 무엇이 헛그물이었나 | 어떻게 했나 |
|---|---|
| **FFT 길이** — 이어지는 순음은 길이를 바꿔도 값이 거의 같아 **설정을 통째로 무시해도 통과** | 낮은 대역(30Hz)으로 바꿔 잡음 |
| **진행 알림 간격** — 시험 파일이 2초(47덩어리)라 **걸러 낼 것이 없었음** | 200덩어리로 늘리고, 횟수가 아니라 **간격 자체**를 봄 |
| **잘림 깃발** — 제가 따로 세던 것이 **엔진이 이미 보는 것과 같았음** | 시험을 덧대지 않고 **코드를 지움** |
| **`SelahApp` → 화면 콜백 한 줄** — 기본값(`= {}`)이 있어 **빠뜨려도 조용히 컴파일**되고 단추만 아무 일도 안 함 | **기본값을 없애 컴파일이 막게** 함. 그 자리에서 **다른 호출부 하나를 잡아냄** |

### 속도는 실기기에서 쟀습니다

SM-S918N 에서 **실제 길이의 32배**(300초 → 9.3초). **1시간이 2분 안**이고
**선형**이며 메모리는 길이와 무관하게 3~6MB 입니다. 발열 없음.
**다만 잰 것은 300초까지**입니다.

### PND-03 — 10초 평균을 실제로 10초로 (단계 A·B)

| | |
|---|---|
| 설계 | [`../superpowers/specs/2026-09-30-rta-coverage-tap-design.md`](../superpowers/specs/2026-09-30-rta-coverage-tap-design.md) |
| PR | #95(설계) · #96(단계 A) · #97(단계 B) |

**무엇이 잘못됐었나**: 저장되던 「10초 평균」은 10초치 소리의 평균이
아니었습니다. ① 화면용으로 **평활된 값**을 다시 평균했고, ② 화면은 66ms 에
한 번만 받으므로 **분석한 장의 3분의 1 이상이 안 들어왔습니다**(실기기에서
초당 23.5장 중 15장 남짓).

**한 일**: 평활 **바로 앞**에 sink 를 달고, **겹친 창을 이중으로 세지 않는**
누적기를 붙였습니다(창들이 덮은 입력 구간의 **합집합**). 단계 A 는 적기만,
단계 B 에서 평균을 그 값으로 바꾸고 `averageVersion` 을 올렸습니다.

**봐 달라**:
- **창 경계 규칙** — 측정 시작·끝에 걸친 창을 넣을지 뺄지. 지금은 **켠 뒤
  첫 창을 0 으로** 삼고 10초를 넘는 꼬리는 자릅니다.
- **「못 받으면 저장 안 함」이 맞는 선택인지.** 옛 길로 돌아가면 같은 이름을
  단 두 값이 섞입니다. 대신 **분석이 안 도는 상황에서는 아무것도 안
  남습니다.**
- `averageVersion` 으로 옛·새 기록을 가르는 방향.

**제가 틀렸던 것**: 「옛 길은 짧고 큰 소리를 **작게** 적는다」고 적었는데
**반대로 나왔습니다**(옛 길이 0.28dB 더 큼). 실제 성질은 **「같은 소리에
같은 답을 못 준다」** 입니다 — 자리만 옮겨도 값이 달라집니다.

**확인 못 한 것**: **문턱값**(단계 D). 기기 여럿에서 정상 측정의 coverage
분포를 먼저 재야 합니다. 지금은 **적기만 하고 판정에 안 씁니다.**
