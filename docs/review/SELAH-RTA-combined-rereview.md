# SELAH RTA 통합 재검증

검증일: 2026-09-21 · 대상: `a236363..b220030` · **판정: 승인 보류**

**High 1건, Medium 2건이 남아 있다. Critical은 발견하지 않았다.** 기존 DSP 회귀 시험과 세대 규칙 시험은 통과했지만, 기록 보존 수정이 새로 만든 종료 경합을 확인했다. 요청서의 질문에 대한 핵심 답은 **캡처 루프와 세대 클래스의 단위 시험만으로는 부족하며, ViewModel의 상태 전이까지 검증해야 한다**는 것이다.

## 남은 결함

### C01 · High — stop이 이미 실행 중인 DSP와 동시에 finish를 호출한다

**위치:** `app/…/ui/CaptureViewModel.kt:1044–1054`, 콜백 입구 `781` 및 DSP 처리 `798–800`; `dsp/…/FeedbackDetector.kt:261–266`.

**원인:** `active=null`과 `generation.end()`는 **이후 입구 검사에 도달한 콜백**을 막는다. 이미 `if (active !== session) return`을 통과한 콜백은 계속 실행한다. 그런데 `stop()`은 `source.close()`보다 먼저 같은 `session.feedback.finish()`를 main thread에서 호출한다. “이미 입구에서 걸려 객체를 건드리지 않으므로 경합하지 않는다”는 주석은 이 실행 순서를 고려하지 않았다.

**재현 순서:** 캡처 콜백이 세션 검사 통과 → main이 stop에서 active 무효화 → main의 finish가 tracks를 순회 → 캡처가 process에서 새 track 추가 또는 만료 track 제거. 일반 ArrayList 순회와 구조 변경이 겹친다. 역순에서는 finish가 비운 뒤 process가 다시 후보/이벤트를 만들 수도 있다.

**독립 실행 근거:** 대상의 실제 `FeedbackDetector.process/finish`를 수정하지 않고, 테스트에서 tracks의 ArrayList iterator에 latch를 넣어 finish 순회 중 작업 스레드의 process를 진행시켰다. 결과는 **`java.util.ConcurrentModificationException`**이었다. 이는 허용되는 스케줄링 순서를 고정한 경합 재현이다. Android나 ViewModel을 실행한 시험, 실기기 발생률 측정은 아니다. ViewModel이 두 호출을 실제로 병행할 수 있다는 것은 위 코드 순서로 확인했다.

**사용자 영향:** 정상 중지, 홈 이동, 자동 장치 전환 중 main thread 예외로 앱이 종료되거나 마지막 기록이 누락될 수 있다. P9-01의 단순 복사 누락은 고쳐졌지만 종료와 기록 확정 전체는 아직 안전하지 않다.

**권장 수정:** detector를 한 실행 주체만 소유하게 하고, 진행 중 처리의 종료와 최종 기록 전달을 명시적으로 동기화한다. 예를 들어 worker의 종료 명령/완료 응답으로 불변 최종 snapshot을 넘기거나, 같은 동기화 경계에서 process와 finish를 직렬화한다. 단순히 active 검사 한 번을 더 추가하는 것으로 해결하지 않는다. `finish()`를 현재 `close()` 뒤로 옮기는 것만으로도 충분하지 않다. close는 500 ms timeout 뒤 worker 종료를 보장하지 않는다. main thread의 장시간 대기는 피해야 한다.

**필요 회귀 테스트:** 입구 검사 **이후** barrier에 멈춘 onBlock → stop/ON_STOP/fallback → worker 재개. 예외 없음, 기록 보존 및 종료 상태, 이전 세션의 최종 결과가 새 세션을 덮지 않음, stop 반복 호출을 검사한다. 기존 FakeRecorder의 **read 중** barrier와는 다른 위치다.

### C02 · Medium — 이전 재생의 늦은 오류 통지가 새 재생 UI를 지운다

**위치:** `app/…/audio/SignalPlayer.kt:163–174`; `app/…/ui/CaptureViewModel.kt:322–328, 615–621`.

**논리적 재현:** A worker의 write 오류 → generation 검사 통과 → `onEnded(reason)`가 main에 상태 변경을 예약 → main이 새 B 재생을 시작 → 예약돼 있던 A 오류 처리 실행. ViewModel의 콜백에는 재생 세대가 없고 처리 시점 검사도 없어 **B가 소리를 내는 중에 playingSignal=null**로 바뀐다. main의 새 start 도중 A 오류가 도착해 queued 상태가 되는 순서도 가능하다.

**사용자 영향:** 새 신호가 출력 중인데 화면에는 중지된 것으로 보이며, 해당 행의 동작도 ‘멈추기’에서 ‘내보내기’로 바뀐다. 원래 P9-05의 오류 무통지는 개선됐지만 새 재생과의 구분은 끝까지 이어지지 않았다.

**권장 수정:** onEnded에 재생 세대/세션 객체를 전달하고 **main에서 소비할 때** 현재 세대와 대조한다. SignalPlayer 내부의 generation·track·playing 정리도 같은 소유/동기화 규칙으로 처리한다. 현재 plain generation 변수와 검사 후 공유 상태 변경만으로는 원자성이 보장되지 않는다. 세션별 취소 상태를 사용해 timeout 후 옛 worker가 공유 running=true를 보고 다시 반복하지 못하게 한다.

**필요 회귀 테스트:** A 종료 통지를 main 큐에 보류 → B start → A 통지 전달; 정상 stop 뒤 늦은 오류; 500 ms를 넘긴 이전 worker; 오류와 start 동시 수행. 새 재생의 UI·track·취소 상태가 보존돼야 한다. 이 항목은 코드의 이벤트 순서 분석이며 Android 출력 오류를 실기기에 주입한 결과는 아니다.

### C03 · Medium — 관측이 끝난 뒤 무음에서 Persistent로 승격된다

**위치:** `dsp/…/FeedbackDetector.kt:245, 343–347, 384–392`.

**독립 실행 근거:** 1 kHz를 t=0부터 43 ms 간격으로 t=1462 ms까지 35프레임 입력했다. 이 시점에는 이벤트가 없다. t=1505 ms에 **무음** 한 프레임을 입력하자 `start=0, duration=1462, end=null`인 Persistent 이벤트가 생성됐다. 설정된 지속 기준은 1500 ms인데 실제 마지막 관측은 그보다 짧다.

**원인:** 오래된 track을 매칭 전에 제거하는 수정은 2초 공백 재현을 해결했다. 그러나 250 ms 유예 안에서는 보이지 않는 track에도 `record(nowMs)`를 호출하고, 판정 duration은 여전히 `now-firstSeen`이다. 따라서 공백 유예 시간이 승격에 필요한 지속 증거로 사용된다.

**사용자 영향:** 지속 기준보다 짧게 나타난 소리가 이미 사라진 뒤 기록에 들어간다. 이벤트 duration과 Persistent의 의미도 어긋난다. 2초 공백 시험 통과만으로 P9-03 전체를 닫을 수 없다.

**권장 수정:** gap은 이미 추적 중인 후보의 유지 유예로 다루고, 새 승격은 마지막 실제 관측까지의 시간 및 관측 업데이트를 근거로 판단한다. 무음 프레임만으로 Suspect→Persistent가 되지 않도록 한다. 판정·표시·기록 duration의 정의를 맞춘다.

**필요 회귀 테스트:** 1462 ms 관측→1505 ms 무음, 지속 문턱 바로 전 종료, 배음의 4500 ms 문턱 직전 종료, gap 안 재출현. 짧은 신호는 무음으로 시간이 흘렀다는 이유만으로 이벤트를 남기지 않아야 한다.

## 요청서의 일곱 질문에 대한 답

### 1. 시험 이음매는 ViewModel까지 필요한가?

**필요하다.** 현재 두 조각은 read 취소와 세대 비교 각각을 확인할 뿐, 실제 호출 순서·상태 합성·종료 snapshot 전달을 증명하지 않는다. P9-01과 이번 C01 모두 그 사이에서 발생했다.

다만 ViewModel 전면 재작성은 필요하지 않다. AudioSource factory, 장치 목록/설정/보정 Flow, main dispatcher/clock을 주입하거나, 그 의존성을 받는 작은 세션 제어 객체를 추출해 **실제 production 상태 전이**를 시험할 수 있게 하면 된다. 테스트 안에 ViewModel 로직을 복제한 모형으로 대신하지 않는다.

최소 시험은 onBlock 진입 후 stop, read-error/장치-removal 순서 교환, 늦은 route 확인, A→B 세션 전환 후 A snapshot, 보정 도착 전후, 기록 종료·보존·새 측정 초기화, 이전 재생 오류의 지연 전달이다. USB 하드웨어 없이 검증할 수 있는 순서 조건부터 고정해야 한다.

### 2. F05를 표본 표시로 마무리해도 되는가?

가능하다. 현재처럼 로그 위치 0.25/0.5/0.75와 1 dB가 자체 기준임을 밝히고 **상한·표준 정확도 인증처럼 표현하지 않는 조건**이다. ‘모든 밴드에 똑같은 오차’라는 주석은 ‘경계 누설은 전 대역에서 발생할 수 있다’ 정도로 완화하는 편이 정확하다. 한 1 kHz 사례만으로 31개 전체의 동일한 손실량을 증명한 것은 아니다. 이 표현 정리는 Low 수준이며 별도 결함 건수에 중복 계상하지 않았다.

### 3. reroute를 분리 정책에 묶어도 되는가?

다른 마이크 PCM과 보정을 섞지 않기 위해 **현재 세션을 종료한다는 기본 동작은 합리적**이다. 원인이 물리적 분리와 다르므로 reason은 구별해야 한다. 반복 실패의 재시작 횟수/시간 상한을 두고 초과 시 사용자 재시작을 기다리게 하는 것이 좋다. 특히 이미 내장 fallback 상태에서 또 ERROR_DEAD_OBJECT가 발생하는 순서를 시험해야 한다. 무한 자동 재시작이 없다는 검증은 아직 없다.

### 4. USB가 두 개면 어느 쪽을 선택해야 하는가?

명세에 유일한 정답은 없다. 권고 정책은 **명시 선택 우선 → 유효한 현재 USB 유지 → 최초 선택 때만 명시된 안정적 우선순위**다. 현재 chooseInput은 48 kHz 지원 여부 다음에 목록의 첫 장치로 결정한다. 그 목록 순서가 제품 정책을 대신하지 않도록 하고, 새 USB가 추가됐다는 이유만으로 정상 USB 세션을 불필요하게 끊지 않게 한다. 둘을 한 번에 연결/순서 반전/하나 제거/명시 선택 소실하는 경우를 시험한다. 현재 안내문의 ‘자동 사용 꺼짐’ 분기는 이미 다른 외부 기기가 선택되는 경우에도 사용될 수 있으므로 실제 사유에 맞춰야 한다.

### 5. finish의 끝 시각과 종료 사유는?

**마지막으로 관측한 시각**은 이벤트의 신호 지속 구간 끝으로 적절하다. 별도로 `closeReason`을 두어 SilenceGap / UserStop / Background / RouteChange / CaptureError 등을 구별하는 편이 맞다. 측정 종료로 관측이 잘린 사건은 소리가 실제로 그쳤다는 증거가 아니다. Phase 10에서 영속화하기 전에 이 의미를 정해야 한다. 필요하면 사건 종료 시각과 세션 종료 시각을 별도로 저장한다.

### 6. 솟은 순서의 일대일 매칭은 충분한가?

중복 계수 문제는 해결하지만 identity 보장은 아니다. 현재는 허용 범위의 **첫 track**을 찾으므로 가까운 두 peak의 prominence 순서가 바뀌기만 해도 정체성이 바뀔 수 있다. 가능한 매칭 중 주파수 거리·예측 연속성을 우선하거나, 모호한 합류/분리는 종료 후 새 track으로 정의한다. EQ용 후보 주파수 표시에서는 어느 선택이든 명시 가능하지만 이벤트 duration과 최대값을 섞지 않는 정책이 필요하다. 주파수 교차, 레벨 역전, 한 peak 소실을 시험하고 두 후보의 개수·주파수까지 단언한다. continuity≤1만 검사하면 둘 다 사라지는 회귀도 통과할 수 있다.

### 7. 5칸/48칸 기준은 지금 고쳐야 하는가?

즉시 모두 Hz로 바꿀 필요는 없다. Hann 순음 주엽 폭은 bin 단위로 정의하는 것이 자연스럽다. 주변 median의 범위는 원하는 음향적 주변 대역이 Hz인지 상대 대역폭인지 선택할 문제다. **44.1 kHz에서도 검증하는 것은 필요**하다. 48 kHz 대비 폭은 약 8.1% 작아지며, 이는 현재 잠정 판정의 샘플레이트 의존성이다. 두 샘플레이트에서 같은 PCM 신호군의 검출 여부·지연·오탐을 비교하고 허용 차이를 정한다. ADR에 한계를 적는 것만으로 이 시험을 대체할 수 없다.

## 잔여 위험과 재검증 조건

합성 주입 제거는 제품 범위 결정으로 기록할 수 있다. 다만 스피커 시험이 합성 입력 시험을 완전히 대체하거나 항상 ‘더 많이 검증한다’는 주장은 성립하지 않는다. 알려진 PCM·재현 가능한 시간축·무음 자동화와 실제 음향 경로 검증은 서로 다른 목적이다. mock을 실제 마이크로 오표시하지 않는 한 debug 주입 자체가 명세 §0과 모순되는 것도 아니다. ADR에는 이 차이를 유지해야 한다.

시험 문구의 말소리 모형 한계와 events 검사 추가는 개선됐다. 실제 설교·찬양의 오탐률/놓침률, 44.1 kHz, USB 복수 장치, 60분 부하·열·메모리, 기준 계측기 비교는 여전히 미확인이다. 후보 표시가 이들 검증을 대체하지 않는다.

**C01을 수정하고 실제 상태 전이 통합 회귀 시험을 통과하기 전에는 게이트 승인을 보류한다.** C02·C03도 수정 또는 명시적인 수용 판단이 필요하다. 이전 지적의 해결 부분은 위 표처럼 인정하되, 전체 ‘모두 해결’로 기록하지 않는다.

같은 outputs 폴더에 `CombinedProbe.kt`, `run-combined-verification.ps1`, `combined-verification-log.txt`를 첨부했다. 실행 스크립트는 저장소 읽기와 임시 사본 컴파일만 수행하며 production 파일이나 전역 Git/Gradle 설정을 변경하지 않는다.
