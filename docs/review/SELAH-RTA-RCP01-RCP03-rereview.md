# SELAH-RTA RCP01–RCP03 독립 재검토

날짜: 2026-09-23
대상: `47ef620..4a8916c` (11파일, +640/−31)

## 판정

**종료 승인 보류. Critical 없음, High 1건 잔존.** 이전 반례에 대한 계산 수정은 확인했다. RCP01의 서로 다른 정규화 지지구간 및 0점 진행 결함, RCP03의 버린 표본 산입 결함은 종료 가능하다. RCP02의 기준 SNR 입력·마스크는 구현됐지만, 최종 승인 판정에 교집합이 연결되지 않아 전체 종료는 불가하다.

production 코드는 수정하지 않았다. 작업 트리는 검토 전후 깨끗하다. 사용자 요청에 따라 독립 검증했으며, 첨부 요청서의 완료·시험 주장은 검증 대상이다.

## RCP-F01 — High: 최종 사용 가능 대역과 품질 승인 판정이 분리돼 있다

위치:

- `dsp/src/main/kotlin/kr/joa/selahrta/dsp/CalibrationQuality.kt:178`: bothUsable은 존재한다.
- 같은 파일 `:231`, `:297`: 대상과 기준의 유효 비율을 **각각** 검사한다.
- 같은 파일 `:314`: 범위 경고는 **대상** usableRangeHz만 사용한다.
- 같은 파일 `:204`: Pass는 mayAutoApply=true가 된다.
- `CalibrationSession.kt:308–330`: CAL 범위와 공통 정규화 지원 여부가 곡선 생성에만 반영된다.

### 독립 재현 A — 각각은 충분하지만 함께 쓸 대역은 부족하다

31개 대역에 신호 70dB, 각 단계 8프레임을 넣는다. 대상의 배경은 index 0–18 및 30에서 40dB, 나머지에서 70dB. 기준의 배경은 index 12–30에서 40dB, 나머지에서 70dB. CAL 범위는 20–20000Hz. DSP 확인 true, CAL 적용 선언 true.

```text
INTERSECTION target=20 reference=19 common=8 total=31
verdict=Pass auto=true correctionValid=24 normPoints=24
```

대상 20/31, 기준 19/31은 각각 기본 최소 60%를 넘지만, 교집합은 **8/31=25.8%**다. 공통 정규화 구간이 있으므로 곡선 생성도 성공한다. bothUsable을 만들어 놓고 judgeQuality에서는 쓰지 않아 이 상태가 Pass다. 대상에 마지막 대역을 포함해 대상 자체 범위 경고가 다른 결함을 가리지 않게 했다.

### 독립 재현 B — CAL 범위가 극히 좁아도 Pass다

모든 경로의 신호 70dB, 배경 40dB, 각 단계 8프레임으로 충분한 SNR을 준다. CAL 범위만 1000–1300Hz로 제한한다.

```text
NARROW_CAL verdict=Pass auto=true correctionValid=4 normPoints=4 bands=2
```

최종 보정은 1kHz 부근 4개 축 점에만 유효하지만, 대상 usableRangeHz는 전체 대역이므로 좁은 범위 경고도 없다. 이 관측은 새 임의 문턱을 요구하는 것이 아니라, 이미 존재하는 최소 사용 비율 및 좁은 범위 정책이 **실제 보정 범위**를 보지 않는다는 증거다.

### 사용자 영향

잡음 때문에 기준과 대상이 서로 다른 구간을 잃거나 CAL 측정 범위가 좁을 때, 일부 대역용 곡선이 검증 완료·자동 적용 가능으로 분류된다. 마스크 자체는 유지되므로 무효 구간의 보정값이 살아난다는 주장은 아니다. 문제는 실제 지원 범위를 반영하지 않는 승인과 안내다. 현재 파일 바인딩·마법사가 없으므로 실제 사용자 프로필 저장이나 기기 자동 적용을 관찰한 것은 아니다.

### 권장 수정

1. 대상 SNR, 기준 SNR, CAL 범위를 합친 **승인용 공통 유효 대역**을 만들고, 기존 최소 유효 비율 및 범위 검사를 여기에 적용한다. 각 경로의 개별 통계는 원인 안내용으로 보존한다.
2. 보간 과정에서 더 줄어든 실제 보정 범위와 정규화 결과도 최종 승인에 전달한다. 품질 계산을 곡선 생성 전후로 나누거나, 세션 판정 함수에서 outcome과 quality를 함께 받는 식으로 연결할 수 있다.
3. 진단 곡선 반환은 허용하되, 진단 계산 성공과 저장/자동 적용 승인을 구분한다. 좁은 범위 보정을 허용한다면 그 범위와 제한이 verdict·안내에 반영돼야 한다.

### 필요한 회귀 테스트

- 위 A: 두 개별 비율이 통과하고 교집합이 8/31임을 먼저 단언한 뒤 최종 Pass 금지를 확인.
- 위 B: 충분한 두 경로 SNR과 양수 정규화 점을 먼저 단언한 뒤, CAL 제한이 최종 판정/범위 안내에 반영됨을 확인.
- 양쪽 모두 충분한 넓은 범위→Pass, 교집합 0→승인 불가, 최소 비율 경계, SNR 제한과 CAL 제한이 동시에 있는 경우.
- 결과를 profile용 품질 요약으로 변환할 때 최종 승인 상태와 유효 범위가 보존되는지 확인.

## 요청서의 정책·설계 질문

- **0보다 큰 정규화 지원의 최소 대역 수:** 근거 없는 숫자를 새로 넣지 않는 판단에는 동의한다. 하지만 숫자를 표시하는 것만으로 신뢰도가 검증되지는 않는다. 특히 현재는 기존 비율/범위 관문조차 최종 지원 범위를 보지 않는다. 우선 RCP-F01을 수정하고, 남은 희소·편중 정규화의 충분성은 실측 검증 전까지 불확실성으로 표시해야 한다. 전체 원래 대역 수뿐 아니라 정규화 안에서의 폭·분포와 오프셋 반복성도 필요하다.
- **referenceCalApplied 타입 개선 연기:** 실제 bin 보정 생산자가 생길 때 제한된 생성자 타입과 함께 연결하는 것은 합리적이다. 다만 그때까지 실제 적용·이중 적용 방지는 미검증이며, Boolean true를 증거로 승격하지 않는 조건이다. 캡처 경로 연결 단계의 필수 통합 시험으로 유지해야 한다.
- **형식 버전 유지:** 배포·저장·외부 교환된 구형 파일이 전혀 없다는 전제라면 개발 중 schema 변경에 migration을 만들지 않는 선택은 가능하다. 현재 decoder는 새로운 refNormalized 필드를 요구하므로 이전 문자열과 호환되지는 않는다. 외부 소비자/fixture까지 없다는 사실은 이번 검토로 증명하지 않았다. 첫 영속화 전에 schema 계약을 확정하고, 알려진 구형 fixture의 거절 또는 migration 동작을 명시하는 것이 좋다.
- **8프레임/2dB:** 이번 코드 변경으로 실측 근거가 생긴 것은 아니다. 기존 잔여 위험을 유지한다.

## 실행 범위와 근거

Kotlin 2.2.20/JBR로 현재 소스를 직접 컴파일하고 JUnit 4.13.2로 **144개 시험을 독립 실행하여 모두 통과**했다.

실행 클래스: RecheckProbeTest, CalibrationSessionTest, CalibrationQualityTest, SpectrumAverageTest, ResponseCalibrationTest, MeasuredProfileTest, ProfileCodecTest, PipelineProbeTest.

별도 `RCP-ApprovalProbe.kt`로 RCP-F01의 두 경우를 재현했다. 모든 시험 통과가 이 두 승인 오류를 배제하지는 않는다.

Gradle 전체 build/lint, 구현자 주장 659개 전체 시험, 변이 4건은 이번에 독립 재실행하지 않았다. 실제 음향 측정·USB·캡처 CAL 적용·저장 바인딩·교정 UI·실기기 비교 화면은 검증하지 않았다. 이전 검토의 다른 기능 전체를 다시 승인한 것도 아니다.
