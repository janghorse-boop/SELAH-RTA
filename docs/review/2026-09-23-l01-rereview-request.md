## 0. 한 줄 요약

F01-R 종료 판정 감사드린다. 차단 항목이 아니라고 하신 **L01 도 고쳤다** —
문구가 사실이 아닌 것을 말하는 부류라 두고 넘기지 않았다.

덤으로 지적해 주신 **사실 오류(18 vs 19)를 좇다가 제 시험 표본이 가짜
주파수 격자를 쓰고 있던 것**을 찾아 고쳤다. §4 에 적었다.

---

## 1. 고치기 전 — 재현됐다

```
CAL_ONLY approved=18 supported=16 maxCorrection=0.0 pre=Fail final=Fail
[… 계산을 마친 뒤 보정이 걸리는 대역이 16/31(52%)뿐입니다 — 60% 는
 되어야 합니다. 보정량이 상한(12dB)을 넘는 자리가 많다는 뜻입니다. …]
```

`BOUNDARY` 줄은 하나도 찍히지 않았다 — CAL 경계 169조합에서 6·12·24점/
옥타브의 지원 대역 수가 갈리지 않았다는 검토서 결과와 같다.

커밋 `8c30512` 가 이 재현만 담는다.

## 2. 고친 뒤

```
CAL_ONLY approved=18 supported=16 maxCorrection=0.0 pre=Fail final=Fail
[… 계산을 마친 뒤 보정이 걸리는 대역이 16/31(52%)뿐입니다 — 60% 는
 되어야 합니다. 까닭: SNR·CAL 범위 밖 15대역. …]
```

수치는 그대로고 **까닭만 바뀌었다.** 「수치 관문을 바꿀 필요는 없다」는
권고 그대로다.

---

## 3. 어떻게 가렸나

지원을 줄이는 길은 셋인데 **셋 다 같은 결과(`valid = false`)를 남겨서**
결과만 보고는 어느 쪽인지 알 수 없었다. 그래서 상한에서 잘린 자리를
따로 기록했다:

```kotlin
limitedByMaxCorrection = BooleanArray(axis.size) {
    smoothed.valid[it] && !limited.valid[it]   // 평활까지는 믿을 만했는데 상한이 잘랐다
}
```

`CalibrationOutcome.unsupportedReasonsKo()` 가 지원 못 한 대역을 나눈다:

| 까닭 | 어떻게 아는가 |
|---|---|
| 분석 축 범위 밖 | 그 밴드 경계 안에 축 점이 하나도 없다 |
| 보정량이 상한을 넘음 | 그 밴드의 어떤 점이 `limitedByMaxCorrection` 이다 |
| SNR·CAL 범위 밖 | 상한 이전에 이미 무효였다 |

**일어난 까닭만 적는다.** 없는 까닭을 나열하지 않는다.

### 요구하신 회귀 시험

| 요구 | 시험 |
|---|---|
| 보정값 전부 0 인 CAL 제한 입력에서 상한으로 단정하지 않는지 | `상한을 넘지 않았으면 상한을 탓하지 않는다` |
| 실제 상한 초과 입력에서는 해당 원인이 나오는지 | `상한에 걸렸으면 상한을 짚는다` |

앞의 것에는 전제 확인을 넣었다 — 보정값이 **정말** 전부 0dB 이고
상한이 자른 점이 없는지 먼저 단언한다. 그러지 않으면 표본이 바뀌었을
때 시험이 조용히 뜻을 잃는다.

「일어나지 않은 까닭은 적지 않는다」와 「전부 지원되면 까닭이 비어
있다」도 함께 잰다.

---

## 4. **제 시험 표본이 가짜 주파수 격자를 쓰고 있었다**

「실제 세션의 정확 중심 주파수에서는 최저 대역이 20Hz 미만이어서 이 CAL
범위의 입력 유효 수는 19가 아니라 18이다」를 확인하러 갔다가 찾았다.

`CalibrationQualityTest.bands()` 가 `20 * 2^(i/3)` 이라는 **호칭** 격자로
`BandNoise` 를 만들고 있었다. 제품 경로(`qualityFromSession`)는
`ThirdOctave.exactCenter` 를 쓴다. 두 격자는 다르다:

| 밴드 | 호칭 격자 | 실제 중심 |
|---|---|---|
| 0 | 20.00 | **19.95** |
| 18 | 1280.0 | 1258.93 |
| 19 | 1612.7 | 1584.89 |

CAL 20~1300Hz 를 걸면 호칭 격자에서는 19개, 실제 격자에서는 **18개**다.
제가 회신서 §3 에 적은 「19/31 = 61.3%」는 그래서 틀렸다 — 실제로는
58% 다.

실제 중심주파수로 바꾸자 **「CAL 이 조금 좁으면 범위를 알린다」가 Fail 로
깨졌다.** 비율 관문에 먼저 걸린 것이다. 관문을 느슨하게 하는 대신
표본을 다시 계산했다 — 19~1300Hz 는 밴드 0~18 = 19/31 = 61.3% 다.

같은 파일의 다른 표본 둘도 실제 격자로 바꿨다.

**이 시험들은 지금까지 「통과」하고 있었지만, 제품이 보는 것과 다른
주파수를 보고 있었다.** 수치가 나오는 시험에서 격자가 다르면 값의
뜻이 달라진다.

## 6. 축 해상도·최종 분기에 대한 말씀

- **169조합 일관성**: 저도 같은 결과를 얻었다(`BOUNDARY` 줄 0개).
  「검사한 조합의 일관성이지 수학적 불변성 증명은 아니다」에 동의한다 —
  저장소 시험도 그 이상을 주장하지 않는다.
- **`supportedBands` 는 축 점에서 평가한 지원**이라는 정의도 그대로
  받아들인다. 실제 FFT bin 적용과 연결할 때 보간·마스크까지 함께
  검증해야 한다는 것을 §7 에 남겼다.
- **최종 함수의 `validCount == 0` 분기**: 말씀대로 지금의 「유효점 0개」
  시험은 세션 **입구**의 거절을 잰다. 최종 outcome 에서 전부 무효인
  경우를 직접 단언하지는 못한다 — `calibrateFromSession` 이 그 전에
  거절하므로 그런 outcome 을 만들 길이 없기 때문이다. 억지로 만들려면
  `CalibrationOutcome` 을 손으로 조립해야 하는데, 그건 실제 계산 경로를
  통과하지 않는 시험이 된다. **저장 통합 단계에서** 실제로 그런 결과가
  나올 수 있는 경로가 생기면 그때 직접 단언하겠다.

## 7. 열려 있는 것 (이번에도 줄지 않았다)

- **`judgeCalibration` 을 production 저장·자동 적용 경로가 아직 쓰지
  않는다.** 남은 위험 중 둘(이것과 `referenceCalApplied`)이 마법사에
  걸려 있어, 다음 작업으로 그것을 만들려 한다.
- `referenceCalApplied` 가 선언 Boolean 인 것.
- `minFramesPerStep = 8` · `maxReferenceBandDriftDb = 2.0` ·
  `minUsableBandRatio = 60%` 의 실측 근거 없음.
- 정규화 충분성이 0 거절 이외 미확정.
- 저장 형식 계약 미확정.
- **실제 음향 측정·USB·CAL 적용·파일 저장·마법사·비교 화면 미검증.**
  `CalibrationCompareCard` 는 아직 한 번도 기기 화면에서 본 적이 없다.
- 앞 회차들에서 열어 둔 것도 그대로: `SignalPlayer.stopSink()` 의
  `releaseStarted` 가드 미고정, 알림 정지 단추 미확인, TalkBack 미청취.
