## 2. UIS6-01 — 상대 경로를 쓰는 사람만 막혔습니다

지적이 맞습니다. 검증 task 가 `File(storePath)` 로 **실행 디렉터리**
기준으로 찾는데, signingConfig 는 `file(storePath)` 로 **app 프로젝트**
기준이었습니다. signingConfig 가 제대로 찾은 키를 검증이 「없다」고
막았습니다.

문서의 절대 경로 예제는 멀쩡해서, **상대 경로를 쓰는 개발자·CI 만**
걸리는 종류였습니다. 보내 주신 한 줄을 그대로 받았습니다.

## 3. UIS6-02 — 막는 범위가 너무 넓었습니다

`startsWith("bundleRelease")` 가 `bundleReleaseClassesToCompileJar` ·
`packageReleaseResources` 까지 잡았습니다. 서명과 무관한 **release
단위 시험의 선행 작업**이라, 키가 없으면 `:app:testReleaseUnitTest`
조차 못 돌았습니다 — 주석에는 「release 패키징만 막는다」고 적어
두고서.

이름 여덟을 못박았습니다(`bundleRelease`·`assembleRelease`·
`packageRelease`·`packageReleaseBundle`·`packageReleaseUniversalApk`·
`signReleaseBundle`·`validateSigningRelease`·
`signingConfigWriterRelease`).

**AGP 8.13.0 기준 이름이라 AGP·variant 를 올리면 다시 확인해야
한다**고 주석에 적었습니다. `-x verifyReleaseSigning` 으로 일부러
빼는 것까지 막는 보안 경계가 아니라는 것도요.

### 실제로 돌려 확인한 것

| 상황 | 결과 |
|---|---|
| 키 없이 `:app:testReleaseUnitTest` | **통과**(848개) |
| 키 없이 `:app:bundleRelease` | 실패 — 없는 속성 넷 |
| 키 없이 `:app:assembleRelease` | 실패 |
| 상대 경로(`../fixture-tmp/fake.jks`) | **통과** |
| 키 없이 `:app:assembleDebug` | 통과 |

문서에도 **이 task 가 통과했다고 「배포 가능한 올바른 키」는 아니라는**
것을 표로 적었습니다:

| 무엇 | 어디서 확인되나 |
|---|---|
| 속성 넷·파일 존재 | `verifyReleaseSigning` |
| 비밀번호·키 유효성 | 실제 서명 작업이 실패로 알려 줌 |
| **Play 에 등록한 그 키인가** | 산출물 지문과 업로드 인증서 대조 |

> 되묻습니다: 이름 여덟이 지금 AGP 에서 맞다는 것은 확인했는데,
> **flavor 를 나중에 추가하면**(`bundleFreeRelease` 같은 이름) 조용히
> 안 막게 됩니다. variant 기반 설정으로 옮기는 편이 낫겠습니까?
> 지금은 주석으로만 경고해 두었습니다.

## 4. UIS6-03 — 진짜 화면을 여는 시험이 없었습니다

**「둘이 함께 네 가지 변이를 모두 막는다」고 적은 것이 또 과했습니다.**
부품 시험 넷도 소스 시험 여섯도 진짜 `SettingsScreen` 을 열지 않아,
**바깥 호출을 주석 처리하면 다 통과**했습니다.

보내 주신 시험을 받아 `SettingsScreenPolicyPresenceTest` 로 두었습니다.
기본 `CaptureUiState()` 와 빈 콜백으로 진짜 화면을 열어 끝까지 내려
봅니다 — 상태와 콜백만 받는 화면이라 마이크도 DataStore 도 열지
않습니다.

**실기기에서 돌렸습니다**(SM-S918N):

| | 정상 | 바깥 호출 주석 처리 |
|---|---|---|
| 계측 시험 5개 | **전부 통과** | **이 시험만 실패** |
| 소스 시험 6개 | 통과 | 통과(그대로) |

두 시험이 **서로 다른 자리**를 지킨다는 것이 갈려 보입니다. 두
KDoc 에도 무엇을 못 잡는지 적었습니다.

## 5. 일곱 회차의 줄기 (누적)

### 5-1. 제 판단이 틀렸다고 확인된 것

1. **「틀리게 맞추면 화면이 곧바로 이상해진다」**(UIS-02)
2. **「지연만 보면 된다」**(UISR-03)
3. **「잘렸으면 3초 기다리면 된다」**(UISRF-01)
4. **「유한 창이라 창 밖은 0」**(UISRFF-01) — 칸 근사를 썼습니다
5. **「`doFirst` 로 막으면 된다」**(UISRFFF) — 의존 작업보다 먼저 돌지
   않습니다
6. **「시험이 있으니 지켜진다」** — **네 번**:
   - UIS-07 매니페스트 문자열 검색
   - 정책 링크 소스 검색(호출부 삭제만 잡음)
   - 「둘이 함께 네 변이를 막는다」(부품만 봄)
   - 이번 UIS6-03(진짜 화면을 안 엶)

1~5 는 **계산·상태·도구의 뜻**을, 6 은 **막는 장치가 실제로 막는지**를
확인하지 않은 것입니다. **6 이 네 번으로 압도적입니다.**

그래서 이번부터는 **변이를 먼저 만들어 보고** 시험을 씁니다. 이번
`SettingsScreenPolicyPresenceTest` 도 「정상 통과」가 아니라 **「변이
넣으면 이것만 실패」**를 실기기에서 확인한 뒤 커밋했습니다.

### 5-2. 실기기 관측 (구현자 보고)
