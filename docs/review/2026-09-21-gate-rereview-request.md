## 먼저 볼 것

검증자의 `CombinedProbe.kt` 를 옮겨 `dsp/…/CombinedRegressionTest.kt` 로
두었고, **고치기 전에 3건이 실패하는 것을 먼저 확인했다.**

**C01 만은 재는 방법을 그대로 쓸 수 없었다.** 검증자는 `finish()` 가
순회하는 도중에 다른 스레드의 `process()` 를 끼워 넣어
`ConcurrentModificationException` 을 냈는데, 둘을 같은 자물쇠로 묶은 뒤에는
**그 지점에서 멈춰 세우면 시험이 교착된다.** 자물쇠가 하는 일이 그것이다.
그래서 「끼워 넣기」 대신 **두 스레드가 실제로 부딪히게** 해서 같은 성질을
본다(20회 반복). 그 까닭을 시험 파일 앞머리에 적었다.

## C01 (High) — 멈출 때 이미 들어와 있던 콜백과 finish 가 부딪혔다

**내 P9-01 수정이 만든 결함이다.** 그리고 **같은 실수를 두 번째로 했다** —
F02 때 「`close()` 가 500ms 만 기다리므로 이미 콜백 안에 들어간 스레드가
있을 수 있다」고 스스로 적어 놓고 두 겹 방어까지 만들었으면서, 이번에 그
교훈을 적용하지 못했다. 입구 검사는 **뒤에 오는** 콜백만 막는다.

수정: `process` 와 `finish` 를 `FeedbackDetector` 안의 같은 자물쇠로
직렬화한다. 오디오 스레드가 무는 시간은 한 프레임(실기기 측정 3.42ms)이고
부딪히는 것은 멈추는 순간 한 번이다 — `join(500)` 으로 기다리는 것보다
짧다. `finish()` 뒤에는 `finished` 표시를 세워, 늦게 온 덩어리가 닫아 둔
기록을 되살리지 못하게 한다.

검증자가 「`finish()` 를 `close()` 뒤로 옮기는 것만으로도 충분하지 않다」고
한 지적을 받아들였다 — 순서를 바꾸는 대신 **동기화 경계**를 만들었다.

## C02 (Medium) — 옛 재생의 늦은 오류가 새 재생 UI 를 지웠다

`onEnded` 에 세대를 함께 넘기고, **주 스레드에서 소비할 때** 현재 세대와
대조한다. `SignalPlayer.start()` 가 세대를 돌려주고 ViewModel 이 그것을
들고 있다가 견준다.

## C03 (Medium) — 무음이 흐른 시간이 승격 증거로 쓰였다

두 곳을 고쳤다:

1. **이번 프레임에 실제로 본 track 만** `record()` 한다(`lastFrame == frame`).
2. 판정·표시·기록의 시간을 전부 `lastSeen − firstSeen` 으로 센다.
   `now − firstSeen` 이 아니다.

검증자 재현(1462ms 관측 → 무음 한 장)에서 이제 기록이 생기지 않는다.
반대로 「관측이 이어지면 문턱을 넘는다」도 함께 시험해 지나치게 막지 않는
것을 확인했다.

## 상태 전이 통합 시험 — 게이트 조건

검증자의 답변 1번을 그대로 따랐다:

> ViewModel 전면 재작성은 필요하지 않다. AudioSource factory, 장치 목록/
> 설정/보정 Flow, main dispatcher/clock 을 주입하거나, 그 의존성을 받는
> 작은 세션 제어 객체를 추출해 **실제 production 상태 전이**를 시험할 수
> 있게 하면 된다.

**`CaptureController` 로 세션 수명주기를 옮겼다**(복사가 아니라 이동).
ViewModel 은 1179줄 → 748줄이 되고 DataStore·Android 배선만 남았다.
안드로이드에 매인 것은 넷뿐이었고 그것만 밖에서 받는다:

| 이음매 | 진짜 | 시험에서 |
|---|---|---|
| `listDevices` | `InputDeviceScanner.list()` | 정해 둔 목록 |
| `openSource` | `MicSource(...)` | `FakeSource` |
| `post` | 주 스레드로 넘기기 | 그 자리에서 실행 |
| `onRouteConfirmedHook` | DataStore 구독 시작 | 기록만 |
| `nowNs` | `System.nanoTime()` | `FakeClock` |

**시험용 사본을 두지 않았다.** 시험이 돌리는 것은 실제 `CaptureController` 다.

### 검증자가 적은 최소 목록을 덮었는가

| 요구한 것 | 시험 이름 |
|---|---|
| onBlock 진입 후 stop | 덩어리를 처리한 직후에 멈춰도 탈나지 않는다 |
| read-error / 장치-removal 순서 교환 | 읽기 오류가 먼저 와도 / 목록 변경이 먼저 와도 내장으로 전환한다 |
| 늦은 route 확인 | 멈춘 뒤 늦게 온 경로 확인은 버린다 |
| A→B 세션 전환 후 A snapshot | 이전 세션의 덩어리는 새 세션에 섞이지 않는다 |
| 보정 도착 전후 | 보정이 도착하기 전에는 미보정으로 그린다 |
| 기록 종료·보존·새 측정 초기화 | 멈춘 뒤에도 하울링 기록이 남는다 / 새 측정을 시작하면 지난 기록을 비운다 |
| 이전 재생 오류의 지연 전달 | **아직 없다** — 아래 「하지 못한 것」 참고 |

그 밖에 더한 것: 「멈춘 뒤 늦게 온 오류는 버린다」, 「경로가 확인되기
전에는 보정을 지켜보지 않는다」, 「분리 정책이 멈추기면 다시 시작하지
않는다」, 「재는 도중 경로가 바뀌면 그 세션을 끝낸다」, 「쓸 수 있는 기기가
없으면 그 사실을 알린다」, 「멈추면 보정을 놓는다」.

### 시험을 만들며 내가 잡은 내 실수 둘

숨기지 않고 적는다.

1. **보정 시험이 아무것도 보지 않고 있었다.** 미보정 기본값이 120dB 인데
   보정값도 120dB 을 줘서 전후 숫자가 같았다. 처음에는 코드를 의심했는데
   재 보니 시험이 틀린 것이었다. 95dB 로 바꾸고 **25dB 차이를 단언**한다.
2. **실제 시계에 기댄 시험이 불안정했다.** 화면 갱신이 66ms 에 한 번이라
   덩어리를 빨리 넣으면 첫 장만 반영되는데, 그 경계가 기계 속도에 좌우돼
   같은 시험이 통과했다 실패했다 했다. `FakeClock` 을 넣고 3회 연속 돌려
   실패 0 을 확인했다.

그대로 뒀으면 「가끔 실패하는 시험」이 되어, 진짜 결함이 났을 때도 무시하게
됐을 것이다.

## 판단을 구하는 곳

1. **자물쇠가 오디오 스레드에 맞는 해법인가.** 검증자는 「worker 의 종료
   명령/완료 응답으로 불변 최종 snapshot 을 넘기거나, 같은 동기화 경계에서
   직렬화한다」고 했고 나는 뒤쪽을 골랐다. 주 스레드가 최대 한 프레임
   (3.42ms) 막힌다. 앞쪽(명령/응답)이 나은지 판단을 구한다.

2. **C03 을 「본 것만 기록」으로 푼 것.** 유예(250ms) 안에서 잠깐 안 보이는
   track 은 **붙들어는 두되 기록은 갱신하지 않는다.** 소리가 아주 살짝
   끊겼다 이어지는 경우 기록의 duration 이 실제보다 짧아질 수 있다.

3. **`CaptureController` 의 경계.** 보정·설정은 여전히 밖(ViewModel)에서
   `update {}` 로 밀어 넣는다. 그래서 「보정이 언제 도착하는가」는 시험이
   직접 정한다 — 실제 DataStore 의 순서와 같다는 보장은 없다.

## 하지 못한 것

- **이전 재생 오류의 지연 전달 시험** — 검증자 목록의 마지막 항목이다.
  `SignalPlayer` 는 아직 이음매가 없어 `AudioTrack` 없이 돌릴 수 없다.
  C02 는 코드 경로만 맞춰 놓은 상태다.
- **44.1kHz 검증** — 검증자가 「ADR 에 적는 것만으로 이 시험을 대체할 수
  없다」고 했다. 아직 하지 않았다.
- **USB 두 대 정책** — 권고안(명시 선택 → 현재 USB 유지 → 최초만 우선순위)을
  아직 구현하지 않았다. 지금은 `chooseInput` 의 목록 순서가 정책을 대신한다.
- **reroute 재시작 상한** — 검증자가 「무한 자동 재시작이 없다는 검증은 아직
  없다」고 했다. 그대로다.
- **현장 오탐률·놓침률·검출 지연** — 가장 중요한 것이고 미확인이다.
- **기준 소음계 비교, 60분 부하·열·메모리, USB 실물** — 미실행.
