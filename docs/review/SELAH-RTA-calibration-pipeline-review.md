# 보정 파이프라인 독립 검토

2026-09-23 · 검토 HEAD 5f33ea4(요청 문서), 구현 c0f6504..3839ea8
대상: SpectrumAverage, CalibrationSession, MeasuredProfile, ProfileCodec 및 관련 품질 계산·시험. 근거: SELAH_RTA_S23Ultra_mic_calibration_instruction.md §2–7.

**판정: 계산 파이프라인 승인 보류. Critical 없음, High 2건, Medium 2건.** 아직 실제 저장·적용·마법사에 연결되지 않았으므로 사용자 측정이 이미 훼손됐다고 판단하지 않는다. 연결 전에 아래 결함을 닫아야 한다. 기존 시험 통과는 아래 반례를 배제하지 않는다.

## CP01 — High: 불안정한 기준 측정과 스펙트럼 변화가 품질 Pass를 받음

위치: dsp/src/main/kotlin/kr/joa/selahrta/dsp/CalibrationSession.kt:108,122,130–147,207–230.

요청서 §5의 「폴백이어도 관문이 막으므로 기록 문구만 틀리다」는 설명은 기준 측정에는 성립하지 않는다. repeatSpreadDb에는 target.levelSpreadDb만 들어가고, before/after의 levelSpreadDb는 품질 판정에 전달하지 않는다.

독립 재현:
1. ReferenceBefore와 ReferenceAfter 각각 평탄한 40 dB/90 dB 두 프레임을 넣는다. 두 프레임 모두 안정 프레임 선택에서 탈락한다.
2. Target에는 안정된 60 dB 프레임 4개, 배경 10 dB, DSP 검증 true를 준다.
3. 결과: 기준 spread=50 dB, kept=2, dropped=0, reference drift=0, **품질 Pass**.

또한 광대역 합만 비교하면 스펙트럼 모양 변화가 상쇄된다. 31밴드 기본 50 dB에서 기준 전에는 20번 밴드만 60 dB, 기준 후에는 24번 밴드만 60 dB로 바꾸고 대상은 기준 전과 같게 했다. 광대역 drift=0, 품질 Pass인데 **최대 6.7337 dB의 보정**이 생성된다. 환경 변화가 마이크 특성으로 기록되는 반례다. 두 측정에 동일한 CAL을 적용해도 이 구조적 문제는 남는다.

영향: 기준 장비/음장이 불안정해도 자동 적용 가능한 보정으로 승인할 수 있다. 요청서의 1 dB 흐름 제한에 따른 「평균 방식 차이 ≤0.03 dB」도 각 밴드의 변화를 제한하지는 않는다.

수정 권고: 세 단계 모두 안정성·유효 표본 수를 검사하고, 안정 프레임이 하나도 없으면 보정 생성/저장 승인은 Fail로 한다. 실패 원인과 원시 자료를 진단 결과로 보존하면 세션이 사라질 필요는 없다. before/after의 대역별 변화와 반복 측정 재현성을 함께 검사하되 광대역 레벨 변화와 분리한다. 단일 프레임의 spread=0을 반복성 입증으로 취급하지 말고 충분한 측정 길이/표본 수 또는 별도 Unknown 상태를 둔다.

회귀 시험: 무안정 프레임이 before/target/after 각각 발생하는 3경우, 동일 광대역·서로 다른 스펙트럼, 단일 프레임, 일부만 안정 프레임인 경우. 실패 결과에 이유/폐기 수를 남기되 maySave/mayAutoApply는 false여야 한다.

## CP02 — High: SNR 및 기준 CAL 유효 범위가 보정 곡선으로 전달되지 않음

위치: CalibrationSession.kt:167–175,188–200,207–230; SpectrumAverage.kt:135–140. 관련: ResponseCalibration.kt:88–116,282–308.

qualityFromSession은 대역별 usable을 만들지만 calibrateFromSession은 품질/마스크를 받지 않는다. bandsToCurvePoints는 모든 밴드를 점으로 만들고, 후속 valid는 주로 축 범위와 보정 상한에 의해서만 결정된다. 따라서 전체 품질 비율이 통과하는 경우 낮은 SNR의 일부 대역도 보정에 남는다. 기준 CAL은 gainDbAt의 끝점 연장을 사용해 범위 밖에서도 숫자를 만들며 그 사실을 valid에 전달하지 않는다.

독립 재현: 한 대역의 배경을 신호와 같게 해 SNR=0으로 만들었다. 나머지 대역은 충분한 SNR이고 품질은 Pass였다. 해당 대역은 quality.usable=false인데 결과 correction.valid=true였다. 기준 CAL 범위를 200 Hz–10 kHz로 한 같은 실행에서 **30 Hz도 correction.valid=true**였다.

영향: 배경 소음이나 기준 마이크를 검증하지 못한 주파수를 보정으로 저장·적용할 수 있다. 「못 믿는 범위에서는 보정하지 않는다」는 품질 안내와 계산 결과가 어긋난다. 최저/최고 유효 Hz만 저장해서는 중간의 저신뢰 구멍도 표현할 수 없다.

수정 권고: 보정 계산 입력에 명시적인 주파수별 validity를 전달한다. 대상/기준 SNR, CAL 검증 범위, 분석 가능 대역, 반복 안정성의 교집합을 정규화·보간·평활 이전부터 유지한다. 무효 구간을 가로질러 유효하게 보간하거나 정규화 기준에 섞지 않는다. 기준 CAL null도 ‘검증된 평탄 기준’과 ‘CAL 누락’을 구분하고, 지시서의 EMM-6 교정에서는 누락을 정상으로 승인하지 않는다. 미검증 기준을 그래프로 보는 진단 동작과 저장 승인은 분리한다.

회귀 시험: 전체 비율은 통과하지만 중간 한 대역 SNR 미달인 경우, 저신뢰 구간이 정규화 대역에 있는 경우, CAL 200 Hz–10 kHz 범위 밖, CAL 없음, 기준 측정만 SNR 미달. 결과 valid와 품질 보고가 일치하고 평활 후에도 무효 구간이 살아 있어야 한다.

## CP03 — Medium: 해석기가 NaN·Infinity 및 잘못된 축을 유효 데이터로 받을 수 있음

위치: app/src/main/java/kr/joa/selahrta/calibration/ProfileCodec.kt:91–94,115–125,233–278,332–350.

toDoubleOrNull은 `NaN`과 `Infinity`를 파싱할 수 있다. Reader는 유한성 검사 없이 이를 수용하고 ResponseCurve도 길이와 비어 있음만 검사한다. 길이가 맞는다는 사실이 유효한 주파수·보정값이라는 뜻은 아니다.

독립 재현: 정상 encodeCurves 출력의 correction.db를 같은 길이의 NaN 목록으로 바꾸었다. decodeCurves는 success이고 **valid=true인 NaN 점 120개**를 반환했다.

영향: 향후 저장 파일 손상·외부 데이터·버전 변환 오류가 정상 곡선으로 읽혀 NaN 계산/그래프로 전파된다. 현재 파일 바인딩이 없으므로 현 사용자 파일 손상 사례라고 주장하지 않는다.

수정 권고: 파싱 뒤 객체 의미를 검증하고 오류 항목과 함께 Result.failure를 반환한다. 숫자의 유한성, 축의 양수·엄격한 증가, 프로파일의 sampleRate/채널 범위/유효 주파수 쌍/품질 비율/설정 범위를 확인한다. 유효하지 않은 값의 직렬화 규칙을 명시한다. encodeCurves에서도 모든 곡선 축이 같음을 확인할 것: 현재 정상 생성 함수는 같은 축을 쓰지만 CalibrationOutcome/ResponseCurve는 공개 객체이고 배열이 가변이므로 길이만으로 모든 호출 경로를 보증할 수 없다.

회귀 시험: NaN, ±Infinity, 0/음수/역순/중복 축, 잘못된 채널 및 sampleRate, 동일 길이·서로 다른 축의 encode 입력. 실패가 예외 누출이 아닌 Result.failure로 돌아오는지도 확인한다.

## CP04 — Medium: 기준 CAL을 밴드 중심 한 점에서 빼는 것은 일반적인 밴드 보정과 같지 않음

위치: dsp/src/main/kotlin/kr/joa/selahrta/dsp/CalibrationSession.kt:167–175.

현재 applyMicCalibration은 이미 합산한 1/3옥타브 레벨에서 중심주파수 응답만 뺀다. 일반식은 각 FFT 칸 전력에 보정을 곱한 뒤 밴드를 합산하는 것이다. 밴드 내 CAL이 일정할 때만 두 연산이 일치한다. 기존 RTA 경로에서 분리했던 칸별 보정 원칙과 새 기준 측정 경로가 다르다.

독립 계산/함수 재현: 같은 밴드의 두 성분이 보정 전 실제 전력 1씩이고 마이크 응답이 각각 +6/−6 dB, 중심 응답이 0 dB인 예를 만들었다. 실제 기준은 전력평균 1 → 0 dB. 측정 전력평균은 (10^0.6+10^-0.6)/2이므로 3.2554 dB이다. 이 레벨을 실제 applyMicCalibration에 넣으면 중심에서 0만 빼 **3.2554 dB가 그대로 남는다**. FFT 창을 포함한 실기기 재현이 아니라 함수 계약을 검증한 합성 전력 반례다.

영향: 급한 CAL 변화 또는 밴드 내 불균등 에너지에서 기준 곡선에 잔여 응답이 남아 대상 마이크 보정으로 전사된다. 실제 EMM-6 파일/핑크 노이즈에서 오차가 3.26 dB라는 뜻은 아니다.

수정 권고: 기준 CAL을 기존 binCorrectionLinear 및 밴드 합산 경로에서 한 번 적용한 스펙트럼을 세션에 넘긴다. API가 raw인지 corrected인지 명확히 해서 이중 적용도 막는다. 밴드 중심 근사를 의도한다면 근사임을 계약에 적고 실제 CAL·신호에서 허용 오차를 검증한다.

회귀 시험: 밴드 내 평탄 CAL(동등), 급변 CAL(위 반례), 비중심 톤/광대역 에너지, 이미 보정된 입력의 이중 적용 방지. 기준과 대상이 같은 이상적 응답이면 생성 보정이 0에 가까워야 한다.

## 요청서의 판단 질문

- **무안정 프레임 폴백:** 진단용 수치/원시 데이터는 보존하되 보정 승인은 실패가 맞다. noStableFrames만 표시하고 기존 품질 계산을 유지하면 CP01을 막지 못한다. dropped/kept/fallbackUsed의 의미도 구분한다.
- **앞뒤 기준 전력평균 vs dB평균:** 한 측정 구간의 동등 시간 잡음 프레임은 전력평균이 맞다. 서로 다른 시각의 기준 두 개를 대상 시점으로 추정하는 것은 별도의 드리프트 모델 문제다. dB상 선형 변화라면 시각 가중 dB 보간, 선형 전력 변화라면 전력 보간이다. 시간 정보가 없는 현재 구현의 1:1 평균에는 ‘대상 시점이 양 기준의 중간’이라는 가정도 있다. dB평균으로만 바꾸면 CP01이 해결되지 않는다. 우선 대역별 안정성 관문을 닫고 시간·모델·허용 오차를 명시할 것. before만 쓰는 방법도 더 정확하다고 일반화할 수 없다.
- **sample rate 불일치 차단:** 지시서와 일치하며 유지하는 편이 타당하다. 48↔44.1 kHz의 곡선 보간 가능성이 마이크 경로 동일성의 증거는 아니다. 완화는 해당 경로의 반복 측정 근거가 있을 때 별도 정책으로 한다.
- **배경 미측정:** 자동 보정 승인은 차단하는 현재 보수적 방향에 동의한다. 다만 실제 SNR=0과 ‘미측정’을 상태·문구에서 구분한다. 실패한 세션을 진단 기록으로 남기는 것은 유효한 보정으로 저장·활성화하는 것과 다르다.
- **객체 생성 후 Reader.problem 확인:** 기본값이 성공 결과로 새지 않는다면 그 순서 자체는 결함이 아니다. 실제 문제는 선택 필드·숫자 의미 검증이다(CP03). deviceAddress는 명세상 식별 메타데이터이므로 없는 값과 빈 값을 구분하는 편이 낫다. 단, 요청서의 ‘저장된 주소가 빠지면 적용 시 케이스 경고도 없어진다’는 설명은 현재 함수 그대로는 맞지 않는다. judgeProfileApply는 `was.isRear`가 아니라 **now.isRear**를 보므로 실제 현재 경로 주소가 back이면 경고는 남는다. 저장된 label/메타데이터 손실은 별개다.
- **judgeProfileApply 통합:** 경로·enabled·품질을 하나의 적용 관문에서 확인하는 것은 적절하다. CalibrationKey를 재사용하고 sample rate를 별도 확인하는 것도 명시된 전체 계약이 있다면 문제없다. 다만 현 MeasuredProfile에는 지시서 §6의 실제 활성 마이크 ID·그룹·채널 매핑과 적용 당시 품질 정책 자체가 없다. 실제 바인딩 시 이 기록과 재대조를 누락하지 말 것.
- **물리 위치 명명과 케이스 확인:** Separable에서만 물리 위치를 쓰는 것은 적절하다. 경고를 세션 시작/경로 확인 시 제시하고 사용자의 확인과 연결하면 된다. 매 DSP 프레임마다 반복할 성격의 경고는 아니다.

## 검증 범위 및 한계

- 원본 소스를 로컬 Kotlin 2.2.20/JVM으로 독립 컴파일. **DSP 316 + 프로파일/코덱 44 = 고유 360건 최종 통과**.
- 첫 실행은 테스트 resources를 classpath에 빠뜨려 표본 파일 시험 10건이 실패했다. 이는 독립 실행기 설정 문제였다. resources 경로를 추가해 그 10건만 재실행했고 모두 통과했다. 다른 350건은 첫 실행에서 통과했다. 전체가 한 번에 깨끗하게 통과했다고 보고하지 않는다.
- 별도 PipelineProbe는 CP01/CP02/CP03/CP04의 반례를 실제 production 계산 함수로 확인했다. 이 probe는 결함 관측을 출력하는 검증 도구이며, 현재 오류를 정답으로 고정하는 제품 회귀 시험이 아니다.
- 전체 app 312건, Gradle build/lint, 실제 파일 저장, 비교 카드 렌더링, 음향 측정, 실제 기기 라우팅/재적용은 이번에 검증하지 않았다.
- 구현이 아직 저장/마법사에 연결되지 않은 점은 확인했다. 과거 서비스·SignalPlayer 지적의 해결 여부는 이번 3커밋 범위에서 다시 승인하지 않는다.
- production 코드를 수정하지 않았다. 검증 코드와 보고서는 Codex 작업 폴더에만 저장했다.
