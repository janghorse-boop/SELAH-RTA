## 이것은 **코드가 아니라 명세** 검토입니다

여느 요청서와 다릅니다. **아직 한 줄도 구현하지 않았습니다.** 지시서를 읽고
「이대로 만들면 막히거나 틀린 결과가 나오는 자리」를 찾은 것이고, 구현을
시작하기 전에 그 자리를 닫고 싶습니다.

**먼저 말씀드릴 것 — 이 지시서는 전반적으로 잘 쓰였습니다.** 특히 이 셋은
그대로 두어야 합니다.

- **개발 순서를 못박고 그 까닭을 적은 것**(§3·§40) — 「시간축이 맞지 않은
  상태에서 그럴듯한 그래프를 만들지 않는다」. 이 문서의 가장 큰 미덕입니다.
- **Reference 는 「다시 생성한 값」이 아니라 실제로 `AudioTrack` 에 넣은
  스트림**(§4) — 정확합니다.
- **threshold 를 실측 뒤에 정한다**(§11·§25) · **기종명 하드코딩 금지**(§22)
  · **USB 기기를 `id` 로 식별하지 않는다**(§2-5). 마지막 것은 2026-10-01 에
  실제로 그 버그를 고쳤습니다(`SameOutputKeyTest`).

아래는 **고칠 자리**입니다.

# 막는 것 1 — §8 의 `H(f) = Y(f)/X(f)` 는 구현 지침으로는 틀렸습니다

## 지시서가 적은 것

```text
기본 전달함수:
H(f) = Y(f) / X(f)
- X(f) = Reference
- Y(f) = Measurement
```

## 왜 막히는가

이대로 읽으면 구현자는 **블록마다 `Y/X` 를 내고 그 결과를 평균**합니다.
그러면 둘이 틀어집니다.

1. **평균이 편향됩니다.** 잡음이 섞인 블록에서 `Y/X` 는 잡음에 끌려가고,
   그 값을 평균하면 참값으로 수렴하지 않습니다.
2. **Coherence 를 아예 낼 수 없습니다.** γ² 는 교차 스펙트럼과 자기
   스펙트럼의 **평균**으로 정의되는데, H 를 먼저 나눠 버리면 그 재료가
   사라집니다.

§34 의 Codex 검증 항목에는 `cross spectrum` · `auto spectrum` ·
`averaging domain` 이 들어 있습니다. **작성자는 알고 있습니다.** 그런데
**정작 구현자가 읽는 §8 에는 안 적혀 있습니다.** 검증 단계에서 잡겠다는
것은 늦습니다 — 그때는 이미 그 구조 위에 UI 와 저장 포맷이 올라가 있습니다.

## 검토자가 직접 확인하는 법 — **단일 블록 coherence 는 항상 1 입니다**

제 말을 믿지 마시고 한 줄로 확인하실 수 있습니다. 평균이 1개면:

```
Sxy = X* · Y        Sxx = |X|²        Syy = |Y|²

γ² = |Sxy|² / (Sxx · Syy)
   = |X* · Y|² / (|X|² · |Y|²)
   = (|X|²·|Y|²) / (|X|²·|Y|²)
   = 1          ← 입력이 무엇이든, 정확히 1
```

**잡음만 재도 1.00 이 나옵니다.** 그런데 §29 는 averaging 후보에
**「None」을 넣어 두었습니다.** 그 조합이 화면에 올라가면, 신뢰도 표시가
**가장 못 믿을 자리에서 가장 높게** 뜹니다. 이건 틀린 숫자보다 나쁩니다 —
사람이 그 숫자를 보고 EQ 를 만집니다.

## 제안하는 고침

§8 을 이렇게 바꿔 주십시오.

```text
스펙트럼을 먼저 평균하고, 그 뒤에 나눈다.

Sxx = ⟨X* · X⟩      (블록 평균)
Syy = ⟨Y* · Y⟩
Sxy = ⟨X* · Y⟩      (복소수로 평균 — 크기만 평균하지 않는다)

H(f)  = Sxy / Sxx                      ← H1 추정자
γ²(f) = |Sxy|² / (Sxx · Syy)
```

그리고 **어느 추정자를 쓰는지 이름을 못박아 주십시오.** H1(=Sxy/Sxx) 은
**잡음이 측정 쪽에만 있다**고 가정합니다. Reference 가 전기 신호이고
Measurement 가 방을 거친 마이크라면 그 가정이 맞습니다. 다만 H2(=Syy/Syx)
나 Hv 를 쓸 자리도 있으므로, **「H1 을 쓴다, 까닭은 이것이다」**가 적혀
있어야 나중에 바꿀 때 근거가 남습니다.

추가로 §29 에:

- **coherence 를 표시하려면 최소 평균 수가 필요하다**(8회를 제안합니다)
- 그 아래에서는 **coherence 를 가리거나 「측정 중」으로 둔다**
- averaging 「None」에서는 **coherence 를 내보내지 않는다**

## 시험으로 못박을 것 (§33 에 추가)

- **평균 1회의 coherence 가 1.00 으로 화면에 나가지 않는다**
- **평균 영역이 다르면 답이 다르다는 것을 드러낸다** — 같은 자료로
  ①H 를 평균 ②dB 를 평균 ③스펙트럼을 평균 세 가지를 내어, 서로 다른
  값이 나오는 것을 시험이 보이게 한다. 그래야 다음 사람이 「아무거나
  평균하면 된다」고 생각하지 않습니다.

# 막는 것 2 — 정밀 모드의 **출력 경로가 정의돼 있지 않습니다**

## 지시서가 적은 것

§5 는 **입력 둘만** 적습니다.

```text
Audio Interface
  CH1 = Reference
  CH2 = Measurement Mic
```

그런데 §14 는 「기존 SELAH RTA Signal Generator 를 재사용한다」고 합니다.
**그 소리가 어디로 나가는지는 지시서 어디에도 없습니다.**

## 왜 막히는가

가장 자연스러워 보이는 답 — **같은 UMC404HD 로 내보내기** — 은 **이미
실패한 것으로 이 저장소에 기록돼 있습니다.**

`docs/manual/calibrator-nd9-check.md` §6-2:

> **앱이 소리를 내보내면 USB 입력이 멎습니다.** 이 폰 + UMC404HD 에서
> 재현했습니다 — 소리를 안 틀면 −76dBFS, 틀면 **−240dBFS(완전 무음)**.

`docs/verify/2026-10-01-builtin-mic-with-usb-c-output.md` §13 도 같은 말을
합니다 — 이번 PASS 는 **출력 전용** 기기(ADAM D3V)에서 나온 것이고,
입출력을 함께 가진 USB 기기로 **일반화하면 안 된다**고.

§23 이 「정밀 모드 구현 전에 multichannel capture 를 별도 검증한다」고
적어 두었지만, 그건 **입력 쪽** 이야기입니다. **출력이 어디서 나오는지는
끝내 안 적혀 있습니다.**

## 제안하는 고침

**정밀 모드의 표준 구성은 「앱이 소리를 내지 않는 것」으로 못박아
주십시오.**

```text
신호원 : 콘솔 / 시스템 프로세서 (앱이 아님)
CH1    : 그 출력을 그대로 받은 Reference
CH2    : Measurement Mic
```

이러면 셋이 한꺼번에 풀립니다.

1. **듀플렉스 문제가 통째로 사라집니다** — 앱은 받기만 합니다.
2. **실제 운용 중인 PA 를 그대로 잴 수 있습니다.** 측정용 신호를 따로 쏘지
   않아도 되고, 예배 중에도 잴 수 있습니다. 전문 측정 도구가 이렇게 하는
   까닭이 이것입니다.
3. **Reference 가 콘솔 뒤의 모든 처리를 포함하지 않게** 되므로, 무엇을
   재고 있는지가 분명해집니다.

앱 생성기는 **선택지**로 남기되, **같은 인터페이스로 내보내는 구성은
검증을 통과하기 전까지 막아** 주십시오(화면에서 고를 수 없게). 「안 될 수도
있습니다」라고 적어 두는 것으로는 부족합니다 — 되는 것처럼 보이다가
**디지털 무음을 정상 그래프로 그리게** 됩니다.

# 막는 것 3 — 마이크 보정이 선행 조건인데 §18 이 「검토한다」로 약합니다

## 왜 이것이 선행 조건인가

간편 모드의 Reference 는 **전기 신호**입니다. 그래서 H 안에는 이것이 전부
들어 있습니다.

```text
H = DAC → 앰프 → 스피커 → 방 → 마이크 → ADC
```

**두 마이크를 견주는 구조가 아니므로 마이크 응답이 상쇄되지 않습니다.**
즉 **간편 모드 Magnitude 는 폰 마이크의 응답을 그대로 뒤집어씁니다.**

그런데 **폰 내장 마이크의 보정 곡선은 지금 존재하지 않습니다.** 그걸
만드는 절차 G 가 2026-10-01 에 **2단계에서 멈춰 있습니다**
(`docs/unverified.md` §1 에 올려 두었습니다).

§18 은 이렇게 적혀 있습니다 — 「TF Measurement 경로에 적용할 수 있도록
**검토한다**」. 너무 약합니다.

## 다만 제 지적을 여기까지로 좁힙니다 — **비교 측정에서는 상쇄됩니다**

정확히 적겠습니다. 마이크 응답은 **절대 응답**을 볼 때만 문제입니다.
**같은 마이크로 두 상태를 견주면 상쇄됩니다.**

| 쓰임 | 마이크 곡선이 필요한가 |
|---|---|
| 「이 스피커의 주파수 응답은 어떤가」 | **필요합니다** |
| Main/Sub 정렬, Main/Delay 정렬 | **아니요** — 지연·위상 문제이고 같은 마이크입니다 |
| EQ 를 만지기 전/후 비교 | **아니요** — 차이만 보면 상쇄됩니다 |
| 여러 청취 위치 비교(§19) | **아니요** — 같은 마이크입니다 |

**그래서 곡선이 없어도 간편 모드는 쓸모가 있습니다.** 이것이 오히려 MVP
경계를 알려 줍니다(아래 보완 5).

## 제안하는 고침

- §18 을 **「적용한다」**로 격상하고, **곡선이 없으면 절대 Magnitude 를
  `LOW CONFIDENCE` 로 두거나 「상대 비교 전용」으로 표시**한다.
- §2 의 「반드시 반영할 제한사항」에 **8번을 추가**: **측정 마이크의 응답
  곡선 확보**가 라우팅 관문과 **같은 급의 선행 관문**이다.
- §39 완료 조건의 간편 모드에도 같은 줄을 넣는다.

# 제가 고쳐 적은 것 — **루프백은 이 구성에서 불가능합니다**

보내기 전에 바로잡습니다. 담당자에게 처음 설명할 때 저는 **「전기적
루프백으로 드리프트를 먼저 재라」**고 말했습니다. **이 구성에서는 안
됩니다.**

간편 모드의 출력은 **출력 전용 USB 기기**(D3V)입니다. 그 출력을 디지털로
되받을 입력이 없습니다. 그리고 폰의 USB-C 포트는 **하나뿐**이라 출력 기기와
입력 기기를 동시에 물릴 수도 없습니다.

**더 나은 방법이 있고, 그게 아래 보완 1입니다.**

---

# 보완하면 좋을 것

## 보완 1 — 드리프트를 **어떻게** 잴지가 없습니다 (§7)

§7 은 「1/5/10/30/60분 구간에서 delay 변화를 추적한다」고만 적습니다.
**방법이 없습니다.** 음향으로 재면 **클럭 드리프트와 방·온도 변화가
섞입니다** — 음속은 1℃ 에 약 0.17% 변하고, 30분이면 실내 온도도 움직입니다.
8 m 에서 1℃ 면 약 0.04 ms 이고, 이건 찾으려는 드리프트와 같은 자릿수입니다.

**§16 에 이미 답이 적혀 있는데 §7 과 이어지지 않았습니다.**

```text
AudioTrack.getTimestamp()   → (framePosition, nanoTime)
AudioRecord.getTimestamp()  → (framePosition, nanoTime)

출력 속도 = Δframes_out / Δt
입력 속도 = Δframes_in  / Δt
drift(ppm) = (출력속도 / 입력속도 − 1) × 1e6
```

**음향이 전혀 필요 없습니다.** 스피커를 울리지 않고, 사무실에서, 한 시간을
조용히 돌릴 수 있습니다. 이것을 **주 방법**으로 삼아 주십시오.

> 다만 `getTimestamp()` 가 모든 경로에서 제공되는 것은 아닙니다. **안 되는
> 경우를 그대로 보고**하고 아래 방법으로 넘어가야 합니다 — 조용히 0 을
> 돌려주면 「드리프트 없음」으로 읽힙니다.

**음향 확인은 가까이서 하십시오.** 폰을 스피커에서 **수 cm** 에 두면 음향
경로가 0.1 ms 수준이 되어 온도 영향이 사라집니다. 멀리 두고 재면 드리프트를
재는 것이 아니라 **방이 데워지는 것을 재게** 됩니다.

**정밀 모드는 구조상 드리프트가 0 이어야 합니다**(같은 인터페이스 = 같은
클럭). 그런데 **그건 가정이지 사실이 아닙니다** — `AudioRecord` 를 **두 개**
열면 같은 기기라도 클럭을 공유한다는 보장이 없습니다. §5 가 이미 단일
multichannel stream 을 권하고 있는데, **그 까닭을 「선호」가 아니라 「요구」로**
적어 주십시오. 확인 방법은 간단합니다 — 두 채널의 sample count 가 끝까지
같은가.

## 보완 2 — **블록 길이 ↔ 저역 분해능 ↔ 반사**의 맞바꿈이 없습니다

§30 은 FFT size 와 window 를 **저장하라**고만 하고, **무엇을 골라야 하는지
기준이 없습니다.** 그런데 여기에 함정이 둘 있습니다.

1. **블록이 지연보다 짧으면 지연이 감겨서 H 가 쓰레기가 됩니다.** 8 m 면
   23 ms 이고, 48 kHz 에서 1024 표본(21 ms)은 이미 모자랍니다.
2. **저역을 보려면 블록이 길어야 하고, 긴 블록은 반사를 끌어들입니다.**

```text
48 kHz 기준
 4096 →  85 ms → 11.7 Hz   ← 31.5 Hz 대역을 못 가른다
16384 → 341 ms →  2.9 Hz   ← 저역은 보이지만 반사가 들어온다
```

예배당처럼 잔향이 긴 곳에서는 이 맞바꿈이 **결과를 지배합니다.** 최소한
**기본값과 그 근거**, 그리고 **지연을 빼기 전/후 중 언제 자르는지**를
적어 주십시오. (다중 시간창 방식은 MVP 밖으로 미뤄도 됩니다 — 다만 **미뤘다고
적어** 주십시오.)

## 보완 3 — Phase 표시 규약이 비었습니다 (§6 ↔ §10 이 안 이어집니다)

덩어리 지연을 빼고 H 를 구하면, 보이는 위상은 **「얼마를 뺐느냐」에 따라
달라집니다.** 지연 추정이 0.1 ms 달라지면 10 kHz 에서 위상이 360° 돕니다.

→ **화면과 저장 자료에 「뺀 지연」을 위상과 함께** 적어 주십시오. 같은
측정을 두 번 해서 위상이 다르게 보일 때, 그게 시스템이 변한 것인지 지연
추정이 달라진 것인지 **지금 지시서로는 가릴 수 없습니다.**

## 보완 4 — 60분 게이트에 **전원 허브가 없다**는 사실이 빠졌습니다 (§24·§35)

폰의 USB-C 는 **하나**이고 그 자리를 오디오 기기가 씁니다. 그래서
**충전하면서 60분을 돌릴 수 없습니다.** 이건 이미 막힌 것으로 기록돼
있습니다 — 30분까지만 했고 배터리 −5%p · 온도 +2.4℃
(`docs/verify/2026-10-01-builtin-mic-with-usb-c-output.md` §10).

지금 지시서는 이걸 **테스트 조건**으로 적었는데, 실제로는 **먼저 사야 하는
물건**입니다. **조달 항목**으로 올려 주십시오. 안 그러면 TF-2 와 §35 가
동시에 막힙니다.

## 보완 5 — MVP 경계가 없고, TF-0 안에 **go/no-go** 가 숨어 있습니다

39개 절 · 10개 Phase · 두 모드는 현실적으로 몇 달입니다. **어디까지가 하나의
쓸 수 있는 덩어리인지**가 안 적혀 있습니다. 제안:

```text
1차  간편 — Delay + Magnitude + Coherence      ← 여기서 멈춰도 쓸 수 있다
2차  Phase (신뢰도 조건부)
3차  정밀                                       ← 2채널 검증이 go/no-go
4차  Multi-Point
```

**1차가 쓸 수 있는 까닭**은 막는 것 3에서 좁힌 그대로입니다 — 마이크 곡선이
없어도 **정렬과 전후 비교**는 됩니다. 절대 응답만 막으면 됩니다.

그리고 **§32 TF-0 의 「2채널 USB capture 가능성 검증」은 아키텍처 작업이
아니라 정밀 모드 전체의 go/no-go 관문**입니다. 실패 가능성이 실제로 있으니
(막는 것 2) Phase 안에 묻지 말고 **독립 관문**으로 올려 주십시오.

## 보완 6 — 작은 것 셋

- **§19 공간 평균**: 「단순 dB 산술평균을 무조건 쓰지 않는다」는 좋은
  경계입니다. 한 걸음 더 — **크기는 전력평균(⟨|H|²⟩)이 기본**이고,
  **위상은 위치끼리 평균하지 않습니다**(위치마다 지연이 달라 뜻이 사라집니다).
- **§12 화면 방향**: 2026-10-01 에 **분석 탭은 가로 고정, 나머지는 세로
  고정**으로 정해졌습니다. TF 화면은 분석 탭에 들어가므로 가로입니다.
  지시서에 없으니 적어 주십시오.
- **§30 저장 자료**: **신호 종류와 레벨**, **평균 횟수**가 빠졌습니다. 나중에
  두 측정을 견줄 때 이 둘이 없으면 비교가 성립하지 않습니다.

# 제가 확신하는 정도

**확신합니다**: 단일 블록 coherence = 1(수식으로 확인 가능) · 평균 영역이
결과를 가른다 · 전기 Reference 에서는 마이크 응답이 상쇄되지 않는다 ·
정밀 모드 출력 경로가 지시서에 없다.

**확신하지 못합니다**: H1/H2/Hv 중 이 용도의 최선 · coherence 최소 평균
수 8 · 블록 길이 기본값 · `getTimestamp()` 가 이 폰의 USB 출력 경로에서
실제로 동작하는지(**아직 안 재 봤습니다**).

**아직 안 한 것**: 이 지시서의 어떤 부분도 구현하지 않았고, 드리프트를
한 번도 재지 않았습니다. 위의 드리프트 이야기는 **설계 검토이지 측정
결과가 아닙니다.**
