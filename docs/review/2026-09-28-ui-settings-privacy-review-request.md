## 1. 가장 먼저 봐 주셨으면 하는 것 — 앱이 한 말과 실제가 맞는가

### 1.1 백업 (#34)

`allowBackup` 이 선언되어 있지 않아 **기본값 `true`** 였다. 그 상태에서
앱은 녹음 직전 이렇게 말하고 있었다:

> 「설교와 성도들의 목소리가 그대로 담깁니다. **폰 안에만 두고, 기록을
> 지우면 함께 사라집니다.**」

홈페이지 개인정보처리방침도 「클라우드 저장·백업 없음」이라 적고 있었다.
**둘 다 거짓이었다** — 안드로이드 자동 백업이 앱 전용 저장소를 통째로
사용자의 구글 드라이브로 올린다.

- `app/src/main/AndroidManifest.xml` — `android:allowBackup="false"`
- `app/src/test/java/kr/joa/selahrta/ManifestPromisesTest.kt` — 새 시험 4개
- release 병합 매니페스트로 확인함
  (`:app:processReleaseMainManifest`, `d869fdf`)

**봐 주셨으면 하는 것**

1. `false` 로 두는 것이 실제로 그 약속을 지키는가. `dataExtractionRules`·
   `fullBackupContent`·`backupAgent` 가 없는 상태에서 **cloud-backup 과
   device-transfer 가 모두 막히는지** — 우리는 안드로이드 문서만 보고
   실기기 이전 시험은 하지 못했다(**미확인**으로 남겨 두었다).
2. `ManifestPromisesTest` 가 **소스 매니페스트**를 읽는다. release 병합본이
   아니다. 그 한계로 놓치는 것이 있는가.
3. 병합본에 권한이 다섯이다 — 다섯째
   `kr.joa.selahrta.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` 은 AndroidX 가
   넣는 서명 수준 자기 권한으로 보았다. 이 판단이 맞는가.

### 1.2 문구가 말하는 동작이 실제와 맞는가 (#45·#48)

오늘 설정 화면 문구를 거의 전부 갈아 끼웠다. **문구는 동작에 관한 주장**
이므로, 아래 넷이 실제와 맞는지 봐 주시기 바란다.

| 화면이 말하는 것 | 대응하는 코드 |
|---|---|
| 「권장 범위 판정은 A 에서만 합니다」 (음압 줄에만) | `MeasureScreen.kt` `canJudge = weighting == Weighting.A && range != null` |
| 「다음 측정부터 적용됩니다」 (FFT) | `CaptureController.needsEngineRestart` |
| 「시간상수는 Fast 125 ms, Slow 1초를 적용합니다」 | `TimeWeight.tauSeconds` |
| 「여러 채널을 합쳐 측정하지 않습니다」 | `planChannels` / `channelIndex` |

**이 묶음에서 실제로 틀린 말 하나를 찾았다.** 세 가중 줄이 같은 설명
문자열을 돌려 쓰고 있어서, 「권장 범위 판정은 A 에서만」이 **주파수 분석
가중 줄에도** 떠 있었다. 그 판정이 보는 것은 음압 가중이므로 그 자리에서는
거짓이다. 줄마다 제 설명을 쓰게 갈라 고쳤다(`splWeightingHelpKo` /
`peakWeightingHelpKo` / `analysisWeightingHelpKo`).

**같은 종류가 더 있는지** 봐 주시기 바란다 — 한 자리에서 참인 문장이 다른
자리에서 거짓이 되는 경우.

## 2. 구조가 바뀐 곳 — 라이트 모드 (#41)

### 무엇을 했는가

`SelahColors` 는 색 13개를 담은 `object` 였고 화면 코드가 **808곳**에서
`SelahColors.X` 로 부른다. 그중 많은 수가 `Canvas` 의 그리기 람다와
`@Composable` 이 아닌 함수(`calibrationTone`, `levelColor`) 안이다.

CompositionLocal 로 바꾸면 읽는 자리가 전부 `@Composable` 이어야 해서 그
800곳을 함께 뜯어야 한다. 그래서 **갈아 끼울 수 있는 한 벌**을 두었다:

```kotlin
object SelahColors {
    var palette: SelahPalette by mutableStateOf(DarkPalette)
        private set
    internal fun apply(mode: ThemeMode) { ... }
    val Background: Color get() = palette.background
    // …
}
```

`SelahRtaTheme(mode)` 가 그리기 전에 `apply(mode)` 를 부른다.

**봐 주셨으면 하는 것**

1. **스냅샷 정합성.** `mutableStateOf` 를 `@Composable` 바깥(그리기 람다,
   일반 함수)에서 읽는다. Compose 가 그 읽기를 지켜보아 **팔레트가 바뀌면
   다시 그리는지** — 우리는 실기기에서 전환이 즉시 반영되는 것을 눈으로
   확인했을 뿐, 놓치는 경로(예: `remember` 안에 갇힌 색, `derivedStateOf`,
   캐시된 `Paint`/`Brush`)가 있는지 정적으로 보지 못했다.
2. **`SelahRtaTheme` 의 부작용.** 컴포지션 중에 전역 상태를 쓴다
   (`SelahColors.apply(mode)`). 재구성 순서에 따라 **한 프레임 어긋남**이
   생길 수 있는가. 값이 같으면 쓰지 않도록 막아 두었다(`if (palette != next)`).
3. **앱에 한 벌뿐이라는 제약.** 한 화면에 두 테마를 함께 그릴 일이 없다고
   보았다. 미리보기(`@Preview`)·시험·프로세스 재생성에서 문제가 되는가.
4. **판정색을 밝기만 뒤집지 않았다.** 다크의 노랑(`#FFE04D`)은 흰 바탕에서
   사라진다. 이 앱에서 색은 장식이 아니라 **판정**이라, 라이트용으로 다시
   골랐다. 또 **계기 바에 칠하는 색과 글자에 쓰는 색을 갈랐다**
   (`lowBar`/`inRangeBar`/`highBar`). 이 분리가 판정의 뜻을 흐리지 않는지,
   대비가 충분한지 봐 주시기 바란다.
5. 표지 로고는 **밝기에 따라 다른 파일**을 쓴다(`SelahColors.IsLight`).
   어두운 판은 「JOA」가 밝은 회색이라 흰 표지에서 사라졌다.

## 3. 동작이 바뀐 곳

### 3.1 Leq 「전체」(세션 누적) 제거 (#44)

`LeqWindow` 를 `10초 · 30초 · 1분 · 3분` 으로 바꾸고 **`Session` 을 뺐다**
(기본 30초). 그 칸 하나 때문에 붙어 있던 것을 함께 걷어냈다:

| 걷어낸 것 | 무엇이었나 |
|---|---|
| `SESSION_MILLIS`(-1) | 창 길이가 아닌 값을 `millis` 자리에 넣던 표시값 |
| `LeqWindow.engineMillis` | 그 -1 이 엔진에 흘러가지 않게 막던 우회 |
| `needsEngineRestart` 의 Session 예외 | 창이 없으니 다시 만들 것도 없었다 |
| 화면의 값 교체 분기 | `leqSessionDbfs` 를 대신 집던 자리 |

**봐 주셨으면 하는 것**

1. **엔진 재시작 판정이 아직 옳은가.**
   `needsEngineRestart(old, new) = old.timeWeight != new.timeWeight ||
   engineLeqLongMs != new.leqWindow.millis`.
   예전에는 `if (new.leqWindow == Session) return false` 가 있었다. 그 줄을
   없앤 뒤 **재는 도중 창을 바꿀 때 엔진이 새로 만들어지는데**, 그때
   하울링 탐지·FR 수집·세션 누적이 끊기는 범위가 예전과 같은가.
2. **옛 기록 호환.** 저장된 `leqWindowMs = -1` 은 이제 리포트에서
   「기록 없음」이 된다(전에는 「전체(측정 시작부터)」). 그 기록을 열거나
   CSV 로 내보낼 때 다른 곳에서 -1 을 창 길이로 쓰는 자리가 남아 있는가.
3. `SplFrame.leqSessionDbfs` 는 **엔진이 계속 낸다**(dsp 시험 15곳이
   지킨다). 받는 곳만 없앴다. 죽은 계산을 남긴 판단이 맞는가.

### 3.2 `Medium` 시간가중 제거, 기본 Slow (#46)

같은 날 `Medium`(τ=350ms)을 넣었다가 뺐다. IEC 61672-1 이 정한 것은
**F(τ=125ms)·S(τ=1s)** 뿐이다.

**이 과정에서 오해가 하나 있었다.** 외부 검토가 「현재 앱은 Fast 0.4초 /
Medium 1초 / Slow 3초라 IEC 와 일치하지 않는다」고 보았는데, **그 숫자는
시간상수가 아니라 자리 잡는 시간(τ×3)** 이다. τ 자체는 처음부터 규격값이
었다. 설정 화면이 τ×3 을 적어 둔 것이 오해를 불렀다.

- 이제 화면이 **τ 를 그대로** 적는다.
- 시험 `Fast 와 Slow 의 시간상수가 IEC 61672 값이다` 가 값을 못박는다.
- 시험 `시간가중은 Fast 와 Slow 둘뿐이다` 가 재추가를 막는다.
  **`Medium` 을 되살려 실제로 실패하는 것까지 확인했다**(변이 시험).

**봐 주셨으면 하는 것** — `settleSamples = sampleRate × τ × 3` 이라는
「자리 잡는 시간」의 정의가 타당한가. 화면이 「Slow 3초」라고 말할 근거가
이 식뿐인데, 규격이 정한 값이 아니라 우리가 고른 어림이다.

### 3.3 PEAK 가중 기본값 Z → C (#49)

「깎지 않는다」는 뜻으로는 Z 가 곧았지만, **순간 최고값을 C 로 재는 것이
널리 쓰이는 방식**이라는 판단이다. 세 자리를 함께 고쳤다 — 데이터 기본값,
저장값 없을 때의 폴백, **「기본값으로」를 띄우는 조건**.

**봐 주셨으면 하는 것**

1. 이 판단의 근거가 충분한가. 청력 보호 기준이 말하는 peak 가 C-weighted
   peak 라는 이해가 맞는가.
2. **PEAK 은 가중 필터를 거친 뒤에 잰다**(`weightedPeakDbfs`). 반면
   **클리핑 판정은 가중 전 값**으로 내린다(`peakClipped`) — ADC 포화는
   가중과 무관한 사건이기 때문이다. 기본이 C 로 바뀌어도 이 분리가
   유지되는가.
3. 기본값이 바뀌면 **옛 기록의 `peakWeighting` 해석**이 달라지는가.
   옛 기록에는 그 값이 없을 수 있어 `null` 로 두고 「기록 없음」으로
   적는다(짐작해서 채우지 않는다).

### 3.4 간편 보정 단순화 (#42)

- 교정기 94/114 dB 단추가 **순음 확인을 통과해야만** 열렸다
  (`enabled = tone?.ok == true`). 그 확인이 오락가락하는 자리에서는
  **아예 보정을 할 수 없었다.** 이제 소리를 읽고 있으면 눌린다.
- 확인을 버리지는 않았다 — 순음이 보이면 테두리가 초록으로 굵어지고,
  아래 한 줄이 상태를 적는다. **막는 대신 보이게 한다.**
- 「또는 다른 소음계에 맞추기」(기준 소음계 값 입력)를 걷어냈다.
  `CalibrationSource.Meter` 와 `computeOffset` 은 교정 마법사가 쓰므로 남겼다.
- 「지금 읽는 값」이 dBFS 와 **보정된 음압을 함께** 적는다.

**봐 주셨으면 하는 것**

1. **막던 것을 풀었다.** 순음이 없는 상태에서 교정기 값을 저장하면 틀린
   보정이 걸린다. 지금은 그것을 **보이게** 만 한다(단추 테두리, 상태 줄,
   저장 뒤 음압 표시). 이 정도가 충분한가, 아니면 확인 한 번을 다시
   넣어야 하는가.
2. 교정기 단추가 저장하는 경로(`onSave(level.db, CalibrationSource.Calibrator)`)
   가 `Meter` 경로와 같은 계산을 쓰는가. 입력칸을 걷어내면서 무엇이
   빠지지 않았는가.
3. **실기기로 확인하지 못했다** — 교정기가 없다. 94 dB 를 누른 뒤 「지금
   읽는 값」이 94.0 이 되는지는 **미확인**이다.

## 4. 이번에 두 번 겪은 실패 유형 — 같은 것이 더 있는지 봐 주십시오

오늘 **조용히 사라진 것**을 두 번 찾았다. 둘 다 **빌드도 시험도 막지
않았다.**

### 4.1 부르는 자리가 없어진 기능

구간별 권장 범위에 **삭제 단추가 아예 없었다.** 확인 대화상자
(`confirmRemove` 를 보는 `AlertDialog`)도, 부르는 쪽의 `onRemove` 배선도
멀쩡히 있는데 **`confirmRemove = true` 로 만드는 자리만** 없었다. 그래서
한 번 더한 구간을 뺄 길이 화면에 없었다.

코드를 지우면 컴파일러가 막는다. **부르는 자리가 빠지는 것은 아무것도
막지 않는다.**

### 4.2 지워진 시험

PR #44 에서 파일을 토막으로 잘라 붙이다가 그 사이에 있던 **응답 속도 시험
넷을 함께 지웠다.** `git show 3dc127e` 로 확인했다. **지워진 시험은
실패하지 않으므로** 빌드가 통과했다. PR #46 에서 되살렸다.

**요청** — 이 범위(`562a6db..4eced7b`)에서 같은 유형이 더 있는지 봐 주시기
바란다:

- 선언은 남았는데 **부르는 자리가 없는** 화면 요소·분기
- 이 범위에서 **삭제된 시험**과, 그 시험이 지키던 성질이 지금도 지켜지는지
- `git diff` 로만 보면 「문구 변경」으로 보이는데 **실제 동작이 함께
  바뀐** 자리

## 7. 요청하는 판정 형식

늘 하시던 대로 **Critical / High / Medium / Low** 로 나누어, 각 지적에
파일·줄과 재현 방법을 붙여 주시기 바란다. 특히:

- **1장(앱이 한 말과 실제)** 에서 어긋나는 것이 있으면 Critical 로 봐도
  좋다. 공개 문서와 스토어 정책에 걸리는 종류다.
- **4장(조용히 사라진 것)** 은 우리가 스스로 찾지 못하는 유형이라,
  하나라도 더 찾아 주시면 그것이 이번 검토의 가장 큰 값이다.
