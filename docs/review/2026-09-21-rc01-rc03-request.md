## RC01 (High) — 목록 정리가 원자적이 아니었다

**지적이 정확합니다.** `CopyOnWriteArrayList` 의 **낱개 연산**이 안전한
것과 **복합 연산**이 안전한 것은 다른 이야기인데, 제가 그것을 섞어
생각했습니다. Kotlin 의 `removeAll { }` 은 RandomAccess 목록에서 **번호로
읽고 지우는** 연산이라, 그 사이에 writer 가 하나를 지우면 번호가
어긋납니다. **주 스레드의 `start()` 에서 터지므로 앱이 죽습니다.**

검증자의 최소 재현을 옮겨 이 환경에서도 터지는 것을 먼저 확인했습니다:

```
[RC01] 최소 재현: ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 0
```

### 수정 — 목록을 떼어 내고 자물쇠 하나로 묶었습니다

`PendingList` 를 만들어 **모든 갱신을 짧은 자물쇠 하나로** 직렬화합니다.

```kotlin
fun sweep(isDone: (T) -> Boolean): Int = synchronized(lock) {
    val i = items.iterator()
    while (i.hasNext()) if (isDone(i.next())) i.remove()
    items.size
}
fun addIfPending(item: T, isDone: (T) -> Boolean): Boolean = synchronized(lock) {
    if (isDone(item)) return@synchronized false
    if (!items.contains(item)) items.add(item)
    true
}
```

- **그 안에서 기다리지 않습니다** — `release`·`stop`·`join` 은 전부
  밖에서 합니다. `isDone` 은 `@Volatile` 읽기뿐입니다.
- **넣을지 말지도 같은 자물쇠 안**에서 봅니다(앞서 짚어 주신 좁은 순서).

### 회귀 시험 — barrier 로 고정했습니다

`PendingListTest.정리 도중에 같은 항목을 지워도 터지지 않는다` 가
**술어 안에서 다른 스레드를 풀어 줍니다.** 예전 구조라면 터지는 자리이고,
지금은 지우는 쪽이 기다립니다. 정리·재시작이 예외 없이 끝나고, 안 끝난
것은 남으며, 상한도 지켜지는지 함께 봅니다.

「되풀이 실행의 통과로 대신하지 않는다」는 말씀 그대로입니다.

## RC02 (Medium) — 놓기 실패를 성공처럼 셌다

검증자 재현: `RELEASE_FAILURE starts=4 unreleased=4 pending=0 warnings=4`.
제 시험에서도 **시작 5 · 실패 5 · pendingCount 0** 이었습니다.

**「다시 소리를 낼 수 있게 한다」가 자원이 없어졌다는 근거가 아니다**는
지적이 맞습니다. 제 정책이 상한의 목적과 어긋났습니다.

### 수정 — 경계까지 함께 고쳤습니다

**1) 계약을 바꿨습니다.** `SignalSink.release(): Boolean`.
실제 adapter 가 예외를 삼키고 성공처럼 굴던 것도 같이 고쳤습니다:

```kotlin
override fun release(): Boolean {
    val t = track ?: return true
    track = null
    return runCatching { t.release() }
        .onFailure { Log.w(SINK_TAG, "release 실패", it) }
        .isSuccess
}
```

**2) 「시도를 끝냈는가」와 「성공했는가」를 나눴습니다.**

```kotlin
val isSlotFree: Boolean get() = releaseAttempted && releaseOk
val releaseFailed: Boolean get() = releaseAttempted && !releaseOk
```

자리를 비켜 주는 것은 **둘 다 참일 때만**입니다. 실패한 것은 계속
상한에 세고, 같은 sink 에 놓기를 되풀이하지 않습니다.

**3) 화면 문구도 나눴습니다.** 실패는 기다려도 풀리지 않으므로
「잠시 뒤 다시」가 아니라 **「소리 장치를 정리하지 못해 더 내보낼 수
없습니다. 앱을 다시 켜 보십시오.」** 로 적습니다.

**결과**: 시작 **2** · 실패 **2** · pendingCount **2**(상한 2).

## RC03 (Low) — 「혼합」 시험이 실은 한쪽만 보고 있었다

맞습니다. 가짜 출력의 `stop()` 이 **언제나** 쓰기를 풀어 주는데
「쓰기 지연」이라 이름 붙였고, **주석에도 사실상 그렇게 바뀐다고 적어
놓고 그대로 뒀습니다.**

이제 **서로 다른 출력 둘**을 씁니다 — A 는 `stop()` 이 쓰기를 풀어 주지
않아 `write` 안에 남고, B 는 풀어 주되 `release` 에서 멈춥니다. 각각 그
상태임을 latch 로 확인한 뒤 합계·추가 open 거절을 보고, 게이트를 하나씩
풀어 하나씩 정리되는 것과 다시 시작되는 것까지 봅니다.

## 판단을 구하는 곳

1. **`PendingList` 의 자물쇠 범위.** `sweep`/`addIfPending` 의 술어가
   자물쇠 안에서 돕니다. 지금은 `@Volatile` 읽기뿐이라 짧지만, 그 계약을
   문서로만 묶어 둔 것이 충분한지.
2. **놓기 실패가 영구히 자리를 막는 것.** 실패가 둘 쌓이면 앱을 다시 켜기
   전에는 시험음을 낼 수 없습니다. 측정은 영향받지 않지만, 되살릴 길을
   두어야 하는지.
3. **`release()` 의 계약**을 「예외를 던져도 되고 false 를 돌려줘도 된다」로
   둔 것이 모호하지 않은지.
