## 3. 지적 사항

### PND-01 — High: Done이 먼저 되면 조건 위반을 발견해도 저장한다

**위치:** `CaptureViewModel.kt:1839–1858` 및 `finishRtaCapture`; `RtaCaptureRun.kt:139–149,168–169`.

구현은 여전히 `run.tick(nowMs())` 다음에 조건을 검사한다. tick 또는 프레임 콜백이 Done으로 바꾼 다음에는 `cancel()`이 아무 일도 하지 않는다. finish는 고정된 설명을 사용하도록 개선됐지만, **유효하지 않은 완료를 거부하는 최종 검사**가 없다. “저장 직전이 아니라 매 틱 검사”는 그 대안이 아니다.

**재현:** 실제 시간으로 11.2초간 공급한 뒤 UI 스레드를 남은 완료 경계까지만 잠시 붙들었다. 같은 UI 작업에서 출력 채널을 변경하고 풀었다. 시계·phase·누적 수 등 제품 필드는 수정하지 않았다. 그 다음 VM tick이 완료와 조건 변경을 함께 처리한다.

```text
PEND_BOUNDARY saved=1 notice=null
```

**영향:** 완료 직전 변경은 정상 파일이 된다. 조건 변경 안내도 후속 reload에 의해 없어질 수 있다. 중간 변경을 잡는 시험만으로 “조건이 구간 내내 유지됐다”는 계약은 성립하지 않는다.

**수정:** 매 프레임의 적용 context 검사와 별개로 저장 승인 직전 검증을 둔다. 출력 확인처럼 suspend하는 작업이 있으면 **그 뒤에** context를 다시 검사하고, 위반 시 `cancel()`에 의존하지 말고 저장 함수를 호출하지 않은 채 실패를 반환한다. 완료 상태 자체보다 유효성 위반이 우선해야 한다. 프레임의 session·curve generation 등 실제 적용 식별도 함께 다룬다.

**회귀:** 마지막 tick의 변경, 프레임 콜백이 먼저 Done이 된 경우, 출력 조회 대기 중 변경, 변경했다 원복한 경우, 정상 완료 대조군. 제공한 반례와 최소 패치에서는 `saved=1 → 0`을 확인했다. 빠르게 바꿨다 원복하는 경로까지 최소 패치가 해결한다고 주장하지 않는다.

### PND-02 — High: 순음 주파수를 바꿔도 같은 구간으로 누적한다

**위치:** `CaptureViewModel.kt:1676–1691,1903–1947`, `startSignalOnCommandThread`의 Custom retune 분기; `RtaMeasurement.kt`, `RtaDifference.kt:67–75`.

RtaCaptureContext에는 신호 이름·채널·세기만 있고 `signalToneHz`가 없다. Custom 순음은 retune으로 주파수를 바꾸므로 **playGeneration도 그대로**다. 따라서 문서가 인정한 “대역 잡음 파라미터 저장 누락”뿐 아니라, **진행 중 순음 평균의 조건 감시도 빠진다.**

**재현:** Custom 1kHz로 차례 측정을 시작하고 6초에 2kHz로 바꿨다. 전후 합성 밴드 값은 -60/-20dBFS로 구별했다. 실제 VM과 silent SignalPlayer를 통과했다.

```text
PEND_FREQUENCY saved=1 signal=Custom mean=97.47937509717681
```

**영향:** 서로 다른 시험 주파수의 자료가 한 곡선에 섞인다. 별개로 저장한 두 Custom/Band 기록도 주파수를 복구할 수 없다. 비교 함수는 measurement의 signal 자체도 보지 않아 Pink와 Custom처럼 자극 종류가 다른 자료도 조건이 같으면 계산 가능하다.

**수정:** 구간 context와 저장 레코드에 실제 적용 `SignalRequest`의 의미 있는 부분을 보존한다. 최소한 Custom/Band 중심 주파수, Band의 폭/필터 정의 버전, 신호 종류가 필요하다. 현재 고정 폭이면 존재하지 않는 사용자 설정을 만들지 말고 실제 상수/알고리즘 버전을 남긴다. 출력 응답도 가능하면 `(intent, generation, appliedRequest)`를 돌려 원하는 요청과 일치하는지 확인한다. 채널·출력 레벨은 설계상 비교 축이므로 두 완료 기록 간 차이 자체를 막지 않는다.

**회귀:** Custom 1k→2k 도중 변경은 취소, 동일 주파수 유지 정상 저장, 서로 다른 Custom/Band 주파수 파일 왕복과 자동 비교 제한, Pink↔Custom, 옛 파일 파라미터 미확인. 최소 패치는 **구간 내 주파수 감시만** 고친다(`saved=1 → 0`). 저장 형식·비교 함수까지 해결한 패치가 아니다.

### PND-03 — Medium, 잔여: 새 장 번호만으로 ‘10초 평균’의 입력 coverage는 검증되지 않는다

**위치:** `CaptureViewModel.kt:1824–1837`; `RtaCaptureRun.kt:130–147`; `RtaEngine.kt:331–340`; `CaptureController.kt:738` 부근 UI 발행 제한.

중복 seq를 걸러 기존 0-frame 반례를 막은 것은 맞다. 그러나 화면용으로 평활한 값을 UI 발행·StateFlow 소비 후 다시 평균하는 경로와, 안정화 구간 관측률로 스스로 낮아지는 minFrames는 그대로다. 누락된 분석 장의 기여 전력을 되찾지 못한다. 이번 지적은 다른 기기에서의 오차량을 새로 측정했다는 주장이 아니라 **코드와 요청서가 모두 인정한 미완료 계약**이다.

**영향:** UI 부하·발행 타이밍에 따라 평균에 반영되는 프레임과 전력이 달라질 수 있다. seq 중복 방지 통과를 “유효 입력 10초 전체를 평균했다”로 확대할 수 없다.

**수정:** 아래 §4의 분석 스레드 누적 방식을 권한다. 화면 경로에 coverage 숫자만 덧붙여도 빠진 전력과 평활 편향은 복구되지 않는다. 저장 시 실제 시작/끝 capture frame·sampleRate·accepted/expected window·missing coverage와 평균 정의 버전을 남긴다.

**회귀:** 같은 PCM의 공급 블록 크기·UI 발행률·UI 소비 속도를 바꿔도 결과가 같아야 한다. 짧은 큰 burst와 정적 톤을 구별하고, 누락·0-frame·세션 재시작은 정상 완료로 둔갑하지 않아야 한다. 기존 중복 seq 시험은 유지한다.

### PND-04 — Medium: EQ 범위 설명과 실제 강조 띠가 어긋난다

**위치:** `ui/instrument/InstrumentGuideScreen.kt:97`.

`remember(region.id)`인데 region.id는 프로필 전체에서 유일하지 않다. 신디사이저 피아노/EP의 `body`는 60~200Hz, 리드/브라스의 `body`는 150~600Hz다. 프로필을 바꿔도 key가 body라 강조 목록을 다시 만들지 않는다.

**재현:** 실제 화면에서 피아노/EP → 리드/브라스로 선택했다. 새 요약 150~600Hz 존재를 확인한 뒤 막대가 없는 고정 입력 상태에서 차트 내부 한 행의 픽셀을 비교했다.

```text
PEND_EQ chartPixelsChanged=0 piano=60..200 lead=150..600 bothId=body
```

**영향:** 사용자는 새 설명을 읽으며 예전 주파수 띠를 보게 된다. “카드를 바꾸면 따라간다”는 기존 시험은 id가 달라지는 같은 프로필 안의 변경만 검사한다.

**수정:** `remember(region.range) { EqBandHighlight.bandsOf(region.range) }`, 또는 작은 계산을 직접 호출한다. 첨부 패치에서 픽셀 변화 **0 → 237**, 회귀 통과를 확인했다.

**회귀:** 같은 id·다른 범위의 프로필 간 전환, 같은 범위 유지, 다른 악기로 전환, 상태 복원. 반대로 `EqBandHighlight`의 80~150Hz → 80·100·125·160 규칙 자체는 밴드 경계 교집합이라는 목적에 맞는다.

### PND-05 — Medium: 결과 페이지만 전달하면 PDF의 경고가 빠진다

**위치:** `recording/ReportPageLayout.kt:40–44,61–69`.

경고는 본문 순서상 한 번만 배치된다. 긴 메모로 숫자가 뒤쪽 페이지로 이동하면 경고를 반복하지 않는다. 전체 PDF에서 경고가 삭제되는 결함은 아니다. **숫자 페이지를 따로 인쇄·전달할 때 해석 조건이 떨어져 나가는 문제**다.

**재현:** 제품 PDF 시험의 fixture에 긴 메모·미보정·클리핑·놓친 조각을 넣어 실제 작성기를 실행했다. 같은 wrap과 배치기를 사용한 독립 단언 및 Poppler 렌더링으로 확인했다.

```text
PEND_PDF total=3 resultPages=[3] warningPages=[1]
```

3쪽에 `SPL 보정: 보정 안 함`, 클리핑 행 수는 남지만 “참고값이며 실제 음압과 10dB 넘게 다를 수 있음”, 입력 신뢰성·클리핑의 해석 경고는 없다. 경고를 수치보다 먼저 보여 주려는 새 PDF의 핵심 목적이 분리된 페이지에서는 약해진다.

**수정:** 매 페이지에 기록 식별과 짧은 신뢰성/미보정 경고를 반복하거나, 최소한 결과가 있는 페이지에 독립적으로 읽을 수 있는 경고 블록을 둔다. 반복 블록 높이를 미리 빼고 paginate해야 본문을 덮지 않는다. 긴 메모를 부록으로 보내 핵심 조건·결과를 첫 페이지에 유지하는 설계도 가능하다.

**회귀:** 긴 메모·긴 마이크 설명에서 결과 페이지별 미보정/입력 경고 유지, 경고 자체가 여러 줄인 경우, section title과 첫 줄 동행, footer 침범 없음. 실제 writer 결과를 다시 렌더링한다. 이번 제안 패치에는 PDF 수정은 포함하지 않았다.

### PND-06 — Low: Type3이므로 검색·복사가 불가능하다는 단정은 출력 파일과 다르다

**위치:** `recording/ReportPdf.kt:37–46`, `ReportPdfTest`의 Type3 설명, `PENDING-REVIEW.md` PDF 절충 설명.

생성된 `warned.pdf`는 Type3을 사용하지만 font resource에 **ToUnicode**도 들어 있다. pypdf가 한글 경고·제목·수치를 추출했고 `"미보정" in extractedText == true`였다. 글리프가 Type3이라는 이유만으로 텍스트 정보가 없다고 판단할 수 없다.

**영향:** 사실과 다른 한계를 전제로 불필요한 PDF 라이브러리 교체를 결정하거나 검색 기능이 없다고 안내하게 된다.

**수정:** “이번 파일에는 Unicode 매핑이 있으며 한글 추출을 확인했다. 읽개별 선택·검색 품질은 별도 확인”으로 정정한다. 줄바꿈·읽기 순서는 추출 결과에서 분절되므로 모든 읽개에서 완벽하다고 반대로 단정하지 않는다.

**회귀:** 결과 파일의 Unicode 추출에서 정규화한 경고·기기명·Leq 확인. 대표 PDF 읽개에서 검색·선택을 따로 확인한다. `/Type3`·파일 크기·검은 픽셀 수만으로 텍스트 의미 보존을 검증하지 않는다.

## 4. coverage 질문의 구체적인 해결안

**분석 스레드에서, 주파수 가중/보정이 적용된 band power를 표시용 smoothing 전에 받아 동기적으로 누적하는 작은 sink**를 권한다. 처음부터 별도 worker 큐가 필수인 것은 아니다. 31칸 합산은 이미 분석 스레드가 수행하는 고정 크기 계산이며, 그 자리에서 소유권을 끝낼 수 있다.

제안 경계(설계 예시이며 아래 API를 새로 구현한 것은 아님):

```kotlin
interface RtaBandPowerSink {
    // power는 이 호출 동안만 빌린 배열. 보관하거나 다른 스레드에 넘기지 않는다.
    fun onFrame(
        sessionId: Long,
        seq: Long,
        windowStartFrame: Long,
        windowEndFrame: Long,
        appliedContextId: Long,
        power: DoubleArray,
    )
}
```

1. attach/reset/detach와 누적 소유자는 capture 스레드로 직렬화한다. 이 sink에서 UI 작업·파일 I/O·대기를 하지 않는다.
2. 측정 전 원래 FFT가 갖고 있던 창을 섞지 않도록, 안정화 뒤의 **캡처 프레임 경계**와 창 채택 규칙을 고정한다. smoothing 이전의 corrected linear band power를 합산하고 scalar SPL offset은 고정 context에서 한 번 적용한다.
3. 각 FFT 창은 겹치므로 `창 수 × FFT 길이`를 유효 시간으로 세면 이중 계산된다. 실제 hop과 입력 프레임 구간의 합집합/누락 구간으로 coverage를 계산한다. 창 경계에 걸친 처음·끝 표본을 포함/제외하는 규칙과 허용 경계 오차를 문서화한다.
4. UI에는 불변 진행/최종 snapshot만 보낸다. UI 발행이 느려도 누적 결과는 변하지 않아야 한다. 최종 배열 복사는 완료 시 한 번이면 된다. 별도 큐가 필요해지는 경우에만 제한된 pool과 명시적 drop/gap 규칙을 추가한다.
5. 실제 10초 경과와 캡처 구간·유효 창 coverage를 함께 검증한다. 입력률이 처음부터 느리다고 기대치가 자동으로 낮아지게 두지 않는다. 0.6이나 새 절대 FPS를 근거 없이 보편적인 통과 문턱으로 정하지 않는다.

**대조 시험은 “10초 PCM 전체에 FFT 한 번”을 정답으로 삼으면 안 된다.** FFT 길이·창·밴드 경계·분해능이 달라져 다른 추정량이 된다. 제품과 같은 FFT 길이·hop·window·밴드 정의를 사용하되, 별도 오프라인 구현이 모든 채택 창의 선형 전력을 빠짐없이 합산하도록 한다. 작은 크기의 직접 DFT나 독립 FFT로 부분 대조하고, 정적 톤·밴드 내/경계 톤·짧은 burst·저/고 레벨 교대 PCM을 사용한다. 허용 오차는 동일 추정량의 부동소수점 오차 및 사전에 선언한 경계 처리에서 정하고 관측 오차를 덮기 위해 늘리지 않는다.

## 5. 다른 질문과 승인 경계

- **자동 재시작을 안 넣은 판단:** 타당하다. 조건 변경 시 현재 구간 취소가 더 작은 계약이다. 재시작을 승인 조건으로 요구하지 않는다. 대신 완료 경계까지 취소/저장 거부가 효력을 가져야 한다.
- **출력 확인:** SerialCommands.ask는 앞에 실행된 명령 뒤의 값을 받는 데 유효하며 기존 queue 지연 반례를 막았다. “원했던 신호 요청 전체와 같다” 또는 실제 스피커에서 소리가 난다는 보장과는 다르다. Custom retune 반례가 그 차이를 보여 준다.
- **EQ 안내 문구:** 숫자를 보고 자동 판정하거나 믹서를 제어하는 경로를 찾지 못했다. 작은 변화·청감 우선·부작용·출처 한계 안내는 유지됐다. `symptomTags`를 “많을 때”로 표시하는 것은 현재 카탈로그의 과다·누적 증상에는 맞지만, 미래에 부족/묻힘 태그를 추가하면 그 전제가 깨진다. 자료 모델에서 excess/deficit 방향을 나누거나 “문제가 들릴 때”라는 중립 라벨을 쓰면 안전하다. “적을 때”를 억지로 모든 대역에 창작할 필요는 없다.
- **문구 시험:** 기본 화면의 네 금지 문자열 검색은 전체 카탈로그·lazy 미표시 카드까지 검사하지 않는다. 모든 프로필·조건부 문구를 순회하는 자료 시험과 대표 화면 시험을 구분한다. 조건부 청취 실험의 “작게 깎아 견준다”를 단순 금지어로 막을 필요는 없다.
- **정지 계약 13개:** 버튼·백그라운드·noisy·LOSS·TRANSIENT·DUCK × 포커스 거절/허용 12개와 onCleared 1개를 확인했다. onCleared는 stop counter 대신 closed/최종 정리로 막는다는 주석도 코드와 맞다. 새 정지 경로를 이 표에 추가하도록 한 설명 위치는 적절하다. 과거 mutation 12개 실패 주장은 이번에 다시 돌리지 않았다.
- **PDF 쪽 나누기:** 제목과 첫 값 줄 동행·긴 값 줄바꿈은 기존 순수 시험과 실제 출력에서 확인했다. 짧은 경고 리포트는 한 장에서 읽힌다. 경고 폭은 12pt 들여쓰기를 뺀 폭으로 측정하는 편이 정확하고, PdfDocument는 write 실패에도 close되도록 try/finally를 권한다. 이 두 권고를 실기기 장애로 재현했다고 주장하지 않는다.
- **schema/원자 교체:** 새 필수 조건이 없는 옛 파일은 null로 보존된다. rename 실패 시 기존 파일 보존 시험이 추가됐고 직접 덮어쓰기가 제거됐다. unreadable 집계는 무응답보다 개선됐지만 신판·파손·권한 문제 구분은 여전히 없다. 다중 인스턴스·프로세스의 동시 쓰기나 전원 차단 내구성까지 승인한 것은 아니다.
