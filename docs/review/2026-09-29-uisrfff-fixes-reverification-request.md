## 2. UISRFFF-01 (Low) — 자체 서명 경고를 실패로 분류했습니다

**지적이 맞습니다.** 「`certificate chain is not validated` 가 보이면
통과가 아니다」라고 단정했는데, 이 문서의 `keytool -genkeypair` 가
만드는 것은 **자체 서명 인증서**라 그 경고는 정상 파일에서도 납니다.

보내 주신 패치를 그대로 적용했습니다. 거절할 것(`unsigned`,
`no manifest`, 검증 실패, 지문 불일치)과 **원인을 확인할 것**(자체
서명·신뢰 체인 경고)을 갈랐습니다.

## 3. 서명 검증을 코드로 옮겼습니다 (5회차 6장 권고)

**그리고 제가 문서에 적었던 방법이 틀렸습니다.**
`assembleRelease.doFirst` 는 그 task 가 **의존하는 작업들보다 먼저
돌지 않습니다** — 서명 task 가 이미 지나간 뒤에 실패하면 막은 것이
아닙니다.

권고하신 네 가지를 그대로 따랐습니다:

1. 속성 **넷을 모두 `orNull`** 로 읽습니다. 예전 문서 예시는 파일
   속성만 `orNull` 이고 나머지는 `.get()` 이라, 비밀번호가 없으면
   **구성 단계에서 실패해 debug 빌드조차 못 했습니다.**
2. release 전용 검증 task(`verifyReleaseSigning`)가 파일 존재와 필수
   속성을 봅니다. **비밀값은 찍지 않습니다** — 무엇이 없는지 이름만.
3. 그 task 를 release 패키징·서명 task 의 **선행 의존성**으로 겁니다
   (`bundleRelease`·`assembleRelease`·`packageRelease`·
   `signingConfigWriterRelease`).
4. 네 경우를 **실제로 돌려** 확인했습니다:

| 상황 | 결과 |
|---|---|
| 키 없음 · `assembleDebug` | **통과** |
| 키 없음 · `bundleRelease` | 실패 — 없는 속성 이름 넷을 알려 줌 |
| 일부만 있음(`STORE_FILE`·`KEY_ALIAS` 만) | 실패 — 모자란 둘만 짚음 |
| 넷 다 있으나 파일 없음 | 실패 — 경로를 확인하라고 함 |

문서의 「설정 누락 시 자동으로 debug 서명으로 떨어질 수 있다」도
걷어냈습니다. 그런 코드를 넣은 적이 없고, 지켜야 할 계약은 **명시적
으로 올바른 서명을 갖춘 release 만 허용한다**는 것입니다.

## 4. 방침 링크 — 누른 결과를 봅니다 (5회차 5장)

**넷 중 하나만 잡고 있었습니다.** 「소스를 읽어 실제로 그려지는지
본다」는 설명이 과했습니다.

| 변이 | 소스 시험 | 이제 |
|---|---|---|
| 호출부 삭제 | 잡음 | 잡음 |
| 호출 줄 `//` 주석 | **통과** | **잡음**(화면 시험) |
| 개인정보를 `TERMS_URL` 로 | **통과** | **잡음**(화면 시험) |
| `failedUrl` 갱신 제거 | **통과** | **잡음**(화면 시험) |

`androidTest` 에 Compose 시험 넷을 두었습니다 — 보내 주신 셋에
**설정 조각 시험 하나**를 더했습니다(부품만 보면 아무도 그 부품을 안
부르는 변이를 못 잡는다는 지적 반영).

그러려고 「앱 정보」 블록을 `AppInfoWithPolicyLinks` 로 뽑았습니다.
설정 화면 전체는 캡처 상태·저장소·기기 목록을 다 받아, 화면 시험으로
띄우면 **링크가 아닌 것들 때문에** 깨집니다.

**실기기에서 돌렸습니다**(SM-S918N, 무선 디버깅): **4개 통과.**
변이 확인 — 주소를 바꾸면 **2개 실패**, 호출 줄을 주석 처리하면
**1개 실패**합니다.

소스 시험의 KDoc 도 **무엇을 못 잡는지** 적도록 고쳤습니다. 남는
값어치는 「주소가 공개 방침의 것과 같은가」 하나입니다.

> 되묻습니다:

> 1. 요청서가 「Compose 시험이 androidTest 에 있다」고 적었는데

## 6. 확인하지 못한 것

- **시험 키로 서명하는 전 과정** — 키가 없습니다. `verifyReleaseSigning`
  은 「없을 때 막힌다」까지만 확인했습니다.
- 교정기 94/114 dB 음향 정확도, 제조사 이전 도구, Play Console.
- 정확 창의 **장시간(예배 두 시간) 부하**와 p95/p99 처리 시간·read
  누락. 아래 6-1 은 20초 표본 셋씩입니다.
- `connectedDebugAndroidTest` 는 **사람이 기기에서** 돌립니다. 정규
  검증 명령에는 안 넣었습니다.

### 6-1. 정확 창의 실기기 부하 (추가 측정)

Galaxy S23, **내장 마이크 48kHz**(USB 로 adb 를 붙여 UMC404HD 는 못
꽂았습니다). 같은 기기·같은 입력에서 정확 창만 켜고 끈 A/B 입니다.
`/proc/<pid>/stat` 의 utime+stime 을 20초씩 세 번 쟀습니다.

| | 표본 1 | 표본 2 | 표본 3 | 평균 |
|---|---:|---:|---:|---:|
| 정확 창 **ON** | 96.5% | 76.4% | 85.0% | **86.0%** |
| 정확 창 **OFF** | 93.2% | 100.7% | 98.9% | **97.6%** |

**차이가 잡히지 않습니다.** 켠 쪽이 오히려 낮게 나왔는데, 한 조건
안의 편차(20 포인트)가 두 조건의 차보다 커서 그렇습니다. 링 갱신
비용은 앱 전체 CPU 에 묻힙니다.

메모리(정확 창 ON, 측정 25초 뒤):

```
TOTAL PSS: 183,493 kB   ·   Java Heap 35,952   ·   Native Heap 11,308
```

**이 수치가 말하지 않는 것**:

- 코어 하나 기준 **약 90%** 는 정확 창과 무관하게 원래 그렇습니다
  (2026-09-28 에 UMC404HD 192kHz 로 쟀을 때도 88~102% 였습니다).
  그 절대값의 원인은 아직 가르지 않았습니다.
- **GC pause·p95/p99 처리 시간·read 누락은 재지 않았습니다.**
- 20초 표본 셋은 **장시간 부하가 아닙니다.** 예배 두 시간에서 링이
  어떻게 되는지는 산술 실험(검토자의 3.456억 표본)만 있습니다.
- 3.3 MiB 는 위 PSS 안에 있지만 **따로 떼어 확인하지 않았습니다.**
