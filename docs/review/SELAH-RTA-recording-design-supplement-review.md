## 좋아진 부분과 수용 가능한 결정

read 완료 시각과 표본 시각 분리, 프레임 좌표 보존, 녹음 손실을 무음과 사건으로 나타내는 방향, UI 스로틀 이전 분기, epoch 도입, float32 타임라인, writer 차단 중 비블로킹 시험은 타당하다. Leq 창 이름과 누적 clipping 문제도 문서상 바로잡았다.

타임라인을 고정 길이 파일로 저장하는 선택 자체는 기술적으로 수용 가능하다. 식별자·저장소 인터페이스와 Phase 10 DB 요구를 유지하고 ADR에 예외를 기록한다는 범위도 적절하다. 다만 파일 기반 복구 계약은 아래 S03을 충족해야 한다. PCM16 MVP도 양자화 한계를 명시하는 조건에서 가능하지만 S06의 포화 규칙이 필요하다.

## S01 — High: anchor 시간과 WAV 미디어 시간의 연결이 아직 정의되지 않았다

**위치:** 보완 설계 46–50, 64–70, 95–99, 120–126행.

**근거:** `captureNs`는 `fsEff`를 쓰지만 WAV 재생 위치는 헤더의 공칭 sampleRate에 따른 프레임 시간이다. 무음을 채우면 프레임 위치는 보존되지만 두 시간의 속도 차이가 없어지지는 않는다. `elapsedMs`가 어느 시간인지 명시하지 않은 채 `rowIndex=elapsedMs/500`과 재생 위치 나눗셈을 동시에 약속할 수 없다.

공칭 48,000Hz, 실제 48,002.4Hz(+50ppm), 단조 시계 경과 7,199.8초에서 프레임 수를 정수화하면 WAV 위치는 약 7,200.160초다. 단조 시계 행은 14399, WAV 위치의 행은 14400으로 달라진다. 프레임 손실이 전혀 없어도 발생한다. 이 50ppm은 반례 입력이며 특정 기기의 실측치가 아니다.

또한 67행의 ‘REC 이전 표본 최대 한 블록’은 성립하지 않는다. 문서 스스로 인정한 버퍼 적체가 있으면 버튼 후 첫 read 블록 전체가 200ms 전 소리일 수도 있다. 블록 길이는 그 블록이 얼마나 오래됐는지의 상한이 아니다.

**사용자 영향:** 긴 녹음의 소리·그래프·마커가 다른 구간을 가리키고, REC 이전 소리의 포함 범위를 잘못 안내할 수 있다.

**권장 수정:** 다음 중 하나를 계약으로 확정한다.

1. 행과 seek를 녹음 상대 프레임 / 공칭 fs 기준으로 통일하고, 단조 시계는 별도 anchor 매핑으로 표현한다.
2. 행을 단조 시계 500ms 격자로 유지한다면, WAV position → 상대 프레임 → captureFrame → anchor 시각 → 행 변환을 반드시 거친다.

버튼 이전 소리는 유효 anchor로 잘라낼지, 제한된 pre-roll을 허용할지 정하고 추정 모드에서는 보장 가능한 범위만 안내한다. anchor 없는 상태에서 적체 상한을 모르면 유한한 시각 오차 상한도 주장하지 않는다. 80행의 정확도 시험은 fitting에 넣은 anchor 자체와의 비교가 아니라 다음 anchor를 예측하는 방식 등 독립된 오차 검증으로 구체화해야 한다.

**회귀 시험:** ±50/±200ppm의 2시간 가상 시계, 44.1/48kHz, 행 경계 직전·직후 seek, 중간 gap, anchor 실패·재획득을 조합해 같은 프레임의 소리·행·사건을 찾는지 확인한다. REC 직전 200ms 적체도 주입한다.

## S02 — High: 합산 제어 슬롯은 손실 위치·epoch 이력을 보존하지 못한다

**위치:** 보완 설계 101, 191–198, 217–224, 238–260행.

**근거:** `droppedFrames += n`은 손실 총량만 보존한다. 예를 들어 동일 길이 블록 10·12를 버린 경우와 10·11을 버린 경우는 총량이 같지만 무음을 써야 할 위치가 다르다. 제어 슬롯을 읽은 시점에 누계만 삽입하면 PCM 순서와 gap 좌표를 복원할 수 없다. 여러 설정 변경 또한 마지막 epoch로 합치면 중간 epoch를 참조하는 행을 복원할 수 없다.

수락한 패킷의 `captureFrameStart`로 중간 손실을 추론하는 방법은 가능하다. 그러나 현재 계약에는 writer가 이를 사용한다는 규칙과 마지막 수락 이후의 손실을 확정할 종료 frame watermark가 없다. 한 칸을 ‘손실 없음’으로 선언하는 것만으로 이 정보가 보존되지는 않는다.

종료도 입구의 세대 검사만으로는 부족하다. producer가 검사를 통과한 뒤 멈추고, stop이 큐가 빈 것을 보고 finalize한 다음 producer가 offer하는 순서를 배제해야 한다.

**사용자 영향:** 손실 후 음성과 그래프의 위치가 틀어지고, 과거 행에 다른 보정이 적용되거나 종료 후 늦은 패킷이 누락될 수 있다.

**권장 수정:** 수락 패킷에 프레임 구간·불변 epoch 식별을 보존하고 writer는 기대하는 다음 frame과 비교해 gap을 확정한다. 종료에는 최종 관측 frame과 마지막 수락 sequence를 보존한다. epoch 이력은 유한 저장소가 포화되면 명시적으로 녹음을 실패 처리하거나 변경을 거절하는 등, 덮어쓰지 않는 정책이 필요하다. offer와 접수 종료 사이에는 늦은 producer까지 포괄하는 선형화 지점과 drain 완료 조건을 정한다. 오디오 스레드를 기다리게 하는 수정은 피한다.

**회귀 시험:** writer를 막고 성공·실패 offer를 번갈아 만들기, 마지막 블록부터 연속 손실 후 stop, writer 정지 동안 여러 epoch 변경, 입구 검사 직후 producer를 멈추고 stop/finalize를 진행하는 barrier 시험. 모든 수락 버퍼의 1회 반환, gap 위치·길이, epoch 연결, 종료 파일 길이를 검증한다.

## S03 — High: checkpoint 기록 중 실패하면 ‘최대 약 1초 손실’ 보장이 깨진다

**위치:** 보완 설계 149–177행.

**근거:** 데이터 세 파일의 fsync 순서는 좋아졌지만 checkpoint 자체의 내구성 있는 교체 방법이 없다. 유효 checkpoint를 제자리에서 갱신하다 일부만 써진 시점에 종료되면 CRC 오류이고, 문서의 복구 규칙상 세션 전체가 failed다. 이 경우 잃는 재생 가능 범위는 마지막 1초가 아니라 그 이전 전부다. 이는 ‘CRC 오류면 failed’라는 명시적 안전 정책 자체의 잘못이 아니라, 그 정책과 손실 상한 보장의 충돌이다.

또한 각 파일의 내구성 있는 길이가 존재한다는 사실만으로 세 길이가 동일한 논리적 시점까지라는 보장은 생기지 않는다. checkpoint에는 포함된 행이 참조하는 epoch·사건이 그 events prefix 안에 있고 audio 범위와도 맞는다는 조건이 필요하다. writer 지연과 fsync 지연이 제한되지 않았으므로 ‘약 1초마다 시도’는 ‘최대 1초 손실’이 아니다.

**사용자 영향:** 강제 종료·저장 실패 뒤 이전까지 저장한 녹음을 전부 복구 불가로 처리하거나, 서로 다른 범위의 오디오·행·epoch를 정상 복구로 오인할 수 있다.

**권장 수정:** 이전 유효 checkpoint를 보존하는 이중 슬롯/세대 저널 또는 플랫폼에 맞는 내구성 있는 교체 절차를 정의한다. checkpoint 자체의 flush/sync와 새 이름 게시의 내구성도 포함한다. 단일 writer의 확정 경계에서 오디오·완결 행·완결 사건·epoch 참조가 일치하는 prefix를 정하고 그 범위만 게시한다. 복구 시 실제 길이, 레코드 정렬, 사건 경계와 참조를 검증한다. 손실 보장은 ‘마지막 성공적으로 영속화한 checkpoint 이후’로 한정하거나 별도의 지연 상한을 실제로 보장한다.

**회귀 시험:** 각 파일 쓰기·flush·sync·checkpoint 부분 쓰기·교체 단계마다 중단. 이전 checkpoint 복구, 첫 checkpoint 전 종료, 파일 단축, 손상 CRC, 존재하지 않는 epoch 참조, writer 5초 정지 등을 검증한다. 실패 시 finalized/recovered로 오인하지 않아야 한다.

## S04 — Medium: RTA 밴드는 이미 주파수 보정된 값이다

**위치:** 보완 설계 183–198행. 실제 코드 `dsp/src/main/kotlin/kr/joa/selahrta/dsp/RtaEngine.kt:118–120, 160–170`.

**근거:** 엔진은 `bands.toBandPower(power, bandPower, binCorrection)` 후 smoothing과 dB 변환을 수행한다. 따라서 RTA 출력의 dBFS라는 단위가 ‘마이크 곡선 보정 전’을 의미하지 않는다. ‘onBlock 결과가 이미 보정 전, 읽을 때 보정’이라는 공통 규칙은 SPL offset과 RTA 주파수 곡선을 혼동한다. 곡선을 다시 적용하면 이중 보정이며, 곡선 보정된 31밴드만으로 원래 FFT bin 데이터를 일반적으로 복원할 수도 없다.

**사용자 영향:** 저장 후 재생한 RTA가 실시간 화면과 달라지고, 과거 보정의 의미가 바뀐다.

**권장 수정:** 필드별 보정 상태를 정의한다. 기존 RTA 출력은 곡선 적용 완료로 저장하고 재생에서 해당 곡선을 재적용하지 않는 방식이 최소 변경이다. SPL 절대 offset은 별도로 처리한다. 원시 스펙트럼을 보관할 계획이라면 명시적으로 별도 데이터로 설계한다. `curveVersion`은 세션 안에서 해당 곡선을 불변하게 식별할 수 있어야 하며, 사용자 파일 삭제·교체 후에도 이력이 유지되어야 한다.

**회귀 시험:** 비평탄 곡선을 사용해 live와 저장/재생 밴드 일치, 곡선 변경 전후 epoch, 원본 곡선 파일 교체·삭제를 확인한다. 절대 offset과 곡선의 각각 1회 적용을 독립적으로 검증한다.

## S05 — Medium: 500ms 마지막 값만으로 녹음의 MAX·Peak를 구할 수 없다

**위치:** 보완 설계 122–124, 206–208행. 실제 코드 `dsp/src/main/kotlin/kr/joa/selahrta/dsp/SplEngine.kt:81–100, 112–113`.

**근거:** 현재 `maxDbfs`와 `peakDbfs`는 reset 이후 누적이다. 이 값을 그대로 저장하면 REC 이전 큰 소리가 들어온다. 반대로 이를 순간 값으로 대체하고 500ms 마지막 결과만 저장하면 중간 짧은 최대값을 놓친다. 블록 Peak가 0.8 → 0.1 → 0.1 → 0.1 → 0.1이면 마지막 값은 -20dBFS지만 구간 Peak는 약 -1.94dBFS다. MAX 역시 DSP가 블록 안의 최대 time-weighted power를 따로 보는 이유가 이미 코드에 설명되어 있다.

**사용자 영향:** 녹음 요약 최대값이 실제보다 낮거나 REC 이전 값에 오염된다.

**권장 수정:** 현재값과 구간 극값을 구분한다. 녹음 전용 500ms extrema와 녹음 전체 extrema를 모든 관련 표본/블록 최대에서 누적하고, live DSP의 reset이나 기존 누적 상태 변경은 하지 않는다. 필요한 블록별 extrema를 DSP 경계에서 제공한다. REC 경계·설정 변경의 극값 포함 규칙도 정한다. Peak 사건으로 보완하려면 모든 필요한 최대값이 보존된다는 계약을 명시해야 한다.

**회귀 시험:** REC 직전 큰 신호, 각 500ms 구간 초·중·말의 짧은 impulse/level burst, 블록 크기 변화, 설정 변경을 포함한다. 모든 타이밍에서 기록한 최대값과 기준 계산이 같고 live 출력은 변하지 않아야 한다.

## S06 — Medium: PCM16 반올림 후 정수 포화가 빠져 있다

**위치:** 보완 설계 268–274행.

**근거:** float 입력을 [-1,1)로 제한하더라도 `roundHalfAwayFromZero(x*32768)`은 +32768이 될 수 있다. 실제 Float 값 0.9999899864는 32768로 반올림된다. 그대로 Kotlin Short로 축소하면 -32768이 된다. 입력 상한을 1 미만으로 둔 것만으로 해결되지 않는다. 아직 변환 구현이 없으므로 실제 앱에서 이 overflow가 발생했다고 주장하지 않는다.

**사용자 영향:** 양의 큰 표본이 음의 full-scale로 바뀌어 녹음에 왜곡·클릭을 만들 수 있다.

**권장 수정:** NaN/Inf 처리 후 입력을 제한하고, 반올림한 **정수를 [-32768,32767]로 포화한 뒤** Short로 변환한다고 명시한다. 예: `q = clamp(roundHalfAwayFromZero(clamp(x,-1,1)*32768), -32768,32767)`.

**회귀 시험:** -1, +1, 0, 양·음 half-LSB, +32767.5/32768 경계 양옆, 1 바로 아래 Float, 범위 초과, NaN/Inf. 변환의 단조성 및 큰 양의 입력에서 부호 반전이 없는지 확인한다.

## 검증 범위와 다음 판정 기준

수치 반례 세 가지를 PowerShell로 독립 계산하고 `recording-supplement-counterexamples.txt`에 저장했다. 이는 새 녹음 구현의 통과/실패 테스트 수가 아니다. 코드 대조는 현존 DSP 출력의 보정·누적 의미 확인에 사용했다.

전체 보완 설계를 지금 승인하기는 어렵다. 우선 S01의 시간 좌표, S02의 순서·종료 계약, S03의 영속화 경계를 확정하고, S04–S06의 데이터 의미와 변환 규칙을 반영해야 한다. 특히 anchor 수집 자체의 탐색·시험과 전체 저장/재생 설계 승인은 구분할 수 있다. 실기기의 timestamp 품질·저장 성능·장시간 녹음은 여전히 미검증이며 이번 문서 검토로 대체되지 않는다.
