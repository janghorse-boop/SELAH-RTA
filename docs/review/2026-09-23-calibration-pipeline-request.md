## 2. dB 를 그냥 평균하면 틀린다 — 재어 보았다

dB 는 로그라 산술 평균이 에너지 평균이 아니다. 핑크 노이즈는 순간마다
출렁이므로 그 차이가 그대로 쌓인다:

```
AVG_GAP spread=±1.0dB   energy=0.03  dB=-0.00  차이=0.04dB
AVG_GAP spread=±6.0dB   energy=1.35  dB=0.06   차이=1.29dB
AVG_GAP spread=±12.0dB  energy=4.52  dB=0.12   차이=4.40dB
```

출렁임이 클수록 dB 평균이 **낮게** 나온다. 저역은 FFT 창 하나에 주기가
몇 개 안 들어가 특히 크게 흔들리므로, 그대로 두면 「저역이 모자란
마이크」로 보여 **없던 보정이 걸린다.**

튄 장(문 닫는 소리)은 광대역 레벨의 **중앙값**에서 벗어난 것을 버린다.
평균을 기준으로 삼으면 튄 장에 끌려가 기준 자체가 오염된다:

```
OUTLIER 전부=70.04dB  걸러냄=50.00dB
```

## 3. 기준 마이크 CAL 을 빠뜨리면 없던 보정이 걸린다

이번 범위에서 가장 조용한 실패다. EMM-6 는 고역을 더 크게 잡는다
(2026-09-23 실측 20kHz 에서 +4.1dB). 그 곡선을 그대로 「참값」으로 쓰면
내장 마이크가 멀쩡해도 「고역이 4dB 모자라다」로 보인다.

방도 휴대폰도 완전히 평탄하게 두고 EMM-6 만 고역에서 +4dB 더 잡게 한 뒤:

```
CAL_MISSING 14kHz 보정: CAL 적용=0.00dB  CAL 빠뜨림=4.00dB
```

옳은 답은 0dB 인데, 빠뜨리면 **그 마이크의 응답만큼 정확히** 없던 보정이
걸린다.

### 제 시험 하나가 아무것도 재고 있지 않았다

`ProfileCodecTest.믿을 수 없는 자리 표시가 살아남는다` 에 넣어 둔 전제
확인이 걸렸다. 표본이 20Hz~20kHz 를 다 덮어서 **못 믿는 자리가 하나도
없었다.** 그러면 `valid` 를 「전부 참」으로 적는 엉터리 부호기도 통과한다.

200Hz~10kHz 만 잰 표본으로 바꿨다(실제 CAL 파일이 대개 그렇다). 이제
축의 양끝이 못 믿는 자리이고, 전제 확인 두 줄을 남겨 두었다 — 앞으로
표본이 다시 넓어지면 또 걸리게.

## 5. **제가 만든 결함 하나** — 고치지 않고 적어 둔다

`CalibrationSession.summarize()` 에서, 튄 장 걸러내기가 **전부 버리는**
경우에 폴백이 돈다:

```kotlin
val keep = keepStableFrames(all, maxFrameDeviationDb)
val used = if (keep.isEmpty()) all.indices.toList() else keep
...
droppedFrames = all.size - used.size,   // ← 폴백일 때 0 이 된다
```

폴백이 돌면 `droppedFrames = 0` 이다. 기록은 「한 장도 안 버렸다」고
말하는데, 실제로 일어난 일은 「**안정된 장이 하나도 없었다**」다. 정반대
뜻으로 읽힌다.

더 나쁜 것은 **제 시험이 그 값을 못 박아 두었다**는 것이다:

```kotlin
// CalibrationSessionTest.다 버려지면 전부 쓰고 벌어짐을 남긴다
assertEquals(0, t.droppedFrames)
```

폴백이 언제 도는가: 장이 둘뿐이고 서로 멀면 중앙값이 그 가운데라 둘 다
허용 편차를 벗어난다(시험에 있는 40dB/90dB 가 그 경우다).

완화되는 부분: 벌어짐(`levelSpreadDb`)은 그대로 남아 `judgeQuality` 의
`maxRepeatSpreadDb` 에 걸린다. 그러니 **세션이 조용히 통과하지는
않는다.** 틀린 것은 기록의 문구이지 관문이 아니다.

제안: `StepResult` 에 `noStableFrames: Boolean` 을 더하고, 화면과
프로파일 기록에 「안정된 장이 없었습니다」로 적는다.

**묻고 싶은 것**: 이 제안이 맞는가, 아니면 폴백 자체를 없애고 실패로
돌려주는 쪽이 맞는가? 저는 폴백을 남기는 쪽이 낫다고 보았다 — 빈손으로
돌려주면 세션이 통째로 사라지고 사람은 까닭을 모른다. 다만 그 판단에
자신이 없다.

## 6. 판단이 갈릴 만한 자리 넷

### 6.1 기준을 앞뒤 **전력** 평균으로 쓰는 것이 맞는가

두 마이크를 같은 자리에 동시에 놓을 수 없어 `기준 → 대상 → 기준` 으로
잰다. 기준값은 앞뒤의 평균을 쓰는데, **전력 평균**으로 했다:

```kotlin
val refMean = DoubleArray(bandCount) {
    val a = 10.0.pow(before.meanDb[it] / 10.0)
    val b = 10.0.pow(after.meanDb[it] / 10.0)
    10.0 * log10((a + b) / 2.0)
}
```

**의심하는 이유**: §2 의 전력 평균은 「같은 양을 여러 번 잰 잡음 섞인
표본」을 합칠 때 옳다. 그런데 여기서 합치는 것은 **서로 다른 시각의 두
값**이고, 그 사이의 변화는 대개 **이득 변화**(스피커 볼륨·거리)다. 이득
변화는 곱셈이므로 중간값은 기하평균 — 즉 **dB 산술평균**이 맞는 것
아닌가?

크기를 재어 보았다(흐름 d dB 일 때 두 방식의 차이):

| 흐름(dB) | 전력평균(dB) | dB평균 | 차이 |
|---|---|---|---|
| 0.5 | 0.2572 | 0.2500 | **0.0072** |
| 1.0 | 0.5287 | 0.5000 | **0.0287** |
| 2.0 | 1.1141 | 1.0000 | 0.1141 |
| 3.0 | 1.7540 | 1.5000 | 0.2540 |
| 6.0 | 3.9629 | 3.0000 | 0.9629 |
| 12.0 | 9.2554 | 6.0000 | 3.2554 |

허용 흐름은 `QualityPolicy.maxReferenceDriftDb = 1.0` 이다. **관문을
통과하는 범위 안에서는 차이가 0.03dB 이하**라 실용적으로는 무시할 만하다.
그래서 고치지 않았다.

**묻고 싶은 것**: 그래도 개념적으로 dB 평균이 맞다면 바꾸는 게 좋은가?
아니면 두 값을 평균하는 것 자체를 그만두고 **흐름이 허용치를 넘지
않았을 때만 `before` 를 쓰는** 편이 더 정직한가?

### 6.2 샘플레이트가 다르면 **막는** 것이 맞는가

보정 곡선은 주파수 영역이고 `binCorrectionLinear(fftSize, sampleRate)` 가
칸 주파수를 그때그때 계산하므로, **곡선 자체는 샘플레이트에 매이지
않는다.** 그런데도 막았다:

- 지시서 6장이 sample rate 를 대조 항목에 명시했다.
- 안드로이드가 레이트마다 다른 내부 경로/리샘플러를 쓸 수 있고,
  나이퀴스트가 달라지면 잰 적 없는 대역이 생긴다(48k 에서 잰 보정을
  16k 에 걸면 8kHz 위는 아예 없다).

**묻고 싶은 것**: 막는 게 과한가? 48k↔44.1k 처럼 나이퀴스트가 둘 다
가청대역 밖인 경우까지 막으면, 사람이 까닭을 모른 채 보정을 못 쓰게 될
수 있다. 「낮아지는 쪽만 막고 비슷한 레이트는 경고」가 나은가?

### 6.3 배경을 안 쟀으면 **모든 대역을 못 믿는 것**으로 두는 것

```kotlin
noiseDb = noiseDb?.get(i) ?: target[i],   // → SNR 0
```

「모른다」를 「괜찮다」로 바꾸지 않으려는 것인데, 결과적으로 **배경
측정이 없는 세션은 절대 저장될 수 없다**(`usableRatio = 0` → Fail).

**묻고 싶은 것**: 의도대로 강한 것인가, 아니면 별도의 「배경 미측정」
상태를 두어 사람이 알고 넘어갈 수 있게 해야 하는가? 지시서 2장은 SNR
기록을 요구하지만 미측정 시의 처리는 말하지 않았다.

### 6.4 손으로 짠 해석기 — 기본값이 샐 길이 있는가

직렬화 라이브러리를 들이지 않고 `key=value` 글 파일로 했다(`CurveStore`
가 이미 그 결이다). `decodeProfile` 은 **객체를 먼저 만들고 나서**
`r.problem()` 을 확인한다:

```kotlin
val profile = MeasuredProfile(
    separation = separation ?: MicSeparation.Indistinguishable,
    quality = ProfileQuality(verdict = verdict ?: QualityVerdict.Fail, ...),
    ...
)
r.problem()?.let { return Result.failure(...) }
return Result.success(profile)
```

빠지거나 깨진 항목은 모두 `missing`/`malformed` 에 쌓이므로 그 기본값이
밖으로 나가지 않는다 — **지금은** 그렇다.

**묻고 싶은 것**: 이 패턴이 위험한가? 나중에 누가 항목을 더하면서
`strOrNull(...) ?: ""` 처럼 **등록하지 않는** 읽기를 쓰면 기본값이 조용히
샌다. 실제로 `env.deviceAddress` 가 그 꼴이다 — 파일에서 사라지면 빈
문자열이 되고, 그러면 `isRear` 가 false 가 되어 **후면 마이크의 케이스
경고가 조용히 없어진다.** 신원 자체는 `deviceKey` 안에 주소가 들어 있어
안전하지만, 경고 하나가 사라지는 것은 맞다. 구조를 바꾸는 게 나은가?

## 7. 그 밖에 봐 주셨으면 하는 것

1. **`judgeProfileApply` 가 「경로가 같은가」와 「사람이 켜 두었는가」를
   한 함수에서 답한다.** 둘을 나누면 부르는 쪽이 한쪽을 잊어 꺼 둔 보정이
   조용히 걸릴 수 있어 합쳤다. 이름도 그에 맞게 `judgeProfileApply` 로
   했다. 관심사가 섞였다고 보는가?
2. **`ProfileEnvironment.key()` 가 `CalibrationKey` 를 그대로 쓴다.**
   특히 「모노면 채널을 열쇠에 넣지 않는다」를 재구현하지 않았다. 그런데
   `CalibrationKey` 에는 `sampleRate` 가 없어 그것만 따로 비교한다 —
   한 곳에서 보고 한 곳에서 안 보는 이 비대칭이 나중에 물릴 자리인가?
3. **곡선 파일이 축을 한 번만 적는다.** `calibrateResponse` 를 읽어
   다섯 곡선이 모두 같은 `logAxis` 배열 위에 있음을 확인했고, 되읽을 때
   길이를 맞춰 본다. 제가 놓친 경로로 축이 갈라질 수 있는가?
4. **`MeasuredProfile.labelKo` 가 `MicSeparation.Separable` 일 때만
   물리 위치를 적는다**(지시서 1장). 그 밖에는 채널 번호나 입력 경로
   이름으로 부른다. 「후면」이라 잘못 적히면 그 이름을 믿고 케이스를
   벗기고 다시 재는 사람이 생긴다고 보았다 — 과한가?
5. **후면 마이크는 케이스 상태를 걸 때마다 되짚는다.** 안드로이드에
   케이스를 묻는 길이 없어 이것이 할 수 있는 전부다. 매번 알리는 것이
   경고 피로를 만드는가?

## 8. 확인하지 않은 것 (명시)

- **실제 음향 측정을 하지 않았다.** 지금까지 잰 것은 계산이지 소리가
  아니다. 사무실에 에어컨·선풍기·사람이 있어 부장님이 조용한 때로
  미루셨다(2026-09-23 SNR 9dB 로 관문이 막을 수준이었다).
- **아무것도 실제로 파일에 쓰이지 않는다.** `ProfileCodec` 은 글자로
  바꾸는 데까지고, DataStore/파일 바인딩이 없다.
- **화면에 붙지 않았다.** 교정 마법사(지시서 6장 마지막 줄)가 없고,
  `CalibrationCompareCard`(`c0f6504`)는 **아직 한 번도 기기 화면에서 본
  적이 없다.**
- 앞선 검토에서 열어 둔 것 그대로 남아 있다: `SignalPlayer.stopSink()` 의
  `releaseStarted` 가드가 어떤 단언에도 묶이지 않은 것, 알림의 정지 단추를
  실제로 눌러 본 적이 없는 것, TalkBack 을 실제로 들어 본 적이 없는 것.
