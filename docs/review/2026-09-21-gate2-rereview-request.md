대응 문서: [게이트 재검증](SELAH-RTA-gate-rereview.md) (판정: **승인 보류**)

## 먼저 인정할 것

**G01·G02 둘 다 제가 `CaptureController` 를 떼어 내며 만든 회귀입니다.**
그리고 제가 그때 함께 쓴 상태 전이 시험 15건이 **둘 다 놓쳤습니다.**
검증자가 그 까닭까지 정확히 짚었습니다 — 시험은 `withMeasurement()` 로
합친 값을 읽는데 `stop()` 은 바탕 상태를 읽고 있었고, 저는 그 차이를
시험하지 않았습니다.

「추출은 방향이 맞다」는 평가를 받은 변경이 **정상 종료 때마다 측정 결과를
지우고 있었습니다.** 승인 보류가 맞습니다.

## G01 (High) — 멈추면 SPL·Leq·MAX·Peak·RTA·진단이 사라졌다

**원인은 검증자가 적은 그대로입니다.** ViewModel 안에 있을 때 `state` 는
측정을 **합친** 흐름이었는데, Controller 로 옮기고 나서는 합치기 **전**
바탕 상태가 됐습니다. 같은 표현을 그대로 옮겨 놓고 뜻이 바뀐 것을 못
봤습니다.

**수정**: 합치는 자리를 하나로 만들었습니다.

```kotlin
/** 지금 **화면에 보이는** 값. 바탕 상태에 측정 결과를 합친 것이다. */
fun composed(): CaptureUiState = _state.value.withMeasurement(_measurement.value)
```

`stop()` 은 세션을 무효로 만들기 **전에** `composed()` 를 굳힙니다.
검증자가 권한 대로 기존 production 합성 함수를 그대로 씁니다.

**재발 방지**(검증자 권고: 「base state 와 composed state 의 역할을
이름·API 로 명확히 구분」): `state` 의 문서에 **「측정 결과는 여기 없다」**
를 못박고 [composed] 를 가리키게 했습니다. 공개 이름 `state` 자체는
바꾸지 않았습니다 — 검증자가 probe 를 그대로 다시 돌리는 데 방해가 되지
않게 하려는 것입니다. 이름을 바꾸는 편이 낫다고 보시면 그렇게 하겠습니다.

**회귀 시험** — 검증자가 적은 항목을 그대로 덮었습니다:

| 요구 | 시험 |
|---|---|
| 중지 전후 Current/Leq/MAX/Peak/RTA/diagnostics 비교 | 멈춰도 마지막 측정 결과가 남는다 |
| 보정 95dB(기본 120dB 와 다르게) | 멈춰도 Leq 와 Peak 와 보정이 남는다 |
| 오류 종료 | 오류로 끝나도 마지막 측정 결과가 남는다 |
| ON_STOP(분리 정책 멈추기) | 분리 정책이 멈추기여도 마지막 측정 결과가 남는다 |
| 반복 stop | 두 번 멈춰도 결과가 그대로다 |
| 새 start 초기화 | 새로 시작하면 지난 숫자를 비운다 |

## G02 (Medium) — 입구를 지난 옛 콜백이 새 세션의 값을 덮었다

**C01 과 같은 성질의 결함이고, 제가 이 실수를 세 번째로 했습니다**
(F02 → C01 → G02). 입구 검사는 **뒤에 오는** 콜백만 막습니다.

**수정**: 세대를 **넣을 때가 아니라 받아들일 때** 봅니다.

```kotlin
// 세션을 갈아 끼우는 것도 이 스레드라, 여기서는 경합할 상대가 없다.
post { if (active === session) _measurement.value = snapshot }
```

검증자가 「emit 직전 검사만 추가하면 검사와 대입 사이의 경합이 남으므로
직렬화 경계를 정해야 한다」고 한 지적을 받아들여, **검사와 대입을 같은
소유 스레드로 옮겼습니다.**

**대가**: 발행이 주 스레드를 한 번 거칩니다(66ms 마다 한 번, 초당 15회).
실기기에서 갱신이 끊기지 않는 것을 확인했습니다(아래).

## 거짓 주석도 고쳤다

검증자 지적: 「Controller 의 옛 주석 '입구에서 막히므로 경합하지 않음'은
이제도 틀린 설명」. **C01 을 낳은 바로 그 문장**이라 그대로 뒀으면 네 번째
실수를 불렀을 것입니다. 실제 근거(`FeedbackDetector` 의 자물쇠)로 고쳤습니다.

## 시험 방식에 대한 지적을 반영한 것

### post 를 실제로 붙들 수 있게 했다

> `post={ it() }` 는 실제 main queue 대기와 순서 역전을 만들지 못한다.
> 보류·배출 가능한 fake dispatcher/queue 를 추가해야 한다.

`HeldMain` 을 만들었습니다 — `held = true` 면 큐에 쌓고, `drain()` 이
들어온 순서대로 처리합니다. 그 위에서 **옛 세션의 스냅샷이 큐에 밀려
있는 동안 stop→start 가 일어나는** 순서를 만듭니다. 이 시험은 G02 를
되돌리면 실패합니다.

### 분리 이벤트를 **둘 다**, 중복까지 보낸다

> error→remove 와 remove→늦은 error 의 두 이벤트 전체, 중복 이벤트,
> post 큐 지연을 함께 넣어야 한 번만 전환된다는 성질을 검증할 수 있다.

두 순서 모두에 대해 **두 이벤트를 다 보내고 중복까지 보낸 뒤**,
`sources.size` 가 **정확히 1 만 늘어나는지** 단언합니다.

### 같은 값 재발행

검증자 답변 3번의 「같은 값 재발행」을 시험으로 넣었습니다 — DataStore 가
같은 설정을 다시 흘려도 엔진을 새로 만들지 않아야 Leq·MAX 가 살아남습니다.

## 44.1kHz 검증

ADR 로 갈음할 수 없다고 하신 항목입니다. **앱과 같은 배선**
(`RtaEngine` → `SpectrumSink` → `FeedbackDetector`)으로 쟀습니다 —
프레임 간격을 시험이 정한 상수로 두면 재려는 차이가 사라집니다.

| 잰 것 | 48kHz | 44.1kHz | 판단 |
|---|---|---|---|
| 순음 250·1k·4k·8kHz 검출 | 4/4 | 4/4 | 같다 |
| 「지속」까지 걸린 시간 | 1621ms | 1625ms | **차이 4ms** |
| 핑크 잡음 오탐 | 0 | 0 | 같다 |
| 비브라토(±70cent) 오탐 | 0 | 0 | 같다 |
| 분석 창 | 85.3ms | 92.9ms | — |
| 칸 폭 | 11.72Hz | 10.77Hz | **8.1% 좁다** |
| 5칸 문턱을 Hz 로 | 58.6Hz | 53.8Hz | 〃 |

**8.1% 는 검증서의 수치와 같습니다.** 시험이 그 값을 직접 단언합니다.

지연 허용치는 **재서 정했습니다**(실측 4ms). 이론상 상한은 첫 FFT 를
채우는 시간 차이(7.6ms) + 프레임 눈금 한 칸(46.4ms) ≈ 54ms 이고,
100ms 로 뒀습니다.

### 폭 문턱은 정밀하게 재지 못했다 — 있는 그대로 적는다

칸으로 적힌 `maxWidthBins` 가 8.1% 좁은 주파수를 가리키므로, **폭이 문턱
근처인 소리**에서 판정이 갈릴 수 있습니다. 그 경계를 재려 했는데 못
했습니다:

- **잡음 구동 공진**은 봉우리가 몇 Hz 씩 떠돌아 한 소리가 track 일곱 개로
  쪼개졌습니다(999·997·998·1001·1000·1002·1003Hz).
- **다중 순음으로 빚은 봉우리**도 간섭 무늬가 프레임마다 달라, 140Hz 폭의
  칸 수가 48kHz 에서 2칸, 44.1kHz 에서 4칸으로 나왔습니다 — 칸 폭 비
  (1.088)가 아니라 **우연**입니다.

원인은 물리입니다 — **85ms 창의 분해능이 11.7Hz 라, 그보다 넓은 구조는 한
창 안에서 잡음과 구별되지 않습니다.**

그래서 우연을 없애는 대신 **셌습니다.** 폭마다 씨앗 12개를 돌려 검출
횟수를 견줍니다:

| 폭 | 48kHz | 44.1kHz |
|---:|---:|---:|
| 2Hz | 11/12 | 12/12 |
| 5Hz | 6/12 | 9/12 |
| 10Hz | 3/12 | 3/12 |
| 20Hz | 0/12 | 1/12 |
| **합계** | **20** | **25** |

**걱정한 방향과 반대입니다.** 44.1kHz 가 덜 잡을 것이라는 가설이었는데
오히려 더 잡습니다 — 창이 92.9ms 로 길어 주파수가 더 또렷해지기
때문입니다. 시험은 그 방향으로 단언합니다(44.1kHz 가 체계적으로 덜 잡으면
실패).

## 아직 하지 못한 것

검증자가 미검증으로 유지한 목록 그대로입니다.

- **Controller 경계의 나머지 순서**(답변 3번) — A 보정 구독 → stop/B start
  → A 결과 지연 도착, 초기 설정 지연, 곡선 변경 중 stop, watcher 취소.
  이들은 **ViewModel 배선** 쪽이라 Controller 시험만으로는 덮이지 않습니다.
- **SignalPlayer** — 출력 오류·timeout·빠른 재시작. `AudioTrack` 없이 돌릴
  이음매가 아직 없습니다. C02 는 코드 경로만 맞춘 상태입니다.
- **USB 두 대 정책** — 권고안(명시 선택 → 현재 USB 유지 → 최초만 우선순위)
  미구현. 지금은 `chooseInput` 의 목록 순서가 정책을 대신합니다.
- **reroute 재시작 상한** — 무한 자동 재시작이 없다는 검증 없음.
- **폭 문턱의 실측 경계** — 위에 적은 물리적 한계 때문입니다. FFT 를 길게
  하면 잴 수 있지만, 그것은 명세의 반응 속도를 바꾸는 일이라 따로
  판단받아야 합니다.
- **현장 오탐률·놓침률·검출 지연**, **기준 소음계 비교**, **60분 부하·열·
  메모리**, **USB 실물**, **Compose/UI instrumentation**.

## 판단을 구하는 곳

1. **`state` 이름을 그대로 둔 것.** 재발 방지로는 문서·`composed()` 로
   충분한지, 아니면 `baseState` 로 바꾸는 편이 나은지.
2. **발행을 주 스레드로 넘긴 대가.** 초당 15회 post 가 늘었습니다.
   실기기에서 갱신이 끊기지 않는 것은 봤지만, 부하가 걸린 상태는 아직
   재지 않았습니다.
3. **44.1kHz 폭 문턱을 못 잰 것**을 미검증으로 남겨도 되는지, 아니면 다른
   재는 방법을 제안해 주실 수 있는지.
