# SELAH RTA M01·L01 후속 독립 검증

2026-09-21 · 검증 대상 `b8b4fa3..e7c55e5` (`e7c55e510dbda8b4c3037bbfdc6d01d18751c130`)

**판정: M01·L01 해결 확인. 이전 개발 게이트 승인을 유지한다. 이번 변경 범위에서 새 Critical/High 결함은 확인하지 못했다.**

이는 일반적인 샘플레이트 동등성, 현장 하울링 정확도 또는 출시 승인이 아니다. production 코드는 수정하지 않았다.

## 독립 실행 근거

- 대상 커밋을 별도 사본으로 추출하고 실제 DSP 및 관련 앱 소스와 JVM 시험을 컴파일했다. **252개 시험 전부 통과.**
- 기존 독립 probe는 `c.state`를 `c.baseState`로만 변경했다. 중지 전후 MeterReading·RTA·diagnostics 보존 및 이미 진입한 옛 콜백의 새 세션 snapshot 덮어쓰기 방지가 다시 통과했다. 중지 전후 Current 103.012611, MAX 103.013066, frames 102400이 유지됐다.
- 별도 임시 사본에서 `needsEngineRestart`를 항상 `true`로 바꿔 OrderingTest 10개를 실행했다. **L01 대상 시험만 실패**했다: MAX 기대 88.236663, 실제 56.195463. 큐가 돌기 전 snapshot만 검사하던 예전 약점을 새 시험이 검출한다.
- Kotlin 2.2.20 / JDK / JUnit 및 로컬 캐시 AndroidX AAR·Android API jar를 사용한 독립 JVM 실행이다. Gradle 전체 build/lint, 실제 AudioRecord, Compose 및 실기기 동작은 이번에 재실행하지 않았다. 구현자의 해당 성공 보고와 구분한다.
- 원본 working tree에 `audio/SignalPlayer.kt` 수정 및 새 `audio/SignalSink.kt`가 있었다. 이번 검증에는 포함하지 않았으며 건드리지 않았다. 검증 대상은 위 커밋으로 고정했다.

## 요청한 세 가지 판단

### 1. 동등성을 주장하지 않는 처리

적절하다. 다만 `Paired.equivalent()`는 정해 둔 허용 오차 안의 표본 일치도 검사다. 모집단에 대한 통계적 동등성 검정이나 오탐·놓침 성능 검증으로 해석하면 안 된다.

직접 실행한 결과:

| 합성 폭 | 48k 검출 | 44.1k 검출 | 둘 다 검출 | 48k만 / 44.1k만 | 로컬 판정기 |
|---|---:|---:|---:|---:|---|
| 2Hz | 11/12 | 12/12 | 11 | 0 / 1 | true |
| 5Hz | 6/12 | 9/12 | 6 | 0 / 3 | false |
| 10Hz | 3/12 | 3/12 | 1 | 2 / 2 | true |
| 20Hz | 0/12 | 1/12 | 0 | 0 / 1 | true |

특히 10Hz의 총 검출 수는 같지만 네 seed의 판정이 엇갈린다. `true`도 두 결과가 동일하다는 뜻이 아니다. ADR의 주장 철회로 M01은 종결할 수 있다. 2층 FFT 포함 원인 분리 시험과 3층 정답 레이블 시험은 계속 남는다. 3층만으로 2층의 원인 설명까지 완료했다고 처리하지 않는 것이 맞다.

### 2. 폭 문턱 70.0 / 64.5Hz

**로렌츠 power 배열, 동일한 bin 상대 위치, 0.5Hz 탐색 간격에서 마지막으로 통과한 입력 폭**이라는 해석으로 타당하다. 수치를 독립 재현했다.

| bin 상대 위치 | 48kHz 마지막 통과 B | 44.1kHz 마지막 통과 B |
|---|---:|---:|
| 0 | 70.0Hz | 64.5Hz |
| 0.25 | 63.5Hz | 58.5Hz |
| 0.5 | 56.0Hz | 51.5Hz |

정확한 연속 경계가 각각 70.0, 64.5Hz라는 뜻은 아니다. 중앙 정렬의 전이 구간은 각각 **70.0–70.5Hz, 64.5–65.0Hz** 사이로 좁힌 것이다. 0.5Hz 간격은 이번 약 8.1% 차이를 구분하는 데 충분하다.

`widthBins`는 half-power 이상인 연속 bin의 **개수**를 센다. 중앙에 맞춘 대칭 봉우리는 5개에서 7개로 바뀌므로, 문턱을 단순히 `5 × fs/N`으로 읽으면 안 된다. 바닥이 없는 이상적 중앙 로렌츠 봉우리에서는 ±3 bin이 half-power에 들어오는 B≈6×fs/N 부근에서 탈락한다. 이것이 약 70.3/64.6Hz와 관측값이 맞는 이유다.

엄밀히 B는 로렌츠 성분 자체의 FWHM이며, 시험처럼 양의 floor를 더하면 전체 power의 half-peak 폭과 미세한 차이가 있다. 현재 peak/floor=10000에서는 이 차이가 0.5Hz 탐색 간격보다 훨씬 작아 판정을 바꾸지 않는다.

이 시험은 **FFT를 통과한 같은 물리 신호의 성능 비교가 아니다.** fs별로 중심을 bin에 맞추므로 실제 중심 Hz도 약간 다르다. bin 기준 판정의 스케일 의존성을 분리하는 1층 시험으로 적절하다. 하드코딩한 `MAX_WIDTH_BINS=5`는 detector 기본값을 바꿀 때 함께 점검해야 한다.

### 3. 큐 합치기를 미룬 판단

**현재 개발 게이트에서 최적화를 유보하는 것은 가능하다. 다만 58개라는 수만으로 실기기 성능 안전성을 입증한 것은 아니다.**

HeldMain에서 0.5/2/5초에 해당하는 입력을 공급했을 때 pending 5/23/58개가 쌓였고, `drain()` 뒤 snapshot의 입력 프레임 차이는 3/1/2블록이었다. 이 결과는 큐를 모두 실행하면 마지막 발행 snapshot으로 도달한다는 것을 검증한다.

`drain()`은 가짜 큐를 동기 실행한다. **벽시계 회복 시간, 실제 Main Looper 지연, Compose 렌더링 비용, 메모리 및 장시간 부하는 측정하지 않는다.** 따라서 “한 발행 간격 안으로 수렴”은 *처리 후 데이터 시점의 차이*로 써야 하며, *회복에 걸리는 시간*이라고 쓰면 안 된다. StateFlow의 conflation이 이미 post된 runnable을 제거하지도 않는다.

실기기에서 enqueue-to-execute 지연·최대 pending·회복 소요 시간·메모리를 측정한 뒤 필요할 때 snapshot만 합치는 방향이 맞다. 경로 확인·종료 등 제어 이벤트의 순서와 전달은 유지해야 한다. 현재 결과만으로 새 결함을 선언하거나 production 큐를 변경할 근거는 없다.
