## 1. 이 구간이 한 일

네 개의 분석 화면이 **같은 FFT 한 장**에서 나오게 만들었다.

| 화면 | 보는 것 | 값의 출처 |
|---|---|---|
| RTA | 1/3옥타브 31밴드 | `BandAnalyzer.toBandPower` (밴드 합) |
| FR | 핑크 잡음 대역 균형 | `RoomResponse` (밴드 누적) |
| **Spectrum** | 연속 스펙트럼 | `SpectrumAxis.reduce` (칸 최대) |
| **Spectrogram** | 시간 × 주파수 × 색 | Spectrum 의 장을 쌓음 |

그 밖에 하울링 오탐 관문, MIN 지표, 교정기 부재 판정, 구간 이름 사용자
수정이 들어 있다.

## 2. 가장 먼저 봐 달라 — 보정이 걸리는 자리

### 2.1 주장

`RtaEngine.runFft()` 는 이제 **두 갈래로 같은 스펙트럼을 내보낸다.**

```kotlin
// 하울링 탐지 — 보정 전
val current = sinks
for (i in current.indices) current[i].onSpectrum(power)

if (spectrumEnabled) updateSpectrum()   // 화면 — 보정 후

// RTA 밴드 — 보정 후
bands.toBandPower(power, bandPower, binCorrection)
```

`updateSpectrum()` 이 `corrected[i] = power[i] * corr[i]` 로 한 번 더 건다.

**내 주장 두 가지:**

1. 화면 스펙트럼과 RTA 밴드는 **같은 계수로** 보정되므로 곡선을 갈아 끼우면
   **같은 dB 만큼** 움직인다.
2. 탐지기(`SpectrumSink`)가 받는 배열은 **한 칸도 바뀌지 않는다.**

`dsp/src/test/.../SpectrumCorrectionTest.kt` 가 둘을 함께 단언한다.

### 2.2 의심해 볼 곳

- **`corrected` 버퍼를 오디오 스레드가 단독으로 쓰는가.** `power` 와 같은
  수명이라고 보고 잠금을 두지 않았다. `spectrumEnabled` 를 주 스레드가
  끄는 순간 `updateSpectrum()` 이 돌고 있으면 어떻게 되는가 — 내 판단은
  「읽기만 하므로 안전하고, 그 장이 버려질 뿐」인데 틀렸는지 봐 달라.
- **`binCorrection` 을 두 번 읽는다.** 싱크 이후 `updateSpectrum()` 에서
  한 번, `toBandPower` 에서 또 한 번. 그 사이에 `setCurve` 가 갈아 끼우면
  **한 장 안에서 화면과 밴드가 다른 곡선으로 계산된다.** `setCurve` 가
  `latest = null` 과 `latestSpectrum = null` 을 함께 비우므로 화면에
  나가지는 않는다고 보았는데, 그 추론이 충분한가.
- **`latestSpectrum` 만 `@Volatile` 이고 `latest`(RTA)는 아니다.** 기존
  코드를 따라간 것인데, 지금 둘을 같은 스냅샷에 담고 있으므로 비대칭이
  문제인지 봐 달라 (`CaptureController` 의 `MeasurementSnapshot` 조립).

### 2.3 남아 있는 비대칭 — 알고 둔 것

**FR(`RoomResponse`)은 이 갈래에 없다.** `MeasurementTap` 을 거쳐 보정 전
스펙트럼을 받는다. 교정용이라 그래야 맞다고 보았는데, 화면에 「방 응답」으로
그려지는 값이므로 **RTA·Spectrum 과 다른 잣대일 수 있다.** 이것이 실제로
문제인지 판단해 달라 — 내가 놓쳤다면 여기다.

## 3. 두 번째 — 칸으로 줄이는 셈

`dsp/src/main/.../SpectrumDisplay.kt`

### 3.1 주장

2049개 FFT 칸을 **로그 등간격 256칸**으로 줄인다. 칸마다 **최대**를 집는다
(평균이 아니다). 까닭은 고역에서 한 화면 칸에 FFT 칸이 20개 넘게 들어가,
평균을 내면 좁은 봉우리가 10dB 넘게 묻히기 때문이다.

### 3.2 의심해 볼 곳

- **경계 셈은 내가 유도해 두었다 — 검산해 달라.** 칸 `c` 는
  `[lo_c, hi_c)` 를 덮고 `hi_c == lo_{c+1}` 이다. 담을 FFT 칸은
  `b·binHz ∈ [lo_c, hi_c)` 이므로 `b ≥ ceil(lo_c/binHz)` 이고
  `b ≤ ceil(hi_c/binHz) − 1` 이다(`hi_c/binHz` 가 정수든 아니든 같은 식이
  된다). 코드가 그대로다 — **이중으로 들어가는 칸도, 빠지는 칸도 없다**는
  것이 내 결론이다. 시험(`칸 값은 그 구간에서 가장 큰 FFT 칸이다`)은 한
  주파수에서만 확인하므로, 틀렸다면 시험이 못 잡는다.
- **제 것이 없는 칸이 「가장 가까운 칸」을 빌린다.** 저역(약 434Hz 아래)이
  모두 여기 해당한다 — 화면 칸이 FFT 칸(11.7Hz)보다 좁기 때문이다. 그래서
  저역이 계단으로 보인다. 이것을 고장이 아니라고 적어 두었는데(분해능이
  실제로 그렇다), **빌린 값이 옆 칸의 것이라 주파수가 어긋날 수 있는가**를
  봐 달라.

### 3.2.1 이 문서를 쓰다 찾아서 고친 것 — `topSpectrumPeak` 의 아래 끝

`from = (lowHz / binHz).toInt().coerceAtLeast(1)` 이었다. `lowHz=20`,
`binHz=11.72` 면 `20/11.72 = 1.706 → 1` 이라 **1번 칸(11.7Hz)부터 봤다.**
버림은 아래쪽 칸을 집으므로 요구한 범위 **밖**이 들어온다.

실해가 있다. 화면에 적히는 「가장 큰 봉우리」는 EQ 로 손댈 자리를 가리키는
숫자인데, 마이크의 직류 치우침과 초저역 울림이 그 칸에 몰려 있어 **들리지도
않는 주파수**가 그 자리를 차지할 수 있었다.

`ceil` 로 고쳤고 시험(`아래 끝 밖의 칸은 봉우리로 치지 않는다`)을 더했다.
**고치기 전 코드에서 그 시험이 실패하는 것을 먼저 확인했다** — 11.7Hz 를
집는 것을 재현했다.

`to` 쪽은 `(highHz / binHz).toInt()` 라 버림이 맞다(위쪽 밖을 배제한다).

### 3.3 절대 레벨 — 두 화면이 다르게 읽히는 것

실기기에서 1kHz 순음을 넣으면 **RTA 가 82dB, Spectrum 이 79dB** 로 나온다.
밴드는 안의 에너지를 다 더하고 화면 칸은 최대 하나만 집으니 당연하다고
보았는데, **3dB 는 설명 가능한 크기인가**를 계산으로 확인해 달라.
1000Hz 는 칸 85.33 이라 칸 사이에 놓인다(Hann 스캘럽 손실 + 주엽 분산).

## 4. 세 번째 — 스펙트로그램

`dsp/src/main/.../Spectrogram.kt`, `app/…/ui/components/SpectrogramChart.kt`

### 4.1 정한 것과 까닭

- **색 눈금을 고정한다**(10~90dB). 지나간 장을 그대로 들고 있는 그림이라
  범위가 움직이면 이미 칠한 색의 뜻이 바뀐다.
- **jet 의 검붉은 꼬리를 뺐다.** 그대로 두면 가장 큰 자리가 오히려
  어두워져, 가장 급한 것이 가장 덜 눈에 띈다. 시험이 101곳에서 「붉은
  기운이 자라기만 할 것」과 「레벨마다 색이 다를 것」을 확인한다.
- **값은 저장하지 않고 시각만 저장한다.** 레벨은 비트맵이 이미 들고 있다.

### 4.2 의심해 볼 곳

- **고정 눈금이 옳은 선택인가.** 교정을 마친 기기에서 만재 음압이 다르면
  그림이 통째로 포화하거나 통째로 파랗게 될 수 있다. 자동 범위의 문제를
  피하려다 더 나쁜 것을 고른 것인지 판단해 달라.
- **`SpectrogramState.push` 가 주 스레드에서만 불리는가.** `LaunchedEffect`
  안에서 부르므로 그렇다고 보았는데, 비트맵 쓰기와 그리기가 같은 프레임에
  겹칠 수 있는지 봐 달라.
- **시간축이 정직한가.** 장이 고르게 들어오지 않으므로 시각을 함께
  저장하고 `spanMs` 로 눈금을 적는다. 그런데 **그림은 칸을 고르게
  늘어놓는다** — 장이 띄엄띄엄 들어온 구간은 실제보다 넓게 그려진다.
  「−19초」 눈금이 그 자리의 실제 시각과 어긋날 수 있다. 얼마나 나쁜가?

### 4.3 실기기에서 잡은 것 — 재발 방지 장치가 없다

값은 쌓이는데 **화면이 빈 채로 있었다.** `SpectrogramState` 가 전부 `val`
이라 Compose 가 「안정」으로 판단해 차트 호출을 통째로 건너뛴 것이다.
`frames`·`head`·`spanMs` 를 `mutableIntStateOf`/`mutableLongStateOf` 로
바꿔 고쳤다.

**이 부류를 막을 시험이 없다.** Compose 안정성 추론은 단위 시험으로 잡기
어렵다. 같은 함정이 `SpectrumView`·`RtaView`(둘 다 `equals` 를 동일성으로
재정의)에 있는지, 그리고 막을 방법이 있는지 의견을 달라.

## 5. 네 번째 — 하울링 오탐 관문

`dsp/src/main/.../FeedbackDetector.kt` 의 `toCandidate()`

```kotlin
val stable = drift <= maxDriftCents && continuity >= minContinuity
val state = when {
    !stable -> FeedbackState.None
    duration >= needed -> FeedbackState.Persistent
    duration >= suspectMs -> FeedbackState.Suspect
    else -> FeedbackState.None
}
```

예전에는 `Suspect` 에 관문이 없어 말소리·악기가 계속 후보로 떴다.

**대조군을 함께 두었다.** 「비브라토 노랫소리는 지속까지 가지 않는다」
옆에 **같은 세기·같은 길이의 440Hz 고정음은 반드시 잡힌다**를 두었다 —
관문을 조이기만 하면 「아무것도 안 잡아서」 통과할 수 있기 때문이다.

**봐 달라**: 관문이 **실제 하울링을 놓칠** 조건이 있는가. 특히 올라오는
초기에 주파수가 조금 움직이는 경우(`maxDriftCents`).

**실기기 사실 하나**: PC 스피커로 1kHz 순음을 내보내면 `Persistent` 로
잡힌다. 정상 동작이라고 본다 — 고정 순음은 정의상 하울링과 구별되지
않는다. 다른 의견이 있으면 달라.

## 8. 실기기 확인 (SM-S918N + UMC404HD + 측정 마이크)

PC 스피커로 1k → 2k → 4k 를 6초씩 내보냈다.

- RTA: 1k 밴드 82dB, 후보 표식 `1.00kHz`
- Spectrum: 최고 봉우리 `1.00kHz 79dB`
- Spectrogram: 세 줄이 로그 축 제자리에, 시간 순서대로

**이것은 「어긋나지 않는다」를 보인 것이지 「맞다」를 보인 것이 아니다.**
절대 레벨은 미보정(짐작한 만재 음압 120dB)이라 확인할 수 없었다.
