## 2. SRL-01~03 — 셋 다 제 손으로 재현했습니다

**패치를 그대로 적용하지 않았습니다.** 같은 진단을 확인한 뒤 이 저장소의
구조·문체로 다시 썼습니다. 보내 주신 파일은 `docs/review/` 에 그대로
두었습니다.

### 2-1. SRL-02 — 고역 대역이 엉뚱한 주파수를 냈습니다

지적이 맞습니다. 제 측정이 회신 숫자와 그대로 맞았습니다:

| 화면이 적는 대역 | 고치기 전 봉우리 | 적힌 자리 이득 | 고친 뒤 |
|---:|---:|---:|---:|
| 8,000 Hz | 7,382 Hz | −2.25 dB | −0.002 dB |
| 16,000 Hz | **12,342 Hz** | **−19.6 dB** | **−0.059 dB** |
| 20,000 Hz | **13,691 Hz** | **−34.7 dB** | **−0.366 dB** |

**제가 알고도 못 고친 자리입니다.** 주석에 「쌍일차 변환이 주파수 축을
휘게 만들어, 그 근처에서는 중심이 눈에 띄게 아래로 밀린다」고 적어 놓고
`fs·0.4` 로 **자르기만** 했습니다. 자르는 것은 휘는 것을 되돌리지
못합니다 — 틀린 자리를 조금 덜 틀리게 옮길 뿐입니다.

보내 주신 양 끝 사전 보정을 받았습니다. `Biquad.fromAnalog` 가 사전 보정을
하지 않는 것을 먼저 확인했습니다(이중 보정이 되지 않습니다).

> 되묻습니다: 맨 위 20kHz 대역의 위 끝(22,449Hz)을 `fs·0.4995` 로
> 묶었습니다. 48kHz 에서는 걸리지 않지만, **44.1kHz 를 쓰게 되면 그 한
> 칸만 폭이 좁아집니다**(중심은 맞습니다). 거절하는 편이 낫습니까?
> 소리를 내는 길에서 던지는 것이 더 나쁘다고 보아 묶는 쪽을 골랐습니다.

### 2-2. SRL-01 — 감쇠가 엉뚱한 각에서 시작했습니다

재현했습니다. 진폭 0.4 · 1kHz 에서 감쇠 첫 표본이 기대 −0.346 인데 실제
0 이었습니다.

**이 결함의 모양을 저는 이미 보고 있었습니다.** 램프를 넣을 때 게인을
`sample` 에 묶은 까닭이 바로 이것이었는데(커밋 메시지에 「따로 세면 램프가
앞서간다」고 적었습니다), **바로 옆에 있는 `phase` 는 「먼저 있던 것」으로
넘겼고 8회차 요청서에 적지도 않았습니다.** 적었더라면 검토자가 찾기 전에
갈렸을 자리입니다.

프레임 경계마다의 각을 적어 두고 나간 만큼 되감습니다(재생당
`DoubleArray(1025)` 하나). **하나의 Hz 로 거꾸로 셈하지 않은 까닭**도
보내 주신 그대로입니다 — 덩어리를 그리는 도중에 슬라이더가 움직이면
프레임마다 Hz 가 다릅니다. `fadeFrom` 도 같은 까닭으로 나간 만큼만
낮춥니다.

### 2-3. SRL-03 — 멎은 까닭이 다른 화면에서 안 보였습니다

지적이 맞습니다. 까닭을 그리는 곳이 `ToolsScreen` 하나뿐이라, RTA 에서는
**사람이 멈춘 것과 장치가 죽은 것이 똑같아 보였습니다.**

Snackbar 대신 **미니 바 위에 한 줄**로 두었습니다 — 까닭은 미니 바가
사라지는 것과 함께 오므로 눈이 가던 자리에 남는 편이 낫다고 보았습니다.
이어폰이 빠져 멈춘 경우도 이 길로 옵니다.

## 3. 3장의 120ms 지적 — 우려보다 나빴습니다

**짐작하지 않고 실기기에서 쟀습니다.** ViewModel 을 주 스레드에서 몰아,
고치기 전후를 **같은 자리에서** 쟀습니다(SM-S918N).

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 대역 슬라이더 한 번 | **143.8ms** | 1.5ms |
| 가장 오래 걸린 한 번 | **154.3ms** | 7.1ms |
| 스무 번(손가락 한 번) 합 | **2,359ms** | 41.5ms |
| `stopSignal` | **128.2ms** | 0.8ms |

한 장이 16.7ms 이니 슬라이더 한 번에 **아홉 장**이 빠졌습니다.
세기·좌우·대역 주파수 슬라이더가 모두 같은 길을 탑니다.

**감쇠를 기다리는 120ms 는 그 중 일부일 뿐이었습니다.** 더 큰 몫은
`AudioTrack` 을 새로 여는 일이었고, 램프를 되돌리는 것으로는 안 풀립니다.

권하신 대로 **직렬 제어 실행자**(`SerialCommands`)로 옮겼습니다.

- **한 줄인 까닭**: 명령마다 스레드를 띄우면 `start` 와 `stop` 이 서로를
  앞질러 단일 제어 계약이 깨집니다.
- **낡은 것을 버립니다**: 줄에 세우기만 하면 화면은 안 멎지만 **소리가
  손가락을 뒤쫓습니다** — 손을 뗀 뒤로도 2.4초를 더 돕니다. 버려진 `stop`
  도 안전합니다: 뒤따르는 `start` 가 제 안에서 먼저 멈춥니다.
- **늦게 끝나는 writer 를 강제 해제하지 않는 계약은 그대로입니다.**
  `SignalPlayer` 는 손대지 않았습니다.
- **`retune` 은 주 스레드에 남겼습니다.** `start()` 의 느린 부분이 자물쇠
  밖이라 순음 슬라이더의 부드러움이 그대로 지켜집니다. (이 판단을 봐
  주십시오 — 자물쇠를 짧게 잡는다는 것이 근거입니다.)
- **`onCleared` 만은 기다립니다.** 돌아가고 나면 아무도 안 남습니다.

## 4. 확인한 것

### 4-1. 변이 (시험이 실제로 막는지)

| 변이 | 실패한 것 |
|---|---|
| 감쇠에서 각을 되감지 않음 | `FadeStartPhaseTest` **3개만**(기존 16개는 그대로 통과) |
| 아래 영역이 까닭을 안 그림 | `SignalMiniBarTest` 의 **새 3개만** |
| 명령을 부른 스레드에서 그대로 돌림 | 지연 시험 **2개**(181.8ms·174.6ms) |

**세 번째 변이에서 `멈추기도_주_스레드를_안_잡는다` 는 못 잡았습니다** —
멈출 때 감쇠를 기다리는 시간이 그때그때 달라 운 좋은 판에서는 한도 안에
듭니다. **약한 그물이라고 KDoc 에 적었습니다.**

SRL-02 는 변이 대신 **고치기 전 측정 자체가 반례**입니다(31개 대역을
순음으로 다시 잽니다).

### 4-2. 시험

- JVM 전체 통과(앱 + DSP).
- 실기기 계측 **28개** 통과(SM-S918N, 무선 디버깅).
- 새 시험: `BandCenterAccuracyTest`(5) · `FadeStartPhaseTest`(3) ·
  `SerialCommandsTest`(4) · `SignalCommandLatencyTest`(3) ·
  `SignalMiniBarTest` 에 4개 추가.

### 4-3. 시험을 쓰다 알게 된 것 둘

- **1kHz 는 48kHz 에서 한 주기가 딱 48 표본**이라, 재는 자리가 하필
  영교차에 떨어져 **시험이 조용히 통과했습니다**(128칸 경우). 997Hz 로
  바꾸니 잡힙니다.
- **계측 시험 이름에 공백을 못 씁니다**(DEX 040 미만). 그리고 앱 APK 를
  다시 안 만든 채 「통과」를 찍은 일이 **두 번** 있었습니다.

## 5. 아직 검토받지 않은 변경

**지시서 §5 인터럽트**(`aec7a59`, PR #70)가 8회차 고정본 뒤에 들어갔고
어느 회차에서도 검토받지 않았습니다. 요약하면:

- 이어폰·USB 가 빠지면(`ACTION_AUDIO_BECOMING_NOISY`) 신호를 멈춥니다.
  안 막으면 PA 에 물린 핑크 노이즈가 **폰 스피커로 터져 나옵니다.**
- 오디오 포커스를 잃으면 멈추고, **되찾아도 저절로 다시 틀지 않습니다.**
- **`CAN_DUCK` 도 멈춥니다**(`setWillPauseWhenDucked(true)`). 줄여서 계속
  내보내면 재는 사람이 모르는 채로 크기가 달라지고, 그 신호로 잰 방의
  응답을 참이라고 읽습니다 — **조용히 틀리는 것이 끊기는 것보다 나쁘다**고
  보았습니다. 이 판단을 특히 봐 주십시오.
- 포커스를 못 얻어도 막지 않습니다.
- 실기기에서 재생 중/멈춘 뒤로 갈라 확인했습니다 — AudioTrack · 방송
  수신기(`#receivers=1`) · 포커스 스택(`PAUSES_ON_DUCKABLE_LOSS`) 셋이
  함께 붙고 함께 떨어집니다.
- **이어폰을 실제로 뽑아 보지는 못했습니다** — 그 방송은 시스템만 보낼 수
  있어 셸에서도 시험에서도 일으킬 수 없습니다.

## 6. 아홉 회차의 줄기 (누적)

### 6-1. 제 판단이 틀렸다고 확인된 것

1. **「틀리게 맞추면 화면이 곧바로 이상해진다」**(UIS-02)
2. **「지연만 보면 된다」**(UISR-03)
3. **「잘렸으면 3초 기다리면 된다」**(UISRF-01)
4. **「유한 창이라 창 밖은 0」**(UISRFF-01)
5. **「`doFirst` 로 막으면 된다」**(UISRFFF)
6. **「시험이 있으니 지켜진다」** — **여섯 번**:
   - UIS-07 매니페스트 문자열 검색
   - 정책 링크 소스 검색
   - 「둘이 함께 네 변이를 막는다」
   - UIS6-03(진짜 화면을 안 엶)
   - 8회차 §5(화면은 열되 안드로이드 경계를 안 넘음)
   - **이번 SRL-02**(대역 맞추기를 **숫자만** 견줌 — 제가 방금 쓴 시험에서)
7. **「즉시 관측이 곧 계약이다」**(UIS7-01)
8. **「먼저 있던 결함이니 지금 일이 아니다」**(SRL-01) — 같은 자리의 게인은
   고치면서 위상은 넘겼고, **요청서에 적지도 않았습니다.**

**6 이 여섯 번입니다.** 이번에 새로 드러난 모양은 **8** 입니다 — 알아차린
것을 적어 두지 않으면 못 알아차린 것과 같습니다.

### 6-2. 실기기 관측 (구현자 보고)

| 무엇 | 회차 | 결과 |
|---|---|---|
| 보정 대화상자 · 계기 바 · 거짓 지연 경고 | 2 | 확인 |
| USB 분리 → 경로 변경 감시 | 3 | 확인 |
| 손뼉 두 번 → 창 초기화·복귀(19.7 dB) | 5 | 확인 |
| 정확 창 부하 A/B · 고른 기기 없을 때 알림 | 6 | 확인 |
| 계측 시험 + 변이 | 7 | 확인 |
| 신호 틀고 RTA 이동 → 소리 유지 → 미니 바 정지 | 8 | 확인 |
| 인터럽트: 수신기·포커스가 함께 붙고 떨어짐 | 8.5 | 확인 |
| **주 스레드 지연 앞뒤 측정** | **이번** | **확인** |

## 7. 확인하지 못한 것

- **실제 PA 에서 귀로** 「딱」이 사라졌는지. 파형이 이어진 것과 들리는 것은
  다른 말입니다.
- **손가락을 끄는 동안 눈에 부드러운지.** 잰 것은 주 스레드가 잡히는
  시간이지 프레임이 실제로 그려진 수가 아닙니다.
- **이어폰을 실제로 뽑는 것.**
- 44.1kHz 출력에서 맨 위 대역.
- 실제 업로드 키·Play Console, 교정기 94/114 dB, 2시간 부하.
- 지시서 §7(저장·L/R 겹쳐 보기) — 저장 자리 자체가 없어 별도 명세로
  넘겼습니다.

## 8. 가장 보고 싶은 것

1. **`retune` 을 주 스레드에 남긴 판단.** `start()` 가 자물쇠를 짧게만
   잡는다는 것이 근거인데, 그 근거가 앞으로도 버팁니까?
2. **낡은 명령을 버리는 규칙에 구멍이 있는지.** 「뒤따르는 `start` 가 제
   안에서 먼저 멈춘다」에 기대고 있습니다.
3. **5장의 `CAN_DUCK` 판단.** 줄여서 계속 내보내는 것보다 끊는 것이
   낫다고 보았는데, 재는 도구로서 맞습니까?
4. **6-1 의 8번이 또 있을 자리.** 제가 알아차리고도 안 적은 것이 더
   있는지 — 이번엔 그것이 Medium 이 되었습니다.
