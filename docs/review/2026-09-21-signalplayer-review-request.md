## 1. SignalPlayer — 결함 두 개를 재현하고 고쳤다

### 왜 지금까지 못 했나

`AudioTrack` 에 직접 매여 있어 **에뮬레이터 없이는 한 줄도 돌릴 수
없었습니다.** 캡처 쪽에서 같은 이유로 `AudioSource` 를 떼어 냈고 그
덕분에 F02·C01·G02 를 잡았는데, 여기만 남겨 뒀습니다.

`SignalSink` 로 떼어 내고 가짜를 끼워 **어느 `write` 에서 멈출지·언제
풀릴지를 시험이 정하게** 했습니다.

### 재현된 결함 (고치기 전 실패 확인)

**S01 — 멈추기가 시간 초과되면 놓은 자원을 계속 쓴다.**

`stop()` 은 내보내는 스레드를 500ms 만 기다립니다. 그 스레드가 아직
`write` 안에 있는데 주 스레드가 `release()` 를 부르면, **놓은 것을 계속
쓰는 셈**입니다 — 실제 `AudioTrack` 이면 정의되지 않은 동작입니다.

**S02 — 살아남은 옛 스레드가 새 재생을 보고 되살아난다. 소리가 둘 난다.**

`running` 이 재생마다가 아니라 **하나뿐**이었습니다. 시간 초과로 살아남은
옛 스레드가 `write` 에서 깨어나 보니 새 재생이 세운 `running = true` 가
있고, **제 출력으로 계속 씁니다.** 두 소리가 동시에 납니다.

둘 다 **「이미 들어와 있는 것」과 「새로 시작한 것」이 같은 공용 상태를
만지는** 문제입니다. 제가 이 실수를 캡처 쪽에서 세 번 했습니다
(F02 → C01 → G02). 네 번째입니다.

### 수정 — 공용 상태를 없앴다

```kotlin
private class Playback(val id: Long, val sink: SignalSink) {
    /** 이 재생이 계속 써도 되는가. **재생마다 따로다.** */
    val running = AtomicBoolean(true)
    private val released = AtomicBoolean(false)
    /** 두 번 놓지 않는다. 실제로 놓은 쪽만 true 를 받는다. */
    fun releaseOnce(): Boolean =
        released.compareAndSet(false, true).also { if (it) sink.release() }
}
```

- 플래그도 출력도 **재생이 소유**합니다.
- 자원은 **마지막에 손을 떼는 쪽**이 `releaseOnce()` 로 한 번만 놓습니다.
- `stop()` 의 기다림이 시간 초과되면 **놓지 않고 물러납니다** — 아직
  `write` 안에 있는 스레드가 깨어날 때 제 손으로 놓습니다.
- 상태를 갈아 끼우는 자리는 자물쇠로 직렬화하되, **`join` 을 자물쇠 안에서
  하지 않습니다**(끝내려면 그 자물쇠가 필요하므로 서로 막힙니다).
- 늦게 끝나는 쪽은 `current === pb` 로 **자기 세대일 때만** 알립니다.

**남는 것**: 장치가 아주 죽어 `write` 가 영영 안 돌아오면 그 출력 하나가
남습니다. **놓은 것을 쓰는 것보다 낫다**고 판단했습니다 — 판단을 구합니다.

## 2. 폭 문턱 — 제가 틀렸고, 지적이 맞습니다

> `widthBins` 는 half-power 이상인 연속 bin 의 **개수**를 센다. 중앙에 맞춘
> 대칭 봉우리는 5개에서 7개로 바뀌므로, 문턱을 단순히 `5 × fs/N` 으로
> 읽으면 안 된다.

**요청서에 「5칸 문턱 = 58.6Hz」라고 적어 놓고, 같은 문서의 실측 경계가
70.0Hz 인 것을 그대로 뒀습니다.** 둘이 안 맞는데 보지 못했습니다.

실제로 재 보니 대칭 봉우리에서 나오는 칸 수는 **1·3·5·7** 뿐입니다 —
**6은 나오지 않습니다.** 그래서 떨어지는 자리는 ±3칸이 드는 폭,
곧 `6 × 칸폭` 직전입니다:

| | 5 × 칸폭 | **6 × 칸폭** | **실측 경계** |
|---|---:|---:|---:|
| 48kHz | 58.6Hz | 70.3Hz | **70.0Hz** |
| 44.1kHz | 53.8Hz | 64.6Hz | **64.5Hz** |

고친 것:

- 시험이 이 관계를 **직접 단언**합니다(`대칭 봉우리의 칸 수는 5 다음이 7 이다`).
- `MAX_WIDTH_BINS` 하드코딩을 **`FeedbackDetector.DEFAULT_MAX_WIDTH_BINS`
  에서 가져옵니다** — 숫자를 베껴 두면 detector 기본값이 바뀌어도 옛 값을
  계속 시험합니다(지적하신 그대로입니다).
- ADR 과 시험 문서의 틀린 수치를 고치고, **왜 틀렸는지**를 남겼습니다.
- ADR 에 「각 fs 에서 봉우리를 칸에 맞추므로 실제 중심 Hz 도 조금 다르다 —
  같은 물리 신호의 성능 비교가 아니다」도 적었습니다.

## 3. 그 밖의 권고

**Leq 보존을 견주는 단언으로.** null 검사만으로는 리셋을 못 잡는다는
지적을 받아, **조용한 소리만 넣은 새 측정과 견줍니다.** 엔진이 새로
만들어졌다면 두 값이 같아집니다. mutation(`needsEngineRestart = true`)에서
**MAX 단언을 꺼도 이 단언 혼자 실패하는 것**을 확인했습니다.

**큐 시험의 문구.** 「한 발행 간격 안으로 수렴」이 *회복 시간*으로 읽히지
않도록, **재는 것이 「데이터 시점」이지 「시간」이 아님**을 시험 문서에
못박았습니다. `StateFlow` 의 conflation 이 **이미 post 된 runnable 을
없애지 않는다**는 점도 적었습니다 — 58개는 실제로 58번 돕니다.

## 판단을 구하는 곳

1. **시간 초과 때 놓지 않는 선택.** 영영 안 깨어나는 스레드가 있으면
   출력 하나가 남습니다. 「놓은 것을 쓰는 것」보다 낫다고 봤는데,
   상한을 두고 강제로 놓는 편이 나은지.
2. **`isReturnDefaultValues = true` 를 전역으로 켠 것.** 다른 시험이
   삼키게 되는 것이 있는지.
3. **폭 문턱의 남은 해석.** `6 × 칸폭` 직전이라는 설명이 칸 사이로
   비켜난 경우(0.25·0.5칸에서 63.5·56.0Hz)까지 옳게 덮는지.
