## RC02 — 제가 절반만 고쳤습니다

지적이 정확합니다. **수동 `stop()` 경로만** 손대고 자동 오류 종료를
빠뜨렸습니다. `endWithError()` 는 `current` 를 먼저 지우므로 그 재생이
**목록에도 없고 현재도 아니어서**, 놓기에 실패해도 아무 데도 세어지지
않았습니다.

| 경로 | 해제 | 시작 | failedReleaseCount | pendingCount |
|---|---|---:|---:|---:|
| 수동 stop | false | 2 | 2 | 2 |
| **자동 오류 종료** | false | **4** | **0** | **0** |

(상한 2)

### 수정 — 규칙을 한 곳으로 모았습니다

```kotlin
/**
 * 이 재생을 **끝낸다.** 등록·해제·정리 규칙을 여기 한 곳에 모은다.
 *
 * **놓기를 시도하기 전에 먼저 등록한다.** 그래야 놓기가 늦어지는
 * 동안에도 상한에 세어진다. 성공했을 때만 목록에서 뺀다.
 */
private fun settle(pb: Playback) {
    stuck.addIfPending(pb) { it.isSlotFree }
    pb.releaseOnce()
    if (pb.isSlotFree) stuck.remove(pb)
}
```

**세 종료 진입점이 모두 이것을 씁니다** — 내보내는 고리의 정상 종료,
`endWithError()`, `stop()` 에서 스레드가 이미 끝난 경우. `stop()` 이
시간 초과된 경우만 등록하고 물러나며, 깨어난 스레드가 `settle()` 로
마무리합니다.

「실패가 반환된 뒤에만 등록하지 말고 **release 진행 중도 추적**해야
한다」는 지적이 이 설계의 핵심입니다 — 등록이 해제보다 **먼저**입니다.

### 회귀 시험 — 적어 주신 목록 그대로

| 요구 | 시험 | 결과 |
|---|---|---|

| 예외로 실패해도 같음 | `…예외로 실패해도 상한에 센다` | 〃 |

## 답변에 대해

1. **`PendingList` 술어 계약** — 지금 범위에서 충분하다는 판단을
   받아들입니다. 새 추상화는 넣지 않았습니다. 계약(블로킹 금지·다른
   자물쇠 금지·재진입 금지)은 주석에 적어 두었습니다.
2. **실패가 슬롯을 막는 정책** — 유지합니다. 카운터만 되돌리는 버튼이나
   자동 재시작은 넣지 않았습니다.
3. **`release()` 계약** — 「예상되는 실패는 `false`, 예기치 않은 예외는
   방어적으로 실패로 정규화」라고 문서를 다듬겠습니다. 두 번째 `release`
   가 `track=null` 이라 `true` 를 돌려줄 수 있다는 점은 **`releaseStarted`
   의 CAS 가 한 번만 시도하고 최초 결과를 보존**하는 것으로 지켜집니다.
   그 성질을 보는 시험도 있습니다(`같은 출력에 놓기를 되풀이하지 않는다`).

1. **`settle()` 을 세 진입점에 둔 것**으로 종료 추적이 한 규칙이 됐는지.

   봤는데, 다른 관점이 있는지.
