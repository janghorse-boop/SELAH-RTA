## 요구하신 M32 반례를 그대로 만들었습니다

> 「500ms 행 중간의 offset 변경을 위 수치로 만들고 writer→reader 까지
> 통과한 최대값이 90인지 단언한다」

```
0번 행 = 프레임 0..23999
  0     .. 11999  epoch 0  offset=100  raw -20 → 80dB
  12000 .. 23999  epoch 1  offset=120  raw -30 → 90dB   ← 실제 최대
```

raw 최대(−20)만 남기고 epoch 하나를 고르면 **80 또는 100** 이 나옵니다.
그래서 **극값을 보정한 값으로 견주고, 이긴 쪽의 raw 와 그 epochId 를
함께 적습니다.** 왕복 뒤 `calibratedMax` 가 **정확히 90.0** 입니다.

### 시험이 그 결함을 실제로 붙드는지 확인했습니다

비교를 **보정 전 raw 로** 되돌려 보았습니다:

```kotlin
val mCal = s.maxRaw   // 원래: epochs.calibrated(s.maxRaw, epochId)
```

→ **11건 중 2건 실패**(90dB 반례, 세 epoch 반례). 고치면 다시 통과합니다.
시험 이름이 단언보다 앞서 나가지 않는지 이 방법으로 봤습니다.

## 시험 11건

| 이름 | 무엇을 단언하는가 |
|---|---|
| 한 행 안에서 보정이 바뀌어도 최대가 90dB | 위 반례. 왕복 뒤 **90.0** |
| current 와 max 가 서로 다른 epoch 일 수 있다 | 값마다 epoch 를 따로 지님 |
| 한 행에 epoch 이 셋이어도 가장 큰 것이 이긴다 | 2개가 아닌 경우 |
| 마지막 부분 행도 나온다 | 500ms 를 못 채운 꼬리 행 |
| 측정이 없던 구간은 missing 행으로 채운다 | 행 번호 = 위치/500ms 유지 |
| 미보정 구간의 값에는 그 사실이 붙는다 | `isReferenceOnly` 가 값까지 따라감 |
| 클리핑은 그 행의 것만 표시한다 | 세션 누적이 아님 |
| 행 경계를 걸친 조각은 거절한다 | 쪼개기 계약 |
| 모르는 판이면 열지 않는다 | 버전 바이트로 열지 않음(S03) |
| 끊긴 꼬리는 버린다 | 반 토막 행을 없는 것으로 |
| epoch 가 상한을 넘으면 알린다 | 256 초과 시 `add` 가 false |

## 스스로 짚은 빈 곳 — 여기를 먼저 봐 주십시오

**1. 아무도 아직 `RowSample` 을 만들지 않습니다.** `CaptureController` 에
붙이지 않았습니다. 그래서 「행 경계·epoch 경계에서 미리 쪼갠다」는 계약은
**거절만 하고 지키는 쪽이 없습니다.** 쪼개는 코드는 이 단계에 없습니다.

**2. 스레드 계약을 적기만 했고 강제하지 않습니다.** 둘 다 잠금이 없는
한 스레드 전용입니다. 이 저장소에서 거듭 틀렸던 자리가
「이미 들어와 있는 것」과 「새로 시작한 것」이 같은 공용 상태를 만지는
곳이었으므로 주석으로 박아 두었습니다만, **컴파일러가 막아 주지는
않습니다.** 3단계(SPSC 링)에서 캡처 스레드와 기록 스레드가 나뉘면
여기가 위험해집니다. 건네는 지점을 어디에 두어야 하는지 봐 주십시오.

**3. `missing` 행의 epochId 가 −1 입니다.** `calibratedMax/Peak/Current`
는 missing 행에 `null` 을 주어 막습니다만, 부르는 쪽이 `epochs[row.maxEpoch]`
를 직접 부르면 **`error("모르는 epoch: -1")`** 로 터집니다. 센티넬을 쓰는
대신 표현을 바꿔야 하는지(예: nullable) 의견을 구합니다.

**4. `MAX_EPOCHS = 256` 은 재지 않고 고른 값입니다.** 예배 중 설정을
256번 바꾸는 일은 없다고 보지만, 근거를 잰 적이 없습니다. 코드 주석에도
그렇게 적어 두었습니다.

**5. 파일 동기화·체크포인트가 없습니다.** `flush()` 뿐이고 `fsync` 도,
이중 슬롯 체크포인트도 아직입니다(4단계 예정). 지금 끊기면 **꼬리 행만**
잃는지(reader 가 반 토막을 버리므로), 아니면 더 잃을 수 있는지 봐 주십시오.

**6. `rowMillis` 를 머리에 적지만 reader 가 검사하지 않습니다.** 판·행
길이·바이트순서·밴드수는 막는데 `rowMillis` 는 읽어서 넘깁니다. 500 이
아닌 파일을 500 으로 가정한 화면이 조용히 틀릴 수 있습니다.

## 묻고 싶은 것

1. 극값을 **보정값으로 견주고 raw+epoch 를 적는** 방식이 M32 를 실제로
   닫는지. 닫지 못하는 경우가 남아 있습니까?
2. 위 빈 곳 1~6 중 **3단계로 넘어가기 전에** 반드시 닫아야 하는 것은?
3. 148바이트 고정 레코드와 little-endian 고정이 나중에 발목을 잡습니까?
4. 시험 11건에서 **이름이 단언보다 앞서 나간 것**이 있습니까? (이 저장소의
   되풀이된 실수라 특히 봐 주시길 부탁드립니다.)
