# SELAH RTA 2차 게이트 재검증

2026-09-21 · 대상 `9218a8f..b8b4fa3`

**판정: G01·G02 해결 확인, 이번 수정 범위의 게이트 승인.**

**Critical/High 결함은 이번 범위에서 확인하지 못했다.** 기존 시험 **245개(DSP 188 + 앱 57) 전부 통과**, 추가 독립 재현도 통과했다. 남은 검증 보완은 **Medium 1건, Low 1건**이며 아래에 명시한다. 이번 승인은 현장 정확도·출시·전체 플랫폼 호환성 승인을 뜻하지 않는다. production 코드는 변경하지 않았다.

- 저장소를 별도 사본으로 추출하고 실제 DSP·관련 앱 production 소스와 전체 JVM 시험을 직접 컴파일했다. Kotlin 2.2.20, JDK 21, JVM target 17, JUnit 4.13.2를 사용했다. 원본 AndroidX AAR/JAR와 Android API jar는 로컬 캐시에서 읽었다.

- 추가 `Gate2Probe.kt`는 이전 독립 재현의 입력과 barrier 순서를 유지하고, 단언을 수정 후 기대 동작으로 바꿨다. Controller와 상태 합성 함수는 production 원본 그대로 사용했다.
- 검증 종료 시 원본 working tree는 clean이었다.

### G01 — 중지 후 측정값 보존: 해결

Controller의 `composed()`가 기존 `withMeasurement()`로 바탕 상태와 측정 결과를 합친다. `stop()`은 세션 무효화 및 calibration 초기화 전에 이 합성 상태를 보존한다.

독립 실행 결과:

| 항목 | 중지 직전 | 중지 후 |
|---|---:|---:|
| Current SPL | 103.012611 | 103.012611 |
| MAX | 103.013066 | 103.013066 |
| RTA | 있음 | 있음 |
| diagnostics.frames | 102400 | 102400 |
| 하울링 기록 | 있음 | 1개 보존 |

추가 probe는 MeterReading 전체와 diagnostics의 동등성도 단언했다. 수치는 기본 미보정 눈금의 합성 입력 결과이며 실제 음압 정확도 인증값은 아니다. 관련 기존 시험은 95 dB 보정, 오류 종료, 분리 정책에 따른 중지, 반복 stop, 새 start의 초기화도 검사하며 통과했다. ON_STOP은 같은 종료 경로를 사용하지만 Android lifecycle 자체를 이번에 실행한 것은 아니다.

### G02 — 늦은 이전 스냅샷의 덮어쓰기: 해결

스냅샷 생성은 worker에서 하고, **수락은 `post { if (active === session) ... }`에서 수행**한다. production의 post는 main dispatcher이며 세션 전환도 같은 스레드에 속한다. 따라서 검사와 저장 사이에 다른 세션 전환이 끼어들지 않는다.

이전과 동일하게 실제 onBlock 입구 검사 이후 명령 큐의 latch에서 A를 멈췄다. stop→B start→B 결과 발행 뒤 A를 풀어도 결과는 다음과 같았다.

```text
LATE_SNAPSHOT active=3 published=3 visibleCurrent=2.1953315869553194
```

이 숫자는 해당 시험 입력에 따른 계산값이며, 핵심은 **published가 새 세션 3으로 유지되고 화면 값이 비지 않는다는 것**이다. 새 HeldMain 시험은 큐에 쌓인 옛 스냅샷을 새 세션 시작 뒤 배출하는 경우도 검증한다. 두 종류의 순서 시험을 함께 본 점이 중요하다.

## 44.1 kHz 결과의 독립 확인

RtaEngine→SpectrumSink→FeedbackDetector 배선의 시험을 실제 실행했다.

| 시험 | 48 kHz | 44.1 kHz |
|---|---:|---:|
| 250/1000/4000/8000 Hz 순음 검출 | 4/4 | 4/4 |
| 위 순음 최초 Persistent 시각 | 1621 ms | 1625 ms |
| 지정된 5초 핑크 잡음 시험 | Persistent 없음 | Persistent 없음 |
| 지정된 ±70 cent 비브라토 시험 | Persistent 없음 | Persistent 없음 |
| 폭 모형 2/5/10/20 Hz, 각 12 seed 총 검출 | 20 | 25 |

4 ms 지연 차이와 약 8.1% bin 폭 차이를 재확인했다. 다만 이는 **지정된 신호·길이·seed 집합에서의 결과**다. 현장 오탐률 0이나 두 레이트의 일반적 동등성을 뜻하지 않는다. 더 많은 검출이 정답인지 오탐인지도 입력의 정답 레이블 없이 결정할 수 없다.

## 남은 지적

### M01 · Medium — ‘검출률 동등성’ 시험의 단언은 한 방향 감소만 확인한다

**위치:** `dsp/src/test/kotlin/kr/joa/selahrta/dsp/SampleRateEquivalenceTest.kt:261–294`; gate2 요청서의 폭 시험 해석.

**근거:** 실패 조건은 `n44 < n48 - 2`뿐이다. 예를 들어 동일 폭에서 48 kHz가 0/12, 44.1 kHz가 12/12를 검출해도 이 단언은 통과한다. 실제 결과인 6/12 대 9/12도 통과한다. 이 조건은 ‘44.1 kHz에서 지정한 수보다 덜 검출하지 않음’이지 시험 이름대로 ‘검출률이 같음’이 아니다. `SEED_NOISE=2`도 통계적으로 검증한 동등성 한계는 아니다.

**사용자 영향:** production 오류가 확인됐다는 뜻은 아니다. 다만 테스트 통과를 일반적 동등성이나 폭 기준 검증 완료로 해석하면 더 높은 오탐 가능성 또는 샘플레이트 의존성을 놓칠 수 있다. Phase 12 정확도 평가의 근거가 과장될 위험이 있다.

**권장 수정:** 현 시험을 ‘이 신호 집합에서의 단방향 검출 감소 점검’으로 정확히 이름 붙인다. 동등성을 목표로 한다면 각 seed의 **짝지어진 불일치**와 양방향 차이를 보고하고, 정답 레이블·허용 차이·검증용 seed를 사전에 정한다. 더 많이 검출하는 쪽도 신호에 따라 오탐일 수 있으므로 무조건 개선으로 해석하지 않는다.

**필요 회귀 테스트:** 한쪽만 모두 검출하는 결과가 동등성 판정을 통과하지 않는지, 동일 총 검출 수이지만 서로 다른 seed에서만 검출하는 경우를 구별하는지 검사한다. 폭 판정 자체는 아래 질문 3의 별도 시험으로 분리한다.

**게이트 처리:** G01/G02 및 원래 C01 종료 안전성의 해결을 뒤집는 결함은 아니므로 이번 수정 게이트를 차단하지 않는다. §24.1에 따라 해석 제한과 보완 시점을 ADR/검증 계획에 기록하고, 일반적 44.1 kHz 동등성 주장은 그때까지 보류한다.

### L01 · Low — 같은 설정 재발행 시험이 큐에 들어간 잘못된 reset을 놓칠 수 있다

**위치:** `app/src/test/java/kr/joa/selahrta/ui/CaptureControllerOrderingTest.kt:289–299`.

**근거:** `onSettingsChanged(same, same)` 직후, 다음 오디오 block을 처리하지 않고 기존 스냅샷의 MAX만 비교한다. 잘못된 구현이 engine 재생성을 명령 큐에 넣더라도 이 시점에는 명령이 실행되지 않았으므로 시험이 통과할 수 있다. 현재 production의 `needsEngineRestart` 조건이 틀렸다는 지적은 아니며 회귀 검출력의 문제다.

**사용자 영향:** 향후 설정 재발행으로 Leq/MAX가 초기화되는 회귀가 생겨도 이 시험은 놓칠 수 있다.

**권장 수정·회귀 테스트:** 높은 레벨로 MAX를 먼저 만든 뒤 같은 설정을 재발행하고, 더 낮은 레벨의 block을 여러 개 처리하여 명령 큐와 발행을 실제로 진행한다. 이전 MAX가 유지되고 Leq 누적 구간도 이어지는지 단언한다. ‘항상 엔진 재생성’ mutation을 넣었을 때 이 시험이 실패해야 한다. 이 항목은 이번 게이트를 차단하지 않는다.

## 요청서의 세 질문

### 1. `state`를 `baseState`로 바꿔야 하는가?

**`baseState`를 권장하지만 게이트 조건은 아니다.** 현재 `composed()`와 올바른 stop 사용, 회귀 시험으로 알려진 결함은 해결됐다. 이름 변경은 이후 작은 정리로 할 수 있다. 독립 probe의 이름 호환 때문에 production API 명확성을 희생할 필요는 없다. API가 바뀌면 검증 코드의 호출 이름만 맞추면 된다. 두 상태의 소유 스레드와 용도를 API 문서에도 유지한다.

### 2. 초당 약 15회 main post는 괜찮은가?

소유 스레드에서 스냅샷을 수락하는 현재 선택은 합리적이다. 최신 숫자 표시용 작업량도 제한돼 있다. 다만 부하 상황에서 큐가 얼마나 쌓이고 회복 때 오래된 같은 세션 값이 연속 표시되는지는 별도다. main 큐를 0.5/2/5초 지연시킨 뒤 최신 값으로 수렴하는 시간·큐 길이·메모리를 측정하고, 필요하면 같은 세션의 미처리 snapshot을 최신 하나로 합친다. 경로 확인·종료 같은 제어 이벤트는 측정 프레임과 달리 무작정 버리면 안 된다. 이번 JVM 시험은 UI 부하 검증을 대신하지 않는다.

### 3. 폭 문턱 경계를 못 잰 상태로 남겨도 되는가? 다른 방법은?

이번 G01/G02 게이트에서는 미검증으로 남길 수 있다. 다만 **‘11.7 Hz보다 넓은 구조는 한 창 안에서 잡음과 구별되지 않는다’는 설명은 올바른 일반적 근거가 아니다.** 넓은 스펙트럼 봉우리의 폭은 여러 bin으로 나타날 수 있다. 현재 모형의 랜덤 위상 간섭, 순간 periodogram 변동, peak 추적·drift·persistence가 폭 조건과 함께 작동한 것이므로, 이 결과만으로 문턱 시험이 물리적으로 불가능하다고 결론 내릴 수 없다.

시험을 세 층으로 나누는 방법을 권한다.

1. **폭 판정 단위 시험:** 알려진 power 배열을 SpectralPeakFinder에 직접 넣는다. 예를 들어 `P[k]=floor+A/(1+((k·fs/N−f0)/(B/2))²)` 같은 봉우리를 만들고 f0의 bin 내 위치와 B를 훑는다. −3 dB 폭이 4·5·6 bins인 경계와 `widthBins<=5` 판정을 두 레이트에서 검사한다. 이 시험은 FFT/Hann 검증이 아니라 finder의 정의 및 경계 검증이다.
2. **FFT 포함 수치 시험:** 동일한 연속시간 신호를 각 fs에 샘플링한다. 정해진 폭의 변조/대역제한 신호를 phase·seed별로 넣고 **검출 횟수만이 아니라 프레임별 실제 widthBins, prominence, drift, continuity**를 함께 기록한다. 어느 조건 때문에 탈락했는지 분리한다. 통계적 스펙트럼 폭 추정에 평균화가 필요하면 검증 참조 측에서 사용하고 production detector의 순간 프레임 결과와 구분한다.
3. **최종 후보 성능 시험:** 실제 피드백과 음악/말소리 정답 레이블이 있는 별도 자료에서 놓침·오탐·지연을 비교한다. 12 seed의 알려지지 않은 broad-peak 정답을 ‘더 검출하면 좋음’으로 대신하지 않는다.

위 1번은 FFT를 길게 바꾸지 않고도 가능하다. 전체 production FFT 길이 변경이나 반응 속도 변경을 선행 조건으로 삼을 필요가 없다. 현 12 seed 결과의 차이가 오직 긴 창 때문에 발생했다는 인과 해석도 별도 분리 실험 전에는 가설로 적는 편이 정확하다.

## 잔여 위험과 승인 범위

G01의 정상 종료 데이터 소실과 G02의 옛 스냅샷 덮어쓰기는 **해결**로 닫는다. 이전 C01의 detector 직렬화와 finished 처리도 이번 전체 회귀 시험에서 유지됐다. 새 Critical/High 문제는 확인하지 못했다.

SignalPlayer의 출력 오류·timeout·빠른 재시작, 복수 USB 정책, reroute 재시작 상한, ViewModel의 보정/설정 구독 취소 및 지연 전달, 실제 ON_STOP/Compose 경로, 기준 소음계 비교, 현장 오탐·놓침·지연, 60분 부하·열·메모리는 계속 미검증이다. 이 잔여 위험을 제거하거나 출시 준비가 끝났다고 승인하는 것은 아니다.

이번 범위의 **개발 게이트는 통과**로 기록할 수 있다. Medium/Low 보완과 남은 검증은 후속 계획에서 추적해야 한다. production 수정·커밋·배포·메시지 발송은 하지 않았다.

재현 자료: 같은 outputs 폴더의 `Gate2Probe.kt`, `run-gate2-verification.ps1`, `gate2-verification-log.txt`. 원시 로그 일부 한국어 라벨은 JVM/PowerShell 출력 인코딩 차이로 깨져 있지만 시험 수·수치·성공 결과는 보존돼 있다.
