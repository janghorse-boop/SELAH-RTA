## 1. 고친 것

### CFRC-01 — 표를 화면 끝까지 들고 다닌다

권고하신 `CurveConfirmationToken(key, sourceSha, rulesVersion)` 그대로입니다.

- `save`/`watch` 가 `ActiveCurve` 에 표를 싣습니다.
- 단추가 `(token, reading)` 을 보냅니다.
- ViewModel 이 **입력 열쇠가 다르면 먼저 거절**합니다 — 저장소도 같은
  것을 보지만, 여기서 걸러야 무엇이 어긋났는지 말할 수 있습니다.
- 저장소가 **디스크 내용의 해시 == `token.sourceSha`** 와 규칙 판을
  확인한 뒤에만 발급합니다.
- 발급 뒤 파일이 또 바뀌는 경우는 기존 `watch` 의 해시 대조가 그대로
  무효화합니다.

**API 서명을 바꿨습니다.** 표 없이 부르던 옛 호출이 컴파일에서
드러나게 하라는 말씀 그대로입니다.

### CFRC-02 — 부호로 못 푸는 형식은 거절한다

넷 다 가져오기·켜기·확인에서 막습니다. **확인 기록이 있어도
거절합니다** — 사람이 승낙할 수 있는 종류의 일이 아닙니다.

화면은 「확인 필요」가 아니라 **「지원하지 않는 형식」**으로 적고
**고르는 단추를 띄우지 않습니다.** 띄우면 고르면 될 일이라고 믿게
만듭니다.

### 사유를 기계가 가르게 했습니다

「보수적 최소안의 한계」로 짚어 주신 자리입니다. `Unsupported` 에는
`Response (dB) (correction)` 같은 **부호만 어긋나는** 것도 섞여 있고,
그것은 Hz·dB 파일이 맞고 방향만 모르는 것이라 사람이 고르면 풀립니다.
함께 막으면 멀쩡한 파일을 영영 못 씁니다.

```kotlin
enum class UnsupportedColumn(val fixableBySign: Boolean, val labelKo: String) {
    Quantity(false, …),        // Phase·Amplitude — 다른 수량
    Unit(false, …),            // kHz 축·Pa·linear — 다른 단위
    ConflictingSign(true, …),  // 한 칸 안에서 방향만 어긋남
    Ambiguous(false, …),       // 선언이 여럿이고 서로 다름
}
```

**한국어 사유 문자열을 견주어 예외를 만들지 않았습니다.**

`ConflictingSign` 은 **설명문에 맡기지 않습니다.** `Corr (dB) (response)`
는 설명문 쪽 낱말이 「응답」 하나뿐이라, 예전 흐름이었다면 그대로
자동 확정될 자리였습니다.

## 2. 진짜 저장소를 지나는 시험을 만들었습니다

> 이 시험은 순수 `confirmedReadingOf` 만 호출해서는 안 되고 **실제 확인
> 발급 API** 를 지나야 한다.

맞는 말씀이라 그대로 했습니다. `CurveStoreConfirmationTest` 는 원본
`CurveStore` + 실제 DataStore + 실제 파일 왕복을 지납니다.
`TestApplication` 이 대신하는 것은 **파일을 둘 자리와 「나 자신」** 둘뿐
입니다.

요구하신 회귀 시험을 이름 그대로 옮겼습니다:

| 요구 | 시험 |
|---|---|
| A 표시 → B 저장 → A 토큰 확인은 거절 | 보여 준 파일이 바뀌었으면 옛 화면의 선택을 받지 않는다 |
| A 표시 → 입력 B 전환 → A 버튼은 거절 | 다른 입력의 표로는 확인되지 않는다 |
| 정상 A 토큰 확인·재실행은 성공 | 보여 준 그 파일이면 확인되고 / 앱을 다시 켜도 확인이 남는다 |
| 규칙 버전 | 규칙 판이 다른 표는 받지 않는다 |
| 네 형식의 save/watch/켜기/확인 미적용 | 지원하지 않는 형식은 가져와도 / 확인으로도 |
| 화면에 두 선택으로 고칠 수 있다고 하지 않음 | 지원하지 않는 형식에는 고르라고 하지 않는다 |
| 정상·Unknown 대조군 유지 | 평범한 파일은 그대로 걸리고 껐다 켤 수 있다 |
| 부호만 어긋나는 것은 확인 허용 | 한 칸 안에서 방향만 어긋나는 것은 고를 수 있다 |

## 4. 봐 주셨으면 하는 것

1. **`Ambiguous` 를 거절 쪽에 두었습니다.** 선언이 여럿이고 서로 다를
   때인데, 그 안에 부호만 어긋나는 경우가 섞여 있을 수 있습니다. 어느
   쪽도 믿을 수 없다고 보아 막았는데, 이 판단이 맞습니까?
2. **`token.sourceSha` 를 화면이 들고 다닙니다.** `ActiveCurve` 가 화면
   상태에 남아 있는 동안은 그 값이 굳습니다. 재구성 없이 오래 떠 있는
   경로가 있다면 제가 못 본 것이니 짚어 주십시오.
3. **규칙 판 상승 안내**는 4번 답대로 사유를 따로 전달하지는 않았습니다.
   지금은 「읽기 규칙이 바뀌었습니다. 파일을 다시 보고 골라 주십시오」
   한 문장입니다. 이 정도로 충분합니까?
4. **`TestApplication` 경계**가 적절한지 봐 주십시오. 이 방식으로 다른
   저장소(`CalibrationStore`·`ProfileStore`)에도 같은 시험을 붙일
   생각입니다.
