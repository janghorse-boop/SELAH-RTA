## 1. REC01 — 버퍼를 돌려주는 쪽을 하나로 (`8bce4af`)

### 재현부터 했다

보내 주신 `EQB-service-PoolProbe.kt` 를 **본문 그대로** 옮겨
`app/src/test/java/kr/joa/selahrta/recording/PoolProbeTest.kt` 로 두었다.
바꾼 것은 JUnit 껍데기와 나중에 더한 단언 두 줄뿐이다. 고치기 전 출력이
보고서의 값과 같았다:

```
CONCURRENT_RETURN rounds=30000 lostReturns=1     (5회 중 4회에서 0 아님: 0,2,1,2,3)
DOUBLE_RETURN_WITH_OTHER_HELD rejected=false next=0,0   (정확히 일치)
```

### 고친 것

| 누가 | 언제 | 어디로 |
|---|---|---|
| writer | PCM 을 다 쓴 뒤 | `release` → free-ring |
| 생산자 | 게시 못 하고 물러날 때 | `cancel` → 제 자리(`producerHeld`) |

- 생산자가 되돌린 버퍼는 **다음 `acquire` 가 그대로 다시 쓴다.**
  free-ring 을 거치지 않으므로 다툴 상대가 없다.
- `borrowed`(AtomicIntegerArray)로 **번호 단위** 이중 반환을 막는다.
- 끝낼 때 `handOverProducerHeld()` 로 쥔 것을 넘긴다.
- **offer/취소 순서를 제품 경계(`PacketPipe`)로 옮겼다** — 지적하신
  그대로다. 시험에만 있는 규칙은 제품이 지키는지 아무도 모른다.

### 되돌려서 확인 (변이 4건, 모두 잡힘)

| 변이 | 실패한 시험 |
|---|---|
| 닫힘 경로 `cancel`→`release` | 3건 (20,000 라운드 **전부**) |
| 복사실패 경로 `cancel`→`release` | 2건 |
| 이중 반환 검사 제거 | 1건 |
| `handOverHeld` 를 빈 함수로 | 2건 |

### **제 시험이 거짓이었던 것 둘** — 봐 주시기 바란다

**하나.** 요청하신 「writer 반환과 생산자 취소가 겹치는」 시험을 처음에는
**「겹친 뒤 잃었는가」로만** 썼다. 그 시험은 변이(1)에도 **통과했다** —
생산자가 예외를 만드느라 느려 두 반환이 실제로 겹치지 않았다. 겹치기를
바라는 시험은 결정적이지 않다.

그래서 **겹침과 무관한 것**을 단언하도록 바꿨다: 라운드마다 free-ring
으로 돌아온 횟수가 **정확히 1**(writer 것 하나)인가. 그 수를 보려고
`BufferPool.releasedToFree` 를 열었다. 바꾼 뒤 변이(1)에서
**20,000/20,000** 으로 잡혔고, **같은 실행의 `lostReturns` 는 0 이었다** —
「잃었는가」만 보는 단언이 왜 쓸모없었는지가 수치로 남았다.

**둘.** 고친 뒤 probe 를 처음 돌렸을 때 `lostReturns=0` 이 나와 「동시
반환도 고쳐졌다」고 적을 뻔했다. 다섯 번 돌리니 `0, 0, 2, 3, 2` 였다.
**`release` 는 지금도 두 스레드가 부르면 잃는다.** 고쳐진 것은 `release`
가 아니라 제품이 두 스레드에서 부르지 않게 된 것이다. probe 의 그 줄은
**규약 밖 사용**이라 회귀 시험이 될 수 없어 단언하지 않고 까닭을 적었다.
대신 **probe 에 단언이 하나도 없어 늘 통과하던 것**은 고쳤다(이중 반환
거절만 단언한다).

### 봐 주셨으면 하는 것

1. `producerHeld` 는 생산자 혼자 읽고 쓴다는 전제가 맞는가. `@Volatile`
   을 붙인 것은 진단이 읽게 하려는 것이지 다툼을 막으려는 것이 아니다.
2. `inUse` 가 `producerHeld` 를 빼고 세는 것이 두 스레드에서 읽힐 때
   일관된가. 화면·진단만 쓰지만 시험도 본다.
3. `handOverProducerHeld` 를 **생산자가 멈춘 뒤에만** 부른다는 규약을
   제품 쪽에서 어길 길이 있는가. 지금은 아직 캡처에 연결돼 있지 않다.
4. `releasedToFree`(= `given - count`)를 시험 관측용으로 연 것이
   적절한가. 더 나은 이음매가 있는가.

## 2. FS01 — 캡처가 끝나면 서비스도 끝난다 (`a45f23e`)

### 설계

`CaptureLifecycle { Active, Finished }` 라는 **최종 신호**를 따로 뒀다.
`emitLifecycle` 은 바뀔 때만 알리고, **갈아타는 중(`switchingDevice`)의
`Finished` 는 삼킨다.** 갈아타기가 끝나면 `applyDisconnectPolicy` 의
`finally` 가 **실제로 살아 있는지로** 다시 맞춘다.

서비스를 띄우고 내리는 자리는 `CaptureViewModel.reconcileService`
**하나뿐**이다.

지적하신 대로 `onStoppedHook` 에 무조건 stop 을 더하지 않았다 —
FallBack 의 `stop→start` 사이에 내리면 백그라운드에서 다시 띄울 수 없다.

### **제 첫 구현에 있던 결함 둘** — 시험을 쓰다가 찾았다

**하나.** `emitLifecycle(Active)` 를 `mic.start` **뒤에** 두었다. 열자마자
끊기는 기기에서는 그 안에서 분리 정책이 끝까지 돌고 돌아오므로, **다 죽은
뒤에 Active 를 내보냈다.** 신호가
`[Active, Finished, Active, Finished, Active]` 로 끝나 서비스만 떠
있었다. `mic.start` 앞으로 옮겼다.

**둘.** `ViewModel.start` 가 서비스를 **먼저** 띄웠는데, 마이크를 못 열면
컨트롤러는 아무 신호도 내보내지 않는다(처음부터 Finished 라 바뀐 것이
없다). 그래서 **띄워 둔 서비스가 그대로 남았다** — 고치려던 FS01 이 그
경로로 되살아나 있었다. 이제 `start` 는 서비스를 건드리지 않는다.

### 회귀 시험 — 요청하신 여덟 갈래 + 넷

`ServiceLifecycleTest` 12건. 각 길의 신호와 최종 상태:

```
입력 없음        → []                        재는 중 false · 서비스 false
open 실패        → []                        재는 중 false · 서비스 false
read 오류        → [Active, Finished]        재는 중 false · 서비스 false
USB Pause        → [Active, Finished]        재는 중 false · 서비스 false
수동 stop        → [Active, Finished]        재는 중 false · 서비스 false
stop 세 번       → [Active, Finished]        재는 중 false · 서비스 false
fallback 성공    → [Active]                  재는 중 true  · 서비스 true
fallback 실패    → [Active, Finished]        재는 중 false · 서비스 false
한도 초과        → [Active, Finished]        재는 중 false · 서비스 false
정상 → 갈아타기  → [Active]                  재는 중 true  · 서비스 true
start→stop→start → [Active, Finished, Active] 재는 중 true  · 서비스 true
start 두 번      → [Active]                  재는 중 true  · 서비스 true
```

되돌려서 확인(변이 3건, 모두 잡힘): `switchingDevice` 검사 제거 → 2건,
`emitLifecycle(Active)` 를 `mic.start` 뒤로 → 1건, `stop()` 의 `Finished`
제거 → 4건.

### 서비스 시작·승격 실패 — **권고와 다르게 갔다**

`startForegroundService` 와 `startForeground` 를 각각 감쌌다. 승격에
실패하면 서비스가 스스로 내려가고 `CaptureServiceBridge.unavailable` 로
알린다 — 그러지 않으면 안드로이드가 5초 뒤 앱을 죽인다.

**다만 「실패 상태로 전달」 대신 측정은 그대로 두었다.** 화면을 보고 있는
동안의 측정은 서비스 없이도 멀쩡하고, 재는 것까지 꺼 버리면 재려던
사람이 잃는 것이 더 크다고 판단했다. 서비스 쪽 상태는 정리한다(내려간다).
**이 판단이 옳은지 봐 주시기 바란다.**

### 추가 — 최근 앱에서 밀어내기 (`9108bed`)

*「onCleared 만으로 보증하지 말 것」* 에 따라 `onTaskRemoved` 를 더했다.
**기기에서 확인**: 측정 중 task 를 없애니 logcat 에 그 줄이 찍히고
서비스가 사라졌다. **로그를 심기 전에는 구별할 수 없었다** — 프로세스도
함께 죽어 서비스가 사라진 것이 이 코드 덕인지 알 수 없었다.

## 3. FS02 — 알림 권한을 묻는다 (`a45f23e`)

백그라운드 측정을 시작하는 그 자리에서 한 번 묻고, **거부해도 측정은
한다.** 막혀 있으면 「앱으로 돌아와 끝내라」고 적는다.

판단은 `NotificationAsk.kt` 로 떼어 내 기기 없이 돌린다(8건).
`묻지 않는데 막혀 있으면 반드시 알린다` 가 sdk×granted×asked 전 조합을
훑어 **「묻지도 알리지도 않는」 구멍**이 없는지 본다.

### 기기에서 확인 (갤럭시 S23 · 안드로이드 16)

```
pm revoke POST_NOTIFICATIONS → 측정 시작 → 시스템 대화상자 떴다
「허용 안함」 → 측정 시작됨(37.2 dBA), 안내 문구 뜸,
                서비스 isForeground=true types=0x80 (microphone)
「측정 종료」 → dumpsys activity services = (nothing)
pm grant 뒤 측정 시작 → 대화상자 없이 바로 측정
권한은 원래대로(granted=true) 돌려놓았다
```

## 4. 검토서의 소소한 지적 다섯 (`9108bed`)

| 지적 | 한 일 |
|---|---|
| `SPEC_BOUNDARY_MISMATCHES=7/7` 이 혼동된다 | `LEGACY_SYMPTOM_EXPECTATION_MISMATCH` 로 바꾸고 까닭을 함께 찍는다. **그 probe 에 단언이 하나도 없던 것**도 고쳐 `STILL_MERGED == 0` 을 단언한다 |
| `stopped \|\| released` 가 중복 | 지웠다. 대신 **놓은 뒤에 stop 을 불렀는지**(`stoppedAfterRelease`)를 센다 |
| latch 로 고정한 사례가 낫다 | 더했다. 다만 **가드를 못박지는 못한다**(아래) |
| TalkBack 에 상태 설명 유지 | `levelStateKo`/`levelSpeechKo` + `stateDescription`. 색은 5dB 에 걸쳐 섞지만 **말은 안 섞는다** |
| CaptureServiceBridge 미검증 | 구독자 없음·뒤늦은 구독·둘이 구독 세 경우를 못박았다. 실패 통로와 종료 통로가 섞이지 않는 것도 본다 |

### **남은 구멍 하나** — 스스로 찾았고 못 막았다

`SignalPlayer.stopSink()` 의 `if (!releaseStarted.get())` 가드를 지워도
**어느 시험도 실패하지 않는다.** 200회 시험의 `stopSkipped` 만 6 → 0 으로
바뀐다. 그 수를 단언하면 부하에 좌우되는 시험이 되므로(이미 한 번 데였다)
그러지 않았다.

latch 사례도 그 가드를 못박지 못한다 — 자동 종료 경로는 `current` 를 먼저
지우므로 `stop()` 이 곧바로 돌아가 가드에 닿지 않는다. 사람이 멈추는
경로에서만 닿는데, `stop()` 이 `running=false` 와 `stopSink()` 를
연달아 하므로 **밖에서 그 사이를 벌릴 수 없다.**

제품에 시험용 이음매를 내야 할 자리인지, 아니면 다른 방법이 있는지
의견을 구한다.

## 5. USB 오디오 지시서 대조 (`3867f1e`)

`SELAH_RTA_UMC404HD_EMM6_USB_AUDIO_REQUIREMENTS.md` 를 `docs/spec/` 으로
들이고, 그 19장이 요구한 대로 **구현 전에** 기존 구조와 한 줄씩 대조했다
(`docs/spec/2026-09-22-usb-audio-gap-analysis.md`).

**이 문서 자체를 검토해 주시기 바란다.** 구현은 아직 없다.

핵심 세 가지:

1. **9.5 의 보간 요구와 9.3 의 파서 요구는 이미 구현돼 있다.** 다시
   만들면 안 된다.
2. **보정 부호를 이미 정해 놓았다**(「파일 = 마이크 응답, 우리가 뺀다」).
   지시서 9.4 가 금지한 「추측」인지 근거 있는 관례 채택인지 **실제 EMM-6
   파일을 봐야 갈린다.** 부호가 반대일 때 뜨는 경고는 ±30dB 를 넘어야
   뜨고 실제 파일은 대개 ±5dB 안쪽이라 **조용히 통과한다.** 막힌 항목.
3. **USB 전용 권한이 필요 없을 수 있다.** `AudioManager` +
   `setPreferredDevice` 경로에는 `RECORD_AUDIO` 외에 받을 권한이 없다.
   `UsbManager.requestPermission` 은 raw USB 로 말할 때의 것이다. 이
   읽기가 맞는지 봐 주시기 바란다.

진짜 구멍은 **채널 선택**이다. `RequestedFormat.channelMask` 가 늘
`CHANNEL_IN_MONO` 이고 `OpenedFormat` 에 `channelCount` 가 없어, 4채널
인터페이스를 꽂아도 **무엇이 열렸는지 기록이 없다.** 다음 작업으로 잡았다.

## 6. 확인하지 않은 것

- **알림의 「측정 종료」 버튼을 누르지 못했다.** 서비스가 exported 가
  아니라 adb 로 그 인텐트를 보낼 수 없다(`Requires permission not
  exported`). 코드 경로는 그대로이고, 앞서 사람이 눌러 확인한 바 있다.
- **TalkBack 을 실제로 켜서 듣지 않았다.** 시험한 것은 말을 만드는
  함수뿐이다.
- open 실패·read 오류·USB 분리는 **시험에서만** 돌렸다. 기기에서 그
  상황을 만들 방법이 없었다.
- 서비스 승격 실패 경로도 기기에서 재현하지 않았다.
- 2시간 연속 측정·화면 꺼짐·절전은 재지 않았다.
- **USB 인터페이스는 장비가 없어 하나도 못 봤다.**
- `PacketPipe` 는 아직 캡처 경로에 물려 있지 않다(녹음 4단계).
