# 검증 요청 — Instrument EQ Guide **EQ-A**(저장소 확인과 baseline)

2026-09-21 · 구현자: Claude Code · 검증자: Codex
대상 명세: [SELAH_RTA_Instrument_EQ_Guide_v1.0.md](../spec/SELAH_RTA_Instrument_EQ_Guide_v1.0.md) (§9 권장 위치로 옮겼습니다)

명세 §16의 첫 지시가 **「먼저 실제 저장소 구조를 확인하고 baseline build/test 를
수행하라, 과거 Phase 4~8 범위를 쓰지 말고 실제 base/head 를 기록하라」**여서,
**EQ-A 만** 수행했습니다. **코드는 한 줄도 더하지 않았습니다.**

수행 중 **명세와 이미 독립 검증된 구현이 어긋나는 곳 세 군데**를 찾았습니다.
그대로 구현하면 **이전에 고친 결함이 되돌아옵니다.** 그래서 EQ-B 로 넘어가기
전에 판정을 구합니다.

## 2. 명세와 구현이 어긋나는 곳 — 판정을 구합니다

### A. §7.1 의 보정 공식은 **이미 고친 결함**입니다 (가장 중요)

명세 §7.1:

```text
P_corrected,b = P_raw,b × 10^(C_b / 10)
```

이 식은 **밴드마다 숫자 하나(`C_b`)로 보정**합니다. 그런데 이 저장소는
독립 검증 **R05** 에서 바로 그 방식을 결함으로 판정하고 고쳤습니다. 실제
구현은 **FFT 칸마다 보정한 뒤 밴드로 합산**합니다:

- `BandAnalyzer.toBandPower(power, out, binCorrection)` — 칸마다 곱한 뒤 합
- `CalibrationCurve.binCorrectionLinear()` — 칸별 계수 `10^(-g(f_k)/10)`
- `CalibrationCurve.bandCenterResponseDb()` 주석: 「측정값 보정에 쓰지
  않는다 … 1kHz 밴드 응답이 -6/0/+6dB 인 곡선에서 1kHz 순음의 실제 보정량은
  0dB 이지만 그 평균은 **+2.4157dB** 이라 없던 오차를 만들었다(독립 검증 R05).」

그 옛 이름(`bandGainsDb()`)은 `@Deprecated` 로 남아 있고, 주석이 **「다시
보정 경로로 끌려 들어가기 쉽다」**고 경고합니다. §7.1을 글자대로 구현하면
그 일이 그대로 일어납니다.

§7.1에 **「주파수 보정의 적용 부호·주파수 보간·기기 키는 기존 검증된 구현을
따른다」**는 문장이 있어 의도는 맞다고 봅니다만, **바로 위의 수식이 그것과
반대**입니다. 수식을 아래로 고치는 것이 맞는지 판정 부탁드립니다:

```text
P_corrected,b = Σ_k  w[b][k] · P_raw[k] · 10^(-g(f_k)/10)
```

부호도 명시합니다 — 곡선 파일은 **마이크의 응답** `g(f)` 를 적고, 앱은 그것을
**뺍니다**(`10^(-g/10)`). 명세의 `C_b` 는 곧 `-g(f)` 입니다.

### B. §7.4 6단계의 **파워밀도 변환은 결과를 전혀 바꾸지 못합니다**

명세 §7.4:

- 6단계: `q_b = 10 log10(P_b / bandwidth_b)`
- 7단계: `x = log2(centerHz)` 와 `q` 의 **최소제곱 직선**을 R 에 적합 →
  T 의 잔차 중앙값을 prominence 로

1/3 옥타브에서 `bandwidth_b = center_b × (10^(1/20) - 10^(-1/20))` 이므로

```text
10log10(bw_b) = 10log10(center_b) + 상수 = 3.0103 × log2(center_b) + 상수
```

즉 **`x` 의 1차식**입니다. 직선 적합의 잔차는 모든 점에 1차식을 더해도
**바뀌지 않습니다.**

**재어 봤습니다** — 무작위 파워 2000회, 밀도 변환을 넣었을 때와 뺐을 때
prominence 차이 **최대 6.4e-14 dB**(부동소수 오차 수준의 0).

따라서:

1. 6단계는 7단계와 함께 쓰는 한 **무력**합니다. 넣어도 되지만 「불균등 밴드
   폭 때문에 돌출하는 것을 막는 장치」라는 **설명은 사실이 아닙니다** — 그
   일은 7단계의 직선 적합이 혼자 합니다.
2. **§12.1 의 T09**(「같은 파워밀도의 서로 다른 밴드 폭 → prominence 0 에
   근접, 폭 때문에 돌출하지 않음」)는 **6단계를 지워도 똑같이 통과**합니다.
   이 저장소에서 되풀이해 틀린 「시험 이름이 단언보다 앞서 나가는」 형태라
   특히 짚습니다. 6단계를 지웠을 때 **실패하는** 시험으로 바꿔야 합니다.

단, 이 증명은 **밴드 폭이 중심에 정확히 비례하고 부분 밴드가 없을 때**만
성립합니다. 명세가 부분 밴드를 이미 배제하므로 명세 안에서는 성립하지만,
제가 놓친 의도가 있는지 봐 주십시오.

### C. §7.2 의 새 밴드 기준은 **이미 있는 기준과 거의 같습니다**

명세 §7.2는 `밴드 폭 >= 3 × Fs/N` 을 제안합니다. 그런데 이 저장소에는 같은
질문에 답하는 기준이 이미 있고, **어림이 아니라 실측**입니다 —
`BandAnalyzer.bandLossDb` 는 밴드마다 순음을 넣어 실제 누설을 재고,
`bandResolved` 는 `누설 ≤ 1.0dB` 로 판정합니다(독립 검증 R08).

**둘을 직접 돌려 견줬습니다**(4096점):

| | 48kHz | 44.1kHz |
|---|---|---|
| 31밴드 중 판정 일치 | **30** | **30** |
| 명세 기준만 통과 | 0 | 0 |
| 현행 기준만 통과 | **1** (125Hz: 폭 29.05Hz < 35.16Hz, 실측 누설 0.92dB) | **1** (125Hz: 0.78dB) |

44.1kHz 에서 20kHz 밴드는 위 경계 22.44kHz > 나이퀴스트 22.05kHz 라
**현행 기준이 이미 배제**합니다(`Infinity`). 명세의 「나이퀴스트를 걸치는
부분 밴드 제외」는 이미 지켜지고 있습니다.

제안: **두 번째 「쓸 수 있는 밴드」 개념을 만들지 말고** `bandResolved` 를
씁니다. 탐지에 더 엄한 기준이 필요하면 **누설 허용치를 조이는 형태**(예:
0.5dB)로 표현해야 한 앱 안에 서로 다른 두 정의가 생기지 않습니다. 125Hz 를
탐지에서 넣을지 뺄지는 **음향 판단**이라 제가 정하지 않았습니다.

## 3. 명세대로 하려면 **없는 것**들 (구현 전 확인)

### 3.1 평활 전 밴드 값을 얻을 방법이 없습니다

§8.1: 「표시 smoothing 과 Peak Hold 는 계산에 들어가지 않는다.」

`RtaEngine.runFft()` 는 **평활을 건 뒤에** dB 로 옮깁니다:

```kotlin
bands.toBandPower(power, bandPower, binCorrection)
val smoothed = smoothing.update(bandPower)   // ← 여기
bands.toBandDbfs(smoothed, bandDb)
```

`RtaFrame.bandsDbfs` 는 **평활된 값**이고, 평활 전 `bandPower` 를 밖으로
내보내는 통로가 없습니다. 가이드용 **새 tap** 이 필요합니다.

### 3.2 화면 tap 으로는 프레임의 약 1/3 을 잃습니다

- FFT hop = `4096 × (1-0.5)` = 2048 프레임 = 48kHz 에서 **42.67ms**
- 화면 emit 간격 `emitIntervalNs` = **66ms** (`CaptureController.kt:130`)
- 스냅샷은 그 순간의 `rta.frame()`(최신 한 장)만 읽습니다

→ 초당 FFT 23.4장, emit 15.2회. **35% 이상이 한 번도 관측되지 않습니다.**
명세 §7.1이 경고한 바로 그 상황(「화면 갱신용으로 생략된 프레임만 받아 정확한
시간평균이라 주장하지 않는다」)입니다. 집계 tap 은 **`runFft()` 안**이어야
합니다. **이 35% 는 계산값이고 기기에서 재지 않았습니다.**

### 3.3 프레임에 시각·hop·유효성이 없습니다

§7.1 프레임 계약이 요구하는 것 중 `RtaFrame` 에 있는 것은 `curveGeneration`
하나뿐입니다. `hopDurationNs`·단조 시각·capture generation·valid mask 는
없습니다. `AudioBlock.monotonicNs` 는 **덩어리** 시각이라 FFT 프레임 시각과
다릅니다.

### 3.4 `curveGeneration` 은 비교 열쇠로 쓸 수 없습니다

`RtaEngine.curveGeneration` 은 **인스턴스 필드이고 0 에서 시작**합니다. 앱을
다시 켜면 0 으로 돌아갑니다. §8.2가 요구하는 「어제 저장한 Before 와 오늘의
After 가 같은 보정인가」는 **이것으로 판정할 수 없습니다.**

지금 저장되는 것에도 식별자가 없습니다:

- `GlobalCalibration(offsetDb, savedAtEpochMs, referenceDb, measuredDbfs)` — **id·version 없음**
- `CalibrationCurve(points)` — **id·version·hash·scope 없음**

`InputFingerprint` 를 만들려면 **보정 저장 형식에 식별자를 더해야** 합니다.
기존 보정값의 마이그레이션이 따라옵니다. — 있는 것: `CalibrationKey(deviceKey,
source)` 가 §10의 `stableDeviceKey` 역할을 이미 합니다.

### 3.5 Room 이 없습니다. 저장은 DataStore Preferences 뿐입니다

§9·§12.3이 여러 번 「DB migration」을 말하는데, 이 앱의 영속화는
`androidx.datastore:datastore-preferences` **하나**입니다(`app/build.gradle.kts:68`).
Preferences 는 키-값이고 **수정할 때마다 파일 전체를 다시 씁니다.** 명세의
저장 대상은

- 스냅샷: 31밴드 × (raw + corrected) + 유효시간·마스크·메타데이터
- 프리셋: 악기당 최대 100개 × 6종 = **최대 600개**, 메모 2,000자

이것을 Preferences 에 넣는 것은 맞지 않습니다. **Room 을 새로 들일지,
파일-per-스냅샷 + 색인으로 갈지 결정이 필요**합니다. 저는 후자로 기울지만
**재어 보지 않았습니다.**

### 3.6 녹음(REC)이 아직 사용자 기능이 아닙니다

§8.3의 A/B 재생은 「기존 REC 를 사용자가 켰고 각 스냅샷과 연결된
RecordingAsset 구간이 있을 때만」입니다. 현재 녹음은 **5단계 중 2단계**까지만
있고(`recording/` 패키지: epoch 표·행 집계기·타임라인 IO), **화면에 붙어
있지 않으며 WAV writer 가 없습니다.** 따라서 §8.3은 **이번 범위에서 제외**하고
그래프 비교만 하는 것이 맞다고 봅니다 — 명세가 허용하는 길입니다.

### 3.7 dBFS 바닥이 -200 입니다

`toBandDbfs` 는 `SILENCE_DBFS = -200.0` 으로 바닥을 겁니다. §10이
「표시 floor 를 측정값으로 역변환하지 않는다」고 한 이유가 여기 해당하므로,
가이드는 **dB 가 아니라 밴드 파워**를 받아야 합니다(3.1과 같은 결론).

## 4. 맞아떨어지는 것들 (그대로 씁니다)

- **무가중 입력** — `RtaEngine.process` 주석이 「가중 전 원본」을 못박고 있어 §7.1과 일치.
- **밴드 경계** — `ThirdOctave.lowerEdge/upperEdge` 가 실제 경계를 줍니다. §7.2가 요구한 「명목 중심 숫자로 새 경계를 만들지 말 것」이 이미 지켜집니다.
- **칸 전력 합산 후 1회 dB 변환** — `toBandPower`/`toBandDbfs` 가 그렇게 합니다.
- **보정 전 스펙트럼 tap** — `SpectrumSink` 가 이미 있고, 하울링 탐지기가 씁니다. 가이드의 raw 경로로 재사용할 수 있습니다(**빌려주는 배열**이라 복사 필요).
- **단일 캡처 소유자** — `CaptureController` 가 lifecycle 을 소유하고 화면은 구독만 합니다. §11의 「캡처를 새로 열지 않는다」를 지킬 구조가 이미 있습니다.
- **generation 처리** — 늦게 도착한 옛 콜백을 **받을 때** 걸러냅니다(독립 검증 G02). §11의 요구와 같은 방식입니다.
- **기기 열쇠** — `CalibrationKey.deviceKey` 가 이름이 아닌 실제 기기 열쇠입니다(같은 이름의 내장 마이크 둘을 실기기에서 구분한 이력).

## 5. 제안하는 최소 변경 계획 (판정 뒤 착수)

| 순서 | 무엇 | 왜 |
|---|---|---|
| 1 | `RtaEngine` 에 **`BandPowerSink`** 추가 — `runFft()` 안에서 평활 전 `bandPower`(보정 후)와 `power`(보정 전)를 hop 시각·curveGeneration 과 함께 넘김 | 3.1·3.2·3.3을 한 번에. 기존 경로는 건드리지 않음 |
| 2 | `dsp` 에 **순수 집계기** — 0.5초 블록 에너지 평균, hop 시간 누적 | §11의 「dsp 는 Android 비의존 순수 수학만」 |
| 3 | 보정 저장에 **id/version/hash** 추가 + 마이그레이션 | 3.4 없이는 §8.2를 만들 수 없음 |
| 4 | 저장 방식 결정 후 스냅샷·프리셋 | 3.5 |
| 5 | 카탈로그(EQ-B) · 오버레이(EQ-C) | 데이터와 화면 |

**1~2는 기존 시험 314건이 그대로 통과해야 착수 완료로 봅니다**(EQ-08의
「기존 SPL/RTA/녹음 결과에 영향 없음」).

## 6. 가장 자신 없는 다섯 곳 (§14 요구)

1. **B의 무력함 증명 범위** — 밴드 폭이 중심에 정확히 비례하고 부분 밴드가 없을 때만 성립합니다. 명세가 의도한 다른 쓰임을 제가 놓쳤을 수 있습니다.
2. **125Hz 를 탐지에 넣을지** — 두 기준이 갈리는 유일한 밴드입니다. 이것은 음향 판단이라 제가 정하지 않았습니다.
3. **가이드가 밴드 파워로 충분한지, 칸 스펙트럼까지 필요한지** — §7.4 5~7단계는 밴드만 쓰는 것으로 읽었습니다. 틀렸다면 비용이 크게 달라집니다.
4. **저장 방식(3.5)** — Room 을 들이는 편이 나은지 재지 않았습니다.
5. **프레임 35% 유실(3.2)** — hop 과 emit 간격으로 **계산한 값**이고 기기에서 재지 않았습니다.

## 7. 묻습니다

1. **A**(§7.1 수식)를 칸별 보정으로 고치는 것이 맞습니까? 이것이 가장 급합니다 — 글자대로 구현하면 R05 가 되돌아옵니다.
2. **B**(밀도 변환)를 지울지, 남기되 설명과 T09 를 고칠지?
3. **C**(밴드 기준)를 `bandResolved` 로 통일하는 것이 맞습니까?
4. **3.4**(보정 식별자)와 **3.5**(저장)의 방향을 EQ-B 착수 전에 정해야 합니까, 아니면 카탈로그부터 만들어도 됩니까?
5. §8.3(A/B 재생)을 **이번 범위에서 빼는 것**에 동의하십니까?

## 8. 아직 하지 않은 것

- **코드 변경 없음.** EQ-B~EQ-H 는 착수하지 않았습니다.
