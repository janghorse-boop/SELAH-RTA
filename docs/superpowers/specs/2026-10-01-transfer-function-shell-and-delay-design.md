# Transfer Function — 문과 지연 찾기 (1차) 설계

> ## ⚠️ 보류 — 범위가 바뀌었다 (2026-10-01 저녁)
>
> **Codex 명세 검토 회신이 1차 MVP 를 `Delay + Clock Drift + Magnitude +
> Coherence` 로 넓혔다**(개발지시서 32장). 이 문서는 **1차를 Delay 하나로
> 잡고** 쓴 것이라 그만큼 어긋난다.
>
> **덮어쓰지 않고 둔다** — 개정된 명세를 Codex 가 **최종 검토한 뒤** 다시
> 쓴다. 그 전에 고치면 두 번 쓰게 된다.
>
> **지금도 유효한 것**: 3장(기준 신호를 덧씌우기로 얻는 법과 `write()` 의
> 함정) · 4장(상호상관) · 5장의 상태 가르기 · 7장(고칠 파일).
> **다시 봐야 할 것**: 1·2장의 범위.
>
> 이미 만든 것: `SampleRing`(커밋 `4064631`, 시험 5/5). 10개 지적 어디에도
> 안 걸리는 순수 자료구조라 가지에 남겨 두었다.

승인: 담당자가 **안 2** 를 골랐다(2026-10-01). 구조 검토는
[`docs/review/2026-10-01-transfer-function-ui-structure-review.md`](../../review/2026-10-01-transfer-function-ui-structure-review.md).

**이 문서가 다루는 범위는 1차뿐이다** — 문, 간편 모드 화면, **지연 찾기**.
Magnitude·Coherence·Phase 는 **막혀 있다**(아래 「안 만드는 것」).

---

## 1. 무엇을 만드는가

```
분석 (가로)
├─ 차트: RTA · Spectrum · Spectrogram · FR      ← 손대지 않는다
└─ [ Transfer Function ▸ ]                       ← 한 줄 추가

        ↓ 누르면 (교정 마법사와 같은 방식으로 덮는다)

Transfer Function · 간편 (가로)
┌────────────────┬──────────────────────────────┐
│  지연           │                              │
│  23.4 ms        │   (2차에 Magnitude 가 온다)   │
│                 │                              │
│  측정 신뢰도     │                              │
│  ○ 측정 중       │                              │
└────────────────┴──────────────────────────────┘
```

### 진입 화면은 **아직 만들지 않는다**

구조 검토는 `[간편] [정밀] [여러 위치]` 고르는 진입 화면을 그렸다. 그런데
**1차에는 간편뿐이다.** 이 저장소의 원칙이 그 경우를 이미 정해 두었다 —
`ToolsScreen.kt`: **「고를 것이 하나인 고르개는 고르개가 아니다」**.

그래서 **문을 누르면 간편 화면으로 바로 간다.** 정밀이 생기는 3차에
진입 화면을 넣는다. 그때 주소가 한 겹 깊어지지만, 그 전에 **없는 것을
고르게 하는 화면**을 두는 것보다 낫다.

**「준비 중」으로 흐리게 띄우지 않는다.** 이 앱은 「화면이 하지 않는 일을
한다고 적고 있었다」로 한 번 데었다(2026-09-30, 「흐리게 그립니다」가
거짓이었던 건).

## 2. 안 만드는 것 — 그리고 **왜 못 만드는가**

| 무엇 | 왜 |
|---|---|
| **Magnitude · Coherence** | 전달함수와 coherence 의 **평균 영역 정의가 막혀 있다.** Codex 검토 중([요청서](../../review/2026-10-01-transfer-function-spec-rereview-request.md) 1장). 답을 받기 전에 만들면 그 위에 화면과 저장 포맷이 올라간다 |
| **Phase** | 지연·드리프트가 안정된 뒤에만 뜻이 있다(개발지시서 §3 순서) |
| **클럭 드리프트 보정** | 아직 **한 번도 재지 않았다.** 재는 것이 먼저다(2차) |
| **정밀 모드** | 출력 경로가 정의되지 않았고, 2채널 동시 입력이 **go/no-go 관문**이다 |
| **Multi-Point** | 4차 |
| **절대 Magnitude** | 폰 마이크 보정 곡선이 없다(절차 G 가 2단계에서 멈춤). 1차는 **상대 비교 전용**이다 |

## 3. 기준 신호를 어떻게 얻는가

**「나중에 다시 만든 값」이 아니라 실제로 나간 표본**이어야 한다
(개발지시서 §4). 이 앱은 그게 이미 가능하다.

`SignalPlayer` 가 출력 장치를 **공장으로** 받는다(`SignalPlayer.kt:56`):

```kotlin
class SignalPlayer(
    private val openSink: () -> SignalSink = { AudioTrackSink() },
)
```

그러니 **덧씌우기** 하나면 된다. `SignalPlayer` 도 `AudioTrackSink` 도
고치지 않는다.

```kotlin
class TappedSink(
    private val inner: SignalSink,
    private val tap: ReferenceTap,
) : SignalSink {
    override fun write(buf: FloatArray, offset: Int, frames: Int): Int {
        val wrote = inner.write(buf, offset, frames)
        // **받아들여진 만큼만 적는다.**
        if (wrote > 0) tap.offer(buf, offset, wrote)
        return wrote
    }
    // open/stop/release 는 그대로 넘긴다
}
```

### 여기가 **조용히 틀리기 쉬운 자리**다

`write()` 는 **일부만 쓸 수 있다**(`SignalPlayer.kt:436` 이 그래서 루프를
돈다). 넘긴 버퍼 전체를 기준으로 적으면 **기준이 실제보다 앞서 가고**,
그만큼 지연이 **작게** 나온다. 조용히, 그럴듯하게.

그래서 `wrote` 만 적는다. 그리고 **그것을 시험으로 못박는다**(6장).

`wrote` 가 음수(`ERROR_DEAD_OBJECT` 등)일 수 있으므로 `> 0` 만 적는다.

## 4. 지연을 어떻게 찾는가

**상호상관(cross-correlation)** 으로 기준과 측정의 시간차를 찾는다.

```
기준  x[n]  (실제로 나간 표본)
측정  y[n]  (마이크로 들어온 표본)

R(τ) = Σ x[n] · y[n+τ]
지연 = R 이 가장 큰 τ
```

- 탐색 범위: **0 ~ 500 ms**(48 kHz 에서 24,000 표본). 500 ms 면 음속으로
  170 m 라 웬만한 공간을 덮고도 남는다. 더 넓히면 **엉뚱한 반사에 걸린다.**
- 계산은 **FFT 로** 한다(직접 곱하면 24,000 × 블록이라 폰에서 못 돈다).
- **분수 표본까지 보지 않는다**(1차). 48 kHz 한 표본이 0.021 ms 이고,
  이 쓰임(정렬)에서는 충분하다. 분수 표본은 위상을 할 때 필요하다.

### 믿을 수 있는지를 함께 낸다

지연 숫자만 내놓으면 **조용한 방에서 잡음에 걸린 값**도 숫자로 보인다.

```
peak      R 의 최댓값
2등       그 다음으로 큰 봉우리
또렷함    peak / 2등        ← 이 값이 작으면 못 믿는다
```

**또렷함이 문턱 아래면 숫자를 내지 않는다.** 「찾지 못했습니다」라고 적고,
까닭을 함께 적는다(소리가 안 들린다 / 너무 조용하다 / 반사가 심하다).

> **문턱값은 지금 정하지 않는다.** 실측으로 정한다(개발지시서 §11·§25 와
> 같은 태도). 1차에서는 **값을 화면에 함께 적어** 담당자가 실제 자리에서
> 무엇이 나오는지 보게 한다.

## 5. 화면이 말하는 것 — **상태를 먼저 정한다**

그래프보다 **상태**가 먼저다. 무엇이 없을 때 무엇을 적는지가 정해져야
「조용히 틀린 숫자」가 안 나온다.

| 상태 | 화면 | 언제 |
|---|---|---|
| `측정 안 함` | 「측정을 시작하면 잽니다」 | 측정이 안 돌고 있다 |
| `신호 없음` | 「테스트 신호를 틀어 주십시오」 + 도구로 가는 길 | 측정은 도는데 기준이 안 나간다 |
| `소리 안 들림` | 「스피커에서 소리가 들어오지 않습니다」 | 기준은 나가는데 마이크 레벨이 안 오른다 |
| `찾는 중` | 「재는 중입니다」 | 블록을 모으는 중 |
| `찾음` | **지연 ms** + 또렷함 | |
| `못 찾음` | 「지연을 찾지 못했습니다」 + 까닭 | 또렷함이 문턱 아래 |

**「측정 신뢰도」 칸은 1차에서 `○ 측정 중` 으로 고정한다.** coherence 가
없으므로 신뢰도를 말할 수 없다. **빈칸으로 두거나 「좋음」을 띄우지
않는다** — 둘 다 거짓말이다.

## 6. 시험으로 못박을 것

**JVM 시험**(`dsp` 와 `app`, 실기기 없이)

| 무엇 | 왜 |
|---|---|
| 지연 0 · 5 ms · 20 ms · 100 ms 를 **합성 신호로** 되찾는다 | 기본 |
| **잡음을 섞어도** 되찾는다(SNR 20 dB · 10 dB · 0 dB) | 실제 방 |
| **반사를 섞으면**(본 신호 + 10 ms 뒤 −6 dB) 본 신호를 고른다 | 잔향이 있는 공간 |
| 조용한 잡음만 주면 **「못 찾음」이 나온다** | **이것이 제일 중요하다** — 못 찾는 것을 숫자로 내놓지 않는가 |
| 탐색 범위를 **넘는** 지연(600 ms)은 「못 찾음」 | 범위 밖을 접어서 엉뚱한 답을 내지 않는가 |
| `TappedSink` 가 **`wrote` 만큼만** 적는다 | 3장의 함정. 일부만 쓴 경우를 흉내 내어 확인한다 |
| `TappedSink` 가 `wrote <= 0` 일 때 **아무것도 안 적는다** | 같음 |

**변이로 확인한다**: `wrote` 를 `frames` 로 바꿔치기했을 때 시험이
**실패해야** 한다. 안 그러면 그 시험은 헛그물이다.

## 9. 1차를 끝낸 뒤에 묻는 것

- 지연의 **또렷함 문턱**을 실제 자리에서 본 값으로 정한다
- 지연만으로 쓸모가 있는가 — **Main/Delay 정렬**에 바로 쓸 수 있을 텐데,
  그 쓰임에 맞는 화면이 더 필요한가(두 지점의 차이 등)
