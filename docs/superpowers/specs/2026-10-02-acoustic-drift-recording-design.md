# 음향 드리프트 기록 — 설계와 **재기 전에 정한** 판정 규칙

날짜: 2026-10-02 · 근거: 7회차 독립 검토 §11 (b)·(c), 6회차 「Claude 추가 요청 회신」

> **왜 이 문서가 먼저인가**
>
> 결과를 본 뒤에 규칙을 정하면 결과에 맞는 규칙을 고르게 된다. 그래서
> **측정하기 전에** 무엇을 기록하고, 어떻게 자르고, 어떤 말까지 할 수
> 있는지를 여기 적는다. 측정 뒤에 이 규칙을 바꾸려면 **바꾼 까닭과
> 바꾸기 전 결과를 함께** 남긴다.

---

## 1. 무엇을 묻는가 — 그리고 묻지 않는가

**묻는 것**: 이 구성(SM-S918N 내장 마이크 하단 경로 + UMC404HD 출력,
48 kHz)에서 **앱이 받는 기준과 측정의 표본 번호 좌표 지연이 시간에 따라
어떻게 움직이는가.** 최소제곱 기울기를 ppm 으로(기술 통계) 내고, 그 구간
전체에서 지연이 1표본 변하는 기울기(환산값)를 함께 적는다. **「밀리는가」에 예·아니오로 답하지는
않는다** — 검증된 불확도 방법이 없다(8회차 R8-01, 4장 4). *(처음에는 「밀리는가 —
불확도를 함께 낸다」였다)*

**묻지 않는 것**:

- **원인.** 밀린다 해도 하드웨어 클럭 차이인지, OS 의 리샘플링·보정인지,
  큐·경로 변화인지 이 측정으로 가리지 않는다. 안 밀린다 해도 「두 클럭이
  같다」는 뜻이 아니다 — OS 보정과도 양립한다(6회차 R6-04).
- **보정이 필요 없다는 결론.** 「N표본 이내면 보정 불필요」 같은 문턱은
  **두지 않는다**(검토자가 승인하지 않음). 기울기와 1표본 환산값만 낸다.
- **다른 구성.** 다른 폰·인터페이스·표본율·경로로 넓히지 않는다.
- **절대 음향 지연.** 지연은 「표본 번호 좌표의 지연」이라 두 스트림의
  시작 시각 차이가 섞여 있다. 같은 epoch 안의 **변화**만 본다.

**첫 저녁 측정은 원자료 수집·방법 검증용이다.** 먼저 `trial` 로 장비·경로·
신호를 확인하고, 그다음 `record` 로 원자료를 모은다. 60분 출시 관문이나 모든
기기의 go/no-go 를 대신하지 않는다.

## 2. 구성

| 항목 | 값 |
|---|---|
| 출력 | UMC404HD, 스테레오 float 48 kHz, **양쪽(Both)에 같은 신호** |
| 신호 | 앱의 `SignalPlayer` 핑크 잡음, **반복 없는 연속 생성**(되감지 않음) — 반복 주기가 짧으면 상관 봉우리가 여럿 생긴다(6회차). seed 는 `SignalPlayer` 가 시각으로 정하므로 **같은 파형을 다시 만들 수는 없다** |
| 기준 | `TappedSink` 가 **실제로 쓰인 칸만** 평균해 `offerReference` |
| 입력 | 앱의 `MicSource`(화면과 같은 열기·가공 끄기), 내장 마이크로 **확인된 경로**(`onRouteConfirmed`), 모노 48 kHz → `offerMeasurement` |
| 엔진 | `TransferEngine` 기본값(FFT 8192 · 평균 16 · 최대 지연 24,000) |
| 배치 | 스피커와 폰 마이크 구멍 **몇 cm**, 테이프로 고정. 사람은 비켜선다 |
| 잴 간격 | **10초**. 지연 추정 창(32,768표본 = 0.68초)은 서로 겹치지 않는다. **그렇다고 관측이 독립이라는 뜻은 아니다** — 방·스피커의 느린 변화는 이어진다(4장 4) *(처음엔 「독립에 가깝다」 — 9회차 R9-04 로 고침)* |
| 길이 | 기본 30분 |

배치를 가까이 하는 까닭은 **온도에 따른 전파 지연 변화를 줄이려는 것**이지,
남는 것이 클럭뿐이라는 보증이 아니다(7회차). 클리핑과 스피커 자체의 시간
변화는 기록으로 본다.

## 3. 무엇을 기록하나 — 한 줄에 하나의 관측

`adb logcat -s ADRIFT` 로 남긴다. 줄마다:

| 필드 | 뜻 |
|---|---|
| `session` | 시험 한 번의 무작위 ID. **epoch 를 세션 ID 로 쓰지 않는다** — 엔진을 새로 만들면 0 부터다 |
| `kind` | `Measured` / `Busy` / `InsufficientData` / `RetentionExceeded` |
| `epoch`, `windowEnd` | 엔진이 같은 잠금에서 뜬 값. `windowEnd` 는 **exclusive end(개수)** |
| `lag`, `found`, `sharpness` | 지연 추정 원자료 |
| `mono` | 부른 시각(`SystemClock.elapsedRealtimeNanos`) — 분석 축이 아니라 참고 |
| `refCount`, `measCount` | 잠금 안에서 뜬 개수(까닭이 있는 결과일 때) |
| `underruns` | `AudioTrack.getUnderrunCount()` |
| `outErr`, `inErr` | 쓰기·읽기 오류 누계 |
| `outRoute` | 실제 출력 경로 id. 종류·이름·주소는 머리줄에 |
| `routeChanged` | 지난 관측 뒤로 경로가 바뀌었나 |
| `peak` | 지난 관측 뒤 입력 최대 절대값 — 클리핑(≥ 0.99) 확인용 |

머리줄에 설정(표본율·FFT·평균·최대 지연·잴 간격·세기·기기·OS 빌드)과
요청·실제 경로를 한 번 적는다. 끝에 구간마다 `SEG` 줄과 정한 결론을 적는다.

## 4. 판정 규칙 — **재기 전에 정한다**

`DriftLogAnalyzer`(dsp)가 아래를 그대로 한다. 사람이 손으로 자르지 않는다.

1. **`Measured` 이고 `found` 인 관측만 쓴다.** 나머지는 **세어서 보고**한다
   (버린 것을 숨기지 않는다).
2. **같은 `(session, epoch, windowEnd)` 는 하나로 센다** — 한쪽이 멈추면
   같은 창을 여러 번 다시 잰다(7회차 재현). 먼저 온 것을 남긴다.
3. **구간을 끊는 자리**: epoch 가 바뀜 · 경로가 바뀜 · `underruns`·
   `outErr`·`inErr` 가 늚 · `windowEnd` 가 늘지 않음(순서 어긋남).
   끊긴 자리 앞뒤를 **한 직선으로 잇지 않는다.**
4. **구간마다** `lag` 를 `windowEnd` 에 대해 최소제곱 직선으로 맞춘다.
   기울기 × 10⁶ = ppm. **기술 통계로만 적는다 — 불확도(구간)는 내지 않는다.**
   함께 **1표본 환산값**(구간 전체에서 지연이 1표본 변하는 기울기)을 적는다.
   크기를 가늠하려는 것이다. **검출 한계도 OLS 의 최소 눈금도 아니다** — 마지막
   관측 하나만 1표본 달라져도 OLS 는 그 값의 수십분의 1 만 움직이고, 초기 분수
   위상에 따라 아주 작은 참 기울기도 서로 다른 두 정수를 만든다(9회차 R9-04).
   *(처음엔 「그보다 작은 기울기는 가를 수 없다 — 산수다」 — 틀렸다)*

   > **측정 전에 고쳤다 (8회차 R8-01).** 처음에는 잔차로 표준오차를 내고
   > √(1/12) 를 바닥으로 깔아 **95% 구간**을 냈다. 검토자가 반례를 냈다 —
   > 참값 +0.008 ppm 은 30분에 0.7표본이라 정수로 내내 같은 값이고, 그러면
   > 「0 ± 0.0017 ppm」으로 **참값을 배제**한다(잡음 없는 분수 위상 200개에서
   > +0.02 ppm 도 31% 만 품음). 반올림 오차는 참값이 정하는 **규칙적인** 오차라
   > iid 바닥으로 덮이지 않고, 잔차가 이어지면(AR(1) 0.97) 구간이 실제보다
   > 좁아진다. 10초 간격만으로 관측이 독립이라고 할 근거도 없다. 검증된
   > 불확도 방법이 생기기 전까지 구간을 내지 않는다.
5. **쓸 수 있는 구간**: 관측 **20개 이상**, 길이 **10분 이상**
   (`windowEnd` 차이 ÷ 표본율).
6. **계단 의심**: 구간 안 어느 관측이든 직선에서 **4표본 넘게** 벗어나면
   그 구간은 「계단 의심」으로 표시하고 **결론에 쓰지 않는다.** 정수 양자화
   잔차는 ±0.5 안이다. 4 는 「사건 기록 없이 생긴 누락·삽입이나 반사음으로의
   봉우리 전환」을 잡으려는 값이고, 실측으로 정한 값이 아니다.
   **이것은 잔차 문턱이지 계단 높이 문턱이 아니다** — 구간 한가운데의
   8표본 계단은 직선이 반쯤 따라가 최대 잔차 3.97 로 문턱을 못 넘고
   「쓸 수 있는 구간」(0.139 ppm)으로 남았다(8회차 재현). 검출 한계다.
7. **결론의 말**: 쓸 수 있는 구간마다
   「이 구성에서 *T* 분 동안 최소제곱 기울기 *b* ppm (기술 통계). 구간 전체에서
   지연 1표본 변화 = *r* ppm (환산값 — 검출 한계도 신뢰구간도 아니다). 불확도는
   검증된 방법이 아직 없어 내지 않는다」. **조건 없이 늘 이 말이다.**
   *(처음엔 |b| < r 이면 「가를 수 없다」를 덧붙였다 — R9-04 로 거둠. 9회차 개정에서
   그 조건절이 남아 코드와 달랐다 — 10회차 R10-04 로 고침)*
   **유의성(「검출 못 함」·「밀렸다」)은 말하지 않는다** — 8회차 R8-01 로
   거뒀다. **그 이상은 말하지 않는다.**

### 계측 시험의 통과·실패 (6회차 R6-05, 8회차 R8-02·03·04 의 교훈)

시험은 **잰 값으로 통과·실패를 가르지 않는다.** 대신 **재지 못했으면
실패**다:

- **`-e mode trial|record` 와 `-e minutes` 를 반드시 준다.** 없거나 NaN·0·음수면
  실패 — 기본값 1분으로 돌며 자료 없이 통과하던 자리다(R8-04).
  `trial` 은 5분 이하, `record` 는 **11분 이상**. 첫 관측이 10초 뒤라 정확히
  10분이면 관측 폭이 9분 50초쯤이 되어 5번 규칙(10분 이상 구간)을 못 채운다(9회차).
- 실제 출력이 **고른 그 USB 기기**(종류·이름·주소)가 아니면 실패. 유선
  헤드폰·헤드셋은 USB 가 아니다(R8-03).
- 입력이 내장 마이크로 확인되지 않으면 실패. 머리줄에 **활성 마이크 조합**
  (`OpenedFormat.activeMics`)을 적는다 — 처음에 「기록할 수 없다」고 적었는데
  `MicSource` 가 이미 넘기고 있었다(R8-02). 그 정보도 안드로이드의 표기이지
  물리 위치의 증거는 아니다.
- **도는 동안 출력·입력 경로나 활성 마이크 조합이 한 번이라도 바뀌면 실패**
  — 이 판정은 `DriftSessionGuard`(app `transfer/DriftSession.kt`)가 하고 JVM
  시험이 지킨다. 9회차에서 세 틈이 드러났다(R9-01): ① 시작 때 조합을 몰랐으면
  그 빈 값을 영원한 기준으로 삼아 나중의 변경을 놓쳤다 → **마지막으로 알려진
  조합**을 따로 들고, 알려진 조합끼리 다르거나 **알던 조합을 잃으면** 무효.
  시작 때 몰랐던 것은 유효하되 그 한계를 `SESSION 한계` 줄로 적는다.
  ② 시작 확인을 읽은 뒤 변경 기록을 비웠다 → 기준 잡기와 감시 시작을 한 번에.
  ③ 마지막 관측 뒤의 출력 변경을 안 셌다 → 끝에서 출력 경로를 읽어 확정.
  구간만 끊고 넘어가면 바뀐 뒤 다른 입력에서 잰 구간이 채택된다(R8-02).
- `trial`: 지연을 찾은 **서로 다른 창**이 3개 미만이거나, 마지막 관측이 새 창으로
  나아가지 않았거나, 입출력 오류가 있으면 실패. **결론을 내지 않는다.** 3 은 동작
  확인이지 통계 기준이 아니다. *(처음엔 줄 수로 셌다 — 멈춘 스트림이 같은 창을
  여섯 번 다시 재도 통과했다, 9회차 R9-02)*
- `record`: 쓸 수 있는 구간이 하나도 없으면 실패.
- **판정을 먼저 확정하고 그다음에 적는다**(9회차 R9-03). 로그의 첫 판정 줄이
  `SESSION VALID`/`SESSION INVALID` 이고, 무효이거나 시운전이면 어느 구간도
  「채택」이라 적지 않는다. 길이 조건을 채운 것(`길이조건=true`)과 채택한 것을
  가른다. 마지막 줄은 `RESULT PASS`/`RESULT FAIL`.
- 시작 뒤의 모든 자원은 `try/finally` 로 놓는다. 출력 껍데기는 `play()` 가
  터지면 스스로 놓는다(R8-05).

## 5. 기록 → 분석 전체를 합성으로 먼저 통과시킨다

실기기 전에 **알려진 기울기**로 기록·분할·기울기까지 통과해야 한다(7회차 표의
「합성 승인 시험」).

| 합성 | 기대 |
|---|---|
| 0 / ±1 / ±20 ppm, 정수 양자화 + 흔들림 | 점추정이 참값 ±0.1 ppm 안 *(처음엔 「구간이 품는다」 — R8-01 로 고침)* |
| +0.008 ppm(특정 위상에서 30분 내내 같은 정수) | 구간을 내지 않는다. 1표본 환산값은 「검출 한계가 아니다」로 적는다 |
| 같은 창 중복 | 하나로 센다 |
| 사건이 적힌 128표본 누락 | 두 구간으로 끊긴다, 각 구간 기울기는 참값 |
| 사건 없는 128표본 누락 | 「계단 의심」 |
| epoch 바뀜 | 끊긴다 |
| 순서 어긋남 | 끊긴다 |
| **엔진을 통과한** ±100 ppm 시간 늘림 + 불규칙 콜백 | 점추정이 참값 ±2 ppm 안(1분 합성, 1표본 = 0.35 ppm) |

## 6. 남는 것 (이 설계가 못 닫는 것)

- **사건 없이 사라진 프레임**은 계단으로만 드러난다. 기울기만 조금 바꾸는
  작은 누락은 못 잡는다.
- **반사음으로의 봉우리 전환**도 계단으로만 드러난다 — 이 추정기는 직접음을
  가려내지 않는다.
- 10초 간격 관측끼리 **독립이라는 보장이 없다** — 그래서 불확도를 내지
  않는다(4장 4). 검증된 불확도 방법은 아직 없다.
- 구간 한가운데의 **작은 계단**(8표본 안팎)은 계단 의심에 안 걸릴 수 있다(4장 6).
- 원인(하드웨어/OS/큐)은 가리지 못한다(1장).
