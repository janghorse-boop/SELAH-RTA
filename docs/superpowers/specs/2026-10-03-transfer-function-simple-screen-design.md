# Transfer Function 간편 화면·배선 — 실험용 앱 연결 단계 설계

상태: **설계 5판 + 34회차 계약 반영. 34회차 판정 「조건부 구현 착수 수용」**(R34-01~03 을 채택하고 생산 코드·시험에 반영하는 조건, 구현 PR 을 다시 독립 검토). 코드는 아직 없다.
작성: 2026-10-03 · 기준 커밋: `main` 의 `eec8133`(PR #152 병합본) · 1판 `8b25e88` · 2판 `1668953` · 3판 `4c888a7` · 4판 `675ceb1`

> ## 이 단계는 **1차 MVP 출시 완료가 아니다**
>
> 지시서 32장의 1차 MVP 는 지연 + 클럭 드리프트 + 크기 + 코히런스 묶음이고, 35장의 60분 실기기
> 관문을 거쳐야 한다. 이 설계는 그 가운데 **크기·코히런스를 앱 화면에 「실험용 진단 표시」로
> 연결하는 단계**다. 클럭 드리프트는 **확인하지 않고 보정하지도 않는다** — 그 사실을 화면에 늘
> 적는다(8장). 판매 설명·UI 약속에 이 기능을 넣지 않는다(CLAUDE.md 5장).

## 30회차 지적과 이 판에서 바꾼 것

| 지적 | 바꾼 곳 |
|---|---|
| R30-01 High — 플레이어 수명주기·배타성 | **4장 신설**: 소리 주인 하나, 명시적 시작 단추, 시작 전 다른 주인 정지·포커스 획득, 중단 경로 목록, 느린 시작과 닫기의 직렬화, 복귀 시 자동 재생 금지, 시작 전 레벨 안내 |
| R30-02 High — 요청 경로 ≠ 실제 경로 | **3장 다시 씀**: 출력은 구조화된 실제 경로 보고(새 콜백)로 **지정 USB 기기에 실제로 붙었는지** 확인, 입력은 `confirmedFormat()` 의 확인된 내장 입력·48 kHz 만. 확인 전엔 게시하지 않음. 도중 변경·언더런·오류 처리. `OutputKind.Wired` 를 쓰지 않음. 계측 실측의 범위를 좁힘 |
| R30-03 Medium — 늦은 결과·반복 창 | **6장 신설**: 세대 번호 + 엔진 epoch + `windowEnd` 증가를 함께 볼 때만 게시. 새 창이 안 오면 곡선 지움. 연속 `RetentionExceeded` 는 멈추고 알림 |
| R30-04 Medium — 「측정 신뢰도 좋음」 과장 | **9장 다시 씀**: 「측정 신뢰도」를 없애고 **「표시 대역 코히런스 중앙값」 진단**으로 이름·뜻을 좁힘(대역·칸 수·빈 집합·안정화 중). 경고 우선순위, 클리핑은 **그 결과 창에 든 블록**으로 |
| R30-05 Medium — 비유한 값·선 끊김·분모 | **10장 신설**: 칸 단위 자료 계약 — 무효·비유한 칸에서 선분을 끊고, 분모는 표시 대역 3,410칸, 「그릴 칸 없음」 상태 |
| R30-06 Low — 기존 플레이어 설명 오류 | **3.1 고침**: 기존 플레이어는 **사용자의 출력 선택을 따른다**(`SignalOutputChoice.wantedKind` = `choice.kind`). 따로 갖는 까닭은 기준 탭·고정 신호·세션 수명주기 분리 |
| 13장 답 | 「못 찾음」 문장, 「찾음」·또렷함의 뜻 도움말(7장), 띠에 클럭 드리프트 미확인 연결(8장), 실기기 3번을 관찰 항목으로(11장) |

## 31회차 지적과 3판에서 바꾼 것

31회차: R30-04·06 닫힘, 8장 띠·KDoc 문구 수용, R30-01·02·03·05 부분 해소.

| 지적 | 바꾼 곳 |
|---|---|
| R31-01 High — UI null ≠ 실제 정지, 인계가 늦다 | **4장 다시 씀**: 앱의 기존 출력은 `CaptureViewModel` 의 **플레이어 하나**뿐임을 확인(마법사·FR 도 `vm.playSignal` 로 낸다). `SoundOwner` 를 **토큰 예약**으로 — 여는 쪽은 열기 전에 예약하고 **열기 직전에 다시 확인**, 놓는 쪽은 **`stop()` 반환 + `pendingCount == 0`** 뒤에만 놓는다. TF 는 먼저 예약을 시도하고, 기존 주인이 쥐고 있으면 정지를 부탁한 뒤 **놓임(=정리 완료 응답)을 기다린다**. 멈춤 요청을 받는 그 순간 게시를 막는다 |
| R31-02 Medium — 원시 통지가 세대까지 안 온다 | **3.3 다시 씀**: `MicSource.onRawRoutingNotice → SourceHooks(새 칸) → CaptureController → TF` 연결을 명시. **준비 구간과 측정 구간**을 「무장」 시점으로 가르고, 무장 뒤의 원시 통지는 값이 같아도 불연속으로. 통지 뒤에는 **새 확인 전까지 옛 확인을 쓰지 않는다**. 출력도 「처음 조회」와 「경로 사건」을 가른다(3.2). 입력 미확인에서 [시작] 의 동작을 하나로 |
| R31-03 Medium — 「연속 3번」이 안 찬다 | **6장 다시 씀**: 「다시 맞추기 시도 횟수」(성공 게시로만 0)로 정의. `InsufficientData`·`Busy` 는 횟수를 지우지 않는다. 「모으는 구간」과 「게시 뒤 구간」을 갈라 박자 세기를 정하고, 남겨 둔 곡선에는 「마지막 결과 n초 전」 |
| R31-04 Medium — 9장·10장 충돌 | **9장 우선순위·10장 다시 씀**: 「기준 유효 칸」·「그릴 크기 칸」·「그릴 코히런스 칸」을 따로. 크기만 없으면 코히런스는 남는다. 둘 다 없을 때의 상태를 따로 |
| 구현 노트(지적 수 밖) | **15장 신설**: ClipLedger 좌표·기록 유실 시 「모름」, USB 출력은 시작 전 이름을 보이고 세션 동안 고정, 3초는 단조 시각·멈춤을 막지 않음, 언더런 null 과 0 구별, 실제 인계·콜백을 가짜 입출력으로 시험 |

## 32회차 지적과 4판에서 바꾼 것 — **방향 전환**

32회차: R31-04 닫힘, R31-03 의 교대 반례 해결, 8장 띠·KDoc 유지. 30~32회차 High 셋(R30-01·R31-01·R32-01)은 **모두
두 플레이어 사이의 소유·인계와 얽혀 있었으므로**(그것만이 원인이라는 뜻은 아니다 — 33회차가 짚었듯 플레이어가
하나여도 정리 미완·취소된 작업의 정지·명령 생략이 남는다), 담당자 승인(2026-10-03 「진행」)으로 **TF 가 앱의 유일한
플레이어를 같이 쓰는 방향**으로 바꿨다.

| 지적 | 바꾼 곳 |
|---|---|
| R32-01 High — 대기 중 생산 작업, 같은 주인 교체 | **4.1** — 플레이어가 하나라 인계가 없다. TF 시작은 **늘** FR·마법사를 취소하고, 그 작업들의 신호 시작 자리에 `ensureActive()`. TF 세션 중에는 `playSignal` 입구에서(의도 번호를 올리기 전) 거절. 같은 주인의 세기·채널 교체는 기존 길 그대로(TF 세션 중엔 관문에 막힘) |
| R32-02 Medium — 열기 실패 자원 | **4.1·15장** — 4판에는 「정리 완료」에 기대는 인계가 없다. 열기 실패 자원은 기존 플레이어의 성질로 `unverified` 에 적고 따로 다룬다 |
| R32-03 Medium — 같은 경로 통지 뒤 확인 생략, 블록 세대 경합 | **3.3** — 경로 리스너가 **통지마다 새 스냅샷**(`onRouteSnapshot`)을 내고, 블록에 `captureId`·`blockSeq` 를 붙이며, 넣기·reset·무장·ClipLedger 를 **`TransferIngest` 한 자물쇠**로 |
| R32-04 Medium — 박자 표 누락 | **6.1** — 옛 결과 → Retention → Busy/부족 → 창 진행 없음 → 못 맞춤 → 게시 의 **순서식 표**, `lastObserved`/`lastPublished` 분리, epoch 마다 처음 값, 못 맞춤 10박자 |
| 그 밖 | 3.1·3.2 — 출력은 사용자 설정 「유선」 + 실제 USB 경로 확인. 4.2 — `nextTap` 으로 TF 재생에만 탭. 4.4 — `onTransferPlaybackEnded` 로 재생 끝을 받는다(UI 값으로 짐작하지 않음) |

## 33회차 지적과 5판에서 바꾼 것

33회차: 공유 플레이어 방향 수용(`SoundOwner` 를 되살리라는 뜻 아님), R32-04 반례 닫힘, V/M/C·띠·KDoc 유지.
R32-02(열기 실패 자원)는 **해결이 아니라 별도 미해결**로 남는다.

| 지적 | 바꾼 곳 |
|---|---|
| R33-01 High — 플레이어 하나여도 옛 재생이 덜 정리된 채 새 싱크를 연다(상한 2) | **4.3** — TF 시작 명령은 명령 실행자에서 옛 재생을 멈춘 뒤 **`pendingCount == 0` 이고 `failedReleaseCount == 0` 일 때만** TF 싱크를 연다. 100 ms 마다 최대 2초 다시 보고, 안 되면 열지 않고 세션을 끝낸다. 열기 실패 자원처럼 이 둘에 안 잡히는 것은 남은 위험(R32-02) |
| R33-02 Medium — 취소된 FR·마법사의 `finally` 가 새 TF 를 끈다 | **4.1** — 재생마다 **주인**(`SignalOwner`)을 적고, FR·마법사의 `finally` 는 **주인별 정지**(`stopSignalOwnedBy(owner)`) — 지금 재생의 주인이 자기일 때만 멈춘다. 사람의 정지·포커스·백그라운드·닫기는 지금처럼 **전체 정지** |
| R33-03 Medium — 명령 큐가 최신 것만 실행해 정지·끝 알림이 생략됨 | **4.4** — TF 세션의 끝을 **명령 실행에 기대지 않는다.** `signalIntent` 를 올리는 모든 길(정지·백그라운드·포커스·noisy·onCleared·다른 시작)에서 **주 스레드에서 그 자리에서** `endTransferSession(까닭)` — 게시 금지·무장 풀기가 그때 일어난다. 쓰기 오류(`onEnded`)는 생략되지 않는 `postAlways` 길로 같은 끝을 낸다. `onTransferPlaybackEnded` 는 물리적 정지의 **참고 소식**일 뿐 정확성에 쓰지 않는다 |
| R33-04 Medium — 읽었지만 아직 안 넘긴 블록이 경계를 지난다 | **3.3** — 블록 번호를 **읽기 전에 예약**(`readSeq`)하고, 스냅샷은 그 순간까지 **예약된** 번호를 적는다 — 읽는 중이던 블록도 경계 앞으로 간다. 「2초 모으니 몫이 작다」는 문장은 거둔다(재지 않았다) |
| R33-05 Low — 「10초 동안」 | **6.1** — 「못 맞춤 관측 10회」로 |
| 구현 조건 | **4.2** — `nextTap` 은 `try/finally` 로 비운다. 경로·탭 콜백은 임시 칸이 아니라 열 때 붙잡은 **불변 재생 세션**(세션 번호·세대)을 쓴다 |

## 34회차 판정과 채택한 계약

34회차: **조건부 구현 착수 수용**(Critical 0 · High 0 · Medium 2 · Low 1). 5판 그대로의 병합 승인은 아니며, 아래
계약을 설계·구현에 채택하면 별도 설계 회차는 필수가 아니고 **구현 PR 로 독립 재검토**를 받는다.
수용: R33-01 미완 출력 차단(실제 플레이어 대조 — 미완 중 opens 1, 해제 뒤 opens 2) · R33-03 즉시 논리 종료 ·
R33-04 읽기 전 예약 · R33-05 횟수 문구 · `nextTap` try/finally · R33-02 방향(R34-01 필수). R32-02 는 별도 미해결.

| 지적 | 채택한 계약 |
|---|---|
| R34-01 Medium — 대기 중인 TF 시작을 옛 `finally` 가 덮음 | **4.1** — `latestRequestOwner`(주 스레드, 큐에 넣기 전 갱신)로 주인별 정지를 먼저 거절, `activeOwner`(명령 실행자)는 물리 정지 직전 검사. 12장 「접수·실행 경계」 |
| R34-02 Medium — 열 때 세대가 아직 없음 | **4.2·4.4** — 열기 전 `attemptId`+`sessionId` 를 붙잡고 실제 세대와 이음. 비동기 끝은 `endTransferSession(expectedSessionId, …)`. 새 시작은 옛 끝 → 새 등록 → 제출, 자기 시작의 의도 증가는 세션 끝 규칙에서 뺌. 12장 「열기 전 번호」 |
| R34-03 Low — 남은 문구·옛 시험 요구 | **15장** 문구 고침, **12장** 「세션의 끝(논리)과 참고 소식」으로 범위를 맞춤 |

## 구현 계획 (34회차 조건)

1. **시험 먼저** — 12장의 R31~R34 반례 시험을 실제 `SignalPlayer`·`SerialCommands`·`CaptureViewModel` 명령 실행자에
   가짜 싱크·가짜 캡처를 붙여 쓴다. 지금 코드에서 **실패하는 것을 먼저 확인**한다.
2. **기존 플레이어 연결점** — `SignalOwner`·`latestRequestOwner`·`activeOwner`·`stopSignalOwnedBy` · FR/마법사 `finally` ·
   `ensureActive` · 2초 정리 조건 · `nextTap` · `attemptId` 표 · `endTransferSession`.
3. **입력 쪽** — `readSeq` 예약, `onRouteSnapshot`, `SourceHooks` 칸, `TransferIngest`·`ClipLedger`.
4. **출력 쪽** — `AudioTrackSink.onRouteState`(origin)·`underrunCount()`.
5. **상태·화면** — `TransferUiState`(6·9·10장 순수 함수), `TransferViewModel`, `SimpleTransferScreen`, 문, 문자열.
6. 각 단계마다 `--rerun-tasks` 로 전체 시험, 핵심 관문은 변이 시험. **구현 PR 하나**로 묶어 독립 재검토 →
   그 뒤 11장 실기기 확인(소리 — 담당자 시각).

## 3. 경로 — 요청이 아니라 **확인된 실제 경로**로 연다

### 3.1 TF 는 **기존 플레이어를 같이 쓴다** (4판에서 바꿈)

*(1판은 「기존 플레이어는 USB 로 잴 때 소리를 폰 스피커로 돌려 방향이 반대라 쓸 수 없다」고
적었다 — 틀렸다, R30-06.)* 지금 `CaptureViewModel` 의 플레이어는 **사용자의 출력 선택을 따른다**
(`meterSettings.signalOutput` → `SignalOutputChoice.wantedKind` 가 `choice.kind` 를 그대로 돌려줌).

*(2·3판은 TF 가 자기 플레이어를 따로 갖고 `SoundOwner` 로 두 플레이어 사이를 중재했다. 30~32회차의
High 지적이 모두 거기서 나왔다 — 플레이어가 둘이면 인계·정리 완료·늦은 시작·같은 주인의 교체·열기 실패
자원까지 새로 만들어야 했고, 회차마다 새 틈이 나왔다(R30-01·R31-01·R32-01·R32-02).)*

**4판은 TF 가 앱의 유일한 플레이어(`CaptureViewModel:769`)를 같이 쓴다.** 이 플레이어는 이미
오디오 포커스·백그라운드·명령 실행자(`SerialCommands`)·의도 번호(`signalIntent`)·정지 의도
(`lastSignalStopIntent`)·재생 세대(`playGeneration`)를 여러 회차 검토로 다듬어 두었다. TF 는 그 길을
그대로 쓰고, 두 가지만 더한다:

- **기준 탭**: 플레이어가 싱크를 여는 순간 그 재생이 TF 의 것이면 `TappedSink` 로 감싼다(4.2).
- **TF 세션 동안의 입구 관문**: 다른 쪽(도구의 신호·FR·마법사)의 `playSignal` 을 막는다(4.1).

기존 플레이어의 **출력 선택 규칙은 바꾸지 않는다.** 그래서 TF 는 사용자의 출력 선택이 USB 로 나갈 수
있는 「유선」일 때만 시작하고, **실제 경로가 USB 기기인지 확인**한다(3.2).

### 3.2 출력 — 지정한 USB 기기에 **실제로** 붙었는가

`AudioTrackSink` 는 `setPreferredDevice` 가 거절돼도 **다른 경로로 재생을 계속**한다
(`SignalSink.kt` 163~183행). 지금 보고(`onRoute`)는 화면용 **문자열**이고, `onRoute` 를 안 주면
리스너도 안 단다. 그래서:

- `AudioTrackSink` 에 **구조화된 경로 보고**를 하나 더한다 — `onRouteState: ((OutputRouteState) -> Unit)?`.
  `OutputRouteState(requestedKey, requestRejected, actualType, actualKey)`(`actual*` 은 모르면 null).
  기존 문자열 `onRoute` 는 그대로 둔다. 리스너는 둘 중 하나라도 있으면 단다.
  **언더런 수**도 읽게 한다(`underrunCount(): Int?`, 트랙이 없으면 null).
- **출력 고르기는 사용자 설정이 한다**(기존 규칙 그대로). TF 시작 조건은 출력 설정이
  「유선」(`OutputKind.Wired`)인 것. 아니면 시작하지 않고 「출력 설정을 유선(USB-C)으로 바꾼 뒤
  시작하십시오」. 「유선」은 3.5 잭도 받으므로 **그것만으로 USB 라 보지 않는다** — 아래 실제 경로 확인이
  가린다. 시작 **전**에 기존 규칙이 고를 기기의 이름을 화면에 보인다.
- **출력 확인** = `requestRejected == false` 이고 `actualType` 이 **USB 종류**(`TYPE_USB_DEVICE`·
  `TYPE_USB_HEADSET`·`TYPE_USB_ACCESSORY`)이고 `actualKey == requestedKey`
  (키는 종류·이름·주소 — id 는 다시 꽂으면 바뀐다, `sameOutput`). 3.5 잭으로 나가면 확인되지 않는다.
- `OutputRouteState` 에 **`origin: Initial | Event`** 를 싣는다 — 트랙을 연 직후 한 번 물어본 값(`Initial`)과
  `addOnRoutingChangedListener` 로 온 **경로 사건**(`Event`)을 가른다. 값이 같아 보여도 사건은 사건이다
  (늦게 처리된 A→B→A 를 「안 바뀜」으로 버리지 않으려는 것 — 계측에서 원시 통지를 따로 둔 까닭과 같다).
- 시작 뒤 **3초**(단조 시각) 안에 출력 확인이 안 되면 멈추고 「출력이 USB 로 가는지 확인하지 못했습니다」.
- **무장(3.3) 전**의 출력 사건은 준비 중의 일로 보고 확인만 다시 한다. **무장 뒤**의 출력 사건은
  값과 상관없이 불연속이다 — **즉시 멈추고 곡선을 지운다.** 저절로 다시 시작하지 않는다.
  앱의 큐(주 스레드 `Handler`)에 아직 들어오지 않은 플랫폼 사건은 이 보장 밖이다.
- 언더런 수가 늘면 그 구간은 버린다 — 엔진 `reset()`, 세대 +1, 「출력이 끊겨 다시 모읍니다」.
- 쓰기 오류로 플레이어가 끝나면(`onEnded`) 멈추고 그 까닭을 적는다.

**계측 실측의 범위**: 1·2판이 기대는 실측(`AcousticDriftRecordingTest`)은 `SignalPlayer`·`TappedSink`
는 같지만 출력이 **`CountingTrackSink`**(실제 경로·언더런을 읽는 시험 껍데기)였고, 원시 입력
통지까지 받았다. **제품 배선(`AudioTrackSink`)이 같은 조건을 채우는지는 아직 확인하지 않았다** —
11장의 실기기 확인과 12장의 시험이 따로 본다.

### 3.3 입력 — 확인된 내장 입력, 48 kHz, 모노

TF 는 입력을 스스로 바꾸지 않는다. **측정을 받는 조건**(모두 참일 때만):

1. 캡처가 돌고 있다.
2. `CaptureController.confirmedFormat()` 이 null 이 아니다 — 즉 `routeConfirmed == true`.
   **열기 직후의 요청한 `micKind` 만으로는 받지 않는다**(`MicSource.kt` 282~299행: 그때는 미확인).
3. 그 형식의 `micKind == BuiltIn`.
4. `sampleRate == 48000`, 측정 블록이 모노. 아니면 「입력이 48 kHz 가 아닙니다」로 멈춘다
   (엔진·기준이 48 kHz 다).

#### 사건이 TF 까지 오는 길 (R31-02 · R32-03)

지금은 원시 입력 통지가 앱에 **연결돼 있지 않다** — `CaptureController.SourceHooks` 에는
`onRoutingChanged`·`onRouteConfirmed`·`onCaptureEnded` 뿐이고, `CaptureViewModel`(698~705행)도 그것만
`MicSource` 에 넘긴다. 이 콜백들은 기기·주소·조합을 견줘 **같으면 생략**한다(`MicSource.kt` 410~448행).

*(3판은 원시 통지 뒤 「새 `onRouteConfirmed` 가 올 때까지 옛 확인을 쓰지 않는다」고 했다. 32회차가
실제 `MicSource` 코드로 보였다 — 같은 기기·주소·조합의 통지 뒤에는 새 확인이 **생략**되고(같은 통지:
raw 1 · 확인은 처음 1번뿐, 22→24→22: raw 2 · 확인 1번뿐), 3판대로면 3초 뒤 거짓으로 멈춘다.)*

그래서 **통지마다 새로 조회한 경로**를 넘긴다:

```
MicSource 의 경로 리스너 (주 스레드 Handler)
  ① onRawRoutingNotice()                 — 지금처럼 값을 견주기 전에
  ② onRouteSnapshot(RouteSnapshot)        — 새 칸. 같아도 늘 낸다
       RouteSnapshot(captureId, noticeSeq, format: OpenedFormat?, readSeqAtSnapshot)
       format = 그 자리에서 다시 조회한 경로(confirmRoute 와 같은 조회). 모르면 null
  ③ 기존 필터와 onRoutingChanged / onRouteConfirmed — 그대로(화면·보정 쪽은 바뀌지 않는다)
  → SourceHooks(새 칸 둘) → CaptureController → TF
```

- `captureId` 는 `MicSource` 의 열기마다 바뀌는 번호 — **옛 캡처의 늦은 스냅샷·블록**을 가린다.
- `noticeSeq` 는 통지마다 +1. `readSeqAtSnapshot` 은 스냅샷을 뜬 순간까지 캡처 스레드가 **예약한** 읽기 번호(아래).
- 구현에서 `confirmRoute` 의 부작용(`opened` 갱신)을 확인해, 한 통지에 조회가 겹치지 않게 한다.
- 「입력 사건」으로 보는 것: 원시 통지 · 입력 재열기(`captureId` 바뀜) · 읽기 오류(`onCaptureEnded`) ·
  캡처 중단. 조합 변경은 원시 통지에 실려 온다(스냅샷의 조합으로 본다).

#### 블록이 엔진에 들어가는 **한 경계** (R32-03)

*(3판은 「블록을 넘기기 직전에 지금 세대를 읽는다」였다. 32회차: 그러면 사건 전에 읽힌 옛 블록이 새
세대로 붙을 수 있고, 검사 → reset → offer 사이의 경합도 남는다.)*

- 캡처 스레드는 `AudioRecord.read` 를 **부르기 전에** 원자 값 `readSeq` 를 +1 해 번호를 **예약**하고, 그 읽기로 나온
  블록에 그 번호를 붙인다(열기마다 0 부터). 세대를 뒤늦게 붙이지 않고 **블록의 출처 번호**를 붙인다.
  *(4판은 「넘긴 블록」의 번호를 스냅샷에 적었다. 33회차: 이미 읽었지만 아직 안 넘긴 블록이 스냅샷 10 뒤에 11 을
  받아 새 무장에 들어간다. 예약 번호를 적으면 **읽는 중이던 블록**도 그 번호 이하라 경계 앞으로 간다.)*
- TF 쪽에 **`TransferIngest`** 하나를 두고, 다음을 **모두 같은 자물쇠 안에서** 한다:
  `offerReference`(기준 탭) · `offerMeasurement`(블록) · `ClipLedger` 기록 · 엔진 `reset()` · 무장 · 무장 풀기.
- 측정 블록을 받는 조건(자물쇠 안에서 한 번에 본다): 무장됨 · `captureId` 가 무장 때와 같음 ·
  `blockSeq > 무장 때의 readSeqAtSnapshot`. 기준 표본도 무장됨일 때만 받는다 — 그래서 `reset()` 뒤 두 흐름의
  표본 0 이 무장 뒤 첫 표본이 된다(엔진의 전제).
- 경계 밖: `AudioRecord` 안의 버퍼에 이미 들어 있던 표본(통지 전에 녹음됐지만 스냅샷 뒤의 읽기로 나오는 것)은
  블록 번호로 가를 수 없다 — **보장 밖이고 그 크기는 재지 않았다.** *(4판의 「2초를 새로 모으니 첫 블록 몫은
  작다」는 근거 없는 문장이라 거둔다 — R33-04.)*

#### 무장 — 준비와 측정의 경계

**무장** = 출력 확인(3.2) **그리고** 내장·48 kHz·모노인 **새 스냅샷**(또는 시작 때의 확인)이 둘 다 선 순간.
`TransferIngest` 자물쇠 안에서: 엔진 `reset()` · `ClipLedger` 비움 · `captureId`·`readSeqAtSnapshot` 기억 · 무장.
시작 때의 확인으로 무장할 때는 그 순간의 `readSeq` 를 경계로 삼는다.

- 무장 **전**의 통지(준비 중): 실패로 보지 않는다. 그 통지의 스냅샷으로 다시 판단한다(3초 상한 안에서).
- 무장 **뒤**의 입력 통지: 그 자리(주 스레드)에서 **무장을 풀고**(자물쇠 안) 게시 금지 · 곡선 지움. 같은
  통지의 스냅샷이 내장·48 kHz·모노면 **곧바로 다시 무장**한다(새 `readSeqAtSnapshot` 으로, 소리는 계속).
  스냅샷이 null 이거나 내장이 아니면 3초 안에 다음 통지의 스냅샷을 기다리고, 없으면 멈춘다.
- 무장 뒤의 출력 사건: 3.2 대로 멈춘다(출력은 다시 무장하지 않는다 — 소리가 다른 데로 났을 수 있다).
- 스냅샷 없이 블록만 계속 오는 경우(통지가 없음)는 무장이 그대로다 — 앱 큐에 들어오지 않은 플랫폼
  사건은 보장 밖.

| 입력 상태 | 화면 |
|---|---|
| 확인된 내장 입력 · 48 kHz | 잰다 |
| 확인 전 | 「입력 확인 중」 — **[시작] 을 눌러도 소리를 내지 않는다.** 확인되면 단추가 「다시 눌러 시작」으로 바뀐다. 저절로 이어서 시작하지 않는다 |
| 내장이 아님(USB 인터페이스·USB 직결 마이크 등) | 「이번 실험용 연결은 폰 마이크 입력만 씁니다. 입력을 폰 마이크로 바꾼 뒤 시작하십시오」 — **시작하지 않는다(소리 없음)** |
| 48 kHz 가 아님 | 「입력이 48 kHz 가 아닙니다」 — 시작하지 않는다 |
| 캡처 멈춤 | 「측정을 시작한 뒤 시작하십시오」 — 시작하지 않는다 |

「폰 마이크 입력만」은 **연결 범위**를 말한다. 마이크의 우열이 아니다(CLAUDE.md 6장).
「간편」은 승인된 연결 모드 이름이다.

## 4. 소리와 수명주기 — 기존 플레이어 하나로 (R30-01 · R31-01 · R32-01 · R32-02)

### 4.1 소리를 내는 플레이어는 앱에 **하나**다

코드로 확인한 사실: 앱에서 `SignalPlayer` 를 만드는 곳은 `CaptureViewModel`(769행) 하나뿐이다. 도구의
테스트 신호·FR 측정(배경 뒤 `playSignal(Pink)`, 1352행)·교정 마법사(`WizardCaptureBridge.playSignal` →
`vm.playSignal`)가 **모두 그 플레이어로** 낸다. 4판은 TF 도 그 플레이어로 낸다. 그래서 **두 플레이어
사이의 인계가 없다** — 2·3판의 `SoundOwner`·토큰·정리 완료 응답은 **없앤다.**

*(3판의 `SoundOwner` 는 「`stop()` 반환 + `pendingCount == 0` 뒤에만 놓는다」였다. 32회차가 실제
`SignalPlayer` 와 가짜 싱크로 보였다 — 열기가 실패하거나 열기 중 예외가 나면 둘 다 채워도 가짜 자원이
남는다(R32-02). 4판부터는 그 조건을 「인계 완료」로 쓰지 않는다. 다만 열기 실패 자원은 **해결된 것이 아니라
별도 미해결**이다 — 남은 자원이 출력 경로에 영향을 주면 TF 결과에도 닿을 수 있으므로 「TF 와 무관」이라 하지
않는다. `docs/unverified.md` 3-5 에 적고 따로 고친다(4.3 의 시작 조건이 잡지 못하는 남은 위험).)*

**TF 세션** = TF 화면의 [시작] 부터 정리(4.4) 끝까지. `CaptureViewModel` 이 `transferSession: Long`
(0 = 없음)을 주 스레드에서 쥔다.

**입구 관문** — `playSignal(...)` 의 맨 앞(주 스레드, `signalIntent` 를 올리기 **전**):
TF 세션 중이면 TF 가 부른 것이 아닌 요청은 **거절**하고 「Transfer Function 이 소리를 내는 중입니다」를
알린다. 의도 번호를 올리지 않으므로 TF 의 재생을 덮지 못한다. 명령 실행자에서 열기 직전에도 「이 요청의
세션 번호 = 지금 세션」을 다시 본다.

**늦게 깨어나는 생산 작업** (R32-01): 플레이어가 비어 있어도 **소리 없이 기다리는 작업**이 있을 수
있다 — 배경을 재는 FR(1286행 `responseJob`), 마법사 작업. 그래서:

- TF [시작] 은 **언제나** `cancelResponse()` 와 `wizard.stopWork()` 를 먼저 부른다(3판처럼 「예약이
  성공하면 건너뛴다」가 없다).
- FR·마법사가 소리를 여는 자리는 **그 작업이 아직 살아 있을 때만** `playSignal` 을 부른다
  (`coroutineContext.ensureActive()` — FR 1352행, 마법사 `WizardWork` 의 신호 시작 자리). 둘 다
  `viewModelScope`(주 스레드)에서 돌고 취소도 주 스레드에서 하므로, 취소된 작업은 다음 재개에서 그 줄에
  닿지 못한다. 그래도 그 줄에 명시적 검사를 둔다 — TF 를 빨리 닫아 관문이 열린 뒤에도 취소된 작업은
  소리를 내지 못한다.
- **주인별 정지** (R33-02): 취소된 FR·마법사의 `finally` 는 지금 「신호가 나고 있으면 `stopSignal()`」이다
  (FR 1392행, `WizardCoordinator` 305·526행) — **전체 정지**라서, TF 시작이 그 작업을 취소한 **뒤에** 돌면 막 연
  TF 재생을 끈다(33회차가 실제 `WizardWork`·`SerialCommands` 로 재현: `executed=[stop]`). 그래서 재생마다
  **주인**을 적는다 — `SignalOwner = User | Response(jobId) | Wizard(workId) | Transfer(sessionId)`.
  주인은 **두 자리**에 적는다 (R34-01):
  - **`latestRequestOwner`**(주 스레드) — **마지막으로 받은 요청**의 주인. `playSignal`·`playTransferSignal` 이 요청을
    받는 순간, **큐에 넣기 전에** 갱신한다. 그래서 TF 시작이 큐에서 기다리는 동안에도 값은 이미 `Transfer` 다.
  - **`activeOwner`**(명령 실행자) — **실제로 재생 중인** 재생의 주인. 싱크를 연 뒤 갱신.
  FR·마법사의 `finally` 와 단계 사이의 끄기는 **`stopSignalOwnedBy(owner)`** 를 부른다:
  1. 주 스레드에서 **`latestRequestOwner != owner` 이면 거절**(아무것도 안 함) — 이미 다른 주인의 요청(대기 중인 TF
     시작 포함)이 접수됐다. *(33회차 5판은 `activeOwner` 만 봤다 — TF 시작이 큐에서 기다리는 동안 그것은 아직
     Response/Wizard 라 옛 `finally` 의 정지가 새 TF 의도를 덮었다. 34회차 재현: `actions=[old-stop]`, transfer 0.
     대조 모형 `actions=[TF-start]`.)*
  2. 같으면 정지 의도를 올리고 명령 실행자에 정지를 넣는다.
  3. 명령 실행자에서 **물리적으로 멈추기 직전** `activeOwner == owner` 이고 그 사이 더 새 의도가 없을 때만 멈춘다.
  사람의 정지 단추·포커스 손실·noisy·백그라운드·`onCleared` 는 지금처럼 **전체 정지**다.
- 그 밖의 `playSignal` 호출(세기·채널·주파수 바꾸기, 1714~1760행)은 **지금 재생 중인 신호를 다시 트는**
  것이다. TF 세션 중에는 관문에 막히고, TF 가 끝난 뒤에는 TF 가 이미 소리를 멈췄으므로
  (`playingSignal == null`) 다시 틀 대상이 없다.

### 4.2 기준 탭 — 그 재생이 TF 의 것일 때만

기존 플레이어의 `openSink` 는 싱크를 **열 때마다** 불린다(`SignalPlayer.start` 266행, 명령 실행자 안).
명령 실행자 전용 칸 `nextTap: ReferenceTap?` 를 두고:

- TF 의 시작 명령은 `startSignalOnCommandThread` 에서 **`nextTap = 이 재생의 탭; try { player.start() } finally
  { nextTap = null }`**. 열기 중 예외가 나도 탭이 다음 일반 재생에 남지 않는다(33회차: 평문 대입이면 다음 일반
  싱크까지 탭이 남음 `[9,9]`).
- `openSink` 는 열 때 `nextTap` 을 **한 번 읽어 지역 값으로 붙잡고**, `val base = AudioTrackSink(... onRouteState =
  { st -> route(session, st) } ...)`; 탭이 있으면 `TappedSink(base, tap)`.
- **불변 재생 세션 — 열기 전에 만든 번호로** (R34-02): `openSink` 가 불릴 때 새 재생의 `playGeneration` 은 **아직
  발급되지 않았다**(34회차 실제 `SignalPlayer`: 붙잡은 값 0, 돌려받은 세대 1). 그래서 콜백은 세대가 아니라
  **열기 전에 정해지는 번호**를 붙잡는다 — `PlaybackSession(sessionId, attemptId)`. `attemptId` 는 `playTransferSignal`
  이 요청을 받을 때 주 스레드에서 발급하는 단조 번호(시작 요청의 의도 번호와 함께 명령으로 넘긴다).
  `player.start()` 가 돌려준 실제 세대는 명령 실행자에서 `attemptId → playGeneration` 으로 **잇는다**. `onEnded(generation,
  …)` 는 그 표로 `attemptId`·`sessionId` 를 찾는다. 나중에 바뀌는 칸을 읽지 않으므로 늦게 온 경로 보고·탭 표본·
  끝 소식이 어느 재생·어느 세션의 것인지 늘 가려진다.
- 탭은 `TransferIngest.offerReference(session, …)` 로 넘긴다 — 세션이 지금 세션이고 무장됐을 때만 받는다(3.3).
  끝난 세션의 늦은 표본은 버려진다.
- **TF 시작은 늘 새로 연다** — `startSignalOnCommandThread` 의 「주파수만 바뀌었으면 다시 열지 않는다」
  지름길은 `Custom` 신호에만 걸리므로 핑크에는 해당하지 않지만, TF 요청에는 명시적으로 지름길을 쓰지 않게
  한다. 그래야 탭이 붙은 새 싱크가 열린다.
- 신호는 **핑크 · 양쪽 · 0.2** 고정. TF 는 `playSignal` 대신 `playTransferSignal(sessionId)` 를 부른다 —
  사용자의 세기·채널 설정을 읽지 않고 이 값으로 만든 `SignalRequest` 로 같은 명령 실행자의 정규 길
  (포커스 획득 포함)을 탄다.

### 4.3 시작 — 사람이 누를 때만

1. 3.3 입력 조건 — 캡처 중·확인됨(그 뒤 사건 없음)·내장·48 kHz·모노. 아니면 그 상태만 적고 끝(소리 없음).
2. 출력 설정 = 「유선」(3.2). 아니면 「출력 설정을 유선(USB-C)으로 바꾼 뒤 시작하십시오」. 기존 규칙이 고를
   기기 이름을 시작 **전**에 보인다.
3. `cancelResponse()` · `wizard.stopWork()` — 늘. 그 작업들의 `finally` 는 주인별 정지라 TF 재생을 끄지 못한다(4.1).
4. `transferSession = 새 번호` · `vm.playTransferSignal(sessionId)` — 그 안에서 `signalIntent` 를 올리고 명령
   실행자에 시작을 넣는다.
5. **명령 실행자에서**(R33-01): 옛 재생이 있으면 정규 길대로 멈춘다(`player.stop()`). 그 뒤
   **`player.pendingCount == 0` 이고 `player.failedReleaseCount == 0`** 일 때만 다음으로 간다. 아니면 100 ms 마다
   최대 2초(단조 시각) 다시 본다 — 이 기다림은 의도 번호가 바뀌면(멈춤·닫기) 즉시 끝난다. 2초 뒤에도 남으면
   **TF 싱크를 열지 않고** 세션을 끝낸다 「이전 소리 정리가 끝나지 않아 시작하지 못했습니다」. *(33회차: 플레이어가
   하나여도 `SignalPlayer` 는 남은 재생이 상한 2 미만이면 다음 싱크를 연다 — `opens=2, pending=1,
   oldReleased=false` 재현.)* 열기 실패 자원처럼 이 두 수에 안 잡히는 것은 남은 위험이다(R32-02, unverified 3-5).
6. 포커스 획득(기존 길 — 거절이면 「다른 앱이 소리를 쓰고 있어 …」로 끝) → 탭을 붙여 연다(4.2).
7. 출력 확인(3.2, 3초)과 입력 스냅샷으로 **무장**(3.3).

**시작 전 레벨 안내**(지시서 27장): 시작 단추 옆에 「스피커에서 핑크 잡음이 납니다. 스피커 볼륨을 낮춘 뒤
시작하고 천천히 올리십시오. 세기 0.2 는 디지털 진폭이며 실제 음압의 안전을 보장하지 않습니다」.

### 4.4 멈춤 — 모든 길이 같은 정리로 간다

중단 경로: [멈춤] · 닫기·Back · 화면 이탈 · `ON_STOP` · `onCleared` · 포커스 손실(일시·덕) · 이어폰 뽑힘
(`noisy`) · 출력 확인 실패·무장 뒤 출력 사건 · 쓰기 오류(`onEnded`) · 입력 조건 깨짐(다시 무장 실패) ·
6장의 멈춤 조건.

#### 세션의 끝은 명령 실행에 기대지 않는다 (R33-03)

*(4판은 「정지 명령을 줄에 세운 뒤 세션을 놓으면 그 뒤 `playSignal` 은 정지 다음에 돈다」, 「재생 끝은 명령
실행자의 `onTransferPlaybackEnded`」였다. 33회차: `SerialCommands.post` 는 차례대로 다 돌리지 않고 **최신 명령만**
돌린다 — TF 정지 → 세션 0 → 일반 시작이면 정지와 그 안의 끝 알림이 생략됐다(`events=[regular-start]`).
포커스 손실을 물리 정지 완료로만 알면 그 사이 게시될 수도 있다.)*

- **논리적 끝 = 주 스레드에서 그 자리**: `CaptureViewModel` 에서 `signalIntent` 를 올리는 **모든 길** —
  `stopSignal()`(정지 단추·포커스 손실·덕·noisy 가 모이는 곳) · `onBackground()` · `onCleared` · 다른 주인의 시작
  (TF 세션 중엔 관문에 막히지만, 세션이 막 끝나는 경계에서도) · TF 자신의 멈춤 — 에서, TF 세션이 살아 있으면
  **그 줄에서 곧바로** `endTransferSession(까닭)` 을 부른다. 그 안에서: TF 세대 +1 · `TransferIngest` 무장 풀기 ·
  게시 금지 · 곡선 지움 · `transferSession = 0`. 명령이 생략되든 늦든 **TF 쪽 끝은 이미 났다.**
- **쓰기 오류**(`onEnded`)는 생략되지 않는 `postAlways` 길로 오고, 그 재생이 TF 세션의 것이면 같은 끝을 주
  스레드로 넘긴다. **비동기로 오는 끝은 모두 대상 세션을 지닌다** (R34-02): `endTransferSession(expectedSessionId,
  까닭)` 은 **`expectedSessionId == transferSession` 일 때만** 끝낸다. 세션 A 의 늦은 실패·`onEnded` 가 이미 시작한
  세션 B 를 끝내지 못한다. (주 스레드에서 의도 번호를 올리는 자리에서 부르는 끝은 그 순간의 세션을 넘긴다.)
- **새 TF 시작의 차례** (R34-02): `playTransferSignal(newSessionId)` 은 주 스레드에서 ① 옛 세션이 있으면
  `endTransferSession(oldSessionId, "새 시작")` ② `transferSession = newSessionId` 등록, `latestRequestOwner =
  Transfer(newSessionId)`, `attemptId` 발급 ③ `signalIntent` 증가와 제출. **③의 의도 번호 증가는 자기 시작이므로
  「의도 번호를 올리는 모든 길에서 세션을 끝낸다」 규칙에서 빠진다** — 그 규칙이 막 등록한 새 세션을 지우지 않게,
  `playTransferSignal` 안의 증가에만 「이 세션의 시작」 표시를 단다.
- **TF 시작이 생략·교체되는 경우**: TF 시작 명령이 더 새 명령에 덮여 안 돌았다면, 그 새 명령을 만든 길이 이미
  위의 논리적 끝을 냈다(의도 번호를 올린 그 자리). 시작 명령이 돌았는데 2초 정리 조건·포커스·열기에서 실패하면
  명령 실행자가 실패 까닭을 주 스레드로 넘겨 `endTransferSession` 을 부른다.
- **물리적 정리**(플레이어 정지·포커스 놓기)는 지금처럼 기존 명령 실행자가 한다. 생략된 정지는 뒤따른 명령의
  정규 길이 옛 재생을 정리한다(기존 동작). `onTransferPlaybackEnded` 는 **참고 소식**으로만 두고 정확성에 쓰지
  않는다.
- **앞으로 돌아와도 저절로 다시 틀지 않는다.**

### 4.5 느린 시작과 닫기가 겹칠 때

기존 플레이어가 이미 데인 자리(SRLR-01·02·04, SRLRO-01)를 그대로 쓴다: 시작·정지는 같은 명령 실행자에서
차례로 돌고, 늦게 끝난 시작은 의도 번호(`signalIsCurrent`)가 가리며, 정지 의도가 지름길을 막는다. TF 가
더하는 것은 세션 번호와 주인 — 늦게 열린 재생의 탭 표본·경로 보고는 붙잡은 재생 세션이 지금과 다르면 버린다.
**기존 명령 실행자의 「최신 것만 실행」 규칙은 바꾸지 않는다** — TF 의 정확성이 그 규칙에 기대지 않게 했다.

## 5. 재는 박자

열려 있고 소리가 나는 동안 **1초마다** `measureOutcome()` — `Dispatchers.Default` 의 코루틴 하나.
엔진은 재진입을 `Busy` 로 막는다. 오디오 콜백(`onBlock`, `TappedSink`)은 `offer*` 만 한다.

## 6. 결과를 게시하는 규칙 (R30-03)

엔진은 `reset()` 이 이미 시작된 계산을 취소하지 않는다(`TransferEngine.kt` 242~245행) — 옛 epoch
결과가 나올 수 있다. 또 **새 표본이 없어도 같은 창을 다시 잰다**(30회차 실행: 두 번 다 `found=true`,
같은 `windowEnd`). 그래서 결과를 게시하는 조건은 **모두**:

1. 재기 시작할 때 잡은 **TF 세대**가 지금 세대와 같다.
2. `result.epoch` 가 지금 엔진 epoch 와 같다.
3. `result.windowEnd` 가 **마지막으로 게시한 `windowEnd` 보다 크다.**
4. 입력·출력 확인이 그대로다(3장).

### 6.1 박자 세기 — 정해진 순서로 한 번에 하나 (R31-03 · R32-04)

*(3판의 표는 「모으는 구간의 `found=false`」가 `gatherTicks` 를 올리지 않아 첫 게시 없는 100박자에도 0 이었고,
「같은 창의 `found=false`」가 두 줄에 걸쳐 `staleTicks=0` 으로 읽힐 수 있었다 — R32-04.)*

**상태**(epoch 마다 새로 시작 — `reset()`·무장·다시 맞추기 때 모두 처음 값으로):
`lastObservedWindowEnd = −1`(마지막으로 **본** 창, 맞춤 여부와 무관) · `lastPublishedWindowEnd = −1` ·
`phase = 모으는 중` · `gatherTicks = 0` · `staleTicks = 0` · `notFoundTicks = 0`.
`recoveryAttempts` 는 epoch 가 아니라 **세션**의 값이다(6.2).

**한 박자는 아래 순서로 판정한다** — 위에서 걸리면 아래로 내려가지 않는다:

| 순서 | 조건 | 처리 |
|---|---|---|
| 1 | 옛 세션·옛 TF 세대·옛 epoch 결과 | **버림. 아무것도 세지 않는다** |
| 2 | `RetentionExceeded` | 6.2 다시 맞추기 |
| 3 | `Busy` · `InsufficientData` | 모으는 중: `gatherTicks+1` / 게시 뒤: `staleTicks+1` |
| 4 | `Measured` 이고 `windowEnd ≤ lastObservedWindowEnd` (창이 나아가지 않음 — `found` 와 상관없이) | 모으는 중: `gatherTicks+1` / 게시 뒤: `staleTicks+1` |
| 5 | `Measured`, 창이 나아감, `found=false` | `lastObservedWindowEnd = windowEnd` · 곡선 지움 · 「기준과 측정의 맞춤을 찾지 못했습니다」 · `notFoundTicks+1` · `staleTicks=0`(자료는 흐른다) · 모으는 중이면 `gatherTicks+1` |
| 6 | `Measured`, 창이 나아감, `found=true`, 6장 1~4 참 | `lastObservedWindowEnd = lastPublishedWindowEnd = windowEnd` · **게시** · `phase = 게시 뒤` · `gatherTicks = staleTicks = notFoundTicks = 0` · `recoveryAttempts = 0` |

**멈추거나 지우는 문턱**(운영값):

- 모으는 중 `gatherTicks = 10`(약 10초 — 첫 결과에 필요한 약 2초의 다섯 배) → 멈춤 「자료가 모이지 않습니다」.
  5번(못 맞춤)도 여기에 센다 — 그래서 맞춤을 한 번도 못 찾은 채 10박자면 멈춘다.
- 게시 뒤 `staleTicks` 1~2 → 남은 곡선에 「마지막 결과 n초 전」. **3** → 곡선 지움 「새 자료가 들어오지
  않습니다 — 입력이나 출력이 멈췄을 수 있습니다」(소리는 계속, 다음 게시가 오면 다시 그린다).
- `notFoundTicks = 10`(못 맞춤 **관측 10회** — Busy 등이 사이에 끼면 10초보다 길다. 게시가 끼면 0) → 멈춤
  「기준과 측정의 맞춤을 연달아 10번 찾지 못했습니다」. *(4판은 「10초 동안」 — 횟수를 시간으로 적었다, R33-05)*

### 6.2 다시 맞추기 — 시도 횟수로 센다 (R31-03)

*(2판의 「3번 연속」은 `InsufficientData → RetentionExceeded → reset` 이 되풀이되는 경우 연속 수가 1
에서 끝나 영원히 차지 않았다 — 31회차 합성 실행.)*

`RetentionExceeded` 가 오면: `recoveryAttempts+1` · `TransferIngest` 자물쇠 안에서 엔진 `reset()`(새 epoch·새
좌표)·`ClipLedger` 비움 · **6.1 의 epoch 상태를 모두 처음 값으로**(모으는 중, 두 창 기준 −1) · 곡선 지움 ·
「한쪽 흐름이 앞서 새 구간으로 다시 모읍니다」.

- `recoveryAttempts` 는 **게시에 성공했을 때만** 0 이 된다. `InsufficientData`·`Busy`·못 맞춤·같은 창은
  지우지 않는다.
- **3** 에 이르면 멈추고 「흐름을 다시 맞추지 못했습니다」 — 되풀이되는 reset 을 정상 복구처럼 숨기지
  않는다.
- 사람이 다시 [시작] 하면 새 세션이다 — 모든 셈이 0.
- `recoveryAttempts` 와 엔진 epoch 는 다른 값이다(epoch 는 reset 마다, 시도 횟수는 위 규칙대로).

3초·3박자·3회·10박자는 **운영값**이다. 경로·통계 정확성의 문턱이 아니다.

**곡선을 지우는 때**: 못 맞춤 · 새 자료 없음(3박자) · 입력/출력 확인 깨짐 · 캡처 중단 · `reset()` ·
출력 오류 · 멈춤 요청. **지난 곡선을 「지금 잰 것」처럼 남기지 않는다.**

## 7. 지연은 숫자로 보이지 않는다

엔진의 `delay.samples` 는 **표본 번호 좌표의 지연**이다 — 두 스트림의 시작 시각 차이가 섞인다(R6-01).
오늘 같은 배치(0.4 m)에서 세션마다 5,605 · 6,044 · 6,458 · 7,190 · 10,341 표본으로 달랐다.

화면은 「기준 맞춤: 찾음 / 못 찾음」만 보인다. 못 찾음의 문장은 **「기준과 측정의 맞춤을 찾지
못했습니다」** — 무음을 단정하지 않는다. [고급] 도움말:

- 「찾음」은 탐색 범위(0~24,000표본) 안에서 상관 봉우리가 조건(또렷함 ≥ 2.0)을 넘었다는 뜻이다.
  직접음·음향 전파 시간·클럭 고정을 확인한 것이 아니다.
- 또렷함은 주 봉우리와, 그 둘레(±8표본)를 뺀 다음 봉우리의 비다. **확률이 아니다.**
- 같은 세션 안에서도 맞춤 값이 수 표본 오르내렸다(원인 모름). 크기에 주는 영향은 재지 않았다.

음향 지연을 보이려면 두 스트림의 시작 시각 차이를 따로 재야 한다. `AudioTimestamp` 를 더한다고
그 문제가 다 풀린다고 약속하지 않는다 — 별도 설계다.

## 8. 시간축 미검증 — 실험용 진단 표시 (R6-02 계약)

30회차 판정: **조건을 보완한 B 를 실험용 표시로 수용**, R6-02 종결이 제품 표시를 승인한 것으로
읽지 않는다. 그래서:

- 곡선 위에 **지울 수 없는 띠**: 「⚠ 실험용 진단 표시 · 시간축 미검증 · 클럭 드리프트 미확인·보정
  안 함 · 상대 비교 — 정상 측정 곡선이 아니며 상대 비교의 정확도도 보장하지 않습니다」.
- 띠는 `timebase` 에서 나온다. **`Verified` 가 되어도 다른 경고(입력·출력·넘침·유효 칸)는 따로
  남는다** — 띠 하나가 사라진다고 모든 경고가 사라지지 않는다. 그리고 「실험용 진단 표시 ·
  클럭 드리프트 보정 안 함」 부분은 이번 단계에서는 `Verified` 와 상관없이 남긴다(앱이 `Verified` 를
  거는 길도 아직 없다).
- `TransferEngine` KDoc 의 소비 계약 문장을 이렇게 고친다:
  「`timebase` 가 `Verified` 가 아닌 결과를 정상·검증된 측정 곡선으로 게시하지 않는다. **진단용으로
  보이려면** 같은 화면에 미검증·클럭 드리프트 미확인임을 밝히는 경고를 결과와 함께 늘 둔다. 이렇게
  보인 결과는 정상 측정도, 상대 비교의 정확도도 뜻하지 않는다.」
- C(타임스탬프 문턱으로 `Verified` 걸기)는 하지 않는다. A(숨김)는 검증 방법이 생길 때까지의 정상
  선택이기도 하다 — 이번에는 **실험용**이라 밝히고 B 로 간다.

## 9. 코히런스 진단 — 「측정 신뢰도」를 쓰지 않는다 (R30-04)

1판의 「측정 신뢰도 ● 좋음/보통/낮음」을 **없앤다**. 30회차 반례: 전체 유효 칸 중앙값 0.99 인데
20 Hz~20 kHz 표시 대역 중앙값은 0.10(3,410칸 중 1,997칸이 0.10). 전체 요약으로 「좋음」을 말하면
과장이다. 또 시간축이 늘 미검증인데 「좋음」이 붙으면 그것을 덮는 말이 된다.

대신 **「코히런스 중앙값(표시 대역)」** 진단 한 줄:

- 대상: 표시 대역 20 Hz~20 kHz 의 칸(k=4…3413, 3,410칸) 가운데 `valid` 이고 코히런스가 유한한 칸.
- 보이는 것: 중앙값 숫자 + 「유효 n / 3,410칸」.
- 코히런스 표시가 숨김(유효 평균 1~7)이면 「— (평균이 모자람)」, 안정화 중(8~15)이면 숫자 옆에
  「안정화 중」. 지금 기본 엔진은 늘 16 이다.
- 이 집합이 비면(그릴 코히런스 칸 0) 「코히런스 표시 가능한 칸 없음」. **크기 칸의 유무와 상관없다**(10장).
- **색이나 좋음/나쁨 말을 붙이지 않는다.** 0.9/0.7 같은 문턱도 이번 화면에 쓰지 않는다 — 실측으로
  정한 값이 없다. 높은 코히런스가 시간축 검증이나 전체 품질을 대신하지 않는다.
- 낮은 코히런스의 원인을 적지 않는다.

**경고 우선순위**(위가 이기면 아래는 보이지 않는다):

1. 입력·출력 확인 깨짐 / 캡처 중단 / 출력 오류 → **두 그래프 모두 없음**, 그 까닭만
2. 못 맞춤 / 새 자료 없음 / 흐름 다시 맞추는 중 / 모으는 중 → **두 그래프 모두 없음**
3. **기준 유효 칸 없음**(표시 대역에 `valid` 칸이 0) → 두 그래프 모두 없음, 「기준이 약해 그릴 칸이 없습니다」
4. 결과가 있을 때 — **그래프마다 따로**(10장): 크기 그래프의 상태와 코히런스 그래프의 상태를 각자
   보이고, 둘 다 그릴 칸이 없으면 「그릴 수 있는 칸이 없습니다」와 이유별 수
5. 함께 붙는 것: **입력 넘침(이 결과)** · 실험용·미검증 띠(늘)

*(2판은 3순위를 「그릴 크기 칸 0 → 유효 칸 없음 → 곡선 없음」으로 두어, 10장의 「크기가 −∞ 여도
코히런스는 그린다」와 부딪혔다 — R31-04)*

**클리핑은 그 결과 창에 든 블록으로 판정한다.** 결과의 평균 창은 `windowEnd` 앞 69,632표본
(약 1.45초)이다. 1판의 「지난 1초」로는 창 앞쪽 약 0.45초의 넘침을 놓친다. 그래서 TF 는 측정 블록마다
(`reset` 뒤 누적 표본 번호로) 끝 번호와 `BlockStats.clipped` 를 짧은 고리에 적고, 게시할 결과의
`[windowEnd − 69,632, windowEnd)` 와 겹치는 넘친 블록이 있으면 「⚠ 입력 넘침 — 이 결과에 넘친 블록이
있습니다」. `BlockStats.clipped`(표본 절댓값 ≥ 0.999)가 모든 아날로그단 넘침을 잡는다는 뜻은 아니다.

## 10. 그래프 자료 계약 (R30-05)

`TransferResult` 는 DC 를 포함해 4,097칸, 칸 간격 5.859375 Hz. **`valid` 는 기준 에너지 관문일 뿐
유한성을 보장하지 않는다** — 유효 칸에서도 `magnitudeDb = -Infinity` 가 나온다(30회차 실행: 기준
잡음·측정 0 이면 유효 4,096칸 모두 −∞).

- 그리는 대상은 표시 대역 k=4…3413.
- **크기 선분**: 칸 k 가 「그릴 수 있음」 = `valid[k]` 이고 `magnitudeDb[k]` 가 유한. 그릴 수 없는 칸이
  나오면 **선분을 끊는다**. 자료는 「칸 번호를 지닌 선분 목록」으로 만든다 — 남은 점을 하나의 경로로
  잇지 않는다. 임의의 값(0 dB 등)으로 메우지 않는다.
- **세로축 아래로 벗어난 유한값**은 축 바닥에 그리지 않고 선분을 끊으며 「축 아래 n칸」으로 센다.
- **코히런스 선분**은 따로: `valid[k]` 이고 코히런스가 유한. 크기가 −∞ 라도 코히런스가 유한하면
  코히런스는 그린다(둘을 따로 다룬다).
- 왼쪽 칸의 「숨긴 칸」: 분모는 **표시 대역 3,410칸**. 이유별로 — 무효(기준 약함) n · 크기 표시 불가
  n · 축 아래 n.

**세 집합을 따로 센다** (R31-04):

| 집합 | 정의 | 비었을 때 |
|---|---|---|
| 기준 유효 V | 표시 대역에서 `valid[k]` | 9장 3순위 — 두 그래프 모두 없음 |
| 그릴 크기 M | V 가운데 크기가 유한하고 축 바닥 이상 | 크기 그래프만 「크기 표시 가능한 칸 없음 — 표시 불가 a · 축 아래 b」. **코히런스는 그대로** |
| 그릴 코히런스 C | V 가운데 코히런스가 유한(축 0~1 이라 「축 아래」 없음). 코히런스 표시가 숨김(평균 1~7)이면 C 를 쓰지 않음 | 코히런스 그래프만 「코히런스 표시 가능한 칸 없음」 또는 「평균이 모자람」. **크기는 그대로** |

- M 과 C 가 **둘 다** 비면 「그릴 수 있는 칸이 없습니다」 + 이유별 수(9장 4순위).
- 「축 아래」는 M 에서만 뺀다. 코히런스 중앙값(9장)은 C 로 셈하므로 크기의 축과 무관하다.
- 30회차 반례(유효 4,096칸 크기 모두 −∞)와 31회차 반례(크기 모두 −∞ · 코히런스 0): V 가득 · M 빈 · C
  가득 → 크기 그래프는 「표시 가능한 칸 없음」, 코히런스 그래프는 0 의 선, 중앙값 0.00(유효 3,410칸).

## 11. 실기기 확인 (구현 뒤, 소리가 난다 — 담당자가 시각을 정한다)

오늘 배치(0.4 m, UMC404HD → D3V L, 폰 내장 마이크).

1. 화면을 열기만 하면 소리가 **안 나는가**. [시작] 뒤 출력·입력에 ✓ 가 뜨는가.
2. 기존 테스트 신호를 틀어 둔 채 TF 를 시작하면 그 신호가 먼저 멎는가. TF 가 내는 동안 도구에서
   신호를 못 트는가.
3. 크기 곡선이 박자마다 얼마나 흔들리는가(관찰).
4. 스피커를 막거나 마이크를 멀리 할 때 무엇이 바뀌는가 — **관찰 항목**이다. 「반드시 낮아져야
   한다」는 합격 조건으로 쓰지 않는다(코히런스를 유지한 채 전달함수만 달라질 수 있다).
5. 입력을 USB 로 바꾸면 시작하지 않는가. 도중에 USB 출력을 뽑으면 멈추고 곡선이 지워지는가.
6. 앱을 뒤로 보내면 소리가 멎고, 돌아와도 저절로 다시 나지 않는가. 닫으면 멎는가.

결과는 `docs/verify/` 에 적는다. **제품 배선(`AudioTrackSink`)이 실제 경로·언더런을 계측 껍데기처럼
보고하는지**도 여기서 본다.

## 12. 시험으로 못박을 것 (JVM, 실기기 없이)

## 14. 검토에 묻는 것 (5판)

1. **4.3 5번**(R33-01) — `pendingCount == 0` · `failedReleaseCount == 0` 을 2초까지 기다린 뒤에만 TF 싱크를 여는 조건,
   그리고 이 두 수에 안 잡히는 열기 실패 자원을 **남은 위험**(R32-02, unverified 3-5)으로 두는 것.
2. **4.1 주인별 정지**(R33-02) — `SignalOwner`·`activeOwner`·`stopSignalOwnedBy` 로 취소된 작업의 `finally` 가 TF 를
   끄지 못하게 한 것, 사람·포커스·백그라운드·닫기는 전체 정지로 남긴 것.
3. **4.4 세션의 끝**(R33-03) — `signalIntent` 를 올리는 모든 길에서 주 스레드로 곧바로 `endTransferSession`,
   `onEnded` 는 `postAlways`, 기존 큐의 「최신 것만」 규칙은 그대로.
4. **3.3 읽기 번호 예약**(R33-04)과 그 경계 밖(AudioRecord 내부 버퍼)을 보장 밖으로 둔 것.
5. **구현에 들어가도 되는가.** 30~33회차의 남은 위험은 대부분 「실제 큐·코루틴·플레이어의 경합」이었고, 이번
   회차까지 그 반례들을 12장의 시험 항목으로 옮겼다. **12장의 시험(특히 R31~R33 반례를 그대로 재현하는 것)을
   구현의 합격 조건으로 삼는 조건으로** 구현에 들어가고, 구현 PR 을 다시 검토받는 길을 제안한다. 설계로 더
   닫아야 할 것이 남았다면 무엇인지.

## 15. 구현 노트 (31회차 「추가 확인 사항」)

- **ClipLedger**: 블록 끝 번호는 엔진이 쓰는 것과 **같은 좌표**(같은 `reset()` 뒤 `offerMeasurement` 로 넣은
  표본 수)로 적고, epoch 를 함께 적는다. 고리 길이는 엔진이 뒤로 뜨는 창(최대 `span + maxLag` = 93,632표본)과
  진행 중 계산 하나를 감당할 만큼(블록 수로 넉넉히). 결과 창에 해당하는 기록이 고리에서 이미 사라졌으면
  「넘침 없음」이 아니라 **「넘침 여부 모름」**으로 적는다. 겹친 블록에 넘침이 있었다는 보수적 표시일 뿐,
  잘린 표본의 정확한 위치를 구한 것이 아니다.
- **출력 기기**: 기존 규칙(`outputDeviceOf(wantedKind)`)이 고른 기기를 시작 **전** 화면에 보이고, 싱크를 연 순간의
  `requestedKey` 를 그 세션의 기준으로 삼는다. TF 세션은 싱크를 한 번만 연다(무장 뒤 출력 사건은 멈춤) — 세션
  중에 다른 기기로 조용히 다시 여는 일이 없다. 키(종류·이름·주소)는 경로를 가르는 수단이지 물리 장치의 영구
  동일성 보증이 아니다.
- **3초 기다림**은 단조 시각(`SystemClock.elapsedRealtime`)으로 재고, 기다리는 동안에도 멈춤·닫기를 막지
  않는다(기다림은 100 ms 걸음으로 의도 번호를 본다).
- **null 과 0**: `underrunCount()` 의 null(트랙 없음·조회 실패)은 「모름」이고, 0 은 정상 카운터다. null 이
  나오면 그 박자는 게시하지 않는다.
- **시험의 층**: 순수 상태 함수만이 아니라 **실제 관문·탭·세션 끝·`TransferIngest` 의 자물쇠**를 가짜
  입력·가짜 출력과 **생산 배선**(실제 `CaptureViewModel` 의 명령 실행자·`SignalPlayer`)으로 시험한다. 아직 없는 Android 화면의 경합을 DSP 시험만으로 확인했다고 적지 않는다.
- **열기 실패 자원**(R32-02): 기존 `SignalPlayer` 는 열기가 실패하거나 열기 중 예외가 나면 `stop()` 반환·
  `pendingCount == 0` 이어도 가짜 자원이 남을 수 있다(32회차 실행). 4.3 5번의 시작 조건이 이것을 잡지 못하므로
  **TF 에도 남은 위험**이다 — 남은 자원이 출력 경로에 닿으면 TF 결과에도 닿을 수 있다. `docs/unverified.md` 3-5 에
  적고 따로 고친다. *(5판은 「TF 의 정확성 문제는 아니지만」이라 적어 4.1 의 정정과 어긋났다 — R34-03)*
