## 1. 무엇을 만드는가 — 한 줄

**분석 화면에 「Transfer Function」 문 하나를 달고, 누르면 간편 측정 화면이 덮는다.** 그 화면은
앱이 USB-C 로 내보낸 핑크 잡음을 기준으로, 폰 마이크로 받은 소리와 견주어 **크기(H1)와
코히런스**를 그린다. 위상·정밀(2채널 입력)·여러 위치는 이번에 만들지 않는다.

```
분석 (가로)
├─ 차트: RTA · Spectrum · Spectrogram · FR      ← 손대지 않는다
└─ [ Transfer Function ▸ ]                       ← 한 줄 추가

        ↓ 누르면 (교정 마법사와 같은 방식으로 덮는다)

Transfer Function · 간편 (가로)
┌──────────────────┬─────────────────────────────────────────┐
│ ‹  [■ 멈춤]      │  ⚠ 시간축 미검증 · 상대 비교 — 정상 측정 곡선이 아닙니다 │
│                  │                                         │
│ 기준 맞춤         │            크기 (dB, 상대)               │
│  ● 찾음 · 또렷함 4.2 │                                      │
│                  │            코히런스 (0~1)                │
│ 측정 신뢰도       │                                         │
│  ● 좋음 / ○ 측정 중 │                                       │
│ 숨긴 칸 312/4096  │   20 Hz ───────────────── 20 kHz       │
│ 입력: 폰 마이크   │                                         │
│ 출력: USB-C      │                                         │
└──────────────────┴─────────────────────────────────────────┘
```

진입 화면(간편/정밀/여러 위치 고르개)은 **만들지 않는다** — 고를 것이 하나다(이전 설계 1장,
`ToolsScreen.kt` 원칙). 「준비 중」으로 흐리게 그린 정밀·위상 단추도 **두지 않는다**.

## 2. 이번에 만들지 않는 것

| 무엇 | 왜 |

| 정밀 모드(2채널 입력) | `MicSource` 가 고른 채널 하나만 넘긴다(`ChannelPick.readOneChannel`). 다채널 한 스트림이 go/no-go 관문(지시서 5장) |

| 저장·내보내기 | 이번 범위 밖 |
| 요금제·잠금·판매 문구 | CLAUDE.md 5장 |

## 3. 신호 경로 — 「폰 마이크로 받고 USB-C 로 내보낸다」

### 3.1 지금 앱의 신호 발생기와 **반대 방향**이다

`CaptureViewModel` 의 `SignalPlayer` 는 USB 로 잴 때 소리를 **폰 스피커로 돌린다**
(같은 USB 카드로 동시에 넣고 빼면 입력이 디지털 무음이 되는 기기가 있었다 — 실측). 간편 TF 는
반대로 **입력이 폰 마이크, 출력이 USB-C** 다(지시서 18장, 2026-10-01 실측
[`builtin-mic-with-usb-c-output`](../../verify/2026-10-01-builtin-mic-with-usb-c-output.md)).
그래서 **TF 화면은 자기 `SignalPlayer` 를 따로 갖는다.** 기존 플레이어의 경로 규칙을 고치지 않는다.

### 3.2 기준 = **실제로 쓴 표본**

`SignalPlayer(openSink = { TappedSink(AudioTrackSink(preferredOutput = USB 출력)) { buf, off, n ->
engine.offerReference(buf, off, n) } })`. `TappedSink` 는 `write()` 가 **실제로 받은 프레임만**
엔진에 넣는다(이전 설계 3장의 함정 — 일부만 쓰인 덩어리). 계측 시험
`AcousticDriftRecordingTest` 가 이 엮음을 실기기에서 돌렸다.

**신호는 핑크 잡음 · 양쪽(Both) 고정.** `TappedSink` 는 (L+R)/2 로 합친다 — 한쪽만 울리면 기준이
6 dB 낮게 잡혀 크기가 그만큼 밀린다. 그래서 TF 화면은 채널 고르개를 두지 않고 양쪽으로 낸다.
세기는 시운전·기록에서 쓴 0.2 를 기본으로 하고, 화면에서 바꾸는 손잡이는 이번에 두지 않는다.

### 3.3 측정 = 지금 측정 중인 입력

`CaptureController.onBlock` 이 받는 블록을 TF 가 열려 있는 동안 `engine.offerMeasurement` 로도
넘긴다. **TF 는 입력을 스스로 바꾸지 않는다.**

| 지금 입력 | TF 화면 |
|---|---|
| 폰 내장 마이크 | 잰다 |
| USB 인터페이스(EMM-6 등)·USB 직결 마이크 | **재지 않는다** — 「간편 측정은 폰 마이크로 받습니다. 입력을 폰 마이크로 바꾼 뒤 다시 여십시오」. 같은 카드로 넣고 빼는 무음 문제를 피하고, 출력과 입력이 둘 다 USB 인 구성은 정밀 모드의 일이다 |
| 측정이 멈춰 있다 | 「측정을 시작하면 잽니다」 |

이 표현은 마이크의 **연결 방식**을 말할 뿐이다. 「간편/정밀」은 지시서·2026-10-01 승인의 **모드
이름**이고, 마이크 등급이 아니다(CLAUDE.md 6장). 화면 어디에도 「입문용·전문용」 류를 쓰지 않는다.

### 3.4 출력 장치가 USB 가 아니면

USB 출력이 없으면(인터페이스·D3V 직결 없음) 「USB-C 로 소리를 낼 곳이 없습니다」로 멈춘다. 폰
스피커로 내보내 재는 길은 이번에 열지 않는다 — 폰 스피커와 폰 마이크의 거리·경로는 이번 설계가
다루지 않았다.

## 4. 엔진을 언제 비우는가

`TransferEngine` 은 두 스트림의 **표본 0 이 `reset()` 뒤 각자 들어온 첫 표본**이라는 전제로
같은 번호의 창을 뜬다. 그래서:

- TF 화면을 열 때 `reset()` → 신호 시작. 닫을 때 신호 멈춤.
- 입력이 다시 열리면(경로 바뀜·측정 재시작) `reset()` 하고 상태를 「다시 재는 중」으로.
- `reset()` 하면 `TimebaseStatus` 는 `Unverified` 로 돌아간다(R6-02).

## 5. 재는 박자와 스레드

화면이 열려 있는 동안 **1초마다** `measureOutcome()` 을 부른다. 무거운 계산(FFT 65,536 · 평균
16블록)은 `Dispatchers.Default` 의 코루틴 하나에서만 돈다 — 엔진은 재진입을 `Busy` 로 막으므로 두
번 부르지 않는다. 오디오 콜백 스레드(`onBlock`, `TappedSink.write`)는 `offer*` 만 한다.

1초는 1초 간격 시운전(세션 `2d3c2c56`)에서 278/287 창을 찾은 박자다. 같은 설정의 첫 세션이 하나도
못 찾고 FAIL 한 일(원인 모름)이 있으므로, 화면은 「못 찾음」을 정상 상태로 다룬다(6장).

## 6. 상태 — 그래프보다 먼저 정한다

| 상태 | 언제 | 화면 |
|---|---|---|
| `측정 안 함` | 캡처가 멈춰 있다 | 「측정을 시작하면 잽니다」 |
| `입력이 맞지 않음` | 입력이 폰 마이크가 아니다 | 3.3 표의 문장 |
| `출력 없음` | USB 출력이 없다 | 「USB-C 로 소리를 낼 곳이 없습니다」 |
| `모으는 중` | `InsufficientData` | 「재는 중입니다」 |
| `자리 잃음` | `RetentionExceeded` | 「한쪽이 너무 앞서 다시 맞춥니다」 → `reset()` |
| `기준을 못 맞춤` | `Measured` 인데 `delay.found == false` | 「소리를 찾지 못했습니다 — 스피커 소리가 마이크에 닿는지 보십시오」 + 또렷함 값. **곡선은 지난 것을 지우고 그리지 않는다** |
| `잼` | `Measured` 이고 `transfer != null` | 그래프 + 9장 |

`Busy` 는 상태를 바꾸지 않는다(이번 박자를 건너뛴다).

**지난 곡선을 남기지 않는다.** 못 맞춘 박자에 앞 박자의 곡선을 그대로 두면 「지금 잰 것」처럼 보인다.

## 7. 지연은 숫자로 보이지 않는다

엔진의 `delay.samples` 는 **표본 번호 좌표의 지연**이다 — 두 스트림이 시작한 시각 차이가 섞여
있다(R6-01). 오늘 실측에서 같은 배치(0.4 m)인데 세션마다 5,605 · 6,044 · 6,458 · 7,190 · 10,341
표본으로 달랐다. 그러니 이것을 「지연 23.4 ms」로 띄우면 **음향 지연이 아닌 값을 음향 지연처럼
적는** 일이 된다.

그래서 화면은 **「기준 맞춤: 찾음 · 또렷함 x.x」 / 「못 찾음」**만 보인다. 구조 검토 5장의 「지연
23.4 ms」 칸은 이번에 만들지 않는다. 음향 지연을 보이려면 두 스트림의 시작 시각 차이를 따로
재야 하고(`AudioTimestamp`), 그것은 별도 설계다.

또 1초 간격 실측에서 같은 세션 안의 지연이 **약 4표본 폭으로 오르내렸다**(원인 모름). 엔진은 박자
마다 그 박자의 지연으로 기준을 잘라 쓰므로 크기·코히런스는 그 영향을 박자마다 따로 받는다. 크기에
어느 만큼 영향을 주는지는 **재지 않았다** — 10장의 실기기 확인 항목이다.

## 8. 시간축 미검증 — R6-02 계약을 어떻게 지키는가 (**검토가 가장 필요한 결정**)

R6-02 는 `TransferMeasurement.timebase` 가 `Verified` 가 아니면 **「`transfer` 를 정상 측정 곡선으로
게시하지 않는다」**는 소비자 계약을 KDoc 에 적었다. 그리고 **앱 어디에서도 `Verified` 를 걸지
않는다** — 드리프트를 검증할 방법이 아직 없다(22장 진단, 불확도 보류).

세 안:

| 안 | 내용 | 문제 |
|---|---|---|
| A — 숨긴다 | `Unverified` 면 곡선을 그리지 않는다 | 앱에서 TF 가 **영영 안 보인다.** `Verified` 를 걸 길이 없기 때문이다 |
| **B — 「미검증」으로 게시(추천)** | 곡선을 그리되, 그래프 위에 **지울 수 없는 띠** 「⚠ 시간축 미검증 · 상대 비교 — 정상 측정 곡선이 아닙니다」를 늘 둔다. 띠는 `timebase` 에서 나온다(`Verified` 면 사라짐) | 계약의 「정상 곡선으로 게시하지 않는다」를 **「정상 곡선이라 하지 않고, 미검증이라 밝혀 게시한다」**로 읽는 것이다. 그 읽기가 맞는지 검토가 필요하다 |
| C — `Verified` 를 건다 | 세션 중 `AudioTimestamp` 드리프트가 어떤 범위 안이면 `Verified(근거)` | 그 「범위」가 검증된 기준이 아니다. 30분 기록 둘과 1초 시운전은 원자료이지 승인이 아니다(R6-02 표). **새 주장을 만드는 일**이라 이번에 하지 않는다 |

**B 를 추천한다.** 다만 B 로 가면 `TransferEngine.kt` KDoc 의 계약 문장을 「`Verified` 가 아니면
정상 측정 곡선이라 **표시하지 않는다** — 게시하려면 미검증임을 같은 화면에 밝힌다」로 고쳐야 한다.
계약을 고치는 일이므로 이 설계의 검토 대상이다. 띠가 늘 있는지는 시험으로 못박는다(11장).

## 9. 그래프가 지킬 것

| 항목 | 규칙 | 근거 |
|---|---|---|
| 크기 | `magnitudeDb` 를 **상대 dB** 로. 세로축 이름 「크기 (dB, 상대)」. 1 kHz 맞춤 같은 정규화는 이번에 하지 않는다 | 절대 크기 없음(2장) |
| 무효 칸 | `valid[i] == false` 인 칸은 크기·코히런스 **둘 다 그리지 않는다**(선을 끊는다). 왼쪽에 「숨긴 칸 n/전체」 | 지시서 25장 근처 · DSP 계획 |
| 코히런스 | `coherenceDisplay()` 그대로: 유효 평균 1~7 숨김 · 8~15 「안정화 중」 · 16 이상 표시. 지금은 늘 16 | 지시서·명세 재검토 1장 |
| 측정 신뢰도 | 유효 칸 코히런스의 **중앙값**으로 ● 좋음(≥0.9) · ● 보통(≥0.7) · ● 낮음(<0.7) · ○ 측정 중(코히런스 숨김일 때). **문턱 0.9/0.7 은 실측으로 정한 값이 아니다** — 화면 [고급] 에 그 값을 적는다 | 구조 검토 5장 「제3의 상태」 |
| 낮은 코히런스 | 원인을 적지 않는다(「반사 때문」 등 금지) — 「낮음」까지만 | 지시서 |
| 클리핑 | 지난 박자에 입력 블록이 클리핑(`BlockStats.clipped`)됐으면 「⚠ 입력 넘침 — 신뢰 낮음」 | 지시서 LOW CONFIDENCE |
| 주파수 축 | 20 Hz~20 kHz 로그. 칸 간격은 48000/8192 ≈ 5.9 Hz(저역이 성기다는 말을 [고급] 에) | |
| 금지 표현 | 「Smaart 와 동일」 · 「Class 1/2」 · 「공인 측정」 · 「자동 EQ 정답」 · RTA 와 섞는 설명 | 지시서 37장 · CLAUDE.md 7장 |

## 10. 실기기 확인 (구현 뒤, 소리가 난다)

담당자가 시각을 정한다. 오늘 배치(0.4 m, UMC404HD → D3V L, 폰 내장 마이크).

1. 문을 열면 소리가 USB 로 나고, 「기준 맞춤: 찾음」이 뜨는가.
2. 크기 곡선이 박자마다 얼마나 흔들리는가 — 7장의 지연 오르내림이 곡선에 보이는가(관찰만).
3. 스피커를 막거나(손·천) 마이크를 멀리 했을 때 「못 찾음」 또는 신뢰도 「낮음」으로 가는가.
4. 입력을 USB 로 바꾸면 「입력이 맞지 않음」으로 멈추는가. USB 출력을 뽑으면 「출력 없음」.
5. 화면을 닫으면 소리가 멈추는가(멈추지 않는 소리는 이 앱이 이미 한 번 데인 자리).

결과는 `docs/verify/` 에 기록하고, 「좋음/보통/낮음」 문턱은 거기서 본 값을 근거로 다시 묻는다.

## 11. 시험으로 못박을 것 (JVM, 실기기 없이)

| 무엇 | 확인 |
|---|---|
| 상태 기계 | 6장 표의 각 줄이 그 조건에서만 나온다 — `TransferUiState` 를 엔진 결과·입력 종류·출력 유무로부터 순수 함수로 만든다 |
| **미검증 띠** | `Unverified` 인 `Measured` 결과로 만든 화면 상태는 **늘** 띠를 가진다. `Verified` 일 때만 없다. 변이(띠 조건을 뒤집기)를 잡는다 |
| 지난 곡선 | `잼` 다음 박자가 `기준을 못 맞춤` 이면 곡선 자료가 비어 있다 |
| 무효 칸 | `valid=false` 칸은 크기·코히런스 점 목록에 없다(선이 끊긴다). 숨긴 칸 수가 맞다 |
| 신뢰도 | 중앙값 문턱 경계(0.9 · 0.7), 코히런스 숨김이면 「측정 중」 |
| 기준 탭 | `TappedSink` 가 `wrote` 만큼만 넣는다 — 기존 시험이 있으면 재사용 |
| 입력 거절 | 입력이 USB 면 엔진에 `offerMeasurement` 하지 않는다 |
| 소리 멈춤 | TF 를 닫으면 플레이어 `stop()` 이 불린다(가짜 싱크) |
| 문자열 | 화면 문자열에 9장 금지 표현이 없다(문자열 자원 검사) |

변이 시험은 `--rerun-tasks` 로 돌린다(CLAUDE.md 4장).
