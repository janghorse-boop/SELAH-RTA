## A01 (High) — 번호를 먼저 발급해서 영영 기다리게 했다

**지적이 정확합니다.** 제가 이렇게 적었습니다:

```
tryAccept()  → 번호 발급
   ...
offer(queue) → 실패할 수 있음   ← 여기서 실패하면?
```

번호는 나갔는데 패킷이 큐에 안 들어가면, writer 는 N 개를 기다리는데
N−1 개만 옵니다. **비움이 끝나지 않아 종료하지 못합니다.**
검증자 모형: `ADMISSION: reserved=0 closeCount=1 consumed=0`.

### 결정 — **버퍼를 잡는 것이 곧 입장권이다**

```
큐 용량 = 풀 크기
```

풀에서 버퍼를 잡았다면 **큐에 자리가 반드시 있습니다** — 떠 있는 버퍼
하나가 큐 칸 하나를 넘게 쓸 수 없기 때문입니다. 그러면 넣기가 실패할
길이 없어집니다.

그리고 **번호 발급과 넣기 사이에 실패할 수 있는 일을 두지 않습니다.**
채우는 것을 **먼저** 합니다:

```kotlin
// 1. 자리부터 잡는다. 못 잡으면 그것이 손실이다.
val buf = pool.tryAcquire() ?: run { droppedFrames += block.frames; return }

// 2. 채운다. 여기까지는 아직 아무에게도 약속하지 않았다.
buf.copyFrom(block)

// 3. 번호를 받는다. 닫혔으면 되돌려 주고 물러난다.
val seq = admission.tryAccept()
if (seq < 0) { pool.release(buf); return }

// 4. 넣는다. **용량이 풀 크기라 실패하지 않는다.**
queue.put(Packet(seq, captureFrameStart, frames, epochId, buf))
```

- 「받아들인 것」과 「큐에 든 것」이 **같은 집합**이 됩니다.
- 비움 완료: writer 가 소비한 수 == `admission.close()` 가 돌려준 수.
- 3번과 4번 사이에는 던질 것도, 기다릴 것도 없습니다.

**시험**: writer 를 막아 풀을 말린 뒤 성공·실패 offer 를 번갈아 만들고,
곧바로 `stop` 해서 **비움이 반드시 끝나는지** 봅니다. 「번호는 나갔는데
안 온 패킷」이 하나라도 생기면 실패입니다.

## A02 (Medium) — 블록이 경계를 걸치면 쪼갠다

검증자 반례가 정확합니다:

```
ROW:   block=[23552,24576) boundary=24000
       23999 의 임펄스와 24000 의 임펄스가 **같은 블록 극값**을 내지만
       서로 다른 행에 속한다
EPOCH: trueMax=90 인데 옛 epoch 로 보면 80, 새 epoch 로 보면 100
```

블록 하나(1024프레임·21.3ms)의 극값 **하나**로는 행별 MAX·Peak 를 맞게
구할 수 없습니다.

### 결정 — 행·epoch 경계에서 블록을 **나눠 넣는다**

들어온 블록을 **500ms 행 경계와 epoch 바뀌는 지점**에서 쪼개고, 조각마다
따로 DSP 에 넣어 **그 조각의 극값**을 받습니다.

```
block [23552, 24576)  →  [23552, 24000)  그리고  [24000, 24576)
                          0번 행             1번 행   (48kHz·시작 0)
```

**이것이 성립하려면 DSP 가 표본 단위로 이어져야 합니다** — 즉
`process(전체)` 와 `process(앞) ; process(뒤)` 의 결과가 **같아야** 합니다.

**재 봤습니다**(`SplitProcessingTest`, 순수 JVM). 1·13·448·1023·1024·
2000·3001 처럼 어중간한 크기로 번갈아 나눠 넣고 한 번에 넣은 것과
견줬습니다 — **오차 0.0 으로 정확히 같습니다**:

```
[SPL A] 한번에 max=-17.049979318 peak=-0.915150041
        쪼개서 max=-17.049979318 peak=-0.915150041
[SPL C] -17.053778601 / -17.053778601
[SPL Z] -17.029959968 / -17.029959968
[RTA]   첫 밴드 -79.639445818 vs -79.639445818   (31밴드·Peak Hold 전부)
[하울링] 한번에 [1000] / 쪼개서 [1000]
```

> ⚠️ **이 결론은 폐기했습니다**(독립 검증 M33). 위 시험이 하울링을
> `hz.toInt()` 목록으로만, SPL 을 MAX·Peak·현재로만 견줘서 **결론이
> 단언보다 앞섰습니다.** 시각·지속·Leq 는 실제로 달랐습니다.
> 바른 내용은 [4차 보완](2026-09-21-recording-design-supplement-4.md)
> 의 M33 을 보십시오 — 시각 계약을 넣고 다시 재면 하울링 기록까지
> 통째로 같고, `leqSession` 만 1e-9dB 안에서 다릅니다.

남은 시험(녹음을 붙일 때):

| 시험 | 무엇 |
|---|---|
| 행 귀속 | 23999·24000 임펄스가 **서로 다른 행**의 극값이 되는지 |
| epoch 귀속 | 경계를 걸친 블록이 양쪽 epoch 에 제 몫만 들어가는지 |

## A03 (Low) — `kotlin.math.round` 를 쓰지 않는다

제가 「half-away-from-zero」라고 적어 놓고 표준 `round` 를 쓸 것처럼
보이게 썼습니다. **둘은 다릅니다**(위 실측):

| x | `kotlin.math.round` | `Math.round` | 내가 적은 규칙 |
|---:|---:|---:|---:|
| 0.5 | 0 | 1 | **1** |
| 2.5 | 2 | 3 | **3** |
| −2.5 | −2 | −2 | **−3** |

**셋 다 다릅니다.** 그래서 **직접 씁니다**:

```kotlin
// NaN·Inf 는 0 으로.
val v = if (x.isNaN() || x.isInfinite()) 0.0 else x.toDouble()
val scaled = v.coerceIn(-1.0, 1.0) * 32768.0
// half-away-from-zero — 표준 함수를 쓰지 않는다.
val r = if (scaled >= 0.0) floor(scaled + 0.5) else ceil(scaled - 0.5)
// **정수를 포화**시킨다(2차 A06 에서 정한 것).
val q = r.coerceIn(-32768.0, 32767.0).toInt().toShort()
```

시험에 `kotlin.math.round` 와 **다른 답이 나오는 값**(0.5·2.5·−2.5)을
반드시 넣어, 나중에 누가 표준 함수로 바꾸면 걸리게 합니다.

## A04 (Low) — 0.36초입니다

2차 문서에 「+50ppm 이면 2시간에 약 **0.16초**」라고 적었습니다.
**0.36초**입니다(`7200 × 50e-6`). 검증자가 예시로 든 7200.160 이라는
숫자를 제가 차이값으로 잘못 읽었습니다.

고쳐 적습니다:

> 기기 클럭이 +50ppm 이면 2시간 녹음의 미디어 시간은 단조 시계보다
> 약 **0.36초** 깁니다. 소리와 그래프는 같은 프레임에서 나오므로 서로
> 어긋나지 않고, 바깥 시계와의 차이는 anchor 로 설명합니다.

## 승인을 나눠 받는 것에 대해

「anchor 탐색만 먼저 분리하는 방향은 타당하다」고 해 주셨으므로 그렇게
하겠습니다.

**1단계(지금 요청)**: 실기기에서 `AudioRecord.getTimestamp(TIMEBASE_MONOTONIC)`
가 실제로 무엇을 주는지만 **재어서 보고**합니다.

- 되는가 / 얼마나 자주 갱신되는가
- `fsEff` 가 얼마나 흔들리는가(공칭 대비 ppm)
- hold-out 으로 다음 anchor 를 예측했을 때의 오차
- 44.1kHz 와 48kHz 각각

**녹음은 만들지 않습니다.** 측정용 경로만 더하고, 결과를 문서로 남긴 뒤
그것을 넣어 S01 의 메타데이터 계약을 확정합니다.
