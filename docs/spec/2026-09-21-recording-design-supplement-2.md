## 먼저 — 확인한 두 가지는 제 잘못입니다

**S04** `RtaFrame.bandsDbfs` 는 `RtaEngine.kt:160` 의
`bands.toBandPower(power, bandPower, binCorrection)` 를 지난 값이라
**이미 마이크 곡선이 걸려 있습니다.** 하울링 탐지기만 보정 전
스펙트럼을 봅니다(`:158`). 「onBlock 결과는 보정 전이니 읽을 때 건다」를
**한 규칙으로 뭉뚱그린 것**이 잘못입니다 — SPL 의 절대 offset 과 RTA 의
주파수 곡선은 다른 것입니다.

**S06** 산술을 직접 돌려 봤습니다:

```
x = 0.9999899864 (float32)  →  x × 32768 = 32767.671875  →  반올림 32768
Short 로 줄이면 → −32768        부호가 뒤집힌다
```

`[−1, 1)` 로 막는 것으로 해결되지 않습니다. **정수를 포화**시켜야 합니다.

## S01 — 시간 좌표를 하나로 정한다 (High)

반례가 정확합니다. `rowIndex = elapsedMs/500` 과 재생 위치 나눗셈을 함께
약속하면서 **`elapsedMs` 가 어느 시간인지 적지 않았습니다.** 공칭 48000Hz,
실제 48002.4Hz 면 손실이 전혀 없어도 행이 14399 대 14400 으로 갈립니다.

### 결정 — **기준 좌표는 프레임이다**

권고 1번을 고릅니다.

- **녹음의 정본 좌표는 「녹음 시작 프레임부터 센 프레임 번호」**입니다.
  `frameFromStart`, 부호 없는 64비트.
- 타임라인 행: `rowIndex = frameFromStart / (nominalFs / 2)`.
  **공칭 샘플레이트**로 나눕니다 — 즉 행 간격은 **미디어 시간** 500ms 입니다.
- WAV 재생 위치(프레임)가 곧 `frameFromStart` 입니다. **변환이 없습니다.**
- 손실 구간에 무음을 채우므로
  `captureFrame = frameFromStart + recordingStartFrame` 이 늘 성립합니다.
- 사건·마커도 전부 프레임으로 적습니다.

**`elapsedMs` 라는 필드를 없앱니다.** 필요하면 화면에서
`frameFromStart × 1000 / nominalFs` 로 만들어 씁니다.

### 단조 시계는 **메타데이터**다

anchor 는 `captureFrame ↔ monotonicNs` 를 맺어 두는 **부가 정보**입니다.
쓰는 곳은 셋뿐입니다.

1. 바깥 세계의 사건과 맞추기(「몇 시 몇 분의 소리인가」)
2. `fsEff` 와 드리프트를 **재어서 적기**
3. 녹음 시작 프레임의 실제 시각을 **추정해 알리기**

**행 번호와 seek 에는 절대 쓰지 않습니다.** 그래서 반례의 불일치가
생길 자리가 없습니다.

**대가를 적습니다**: 기기 클럭이 +50ppm 이면 2시간 녹음의 미디어 시간은
단조 시계보다 약 0.16초 깁니다. **소리와 그래프는 같은 프레임에서
나오므로 서로 어긋나지 않고**, 바깥 시계와의 차이는 anchor 로 설명합니다.

### 버튼 이전 소리 — 「한 블록」은 틀렸다

적체가 있으면 버튼 뒤 첫 블록 전체가 200ms 전 소리일 수 있다는 지적이
맞습니다. **블록 길이는 그 블록이 얼마나 오래됐는지의 상한이 아닙니다.**

- anchor 가 있으면: 첫 저장 프레임의 추정 시각을 `recRequestedNs` 와
  견주어 **「버튼보다 N ms 앞선 소리가 포함됨(±오차)」**으로 적습니다.
- anchor 가 없으면: **「얼마나 앞선 소리가 포함됐는지 알 수 없음」**이라고
  적습니다. 유한한 상한을 주장하지 않습니다.
- 잘라내지 않습니다 — 자르려면 그 추정에 기대야 하는데, 추정이 없는
  기기에서는 자를 근거도 없습니다.

### 정확도 시험 — **넣은 anchor 로 자기를 재지 않는다**

지적대로 고칩니다. anchor 1..k 로 맞춘 모형으로 **k+1 번째 anchor 를
예측**하고 실제와 견줍니다(hold-out).

| 조건 | 기준 |
|---|---|
| 다음 anchor 예측 오차 | **≤ 20ms** |
| `fsEff` 변동 | 공칭 대비 **≤ 200ppm** |
| anchor 없음 | 기준 없음 — **추정임을 표시** |

## S02 — 손실 위치를 **전달하지 않고 유도한다** (High)

`droppedFrames += n` 이 위치를 잃는다는 지적이 맞습니다. 그런데 **위치를
보낼 필요가 없습니다.**

### 결정 — 수락 패킷이 프레임 구간을 지닌다

```
Packet(seq, captureFrameStart, frames, epochId, samples)
```

writer 는 `expectedNextFrame` 을 들고 있다가:

```
if (packet.captureFrameStart > expectedNextFrame) {
    gap = packet.captureFrameStart − expectedNextFrame   // 정확한 프레임 수
    무음 gap 프레임을 쓰고 Gap(위치=expectedNextFrame, 길이=gap) 을 남긴다
}
```

**손실은 받아들인 프레임 번호의 불연속에서 그대로 나옵니다.** 제어
자리에 위치를 실어 보낼 일이 없으니 합산이 위치를 잃는 문제도 없습니다.

### 끝자락 손실 — watermark

마지막 수락 이후의 손실은 패킷으로 알 수 없습니다. 그래서 `stop` 이
**그 순간의 캡처 프레임 카운터(`finalObservedFrame`)**를 함께 넘기고,
writer 가 마지막으로 쓴 프레임과 견주어 끝자락 gap 을 확정합니다.

### epoch 는 **합치지 않는다**

epoch 기록은 유한한 고리(256개)에 **하나씩** 쌓습니다. 넘치면
**녹음을 실패로 끝냅니다** — 덮어쓰면 과거 행이 가리키는 epoch 가
사라집니다. (설정을 녹음 중 256번 바꾸는 일은 사실상 없지만, 말 없이
잃는 것보다 실패가 낫습니다.)

### 접수 종료 — 선형화 지점을 **번호 발급과 같은 자리**에 둔다

입구 검사만으로는 「검사를 지난 producer 가 아직 offer 하지 않은」 순서를
막지 못한다는 지적이 맞습니다. **번호를 발급하는 그 원자 연산이 곧
접수 여부**가 되게 합니다.

```kotlin
// 음수면 닫힘. 아니면 다음 번호.
private val nextSeq = AtomicLong(0)

/** 받아들이면 번호를, 닫혔으면 −1 을 돌려준다. */
fun tryAccept(): Long {
    while (true) {
        val cur = nextSeq.get()
        if (cur < 0) return -1
        if (nextSeq.compareAndSet(cur, cur + 1)) return cur
    }
}

/** 접수를 닫고 **받아들인 개수**를 돌려준다. */
fun close(): Long {
    while (true) {
        val cur = nextSeq.get()
        if (cur < 0) return -cur - 1
        if (nextSeq.compareAndSet(cur, -(cur + 1))) return cur
    }
}
```

- 닫은 **뒤에** CAS 하는 producer 는 반드시 거절됩니다.
- **비움 완료 조건**: writer 가 `close()` 가 돌려준 개수만큼 소비했을 때.
- **오디오 스레드를 기다리게 하지 않습니다.**

## S03 — checkpoint 를 두 칸으로 (High)

「제자리 갱신 중 끊기면 CRC 오류 → 세션 전체 failed」가 **1초 손실 보장과
충돌한다**는 지적이 정확합니다.

### 결정

- `checkpoint.bin` 에 **슬롯 두 개**를 두고 **번갈아** 씁니다.
  각 슬롯: `(seq, audioFrames, timelineRows, eventBytes, epochCount, crc)`.
- 복구는 **CRC 가 맞는 것 중 `seq` 가 큰 것**을 고릅니다.
  찢어진 쓰기는 **쓰던 슬롯 하나만** 망가뜨리므로 직전 것이 살아남습니다.
- **게시 전 자기 일관성**을 writer 가 보장합니다:
  - `timelineRows` 까지의 행이 가리키는 epoch 가 모두 `epochCount` 안에 있고,
  - 마지막 행이 덮는 프레임 범위가 `audioFrames` 안에 있다.
  그 조건이 성립하는 **경계에서만** 게시합니다.

### 보장 문구를 고칩니다

「최대 약 1초 손실」은 **틀렸습니다** — writer·fsync 지연에 상한이 없습니다.

> **마지막으로 영속화에 성공한 checkpoint 이후를 잃습니다.**
> 그 간격은 저장장치 상태에 따라 1초보다 길 수 있습니다.

복구 시 **실제 파일 길이·레코드 정렬·사건 경계·epoch 참조를 모두 검사**하고,
하나라도 어긋나면 `recovered` 가 아니라 **더 앞선 checkpoint 로 물러납니다.**

## S04 — 필드마다 보정 상태를 적는다 (Medium)

| 저장하는 값 | 보정 상태 | 재생에서 |
|---|---|---|
| **31밴드 RTA** | **곡선 적용됨**(엔진이 이미 걸었다) | **다시 걸지 않는다.** SPL offset 만 더한다 |
| SPL·Leq·MAX·Peak (dBFS) | 곡선과 무관, **offset 적용 전** | epoch 의 offset 을 더한다 |
| 하울링 후보 | **곡선 적용 전** 스펙트럼에서 나온 값 | 그대로 |

**이중 보정이 나던 자리**입니다. 곡선이 걸린 31밴드만으로는 원래 FFT
칸 값을 되돌릴 수 없으므로, 「원시 스펙트럼 보관」은 **별도 자료**로
설계해야 하고 이번 범위에 넣지 않습니다.

`curveVersion` 은 **곡선 내용의 해시**로 두고 세션에 곡선 요약을 함께
적습니다 — 사용자가 원본 파일을 지우거나 바꿔도 **그때 무엇이 걸려
있었는지**가 남아야 합니다.

## S05 — 구간 극값을 따로 누적한다 (Medium)

반례가 맞습니다. 블록 Peak 가 0.8 → 0.1 ×4 면 **마지막 값은 −20dBFS,
구간 Peak 는 −1.94dBFS** 입니다.

### 결정

- 행에 **세 가지를 나눠** 적습니다:
  - `current` — 그 구간 마지막 값(지금 화면과 같은 뜻)
  - `maxInRow` · `peakInRow` — **그 500ms 안의 극값**
- 극값은 **모든 블록에서** 누적합니다. 그러려면 DSP 가 **블록별 극값**을
  내줘야 하므로, `MultiWeightEngine`/`SplEngine` 에 **더하기만** 합니다
  (기존 누적값과 live 출력은 **건드리지 않습니다**).
- 녹음 전체의 최대는 **행에서 구합니다.** REC 이전에 쌓인 live 누적값을
  「이 파일의 최대」라고 적지 않습니다.
- **REC 때문에 live DSP 를 reset 하지 않습니다.**
- REC 경계·설정 변경 시점의 블록은 **새 epoch 쪽 구간에** 넣습니다.

## S06 — 정수를 포화시킨다 (Medium)

```kotlin
// NaN·Inf 를 먼저 0 으로, 입력을 [-1,1] 로 막고,
// **반올림한 정수를** [-32768, 32767] 로 포화시킨 뒤 Short 로.
val q = round(clamp(x, -1.0, 1.0) * 32768.0)   // half-away-from-zero
val s = clamp(q, -32768.0, 32767.0).toInt().toShort()
```

시험은 지적한 경계를 그대로 봅니다 — `-1`·`+1`·`0`·양음 half-LSB·
`32767.5`·`32768` 양옆·1 바로 아래 float·범위 초과·NaN/Inf,
그리고 **큰 양수 입력에서 부호가 뒤집히지 않는지**와 **단조성**.

## 다음 단계 — 승인을 나눠 받기를 제안합니다

검증자가 적은 대로 **「anchor 수집 자체의 탐색·시험」과 「전체 저장/재생
설계 승인」은 나눌 수 있습니다.** 그렇게 하기를 제안합니다.

1. **먼저 anchor 탐색만** — 실기기에서 `getTimestamp(TIMEBASE_MONOTONIC)`
   가 실제로 무엇을 주는지(되는가·얼마나 자주·`fsEff` 가 얼마나 흔들리는가)
   **재어서 보고**합니다. 코드는 측정용 경로만 더하고 녹음은 만들지
   않습니다.
2. 그 결과를 넣어 **S01 의 메타데이터 계약을 확정**합니다.
3. 그 뒤 저장·복구·재생 설계 승인 → 구현.

지금 모르는 것을 모르는 채로 「기기가 이러이러할 것」이라고 적고 진행하는
것보다 낫다고 봅니다.

## 아직 정하지 못한 것

- 실기기의 timestamp 품질·저장 속도·장시간 녹음 — **미측정**.
- 손실 문턱(2초 / 1%) — **미측정**. 저장 속도를 본 뒤 정하고 근거를 남깁니다.
- epoch 고리 256 — 임의로 고른 값입니다. 넘칠 일이 사실상 없다고 보지만
  **재지 않았습니다.**
