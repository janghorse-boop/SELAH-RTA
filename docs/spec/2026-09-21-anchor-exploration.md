# anchor 탐색 결과 — 기기가 실제로 무엇을 주는가

2026-09-21 · 구현자: Claude Code
대응: [4차 보완 설계](2026-09-21-recording-design-supplement-4.md) 의 다음 단계 1
기기: **Galaxy S23 (SM-S918N)** · 내장 마이크 · **48kHz**

녹음 설계의 S01 이 「`AudioRecord.getTimestamp(TIMEBASE_MONOTONIC)` 로
프레임과 시각을 맺는다」인데, **그 기기가 실제로 무엇을 주는지 몰랐습니다.**
모르는 채로 계약을 쓰지 않으려고 먼저 쟀습니다.

## 어떻게 쟀는가

- `CaptureRecorder` 에 `timestamp()` 를 더했습니다(**기본 구현은 null** —
  가짜 구현이 몰라도 되게).
- `runCaptureLoop` 이 **약 1초마다** 한 번 물어보고, 읽은 전체 프레임
  수와 함께 로그로 남깁니다. **캡처 스레드에서 동기로 부르며, 그것이
  캡처에 얼마나 영향을 주는지는 아직 재지 않았습니다**(독립 검증 AN04).
  이 로그에서 캡처가 멎은 흔적은 없습니다.
- 녹음은 만들지 않았습니다. 측정 경로뿐입니다.
- 더하기 전후로 **시험 298건이 그대로 통과**합니다.

71.2초 동안 **표본 72개**를 모았습니다.

## 잰 값

| 무엇 | 값 |
|---|---|
| `getTimestamp` 가 되는가 | **된다** — 72번 물어 72번 다 성공 |
| 표본 클럭 추정 | 끝점 **−2.002ppm** · 전체 회귀 **−0.295ppm** (둘은 다르다) |
| hold-out 예측 오차 | 중앙 **0.146ms** · 95% 0.426ms · **최대 0.750ms** (규칙은 아래) |
| 받은 anchor 의 나이(`nowNanos−tsNanos`) | 중앙 **1.011ms** · 최대 22.995ms |
| `tsFrames − capFrames` | **−704 ~ +896** (중앙 +448) = −14.7 ~ +18.7ms |
| anchor 없이 프레임만 셌을 때 | 71.2초에 −0.14ms → **2시간 −14.4ms** |

## 읽은 것

**1. anchor 를 쓸 수 있습니다.** 이 기기에서는 늘 주고, 앞선 anchor 들로
다음 anchor 를 예측한 오차가 **최대 0.750ms** 입니다. 4차 설계에서 제가
미리 정한 기준(≤20ms)보다 **훨씬 작습니다.**

> **처음에 적은 0.138 / 0.400 / 0.590ms 는 재현할 수 없는 수였습니다**
> (독립 검증 AN01). 제가 **계산 규칙을 적지 않았고**, 말없이 앞 네 점을
> 건너뛰었기 때문입니다. 규칙을 코드로 옮기고 원시 로그를 fixture 로
> 두었습니다 — `AnchorEstimatorTest`. 이제 누구든 같은 수를 얻습니다.

**규칙** (이대로 시험에 들어 있습니다):

1. anchor 가 **둘** 모이면 시작한다(준비 구간 2).
2. `fsEff` 는 **첫 anchor 와 직전 anchor** 로 잰다.
3. `pred = t[k−1] + (f[k] − f[k−1]) × 1e9 / fsEff`
4. **평가 대상은 학습에 넣지 않는다.** 세 번째 anchor 부터 끝까지(70개).

**2. 이 기기의 클럭은 이번 구간에서 −2ppm 쯤으로 아주 좋습니다.** anchor 없이 프레임만
세도 2시간에 **−14.4ms** 밖에 안 벌어집니다. **다만 이 기기 이야기일
뿐입니다** — 흔히 쓰는 크리스털은 ±50ppm 까지 갑니다. 그러면 2시간에
0.36초입니다. **한 대로 일반화하지 않습니다.**

**3. `tsFrames − capFrames` 가 음수도 나옵니다**(−704). 처음에는 이상해
보였는데, 뜻을 따져 보면 자연스럽습니다:

- 그 쌍 `(tsFrames, tsNanos)` 는 **기기가 제 시점에서 맺은 것**이고,
- `capFrames` 는 **우리가 물어본 시점**의 값입니다.
- 둘은 **다른 순간**이라 차이가 양수도 음수도 됩니다. 양수면 아직 안
  읽은 버퍼가 쌓인 것이고, 음수면 받은 쌍이 그만큼 **지난 것**입니다.

그래서 **「지금 몇 프레임인가」로 시각을 맞추면 안 됩니다.** 쌍을 그대로
쓰고 **프레임으로 환산**해야 합니다 — 4차 설계의
`captureNs(f) = anchorNs + (f − anchorFrame) × 1e9 / fsEff` 가 바로 그것이고,
쌍이 조금 지난 것이어도 상관없습니다.

**4. 좌표가 같다는 가정과 어긋나는 것을 보지 못했습니다.**
첫 표본에서 `capFrames=1024, tsFrames=1920` 이고, 차이 896 은 아직 안 읽은
버퍼로 **설명됩니다.**

> **「확인됐다」고 적었던 것을 낮춥니다**(독립 검증 AN02). 첫 값 하나로
> 896 이 전부 미소비 버퍼임을 **잰 것이 아닙니다** — 같은 원점을 가정하면
> 그렇게 설명된다는 관찰입니다. 그리고 **hold-out 계산에는 `capFrames` 가
> 들어가지 않으므로**, 오차가 작다는 것이 「앱의 PCM 과 anchor 의 절대
> 정렬」을 증명하지 않습니다. 앱 프레임에 일정한 오프셋이 있었어도 그
> 수치는 똑같이 나옵니다.

그래서 이렇게 적습니다 — **「같은 시작·연속 전달 가정과 일치하며, 이
로그에서 모순을 보지 못했다」.** start/stop/start, 부분 read, 읽기 유실이
섞인 경우의 재설정 규칙은 **아직 정하지 않았고 재지도 않았습니다.**

**5. `nowNanos − tsNanos` 는 「받은 anchor 가 얼마나 지난 것인가」입니다.**
중앙 1ms, 최대 23ms 입니다.

> **이것을 `read()` 지연이라고 부르면 안 됩니다**(독립 검증 AN04).
> `nowNanos` 는 조회한 **뒤** 찍은 값이라, 이 차이는 **조회한 anchor 의
> 나이**에 가깝습니다. 「블록 첫 표본의 시각과 read 가 돌아온 시각의 차」를
> 잰 값이 아닙니다.

`read()` 가 돌아온 시각을 표본 시각으로 쓰면 안 된다는 결론 자체는
그대로입니다 — 다만 **그 근거를 이 숫자로 대지 않습니다.**

## 그래서 계약을 이렇게 확정합니다

| | 확정 |
|---|---|
| 정본 좌표 | **녹음 시작부터 센 프레임 번호** (4차 그대로) |
| 시각 맺기 | anchor 쌍으로 `captureNs(f)` |
| `fsEff` | 위 규칙으로 **재어서** 쓴다. 공칭을 믿지 않는다 |
| ppm 기준을 **어디에 거는가** | **안정화된 추정기**(10개 창 ≈ 10초)에 건다 |
| 통과 기준 | hold-out 예측 오차 **≤ 20ms** — 이 기기는 0.750ms 로 여유가 크다 |
| anchor 를 못 주는 기기 | `timeAnchor = ESTIMATED`, 화면에 표시, **유한한 오차 상한을 주장하지 않는다** |

## ±200ppm 기준을 어디에 걸지 정합니다

2차 설계에 「anchor 간 `fsEff` 변동 ≤200ppm」이라고 적어 놓고 **어디에
적용하는지를 안 적었습니다.** 이웃한 두 점(약 1초)에 그대로 걸면 이
자료에서 **26/71 구간이 벗어납니다**(−589 ~ +511ppm).

**하드웨어가 그만큼 흔들린다는 뜻이 아닙니다.** 짧은 구간에서는
timestamp 의 작은 오차가 속도로 크게 증폭됩니다. 그래서:

| 무엇에 거는가 | 결과 |
|---|---|
| 이웃 두 점(약 1초) | **밖 26/71** — 기준으로 쓸 수 없다 |
| **10개 창(약 10초)** | 가장 큰 편차 **56.8ppm**, **밖 0** ← 여기에 건다 |

그리고 **끝점 추정(−2.002ppm)과 전체 회귀(−0.295ppm)가 다릅니다.**
하나를 「이 기기의 실제 클럭」이라 부르지 않고, **이번 구간의 추정치**로
적습니다. 위 세 줄 모두 `AnchorEstimatorTest` 가 붙들고 있습니다.

## 아직 모르는 것 — 한 대, 한 조건입니다

- **44.1kHz 는 재지 않았습니다.** 앱이 기기가 고른 레이트로 여는데, 이
  기기는 48kHz 로 열립니다. 강제할 길을 만들지 않았습니다.
- **USB 마이크**는 재지 않았습니다. 외부 기기가 timestamp 를 어떻게
  주는지는 다를 수 있습니다.
- **화면이 꺼진 채, 부하가 걸린 채, 장시간(2시간)** 은 재지 않았습니다.
  71초로 본 −2ppm 이 두 시간 내내 유지된다는 근거는 없습니다.
- **다른 기기**는 전혀 모릅니다.

## 남은 처리
