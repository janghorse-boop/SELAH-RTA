## M33 — 제 결론이 제 시험보다 앞섰습니다 (먼저 고칩니다)

3차 문서에 이렇게 적었습니다:

> **오차 0.0 으로 정확히 같습니다** … 순음·임펄스 섞인 신호와 잡음 둘
> 다에서 같았습니다.

**그 결론을 제 시험이 뒷받침하지 않았습니다.** 하울링은
`events.map { it.hz.toInt() }.sorted()` 만 견줬고 — 시각·지속·솟음·종료
사유가 전부 지워집니다 — SPL 은 Leq 를 아예 보지 않았습니다. 검증자가
넓게 재니 실제로 달랐습니다(`startMs` 85 vs 93, `durationMs` 2901 vs
2907, session Leq 끝자리).

**이 프로젝트에서 되풀이되는 제 실수입니다** — 시험 이름과 결론이 단언보다
앞섭니다. C01·M01·RC03 때와 같은 모양입니다.

### 계약을 먼저 적고 다시 쟀습니다

**1. 시각은 캡처 블록이 정한다.** 한 블록을 몇 조각으로 나누든 조각들은
**같은 블록 시각**을 씁니다 — 실제 `CaptureController` 가
`session.spectrumMs` 를 블록마다 한 번 세우는 것과 같습니다.

**2. 비트 단위로 같아야 하는 것**: current·MAX·Peak·peakClipped·
leqShort·leqLong·leqLongFull·settled, 31밴드, Peak Hold,
**하울링 기록 전체**(주파수·시각·지속·솟음·종료 사유).

**3. 오차를 허용하는 것**: `leqSession` 하나뿐, **1e-9 dB**.
까닭은 `EnergyAverage` 가 블록별 RMS 를 다시 제곱해 더하므로 **더하는
묶음이 달라지면 부동소수점 끝자리가 흔들리기** 때문입니다.
**이 허용치는 재기 전에 정했습니다.**

### 다시 잰 결과

```
[하울링] 한번에 FeedbackEvent(hz=1000.1803242626909, …, startMs=85, durationMs=2901, …)
[하울링] 쪼개서 FeedbackEvent(hz=1000.1803242626909, …, startMs=85, durationMs=2901, …)
                                                    ← 통째로 같다
[RTA]    첫 밴드 -79.634882462413 vs -79.634882462413
[SPL A]  max -16.979742585091 / -16.979742585091
         session -16.987394982269134 / -16.98739498226914   ← 끝자리만
[SPL Z]  session -16.973783164086015 / -16.973783164086022  ← 끝자리만
```

**계약을 지키면 하울링 기록이 통째로 같습니다.** 3차 문서의 차이는
**제 시험이 조각마다 시각을 다시 센 탓**이었습니다.

그리고 **계약을 어기면 달라진다**는 것도 시험으로 못박았습니다:

```
[시각 계약] 지킴 [(85, 2901)]
[시각 계약] 어김 [(93, 2904)]
```

### 3차 문서의 해당 결론은 폐기합니다

「오차 0.0, live 결과 전부 동일」은 **잘못된 문장**입니다. 바른 문장은:

> 위 계약을 지키면 current·MAX·Peak·31밴드·Peak Hold·하울링 기록은
> **비트 단위로 같고**, `leqSession` 만 1e-9dB 안에서 다릅니다.

## M31 — 큐의 구현 계약을 못박습니다

「용량이 남아도 표준 큐는 던질 수 있다」는 반례가 정확합니다.
`ArrayBlockingQueue(1)` 을 비운 채 interrupt 를 걸고 `put` 하니
`accepted=1, consumed=0, interrupted=true` 였습니다. 그리고 제 예시의
`Packet(...)` 은 **번호 발급 뒤 오디오 경로에 할당을 남깁니다.**

### 결정 — 전용 SPSC 링, 미리 잡아 둔 칸

| 무엇 | 정한 것 |
|---|---|
| 큐 | **직접 만든 SPSC 링**. 표준 blocking queue 를 쓰지 않습니다 |
| 용량 | **풀 크기와 같다** |
| 칸 | `PacketSlot(seq, captureFrameStart, frames, epochId, bufferIndex)` 를 **미리 만들어 두고 돌려 씁니다** — 게시할 때 새로 만들지 않습니다 |
| 게시 | 칸의 필드를 채우고 **쓰기 색인을 release-store** 하는 것이 전부입니다 |
| 금지 | 자물쇠 대기·용량 대기·interrupt 가능한 API·일반 예외·할당 |
| 소비 | **쓰기 색인을 acquire-load** 한다(아래 순서 참고) |

**producer 가 하나(오디오 스레드), consumer 가 하나(녹음 스레드)** 라서
색인 두 개면 충분합니다.

### 순서를 정확히 적습니다 (독립 검증 M41)

제가 「소비는 **읽기** 색인을 acquire-load 한다」고 적었는데 **거꾸로**
였습니다. 소비자가 자기 색인을 acquire 해 봐야 **생산자가 쓴 필드와
동기화되지 않습니다.** 맞물려야 하는 것은 상대가 게시한 색인입니다:

```
producer: slot 필드 채움        → writeIndex  release-store
consumer: writeIndex acquire-load → 게시된 slot 읽기
consumer: slot 사용을 마침       → readIndex   release-store
producer: readIndex acquire-load  → 회수된 slot 재사용
```

### 버퍼를 돌려주는 시점과 칸을 돌려주는 시점은 다릅니다

메타데이터를 소비자가 제 쪽으로 가져왔더라도, **writer 가 그 PCM 을 아직
쓰고 있으면 버퍼를 풀에 돌려주지 않습니다.**

| 무엇 | 언제 돌려주는가 |
|---|---|
| 링 **칸**(PacketSlot) | 메타데이터를 인수한 직후 — `readIndex` 를 올릴 때 |
| PCM **버퍼** | writer 가 그 PCM 을 **다 쓴 뒤** |

둘을 같은 시점으로 묶으면, 아직 쓰고 있는 PCM 이 다음 블록으로 덮입니다.

### 왜 실패할 수 없는가

- 버퍼 하나 ↔ 칸 하나, 용량 == 풀 크기.
- 그래서 **버퍼를 잡았다면 빈 칸이 반드시 있습니다.**
- 순서: `풀에서 버퍼 잡기` → `복사` → `번호 받기` → `게시`.
  **번호 받기와 게시 사이에는 필드 대입과 색인 저장뿐**입니다.
- 복사가 실패하면(범위 오류 등) 그때는 **아직 번호를 받기 전**이므로
  버퍼만 한 번 돌려주고 물러납니다.
- admission 이 닫혀 있으면 번호 대신 −1 을 받고, 역시 버퍼만 돌려줍니다.

### 시험 (검증자가 적은 구분을 반영)

「성공·실패 offer 를 번갈아」는 제가 잘못 적었습니다. 두 가지는 다릅니다:

| 무엇 | 뜻 |
|---|---|
| **풀에서 못 잡음** | **정상**입니다. 그것이 곧 손실이고 세어서 남깁니다 |
| **번호 받은 뒤 게시 실패** | **불변식 위반**입니다. 일어나면 안 됩니다 |

시험: 풀을 말린 상태, writer barrier 정지, 번호 받은 직후 close,
interrupt 를 건 상태, 복사 실패 주입 — 모든 경우에 **비움이 끝나고 모든
버퍼가 정확히 한 번 돌아오는지** 봅니다.

## M32 — 한 행 안의 epoch 혼합

반례가 정확합니다. 블록을 쪼개도 **두 조각이 같은 행 번호**에 속하면,
raw 극값 하나와 epoch 하나로 합치는 순간 되돌아옵니다:

```
옛 epoch: -20dBFS + 100 =  80dB
새 epoch: -30dBFS + 120 =  90dB      ← 실제 최대
raw 최대 -20 만 남기면 → 80 또는 100
```

### 결정 — **극값마다 제 epoch 를 지닌다**

고정 길이 행을 유지하되, 값마다 짝을 둡니다:

```
Row(rowIndex,
    currentRaw, currentEpoch,
    maxRaw,     maxEpoch,
    peakRaw,    peakEpoch,
    flags, bands[31])
```

- 행의 극값을 고를 때는 **보정을 적용한 값으로 견줍니다**
  (`raw + epoch.offset`). 위 반례에서 −30@120 이 이깁니다.
- 저장은 **이긴 쪽의 raw 와 그 epochId** 입니다.
- 읽을 때 `raw + 그 epoch 의 offset` 으로 되살리면 **정확히 90dB** 입니다.
- 재분석은 raw 를 그대로 쓰므로 뜻이 보존됩니다.

**epochId 는 2바이트**면 됩니다(고리 상한 256).

크기를 잘못 적었습니다(독립 검증 L41). 2시간이면 `7200 / 0.5 = 14,400`행
이므로:

| | 바이트/행 | 2시간 |
|---|---:|---:|
| 세 필드를 전부 새로 넣는다면 | +6 | **0.086MB** |
| 2차 설계의 `epochId` 한 개에서 **순증가** | +4 | **0.058MB** |

제가 적은 **0.17MB 는 두 배쯤 크게 잡은 값**입니다. 최종 wire format 이
정해지면 실제 `recordSize` 로 다시 셉니다.

### 적어 두어야 할 한계

**「어느 조각이 최대였는가」는 녹음 당시 보정 기준입니다.** 나중에 보정을
바꿔 오프라인 재분석하면 승자가 달라질 수 있습니다. 그때는 WAV 원본에서
다시 계산해야 하며, **저장된 행이 그 답을 대신하지 않습니다.**

### 시험 — 녹음 전체 없이 지금 만들 수 있습니다

검증자가 짚은 대로, 이 집계는 **행 집계기 단위**로 떼어 시험할 수
있습니다. 반례 수치를 그대로 씁니다:

- 500ms 행 **한가운데**에서 offset 100 → 120 으로 바뀌고,
  −20dBFS 와 −30dBFS 가 각 구간에 있을 때 **reader 까지 통과한 최대가
  90 인지**
- 행의 `current` 와 `max` 가 **서로 다른 epoch** 에서 나온 경우
- 여러 epoch 가 한 행에 있는 경우, 마지막 부분 행

## 작은 정정

3차 문서의 예시에서 `block [23552, 24576)` 를 **17번/18번 행**이라
적었는데, 48kHz·시작 프레임 0 이면 **0번/1번 행**입니다(500ms = 24000
프레임). 오프셋이 있는 예시가 아니었으므로 제 표기가 틀렸습니다.
